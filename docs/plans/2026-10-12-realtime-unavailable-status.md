# 실시간 미가동 배너와 수집 상태 판정 개선 계획

작성일: 2026-10-12 KST. 상태: P0·P1 구현과 로컬 검증 완료. 운영 미적용.

수집 설정을 동기화하는 동안 정상 WS 연결이 `0`으로 표시되어 「실시간 미가동」 배너가 뜨는 문제를 고친다. 최근 연결 증거와 현재 설정의 반영 완료 여부를 분리하고, 실제 단절·수집 상태 유실·저장 오류는 각각 드러낸다. 첫 구현의 완료 기준은 동기화 중 거짓 단절 표시 제거와 실제 장애 탐지 보존이다. 오늘 발생한 WS 단절과 처리 큐 포화는 원인별 후속 작업으로 다룬다.

## 확인된 현상과 원인

`CaptureProcessSession.fresh()`는 프로세스와 IPC의 생존, 상태 보고의 나이뿐 아니라 설정 버전·ACK·자식 상태 버전의 일치까지 확인한다. `_sync_locked()`가 버전을 올리면 다음 상태 frame이 도착하기 전까지 이 술어가 False가 된다. `status()`는 그 순간 최근 계정 연결 증거까지 지우고, lifecycle은 연결 0을 `offline`으로 투영한다. 프론트는 이 값을 받아 배너를 표시한다. 5초 폴링과 짧은 상태 전환이 겹치면 다음 조회까지 배너가 남는다.

약 0.4초는 장애 지속 시간을 정밀 측정한 값이 아니라 다음 GET 표본까지의 간격이다. 사용자가 본 배너의 정확한 시각은 없어 모든 사례를 이 경로로 단정하지 않는다. 설정 동기화가 사용자 조작 없이 반복된 이유는 별도 계측으로 확인한다.

## 상태 판정과 표시 계약

최근 연결 증거는 현재 수집 epoch의 상태만 사용한다. 자식 생존, 필수 IPC 작업 생존, 열린 제어 채널, 부모 수신 시각과 자식 관측 시각의 10초 미만 신선도를 모두 확인한다. 설정 버전 불일치만으로 이 증거를 지우지 않는다. 자식 교체·IPC 종료·상태 만료에서는 이전 연결을 현재 연결로 재사용하지 않는다.

설정 준비 완료는 기존 `fresh()`의 엄격한 조건을 유지한다. 최근 연결 증거가 있어도 설정 ACK나 상태 버전이 맞지 않으면 `collector.ready=false`, `capture_healthy=false`다. 연결 증거 보존을 새 종목의 구독 준비 완료나 정상 수집으로 해석하지 않는다. 표시 frame의 desired version 필터, 이전 epoch 차단, 조회·저장 접근의 엄격한 준비 조건도 유지한다.

| 상태 | 연결 증거 | 제안하는 capture_reason | 화면 동작 |
| --- | --- | --- | --- |
| 거래일·시간 게이트 닫힘 | 기존 게이트 계약 유지 | `closed` | 장 마감 표시 |
| 연결·설정·등록·저장 정상 | 최근 실제 연결과 현재 등록 | `healthy` | 정상 LIVE 표시 |
| 최근 연결은 유지되고 설정 반영 대기 | 연결 수와 최근 수신 보존, 준비 미완 | `syncing` 신규 | 「실시간 설정 반영 중」 pill, 미가동 배너 없음 |
| 최근 상태에서 실제 연결 0 확인 | 연결 0 | `offline` | 연결 미가동 배너, 기존 자동 복구 안내 |
| 현재 설정의 REG 미완료 | 최근 연결 보존, 준비 미완 | `registration_incomplete` | 구독 등록 미완 표시 |
| 자식 사망·IPC 종료·상태 만료·동기화 실패 | 최근 유효 증거가 없으면 연결 수 초기화 | `collector_unavailable` 신규 | 「실시간 수집 상태 확인 불가」 경고 |
| 필수 저장 실패 | 신선한 연결 증거는 보존 | `storage_error` 신규 | 「실시간 데이터 저장 오류」 경고 |

게이트가 열려 있는 동안 저장 오류와 수집 감독 오류를 단순 동기화 대기보다 우선한다. 최근 상태가 실제 연결 0을 보고하면 설정 동기화 중이라도 단절 표시를 유지한다. 부팅 시 유효한 연결 상태를 한 번도 받지 않은 경우 연결이 살아 있다고 추정하지 않는다.

`syncing`에는 무기한 유예를 주지 않는다. 제어 ACK 대기는 기존 RPC 제한 30초를 사용하고, ACK 이후 해당 버전의 준비된 상태 보고는 최대 10초를 기다리는 안으로 구현한다. 두 단계의 시작 시각은 monotonic clock으로 기록한다. RPC 실패·제한 초과·상태 만료 시 `collector_unavailable`로 전환하고 기존 복구 경로를 따른다. 단순 버전 변경이 타이머를 계속 갱신해 장애를 숨기지 않도록 실제 sync 시도별로 추적한다.

## P0 상태 판정 수정과 회귀 검증

1. **연결 증거와 설정 준비를 분리한다.** `collector_process.py`에서 상태 조회 한 번에 생존·신선도·버전·저장 오류를 한 번씩 평가하고 공통 결과를 사용한다. `status()`는 동기화 중 최근 연결 수, 계정 연결 세대, 마지막 수신·틱 시각을 보존한다. 현재 설정과 일치하지 않는 `ready_codes`, `ready_registrations`, 계정 `registration_ready`는 준비 완료로 노출하지 않는다.
2. **수집 비준비 사유를 명시한다.** `kiwoom.collector`에 제한된 `state_reason`과 동기화 단계·시작 시각·관측된 상태 버전을 추가한다. 버전 불일치, 상태 만료, 자식/IPC 종료, 저장 실패를 lifecycle이 하나의 False에서 역추론하지 않게 한다. 필드의 이름과 enum은 구현 전에 BE·FE 계약으로 확정한다.
3. **lifecycle과 공급자 상태를 맞춘다.** `lifecycle.py`는 위 상태표로 `capture_reason`을 투영한다. `service_status.py`와 설정 상세에서도 연결 수와 준비 계정 수를 구분한다. 동기화 중 연결 6을 유지하더라도 모든 구독이 준비됐다고 표시하거나 미해결 공급자 실패를 해제하지 않는다.
4. **프론트 표시와 wire 계약을 함께 갱신한다.** `api/liveStatus.ts`, `liveStatusProjection.ts`, `captureHealthPill.ts`, `LiveStateBanner.tsx`, 설정 상세·진단 복사를 갱신한다. `syncing`용 warn 등급을 추가하고 수집 확인 불가·저장 오류에는 해당 사유의 경고를 표시한다. 동기화 정보와 오류는 기존 색·배치 규칙을 사용한다. 캔들·지수의 정상 여부를 확인하지 않고 정상이라고 단정하는 문구는 일반 장애 안내에서 제거한다.
5. **결정론적 회귀 조건을 검증한다.** fake IPC 응답과 상태 frame을 Event로 보류하여 동기화 전, ACK 전, ACK 후 다음 상태 전, 준비 완료를 각각 검사한다. HTTP 직렬화와 화면 투영까지 확인한다. 공급사 접속이나 임의의 sleep 길이로 테스트 성공을 판단하지 않는다.

핵심 변경 파일은 `hoga/live/collector_process.py`, `hoga/live/lifecycle.py`, `hoga/live/service_status.py`와 위 프론트 파일이다. `/health?deep=1`은 설정 비준비 시 503을 유지한다. ADR-0174의 「ACK 불일치·죽은 자식·상태 만료·저장 오류를 정상으로 판정하지 않는다」는 결정과 일치한다. 같은 ADR의 상태 설명과 CONTEXT의 관련 용어는 구현 시 함께 갱신한다. 새 ADR 번호가 필요하면 저장소 지침대로 열린 PR까지 확인한다.

## P1 동기화 계측과 외부 워치독 보호

동기화가 발생한 경우 변경된 설정 항목의 이름만 기록한다. 예를 들어 저장 대상, 표시 참조, 거래일 판정, 종목 메타데이터 중 무엇이 달라졌는지 남긴다. token, 원문 frame, 계정 자격증명, 전체 표시 참조 목록은 기록하지 않는다. 시작·ACK·첫 준비 상태·실패를 PID·epoch·버전으로 연결하고, 정상 동일 설정의 주기 점검은 로그를 만들지 않는다.

현재 외부 `deploy/hoga-ops-watchdog.sh`는 deep health의 실패 응답 한 번으로 서비스를 재시작한다. 정상 sync의 짧은 503과 겹치면 불필요한 재시작이 가능하므로 운영 적용 전에 이 경로를 함께 보완한다. 이번 조사에서 이 워치독의 실제 재시작이 발생했다는 증거는 없다.

deep health를 200으로 바꾸는 대신 외부 워치독이 **유일한 실패 사유가 제한 시간 안의 `syncing`일 때만** 1초 후 한 번 재조회하도록 한다. 첫 응답·재조회 응답·재시작 결정을 남긴다. 두 번째 응답도 실패하면 기존 정책으로 처리하고, 다른 죽은 태스크·큐 비준비·저장 오류·상태 만료가 함께 있으면 sync라는 이유로 무시하지 않는다. 응답 파싱 실패와 예상하지 못한 HTTP 코드는 기존 오류 정책을 유지한다. fake curl과 fake systemctl로 복구 시 재시작 0회, 지속 실패 시 1회, 복합 실패 탐지 보존을 검사한다.

관측 결과 동일 설정인데 불필요한 버전 증가가 확인되면 해당 비교·정규화만 수정한다. 현재의 반복 주기만으로 그 원인을 추정해 watchdog이나 구독 정합화를 제거하지 않는다.

`test_collector_process.py`, `test_lifecycle_kiwoom.py`, 공급자 상태 테스트, wire 계약 검사, 프론트 투영·배너 테스트를 확장한다. 실제 spawn 자식으로 sync를 보류하는 통합 검사와 mock 상태 전환을 사용하는 Playwright 검사를 추가한다. 두 번째 sync 중 취소, ACK 후 지연 frame, 실제 단절을 합성해 정상처럼 숨겨지지 않는지 확인한다.

PR 전 검증은 저장소 기준대로 전체 Ruff와 `pytest -m 'not wallclock'`, 프론트 typecheck·Vitest·빌드·Playwright를 실행한다. 기존 실패가 있으면 동일 기준 커밋에서 재현하고 이번 변경의 실패와 구분한다. 검증 가드나 기대 계약을 느슨하게 바꿔 통과시키지 않는다.

## 운영 적용과 비교

구현과 로컬 검증을 완료한 뒤 적용할 커밋을 확정한다. 적용을 요청받은 서버만 갱신하고 적용 전후 커밋, API·수집 PID, epoch, 시작 시각을 기록한다. 운영의 같은 앱키로 추가 WS를 연결하지 않는다.

적용 후 같은 종목·창·계정 구성으로 최소 30분 장중 표본을 수집한다. 사용자 조작이 없는 구간과 저장 대상·표시 참조가 실제 바뀌는 구간을 포함한다. 설정 버전 전환이 최소 10회 관측돼야 동기화 경로 검증 완료로 본다. 전환이 부족하면 자연 관측을 연장하고, 운영 장애·강제 GC·토큰 무효화로 사례를 만들지 않는다.

- 최근 연결이 유지된 sync에서 `connected_accounts=0` 또는 거짓 `offline`이 발생하지 않아야 한다.
- sync는 해당 버전의 준비 상태를 받은 뒤 해제되고, 제한 초과는 지정 사유로 드러나야 한다.
- 수신→처리 완료 카운터와 지연, 표시 gap·폐기, 저장 오류, 재연결·등록 실패가 악화되지 않아야 한다.
- 외부 워치독의 일시 sync 재시작이 없어야 한다. 실제 장애 탐지는 로컬 합성 검사와 자연 장애 기록으로 확인한다.

새 프로세스에서 카운터가 0으로 시작한 것을 개선 효과로 계산하지 않는다. 오래된 연결이 정상처럼 남거나 실제 오류가 숨겨지면 원인과 해당 버전을 기록하고 검증한 이전 버전으로 되돌린다. 이번 완료 보고는 배너 판정 개선과 수집 처리 성능 개선을 별도로 평가한다.

## 실제 WS 단절과 큐 포화의 후속 작업

09:00:56의 6계정 동시 종료와 09:04의 일부 종료는 `ConnectionClosedError`가 확인됐지만 최초 원인이 공급사인지 네트워크인지 구분되지 않았다. 08:39의 DNS 일시 실패도 별도 사건이다. 다음 자연 장애에서 안전한 close code, 실패 단계, 동일 시각 계정 분포, 호스트 네트워크·DNS 기록을 대조한다. 공급자 제한이나 네트워크 문제가 확인된 뒤 그 원인에 맞는 조치를 정한다.

10:11의 큐 포화는 계정 0·2·3에서 128개 상한과 약 4.3~4.4초 대기가 기록됐다. 당시 수신률은 약 29프레임/s, 완료율은 약 21~23프레임/s였다. 이 사건은 상태 판정 수정으로 해결되지 않는다. 다음 분석은 계정별 입력률·완료율·in-flight 경과, 수집 프로세스 CPU·GC, 디스크 쓰기 지연과 콜백별 비용을 함께 측정한다. 병목이 확인된 콜백·배치·실행 양보 경로만 최적화하고 실제 저장·집계 결과가 같은지 검증한다. 큐 상한 확대만으로 처리 능력이 개선됐다고 판단하지 않는다.

P0·P1은 하나의 기능 개선으로 구현·검증하고, 원인이 다른 네트워크와 처리량 변경은 각각 별도 작업으로 진행한다.

## 구현 결과

연결 증거와 준비 상태를 분리하고 `syncing`, `collector_unavailable`, `storage_error`를
BE·FE에 함께 추가했다. 현재 epoch의 이전 설정 상태는 연결 증거에만 사용하고,
최대벽·표시 데이터·구독 준비의 버전 필터는 유지한다. 저장 오류·상태 만료·IPC 종료·
취소·동기화 제한 초과는 동기화 대기로 숨기지 않는다.

동기화 시작·ACK·첫 준비·실패에 PID·epoch·버전과 변경된 설정 항목 이름을 기록한다.
자식의 sync가 표시 참조를 이미 복원하므로 부모에서 동일 view_subscribe를 다시
보내던 중복을 제거했다. 외부 워치독은 다른 실패 없는 syncing 응답만 한 번 재조회한다.
새 reason과 sync 진단 enum의 미러 검사를 추가했고 의도적 불일치가 실패하는지 확인했다.

실제 spawn 자식의 두 번째 sync를 보류한 HTTP 검사에서 연결 증거 유지와 deep health
503을 확인했다. 현재 로컬 검사 결과는 백엔드 전체 5,678 통과·2 skip·13 wallclock 제외,
Ruff 통과, 앱·단위·E2E 타입 검사 통과, 프론트 전체 7,801 통과, 빌드 통과다.
Playwright 전체는 190 통과와 신규 테스트의 선택자 오류 1건이었다. 정상 상태에서
pill이 점으로 바뀌는 실제 UI에 맞춰 테스트를 수정했고, 신규 전환 검사와 시장·서비스
상태 관련 18개를 최종 코드로 재실행하여 모두 통과했다. 전체 191개를 수정 뒤 다시
실행한 결과는 아니며, 최종 코드에서 확인된 미해결 실패는 없다. 타입 검사·전체
프론트 단위 검사·빌드도 최종 코드로 재실행했다. 빌드에는 기존 큰 chunk 경고가 남는다.
운영 GET 응답은 새 모델의 validate/dump 전후 값과 필드가 같은지 읽기 검증했다.

운영 서버 재시작·배포·자격증명 변경은 수행하지 않았다. 장중 30분과 자연 설정 전환
10회 비교는 운영 적용 후 검증 항목으로 남는다. 실제 네트워크 단절과 처리 큐 포화의
후속 분석은 이 상태 판정 변경의 해결 범위에 포함하지 않는다.
