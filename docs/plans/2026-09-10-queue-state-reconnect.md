# 큐 저장 상태 순서 보존과 재연결 복구

## 구현

- 큐 응답과 저장 상태 푸시에 서버 실행별 `persistence_epoch` 및 증가하는
  `persistence_revision`을 넣는다. 저장 시도가 끝날 때마다 revision을 올린다.
  서버 실행/테스트 초기화 시 epoch를 바꾸고 revision을 0으로 시작한다.
- 프론트는 QueryClient에 최신 저장 상태를 별도로 보존한다. 첫 HTTP 응답보다 푸시가
  먼저 도착해도 가짜 빈 큐를 만들지 않는다. 같은 epoch에서는 낮은 revision이 높은
  revision을 덮지 못한다. 큐 행은 HTTP 응답에서 갱신하고 저장 상태만 순서대로 합친다.
- HTTP 요청 시작 epoch도 기록한다. 첫 WS 연결과 서버 재시작을 가로질러 과거 서버
  응답이 도착해도, 요청 도중 새 epoch의 푸시가 왔다면 그 상태를 유지한다. 취소한
  요청은 메타데이터를 갱신하기 전에 AbortSignal을 검사한다.
- 연결 단절 시에는 재동기화가 필요함을 기록하고, 다음 연결 성공에서 큐·인벤토리·
  캘린더·range와 목록 동기화 표의 키만 취소 후 재조회한다. 처음 연결과 중복 연결
  이벤트는 재조회를 추가하지 않는다. 관계없는 진행 중 요청은 취소하지 않는다.
- 히트맵 종속 키 목록은 heatmapKeys에서 공유해 평상시 변경/재연결 복구가 같은 범위를
  사용한다. ADR-0004의 wire 미러와 ADR-0019의 재연결 복구 정책을 유지한다.

## 검증

지연 HTTP, 첫 응답 이전 푸시, 순서가 뒤집힌 실패/복구 푸시, 새로운 서버의 낮은
revision, 첫 연결을 가로지르는 과거 서버 응답, 취소 요청의 메타데이터 오염 방지,
재연결 때 필요한 요청만 취소·재조회하는 동작을 테스트한다. E2E는 저장 경고 순서와
단절 중 변경된 상태가 재연결 후 반영되는 흐름을 검증한다.

전체 E2E 재실행에서 히트맵 드래그 직후 되돌리기 클릭이 한 번 누락됐다. 단독 반복
3회는 통과했다. 설치된 dnd-kit의 AbstractPointerSensor.detach가 document 클릭 차단을
드롭 후 50ms 유지하는데 테스트는 즉시 클릭할 수 있었다. 해당 드래그 테스트 helper에
60ms 라이브러리 정리 대기를 명시했다. 제품 코드나 네트워크 타임아웃은 바꾸지 않았다.

최종 검증: Ruff 통과, 백엔드 5,027 passed / 2 skipped / wallclock 13 deselected,
프론트 타입 검사·Vitest 7,325 passed / 560 files·Vite build 통과, Playwright 110 passed.
기존 큰 청크 빌드 경고는 유지된다. SSE 버전 필드를 고의 누락한 검사가 실패함을
확인한 뒤 정상 계약으로 검사했다.

## 실제 서버 지연 관측 (2026-09-10 15:43~15:46 KST)

서버 재시작/배포 없이 `127.0.0.1:8000/api/live/status`의 제한된 통계와
`127.0.0.1:5173/live?code=005930`의 별도 browse 탭을 관측했다. 측정 탭의 거래소를
통합(UN)으로 맞춰 KRX 화면과 UN 체결을 비교하는 오류를 피했다. 임시 구독/DOM
관측기를 해제하고 측정 탭을 닫았다. 계정 식별자·자격증명은 기록하지 않았다.

| 구간 | 관측값 | 범위 |
|---|---|---|
| 키움 수신 처리 | 연결별 p95 0.35~8.44ms | 각 연결의 최근 256 표본 |
| 서버 전송 대기 | 연결별 p95 2.46~3.61ms | 각 outbox 최근 256 표본 |
| 서버 send 호출 | 연결별 p95 0.14~0.17ms | 각 outbox 최근 256 표본 |
| 브라우저 WS 메시지 처리 | p50 0.10 / p95 0.40 / 최대 5.40ms | 최근 256 프레임, 모든 채널 포함 |
| 체결 수신 → 일치하는 현재가 DOM | p50 153.2 / p95 198.3 / 최대 301ms | 삼성전자 UN, 가격이 바뀌어 일치 확인된 54건 |
| 최신값 콜백 → 다음 rAF | p50 5.4 / p95 16.3 / 최대 68.8ms | 최근 256 표본, 참고용 |

DOM 관측은 UN 체결 342건 중 화면과 가격이 달라진 표본만 대상으로 한다. 중간 체결이
새 체결로 대체되면 최신 체결의 도착 시각으로 비교하므로 모든 틱의 표시 지연이나
무조건적인 지연 분포를 의미하지 않는다. 값 일치를 MutationObserver로 확인했으며
실제 픽셀 표시 완료를 측정한 것은 아니다. rAF 값도 픽셀 표시 완료의 증거가 아니다.

현재가 경로의 `liveTickOverlay.ts`에는 150ms 갱신 묶음 주기가 있다. 관측된 p50은
그 주기와 부합하지만, 이 관측만으로 모든 화면 지연의 원인을 확정하지 않는다.
브로커/네트워크 수신 이전 구간은 측정하지 않았고, 서로 다른 구간의 p95를 더해
종단 지연으로 계산하지 않는다. 같은 호스트에서 회귀 테스트가 병행됐으며, 단일 종목·
짧은 관측으로 장중 전체 성능이나 변경 전후 개선율을 주장할 수 없다. 이번 표본에서
초 단위 지연은 재현되지 않아 150ms 주기 변경은 이 PR 범위에 넣지 않았다.
