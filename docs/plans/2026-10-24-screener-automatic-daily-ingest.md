# 일반 자동 갱신의 잠정·확정 관측과 충돌 격리

2026-10-24 사용자 요청. 기존 parquet·계수·저장된 조건검색·발생 제외와 승인된 v2 정정 선택을 보존한다.
공급자 일봉은 영구 무정정 원본이 아니라 특정 시각에 관측한 KRX 공급자 전체 세션 값이다.
22시 수신을 정규장 종가나 거래소 최종 공표로 부르지 않는다.

## 관측과 저장

- 기존 22시 자동 갱신에서 종목별 원주가 요청 한 번으로 최근 **5거래일**을 함께 검사한다.
  오늘의 달력이 아직 미확인이라도 확인된 과거 날짜의 재대조는 허용하며 새 거래일을 추정하지 않는다.
- 활성화 이후 당일 관측은 별도 `screener/daily_ingest/` 원장에 잠정으로 보존한다.
  당일 22시 이전의 정상적인 값 변화는 잠정 값의 수렴으로 취급한다.
- 해당 거래일 22시 이후 시작한 관측과 **그다음 날짜**의 독립 관측이 OHLCV 전체에서 정확히
  일치해야 확정한다. 금요일 관측은 토요일 22시에도 확인한다. 휴장일에 새 거래일 봉은 만들지 않는다.
- 과거 누락 날짜를 최초 수집할 때만 두 번째 조회를 사용한다. 요청 시작과 직전 응답 종료 사이
  최소 2초를 공유 대기한다. 중단 후 재사용한 응답의 원래 시각·해시는 바꾸지 않는다.
- 확정된 **없는 `(code,date)` 행만** 원주가에 추가한다. 기존 원주가·수정주가 행은 그대로 복사하며,
  추가된 날짜의 기존 정책상 수정주가만 계산한다. 계수 파일은 수정하지 않는다.
  계수 미보유 종목의 기존 휴리스틱에는 해당 날짜 이후의 기존 봉을 문맥으로 제공한다.
- 대량 0거래량 날짜 차단(`>50%`)을 유지한다. 누락 응답을 거래정지나 0거래량으로 만들어 넣지 않는다.
- 활성화 이전 데이터는 기존 값으로 남긴다. 최근 재검사에서 값이 같다는 사실은 모든 과거 데이터가
  새 확정 계약을 충족했다는 소급 인증이 아니다.

## 충돌과 검색

기존 행, 이전에 확정한 행, 마감 이후 선행 관측과 값이 다르면 1주 차이도 격리한다.
원본 응답·수신 시각·후보·보존값·충돌 필드·근거 해시를 남기며 반복 조회만으로 격리를 풀지 않는다.
이미 명시적으로 승인한 v2 정정과 정확히 같은 관측은 그 선택을 보존한다.

Legacy 검색은 조건이 실제 사용하는 날짜에 한해 가용성을 검사한다. 가격만 사용하는 조건은
거래량만 바뀐 충돌 때문에 보류하지 않는다. 거래량·거래대금 조건은 원주가 관측의 잠정·충돌을
보류하며, OR의 다른 정상 조건은 계속 평가한다. 진행 중 당일의 명시적인 장중 오버레이는 유지한다.
원장 최초 적용 전에는 기존 검색 동작·응답을 그대로 유지한다.

v2의 원주가 수량·금액에는 스냅샷에 고정한 원장 가드를 적용한다. 공급자 수정 OHLC는
기존의 독립 확정 계약을 따른다. 원주가 수량 충돌로 독립 검증된 수정 OHLC를 무효화하지 않는다.
자동 원주가 관측으로 수정 OHLC·주식 수 이력을 인증하거나 기존 pair 관측을 덮어쓰지 않는다.
따라서 새 날짜의 v2 수정주가·수량 근거 준비는 기존 별도 경로의 책임이다.
이전 스냅샷과 실행 결과는 보존되며, 정확 재실행은 같은 코드·런타임 지문을 요구한다.

`daily_coverage`는 조건별 평가 보류를 설명한다. 상태 응답의 `daily_ingest`와 기존 갱신 표시에서
확정·잠정·충돌 격리·확인 실패·저장 재시도 상태를 제공한다. 추가 행이 없어도 격리가 달라질 수
있으므로 갱신 종료 시 이전 검색 결과에 재조회 필요 표시를 한다. 저장 조건 자체는 수정하지 않는다.

## 부하와 실패 예산

- 기존 background 거버너와 우선순위를 사용한다. 동시 종목 조회 **3개**, 조회당 최대 **2페이지**.
- 평시 종목당 한 번의 요청에서 5거래일을 읽는다. 다음 날 확인에 별도 전체 조회를 추가하지 않고
  그날의 정기 요청을 사용한다. 금요일의 확인을 위한 토요일 실행은 추가 비용이다.
- 과거 누락 확인에만 두 번째 요청을 사용한다. 공급자 내부 재시도는 기존 거버너 정책을 따른다.
- 일일 시도 2회, 실패 시 최소 30분 간격. 성공 응답은 체크포인트로 재사용하고 실패한 종목만 새로
  요청한다. 네트워크 시작 전 예산을 기록한다. 하루 예산 소진 후는 다음 날 다시 시도한다.
- 오래된 누락 하나가 모든 요청을 무한히 늘리지 않게 자동 범위는 최대 180일로 제한한다.
  더 오래된 잠정·충돌 기록은 지우지 않으며 명시적인 복구 검토 경로에서 다룬다.
- 완료 후 스케줄러 매분 확인은 작은 상태 파일로 끝내며 과거 parquet를 스캔하지 않는다.
- 종목코드는 기존 복구 계약과 동일한 ASCII 대문자·숫자 6자리다. 숫자 변환·문자 제거를 하지 않는다.
  출처로 확인한 상장 전·폐지 후·정지 구간의 누락은 수집 대상 외로 설명한다.
  정상 응답의 일봉 미제공과 처리 예외는 별도로 표시하며 미제공도 같은 재시도 예산을 따른다.
  기존 이력 자료는 읽기만 하고, 빠진 날짜·분류 근거·원본 응답 해시는 새 원장에 남긴다.
- 저장은 65,536행 묶음으로 과거 행을 복사한다. parquet의 물리적인 전체 정렬을 계약으로 삼지 않고,
  검색·조회가 필요한 논리적 날짜 정렬은 기존 읽기 경로에서 수행한다.
- 네트워크 중 writer lock을 잡지 않는다. 공개 시 기존 writer lock·journal을 사용하고,
  공개 중 취소는 디스크 쓰기를 끝낸 뒤 소유권을 놓는다. 저장 대기 중 확정 후보는 검색에서 잠정으로
  취급한다. 동시 기록이 먼저 들어오면 기존 값을 보존하고 새 충돌을 격리한다.

실측과 검증 입력은 [검증 보고서](../diagnostics/2026-10-24-screener-auto-ingest/README.md)에 기록한다.

## 종료 종목과 반복 미제공

빈 응답이나 마스터 부재만으로 상장폐지·만기를 추정하지 않는다. 최종 KRX 공시에서 확인한
종료일·종료 사유·확인 시각과 원문 해시를 별도 `daily_ingest/lifecycle`에 보존한다.
ETN의 종목코드가 없는 공시는 코드·상품명이 함께 있는 KRX 상품 상세 자료와 연결한다.
기존 `history_evidence.json`은 수정하지 않고 이번 수집 범위에만 검토 근거를 겹쳐 적용한다.
공시의 종료일과 기존 출처의 폐지일이 다르거나 원문·검토 객체 해시가 변하면 적용을 중단한다.

종료일이 지난 검토 종목은 정기 공급자 요청에서 제외한다. 종료 전 미확인 날짜는
`retired_history_unavailable`로 남기고 자동 재시도 대상에서만 제외한다. 기존 봉·잠정·충돌을
삭제하거나 누락을 0거래량으로 채우지 않는다. 거래 중인 종목의 미제공은 기존 일일 2회·30분
예산을 유지한다. 새 거래일·활성 미제공·확인할 잠정 봉이 없으면 주말 전체 재시도를 하지 않는다.

이미 완료된 수집의 분류 보정은 저장된 원본 응답만 재사용한다. 실제 관측 시각·당일 시도 횟수·
공급자 사용량은 유지하며 새로운 독립 확인으로 인정하지 않는다. 검토 등록과 분류 보정에는 기존
복구 소유권과 writer lock을 사용한다. 검토 철회 후에는 다음 수집부터 정상 요청 대상으로 복귀한다.
상태 응답은 종료 확인 수·미확인 수·재시도 가능한 미확인 수·실제 건너뛴 수를 별도로 제공한다.

37종목의 최종 공시 분류와 운영 비교는 [종료 종목 검증 보고서](../diagnostics/2026-10-24-screener-lifecycle-37/README.md)에 기록한다.

## 갱신 버튼과 과거 데이터 복구의 분리

`POST /api/screener/update`와 22시 스케줄러는 같은 작업 계획·수집·확정 원장을 사용한다.
버튼을 눌러도 최근 5거래일과 기존 갭 범위, 종료 종목 제외, 잠정·다음 날 확인·충돌 격리,
당일 예산과 체크포인트를 우회하지 않는다. 장중에는 기존 16시 컷오프 이전의 오늘 봉을
수집 범위에 넣지 않는다. 낮에는 한 번만 시도해 기존 하루 두 번 중 밤 22시 이후 관측의
예산을 남긴다. 버튼은 재시도 간격 대기·당일 예산 소진·밤 검증 대기를 최신 완료와 구분한다.

기존 종목 목록 갱신·깊은 과거 누락 보충은 `POST /api/screener/repair-history`와 화면의
‘과거 데이터 복구’ 버튼으로 옮긴다. 기존 보충·원주가/수정주가 대조·추가 저장 기준은 유지한다.
이 명시적 복구는 일반 갱신 버튼이나 정기 갱신이 자동으로 요청하지 않는다.

두 진입점과 스케줄러의 사전 계획·작업 시작은 같은 admission lock과 서버 소유 작업을 공유한다.
진행 중 일반 갱신의 재요청은 현재 작업에 합류하며 깊은 복구를 추가하지 않는다. 명시적 과거
복구가 일반 갱신 중에 요청되면 기존 작업이 끝난 뒤 한 번 이어 실행한다. 복구 중 재요청도
중복 복구를 만들지 않는다. HTTP 연결 취소는 시작한 공유 작업을 취소하지 않는다.
페이지는 두 버튼에 같은 진행 상태를 적용하고 새로 열 때 서버 상태로 복원한다.

`last_refresh`의 과거 복구 기록은 삭제하지 않는다. 화면에서는 그보다 새 일봉 재대조가 있으면
옛 복구 결과를 최신 일반 갱신의 실패로 다시 표시하지 않는다. 저장 조건·검색 정책·기존 데이터는
이 진입점 분리로 변경하지 않는다. 비교와 중복 실행 검증은
[버튼 통합 검증 보고서](../diagnostics/2026-10-24-screener-update-unification/README.md)에 기록한다.
