### 전송 계약과 관측 방법

- 새 프론트는 `{action: "subscribe", code, protocol: 2}`를 보낸다. 이전 서버는 기존 `live` 프레임으로 응답할 수 있으며 새 프론트도 이를 처리한다. 새 서버는 이전 클라이언트에 기존 경로를 유지한다.
- `live_batch`는 `code`, `data`(최대 128개 순서 보존 이력), `latest`(venue/kind별 최신값), `dropped`, `queue_age_ms`를 보낸다. 종목별 이력은 각 애플리케이션 큐에서 최대 1,024개로 제한한다.
- `seq`는 발행 순번이다. 브라우저는 최신값 역행을 막는 데 사용하고 이력·지표 소비 전에 제거한다. 저장 데이터 형식은 바뀌지 않는다. 브라우저 재연결 시 순번 기준을 초기화한다.
- `subscribed`는 요청 접수 ACK다. 실제 준비 여부는 상태 응답의 `ready_registrations`와 `data_received_ms`로 구분한다. `ready_codes`는 저장 대상 종목의 요구 venue ACK 완료 집합이다.
- 누락과 브라우저 재연결은 이력 partial 표시를 유지한다. 반복 누락마다 재조회 이벤트를 내되 종목별 1초로 병합한다. REST 재조회로 이미 축출된 원본 틱 전체를 복원했다고 간주하지 않는다.
- 제어 큐 포화 시 제어 메시지를 조용히 버리는 대신 연결을 1013으로 종료해 재접속·재동기화를 유도한다. 이전 클라이언트의 개별 live 큐에는 기존 혼잡 정책이 남아 있으므로 최신값 보장은 protocol 2 경로에 해당한다.
- 계정 계측은 상태 응답의 `kiwoom.accounts[].latency`, 송신 계측은 `cache_stats.live_buffer.ws_delivery`에서 확인한다. 지연 표본은 최근 최대 256개이며 p95는 이 제한된 표본의 값이다. outbox 큐 시간은 해당 큐 구간이고 공급자부터의 총 지연이 아니다.
- 프론트 `wsDispatchTimings()`는 최근 최대 256개 처리 시간, `wsLastReceivedAt()`는 브라우저 monotonic 수신 시각이다. 서버 시각과 직접 빼지 않는다. 토큰이나 원문 인증 메시지를 계측 로그에 추가하지 않았다.

### 검증 결과와 남은 확인

- 백엔드 전체 테스트: 4,973 passed, 2 skipped, 13 deselected. 이후 마지막 보완은 관련 경계 및 wire 계약 테스트 71개로 재검증했다.
- 프론트 최종 전체 테스트: 559개 파일, 7,312개 테스트 통과. 기존 스크리너 테스트의 비동기 DOM 교체 경합은 현재 DOM 재조회와 검증을 같은 `waitFor` 안에서 수행하도록 보완했다.
- Ruff, TypeScript 타입 검사, 프로덕션 Vite 빌드 및 `git diff --check` 통과. 빌드의 기존 700KB 초과 chunk 경고는 남아 있다.
- 브라우저 전체 E2E에서 기존 107개 시나리오 통과. 새 시나리오는 가격 표시 검증은 통과했으나 초기 측정 코드가 실패하여 측정 방식을 수정했고, 관련 3개 시나리오가 모두 통과했다.
- 새 모의 배치 시나리오에서 오래된 이력과 최신 가격을 함께 보냈을 때 최신 가격 표시, 오래된 순번 거부, 후속 최신값 반영, 이력 누락 안내를 확인했다. **브라우저 메시지 수신→DOM 반영 157ms**는 단일 합성 입력의 관측값이며 p95나 실제 키움→화면 지연 보장이 아니다.
- 저장 10초 주기, 원본 저장 포맷, 캔들 합성 의미는 유지했다. 브라우저 표시는 이 주기를 기다리지 않는다.
- 실제 장중의 첫 표시/지속 갱신 지연, 공급자 연결 종료 원인, 서버 수신→송신 전체 trace, canvas paint, 저장 flush의 이벤트 루프 점유는 운영 적용 후 별도 측정이 필요하다. 초기 목표 충족 및 사용자가 겪은 실제 지연 해소는 아직 단정하지 않는다.

## 1. 목표와 범위

사용자가 종목을 열었을 때 실시간 구독이 준비되는 시간을 줄이고, 이미 수신된 최신 호가·현재가가 브라우저에서 오래된 데이터 뒤에 밀리지 않도록 한다. 연결 여부와 해당 종목의 데이터 준비 여부를 구분해 표시한다.

대상 경로:

`KiwoomWsClient → LiveStream.on_tick 또는 표시 전용 publish → LiveBuffer → /api/ws → sharedLiveSeries / liveTickOverlay → UI`

저장 경로의 10초 다운샘플·JSONL 기록 주기는 유지한다. 현재 표시 경로는 저장 flush를 기다리지 않는다. 다만 저장 작업이 공유 이벤트 루프를 얼마나 점유하는지는 측정 대상이다. 프론트의 150ms 반영 주기도 먼저 유지하고, 계측으로 필요성이 확인된 경우에만 조정한다.

## 3. PR 1 — 구간별 지연 계측과 재현 테스트

### 구현

- 기존 미커밋 `ws_latency_probe.py`와 연관 변경을 먼저 검토해 재사용 여부를 정한다. 운영 서버 재시작이나 별도 키움 LOGIN 없이 읽을 수 있는 자료부터 사용한다.
- 서버에서 계정·연결 세대별로 연결 종료 사유, LOGIN/REG 소요 시간, 기대/ACK 구독 수, 최초 틱 시각, 재연결 횟수를 기록한다. 토큰과 원문 인증 메시지는 기록하지 않는다.
- 수신→파싱→publish→송신 시작/완료의 구간 시간, 큐 깊이뿐 아니라 가장 오래된 프레임의 대기 시간을 측정한다. 전체 종목 무제한 로그 대신 대상 종목·기간·표본 수를 제한한다.
- 브라우저에서 메시지 수신→공유 버퍼 반영→React 커밋 및 차트 적용 시간을 측정한다. 차트 적용과 실제 화면 paint를 동일시하지 않고 필요 시 브라우저 성능 trace로 paint까지 검증한다.
- 구독 요청→REG ACK와 REG ACK→첫 틱을 분리한다. 무거래·장외 종목의 첫 틱 대기는 프로그램 처리 지연으로 계산하지 않는다.
- 서버 내부는 monotonic clock, 브라우저 내부는 `performance.now()`를 사용한다. 서로 다른 시계의 값을 직접 빼지 않는다. 종단 측정에는 프레임 식별자와 시계 오차를 고려한 상관 분석 또는 동일 환경 trace를 사용한다.
- 거래소 이벤트 시각과 수신 시각을 분리한다. 이벤트 시각의 초 단위 정밀도와 공급자 대기가 포함된 age를 서버 처리 지연으로 보고하지 않는다.

### 검증

- 기존 두 재현을 자동 테스트로 고정: 즉시 LOGIN→킥 반복, 느린 구독자의 최신값 유실.
- 한 계정의 REG 응답을 보류한 상태에서 다른 계정의 신규 구독이 진행되는지 확인하는 manager 경계 테스트를 추가한다. 현행 실패를 확인한 뒤 PR 3에서 통과시킨다.
- 장중 활성 종목·거래가 드문 종목·여러 창·여러 탭·재연결 중 종목 전환의 기준 측정값을 남긴다.
- 코드 배포 버전, 대상 종목/venue, 계정 수, 열린 창·탭 수, 틱 유량을 결과와 함께 기록한다.

## 4. PR 2 — 재연결 보호와 준비 상태 수정

대상: `hoga/live/kiwoom_ws_client.py`, `kiwoom_session.py`, `lifecycle.py`, 프론트 상태 소비자.

### 구현

- LOGIN 성공 시 `_attempt`와 `_consecutive_kicks`를 즉시 초기화하지 않는다.
- 구독 정합화 완료 후 연결이 설정된 안정 기간을 유지했을 때 초기화한다. 안정 기간은 우선 30초를 제안하며 기준 측정으로 조정한다. 장외·무거래를 고려해 모든 종목의 틱 도착을 초기화 조건으로 요구하지 않는다.
- 일시적 일반 연결 실패와 동일 키 점유로 인한 킥을 구분한다. 일반 실패는 상한 있는 백오프와 지터로 복구하고, 반복 킥은 계정 단위 cooldown을 적용한다.
- cooldown과 실패 이력은 클라이언트 재생성에도 유지한다. manager 워치독이 죽은 클라이언트를 바로 재생성해 킥 보호를 우회하지 못하게 한다. 해제 시각 이후 해당 계정 하나만 재시도한다.
- transport 연결, LOGIN 완료, REG 진행/완료를 별도 상태로 둔다. 데이터 신선도는 종목·venue·kind별 마지막 수신으로 별도 표현한다.
- 기존 `ws_connected`는 호환용 연결 정보로 유지하되, UI에서 이를 해당 종목의 실시간 준비 완료 판정으로 사용하지 않는다.
- 새 연결 세대에서는 이전 ACK 상태를 준비 완료로 재사용하지 않는다. 만석·등록 거부·복구 대기·첫 틱 대기를 구분한다.

### 검증

- LOGIN 직후 반복 킥에서 설정한 임계값과 cooldown이 작동한다.
- 안정 기간을 통과한 연결의 간헐 실패는 오래된 실패 이력 때문에 즉시 차단되지 않는다.
- 워치독이 cooldown 계정을 재생성해 반복 LOGIN하지 않는다.
- 일부 계정만 연결되거나 등록이 진행 중인 경우 해당 종목이 준비 완료로 표시되지 않는다.
- 조용한 종목·장외에서 틱이 없다는 이유만으로 재연결이 반복되지 않는다.

## 5. PR 3 — 구독 상태와 네트워크 대기 분리

대상: `hoga/live/kiwoom_session.py`, `kiwoom_ws_client.py`, `hoga/api/ws.py`.

### 구현

- manager 잠금 안에서는 참조 수·슬롯 소유권·desired 구독 집합과 버전만 원자적으로 갱신한다.
- REG/REMOVE와 재시도는 계정별 작업 루프가 잠금 밖에서 수행한다. 같은 계정은 직렬, 서로 다른 계정은 독립적으로 진행한다.
- 같은 계정의 LOGIN/REG/REMOVE ACK 라우팅과 remove-before-add 순서를 유지한다. ACK가 trnm으로만 식별되므로 같은 연결에 동일 control 요청을 병렬 송신하지 않는다.
- 구독 상태 변경을 요청마다 무한 큐에 쌓지 않고 최신 desired 집합으로 병합한다. 처리 중 변경되면 완료 후 최신 버전과 다시 정합화한다.
- 연결 세대와 desired 버전을 함께 추적한다. 오래된 ACK가 새 연결의 등록 상태나 취소된 슬롯 소유권을 부활시키지 못하게 한다.
- `/api/ws` receiver는 구독 요청 접수와 upstream 준비 완료를 분리한다. 첫 요청의 REG를 기다리느라 후속 subscribe/unsubscribe를 읽지 못하는 구간을 제거한다.
- 기존 `subscribed` 메시지의 소비자를 확인하고, 접수 ACK와 준비 상태 알림을 명확한 계약으로 정한다. 접수 ACK를 수신 가능 보장으로 바꾸지 않는다.
- 종료 시 계정 작업 루프를 취소·회수하고, 화면 참조 해제와 잔여 슬롯 반환을 검증한다.

### 검증

- 계정 A의 REG ACK를 10초 보류해도 계정 B에 여유 슬롯이 있으면 신규 구독이 독립적으로 진행된다.
- 빠른 종목 전환, 두 탭의 동일 종목 구독/해제, reconnect와 unsubscribe 경합을 검증한다.
- 슬롯 상한 초과, 중복 등록, 유령 구독, 예전 ACK에 의한 상태 복원이 없다.
- 기존 구독 종목의 틱 전달은 신규 구독이나 복구 작업 때문에 중단되지 않는다.

## 6. PR 4 — 현재값 전송과 이력 소비의 혼잡 정책 분리

대상: `hoga/live/buffer.py`, `hoga/api/ws.py`, 프론트 `ws.ts`, `sharedLiveSeries.ts`, `liveTickOverlay.ts`, 지표·체결 소비자.

### 선행 결정

현재 같은 스냅샷 배열을 최신 호가 표시와 지표·체결 이력 계산이 함께 소비한다. 전체 큐를 단순히 drop-oldest 또는 latest-only로 바꾸면 지표 결과가 달라질 수 있다. 구현 전에 kind별 소비자를 조사하고, 표시용 최신값 채널과 이력 갱신 채널의 계약을 문서화한다. 필요 시 ADR-0053의 단일 소켓 안에서 메시지 종류를 확장한다.

### 구현

- 현재값 표시는 `(code, venue, kind)`별 최신 완결 스냅샷을 병합하고, 전송 전에 오래된 미송신 값을 대체한다. delta 성격의 메시지는 그대로 대체하지 않고 완결 상태로 정규화 가능한지 먼저 확인한다.
- 체결·지표 입력은 순서와 의미를 보존하는 배치 전달을 사용한다. 체결 방향·수량·가격·시간 버킷에 영향을 주는 임의 생략이나 집계를 하지 않는다.
- 이력 큐 한계에 도달하면 명시적 gap과 재동기화 절차를 제공한다. 프레임 순번/연결 세대를 이용해 누락을 감지하고 복구 응답과 라이브 꼬리를 중복 없이 병합한다.
- `/api/live/series`의 보존 범위만으로 모든 누락을 복구할 수 있다고 가정하지 않는다. 서버 버퍼가 이미 축출한 per-tick 이력은 복원 불가능할 수 있다. 복구 불가 구간은 partial로 표시하고, 집계 저장본과 원본 틱을 같은 해상도로 취급하지 않는다.
- 현재값·이력·제어 메시지를 논리적으로 분리하고, 현재값 전송이 대량 이력 뒤에 계속 밀리지 않도록 공정하게 스케줄링한다. 제어 메시지 유실도 방지한다.
- 서버 내부 큐뿐 아니라 소켓 전송과 브라우저 수신·처리 속도를 함께 측정한다. 애플리케이션 큐 개선만으로 네트워크 혼잡 전체가 해결됐다고 판단하지 않는다.

### 검증

- 느린 소비자와 버스트 입력 후 현재값이 최신 스냅샷으로 수렴한다. 조용해진 뒤에도 마지막 값이 유실되지 않는다.
- KRX/NXT/UN, 다른 종목, 서로 다른 kind가 잘못 병합되지 않는다.
- 정상 부하에서 변경 전후 체결 수량 합·방향·지표 결과가 동일하다.
- 과부하에서는 이력 누락이 조용히 발생하지 않고 gap 및 복구/partial 상태로 드러난다.
- 다중 탭 중 느린 탭 하나가 다른 탭과 수집·저장 경로를 지연시키지 않는다.

## 7. PR 5 — 브라우저 처리 최적화와 종단 검증

PR 1 계측에서 브라우저 구간이 의미 있는 병목으로 확인될 때 수행한다.

- 150ms publish마다 배열 복사·venue 필터·지표 계산·차트 전체 재설정 중 무엇이 시간을 쓰는지 프로파일링한다.
- 최신 호가·현재가 소비자는 전체 15분 배열 대신 최신값 참조를 사용한다. 이력 소비자는 변경된 kind와 새 구간만 처리하도록 개선한다.
- 첫 현재값은 즉시 게시하고 후속 연속 틱만 150ms로 묶는 방식을 비교 측정한다. 갱신 빈도를 높여 메인 스레드 부하가 증가하면 적용하지 않는다.
- 같은 종목의 여러 창에서 공유 버퍼·구독이 중복 생성되지 않는 기존 계약을 유지한다.
- 저장 flush 시각과 loop lag를 대조한다. 지연이 확인되면 해당 동기 CPU/I/O 작업만 별도 개선 범위로 분리한다.

## 8. 완료 기준과 적용 순서

순서: **PR 1 기준 측정 → PR 2 재연결/상태 → PR 3 구독 격리 → PR 4 혼잡 정책 → 필요 시 PR 5 렌더 최적화**.

아래 지연 수치는 현재 실측 보장이 아닌 초기 목표다. PR 1에서 환경과 측정 방법을 고정한 뒤 확정한다.

| 항목 | 초기 목표 / 판정 |
|---|---|
| 정상 부하 서버 수신→송신 시작 | p95 50ms 이내 |
| 전경 브라우저 수신→현재값 적용 | p95 250ms 이내. 150ms 반영 주기 포함 |
| 장애 계정 격리 | 다른 계정의 구독이 장애 계정의 ACK timeout을 기다리지 않음 |
| 반복 킥 | 임계값 이후 cooldown, 워치독 우회 없음 |
| 상태 정확성 | 연결됨·구독 준비·종목별 데이터 신선도를 구분 |
| 혼잡 후 현재값 | 최신값 유실 없이 수렴, 큐 대기 시간·유실/병합 수 관측 가능 |
| 이력 정확성 | 정상 부하 의미 보존, 과부하 누락 감지와 복구 또는 partial 명시 |
| 저장 정합성 | 10초 저장 스냅샷과 캔들 합성의 기존 의미 및 회귀 테스트 유지 |

각 PR은 해당 경계의 회귀 테스트와 장중 전후 비교를 통과한 뒤 적용한다. 같은 조건에서 첫 표시 지연과 지속 업데이트 지연을 따로 보고한다. 전송 프로토콜 변경은 이전 클라이언트와 호환되는 추가 필드/채널로 시작하고, 지원 여부에 따라 기존 경로를 유지한다. 새 필수 데이터의 유실이나 저장·지표 정확성 회귀가 발생하면 해당 PR을 되돌릴 수 있도록 변경을 분리한다.

이 플랜의 완료는 코드 결함 수정과 측정된 사용자 증상 개선을 모두 요구한다. 재현 테스트 통과만으로 실제 브라우저 지연이 해결됐다고 선언하지 않는다.
