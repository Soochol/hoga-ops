# 토스와 키움의 호가 주문 연동 설계

**상태: 구현 설계 확정. 키움 주문 기능의 운영 활성화는 수용 테스트 완료 전까지 금지.**

2026-10-19: 이 설계에 따른 연동을 구현했다. [사용·설정 안내](../kiwoom-trading.md)와
[구현 검증 기록](../research/2026-10-18-kiwoom-trading/implementation-validation.json)을 함께 참고한다.
아래 264/181개와 실전 조회 26건은 설계 확정 단계의 기록이며 구현 후 회귀 결과와 구분한다.

기존 호가주문 조작을 유지하고, 주문 서비스의 공통 안전장치 아래 토스·키움 어댑터를 둔다.
키움 시세용 계좌 분산과 재시도 경로는 주문이나 계좌 조회에 사용하지 않는다.
판단 근거는 [검증 결과](../research/2026-10-18-kiwoom-trading/README.md)이며, 백엔드 264개,
프론트 181개 통과와 실전 조회 26건을 포함한다. 키움 신규·정정·취소는 전송하지 않았다.

## 확정한 경계

| 구성 | 책임 |
|---|---|
| `TradingService` | 대상 계좌 검증, 공통 명령 기록, 중복 방지, 금액 확인, 잠금, 전체 취소 대상 고정 |
| `TradingBroker` 포트 | 주문·잔고·주문 여력 조회, 신규·정정·취소, 원본 결과와 정규화 결과 반환 |
| `TossTradingAdapter` | 토스 API·이벤트 계약을 공통 모델로 변환 |
| `KiwoomTradingAdapter` | 키움 조회·주문 필드, 원주문 연결과 이벤트를 공통 모델로 변환 |
| `KiwoomAccountGateway` | 계좌와 환경에 고정한 전송, 조회·쓰기별 오류 분류, 주문 재전송 금지 |
| 키움 공용 인증·연결 관리자 | 인증 정보별 단일 토큰 소유권, WebSocket 한 연결에서 시세·계좌 이벤트 분배 |
| 공용 유량 예산 | 같은 제한 주체를 사용하는 시세·계좌 조회를 함께 계수, 주문 그룹 별도 계수 |

별도 Windows 서버, 범용 플러그인 시스템, 메시지 브로커를 도입하지 않는다. 기존 HTTP 연결
재사용과 인증 코드를 활용하되, 실전 주소가 고정된 현재 인증·REST·WS 설정에는 명시적 환경
문맥을 추가한다. 검증 프로브는 제품용 주문 어댑터로 편입하지 않는다.

## 계좌와 환경

서버 내부 `account_ref`는 `(증권사, 실전/모의/로컬, 실제 계좌)`에 연결되는 안정적인 참조다.
인증 정보 참조와 분리하며, 숫자형 키움 `account_id`는 인증 설정을 찾는 인덱스로만 취급한다.
계좌 목록과 명령에는 마스킹 이름·증권사·환경·기능을 제공하고 실제 계좌번호와 키는 노출하지 않는다.

새 인증 연결은 `ka00001`로 실제 계좌를 검증한 후에만 주문에 사용한다. 인증키 교체로 응답
계좌가 바뀌면 기존 `account_ref`를 새 계좌로 재해석하지 않고 연결을 거절한다. 같은 계좌에
인증키가 여러 개 연결되어도 잔고·주문을 별도 계좌처럼 중복 집계하지 않는다.

계좌 조회, 명령, 이벤트, 캐시, 중복 제거 키, 알림, 잠금에는 모두 이 문맥을 사용한다.
선택 계좌가 연결되지 않으면 해당 계좌에서 멈추고 다른 계좌로 자동 전환하지 않는다.
모의 인증 누락을 실전 키로 대체하거나 실전 주소로 폴백하지 않는다.
이번 실측에서 등록 키 6개가 서로 다른 계좌 6개에 연결되었다. 이 환경에서는 시세용
인증 계정 자동 전환이 실제 주문 계좌 변경으로 이어질 수 있다.

## 주문과 변경 요청

`command_id`는 사용자 요청, `order_ref`는 증권사 주문, `operation_ref`는 정정·취소 요청을
참조한다. 증권사가 반환한 새 번호를 정정 완료나 원주문 교체 완료로 즉시 해석하지 않는다.
번호는 앞자리 0을 보존하는 문자열이며 내부 식별에는 증권사·환경·계좌·주문 영업일을 포함한다.

공통 주문에는 최소한 다음이 필요하다.

- 계좌 참조, 내부 주문 참조, 증권사 주문번호, 원주문·모주문 연결
- 종목, 방향, 주문 유형, 요청 경로와 관측된 체결 거래소
- 주문수량, 확인된 체결수량, **명시적 잔여수량**
- 정규화한 상태, 증권사 원본 상태, 조회·이벤트 출처와 시각
- 미확인 값에 대한 `null`, 알 수 없는 상태에 대한 `UNKNOWN`

정정·취소 누계와 체결 누계가 어느 주문 노드 기준인지 실제 자료로 확정하기 전에는
`원수량 - 체결수량`으로 키움 잔량을 생성하지 않는다. `oso_qty`·`ord_remnq`와 주문 변경 연결을
대조한다. 확인하지 못한 수수료·평균 체결가·보유 또는 가능 수량을 0으로 채우지 않는다.

실시간 `913` 주문 상태 하나만으로 최종 상태를 결정하지 않는다. 주문 구분·체결 정보·잔량·
거절 사유·원주문과 정정·취소의 확인을 함께 해석한다. 미체결 목록에서 사라진 사실만으로
체결·취소 완료를 추정하지 않는다. 이력은 모든 페이지를 읽고, 실패하거나 절사된 조회를
완전한 계좌 스냅샷으로 게시하지 않는다.

정정·취소는 화면에서 현재 선택한 시세 거래소가 아니라 대상 주문의 경로를 사용한다.
키움의 잔량 전체 정정·취소 값 `0` 사용 여부는 수용 테스트로 확정한다. 토스의 최신 잔량을
숫자로 전송하는 정책을 키움에 강제로 이식하지 않는다.

## 전송과 영속 기록

명령 상태와 주문 상태를 분리한다. 명령의 전송 대기는 `PREPARED`, 전송 시도는
`SENDING`, 접수 응답은 `ACCEPTED`, 명시적 거절은 `REJECTED`, 결과 미확인은 `UNKNOWN`이다.
`ACCEPTED`는 체결이나 정정·취소 완료가 아니다.

1. 계좌·종목·지원 기능과 요청 형태를 검증하고 전송 대기 요청을 기록한다.
2. 계좌·종목별 신규 주문 잠금과 대상 주문별 정정·취소 잠금을 취득한다.
3. 유량 슬롯을 얻은 뒤 요청 유효 기간과 대상 주문 상태를 다시 확인한다.
4. `SENDING`을 커밋한 뒤 주문 HTTP 요청을 한 번 전송한다.
5. 업무 응답과 주문번호를 보존하고 이벤트·이력으로 실제 주문 상태를 대조한다.

전송 대기 만료와 전송 후 타임아웃은 다르다. 전자는 전송하지 않은 결과를 기록하고,
후자는 `UNKNOWN`으로 보존한다. 쓰기는 HTTP transport도 `retries=0`으로 구성한다.
인증 실패 후 재발급·재전송이나 다른 계좌로의 전환을 내부적으로 수행하지 않는다.
HTTP 200만으로 성공을 판단하지 않는다. 주문 응답 유실·5xx·유효하지 않은 접수 응답은
접수가 없었다고 단정하지 않는다. 접수 후 로컬 결과 저장이 실패해도 재전송하지 않는다.

재시작 후 `SENDING`과 `UNKNOWN`은 복구 대상으로 남긴다. 동일 조건 주문을 발견했다는
이유만으로 동일 요청이라고 자동 확정하지 않는다. 키움 주문 계약에는 확인된 사용자 요청
ID 필드가 없어 증권사까지 포함한 exactly-once 보장을 약속할 수 없다.
수동 확인으로 차단을 해제할 때도 원요청과 확인 사유·시각을 보존하고 재전송하지 않는다.

전체 취소는 기존의 대상 고정과 하위 요청 ID 정책을 유지한다. 전송 중 새로 생긴 주문을
같은 전체 취소에 추가하지 않으며, 이미 접수됐거나 결과가 불명확한 하위 취소를 반복하지 않는다.

## WebSocket과 연결 수명

인증 연결별 물리 WebSocket 소유자는 하나다. `00`·`04`는 시세 틱 파서 앞에서 분기해 계좌
전용 큐로 보낸다. 계좌 이벤트의 `9201`을 검증한 뒤 해당 계좌의 주문 상태를 갱신한다.
시세 종목 등록과 계좌 등록은 별도 구독 상태로 관리하고 REG/REMOVE 조작이 서로를 제거하지
않도록 한다. ACK 대기는 기존 단일 reader와 등록 직렬화 규칙을 유지한다.

연결 유지 조건은 `시세 참조 또는 계좌 이벤트 참조가 존재함`이다. 시세 종목이 없어지거나
시장 수집 게이트가 닫히는 조건만으로 사용 중인 주문 연결을 종료하지 않는다. 계좌 이벤트
사용 시간과 연결 허용 시간은 별도로 정의하고, 연결할 수 없는 시간에는 REST 상태를 명시한다.

계좌 이벤트 순서를 보존하고, 시세 부하 때문에 계좌 큐가 넘치면 조용히 버리지 않는다.
동기화 필요 상태로 전환해 재연결·REST 대조를 수행한다. 이벤트 수신 경로에서 느린 조회나
전체 잔고 계산을 직접 기다리지 않는다. 등록 ACK, 이벤트 연결, 대조 완료는 다른 상태다.
재연결 직후에는 미체결·이력·잔고 조회가 완료되기까지 동기화 중으로 표시한다.

## 조회와 호출 예산

계좌 조회도 계좌 고정이 필수다. 현행 `run_with_capacity(..., client=A)`는 계좌 고정을
보장하지 않으므로 그대로 사용하지 않는다. 시세용 큐를 복제하는 대신, 명시적으로 바인딩된
전송과 공용 유량 슬롯 예약을 분리한다. 조회만 제한된 재시도가 가능하며 계좌는 바뀌지 않는다.

초기 한도는 공식 계좌·토큰별 주문·조회 한도와 모의 TR별 한도를 상한으로 삼고 여유 간격을
둔다. 같은 제한 주체를 쓰는 기존 시세 경로도 같은 예산을 보도록 연결해야 한다. 과거의 시세
TR별 실측만으로 주문 TR 사이의 독립성이나 계좌 그룹 한도가 없다고 가정하지 않는다.
추가 한도 실측 전에는 계좌·환경 그룹과 TR별 제약 중 더 엄격한 조건을 적용한다.

현금 주문 정책에서 주문 가능 금액·수량은 미수·대용을 포함하는 값과 구별한다. 실측에서
정상 응답한 `kt00011`의 미수불가 필드가 우선 검증 대상이다. `kt00010`은 휴장일에 거절될 수
있으므로 필수 성공 조건으로 두지 않는다. 어떤 조회가 실패해도 임의의 다른 금액 필드로
대체하거나 0원을 표시하지 않는다. 가격에 의존하는 여력은 `(계좌, 종목, 가격, 정책)`으로
캐시하고 마지막 확인 시각과 조회 상태를 제공한다.

## API와 호환성

새 계약은 `/api/trading/v2`에 둔다. 숫자 계좌 ID와 토스 주문 스키마의 의미를 조용히 바꾸는
방식은 반례 테스트에서 계좌 충돌과 잔량 손실을 일으켰다. 명시적 계약 버전이 이 이관 범위를
분리한다. 기존 `/api/trading`과 로컬 모의 경로는 호환성을 유지한다.

- `GET /accounts`: 계좌 참조, 증권사·환경, 연결·지원·활성 기능
- `GET /state?account_ref=...&code=...`: 주문과 잔고를 독립 조회
- `POST /orders`: 계좌·명령 참조와 명시적 주문 경로
- `POST /orders/{order_ref}/modify`, `/cancel`: 원주문 문맥에서 검증
- `GET /commands/{command_id}`: 같은 요청의 처리 상태 확인
- 전체 취소·수동 확인: 기존의 대상 고정·확인 기록 정책 유지

기존·새 라우트 모두 같은 명령 엔진과 계좌·주문 잠금을 사용해야 한다. 명령 저널은
스키마 버전을 추가해 이관하고, 기존 payload와 미해결 기록을 보존한다. 구 기록의 토스
계좌 별칭은 검증된 새 참조에 연결하되, 매핑할 수 없으면 차단을 유지한다. 계좌 목록의
배열 순서나 새로 발급한 인덱스로 과거 기록을 재해석하지 않는다. 이관 완료 조건에는
구·신 라우트 사이의 중복 요청과 동시 정정·취소 테스트를 포함한다.

## 화면과 초기 구현 범위

기존 클릭 주문·드래그 정정·호가 밖 취소를 유지한다. 계좌 이름에는 증권사·실전/모의 구분을
표시하고, 시세 거래소와 주문 경로를 함께 표시한다. 계좌 변경 시 미제출 동작을 초기화하고
새 계좌 조회가 완료된 후 활성화한다. 연결 실패가 다른 계좌 자동 선택으로 이어져서는 안 된다.

초기 구현 대상은 국내 현금 지정가, 잔량 전체 정정·취소, 미체결·주문 이력·보유 조회다.
KRX·NXT·SOR는 계약상 표현하되 **각 경로의 서버 수용 테스트를 통과하기 전에는 활성 기능으로
노출하지 않는다.** 이번 조회로 NXT·SOR 주문 지원이 검증된 것은 아니다. 시장가·신용·부분
취소·시간외 전용 주문은 후속 범위다. 기존 로컬 모의와 키움 서버 모의는 별도 계좌다.

## 구현 순서와 수용 조건

| 순서 | 구현 | 완료 조건 |
|---|---|---|
| 1 | 계좌·환경 참조, 공통 계약, 토스 어댑터 추출 | 기존 회귀 유지, 구·신 문맥 충돌과 이관 미해결 기록 테스트 |
| 2 | 키움 고정 계좌 조회와 공용 예산 | 페이지 누락·업무 오류·휴장일·가격별 여력 처리 검증 |
| 3 | 단일 세션의 계좌 구독과 연결 참조 | 시세 대상 0개, 연결 게이트 변경, 재연결, 큐 포화 테스트 |
| 4 | 비활성 상태의 키움 주문 어댑터 | 쓰기 1회, 결과 유실·저장 실패·동시 변경·전체 취소 복구 테스트 |
| 5 | 증권사 서버 수용 테스트와 경로별 활성화 | 아래 실제 응답·이벤트 대조 완료 |

수용 테스트에는 신규 → 부분 체결 → 잔량 정정 → 취소, 전송 중 체결, HTTP 응답보다 빠른
이벤트, 중복·지연 이벤트, 조회 지연, 서버 재시작을 포함한다. 주문과 변경 요청의 연결,
확인 수량·누계 체결·잔량, 주문 가능 수량에서 미체결 매도 예약의 차감, 거래소별 보유 조회의
중복 여부를 확인해야 한다. 모의투자에서는 KRX 범위를 검증하고, 실전 SOR·NXT는 별도다.

실계좌 주문 금지 상태에서는 마지막 단계를 수행하지 않는다. 이번에 확정한 것은 이 검증을
수용할 구현 구조와 활성화 조건이며, 키움 주문 기능의 운영 검증 완료가 아니다.
