# 키움 실시간 시간 초과 개선 계획

작성일: 2026-10-01. 기준 커밋: affb41a8e. 상태: 구현·검증 실행 완료, 운영 서버 미적용.

10월 1일 11:25의 실시간 시간 초과와 연결 5/5 표시를 조사한 결과, 반복 재연결,
구독 미완료, 서버 내부 GC 정지를 확인했다. 이번 작업은 실패 위치를 식별하고,
구독 준비 상태를 정확히 표시하며, 데이터 처리 대기가 제어 응답 수신을 막는 경로를
제거한다. 실제 키움 서버와 네트워크 구간의 장애 원인은 별도 관측으로 판단한다.

## 관측 근거

- 실행 서버 8000의 로그에서 11:25:10 시간 초과와 계정 0의 구독 50개 미완료를
  확인했다. 11:25:51에는 등록이 완료됐다.
- 10:33 이후 재연결 기록 84건 중 단순 TimeoutError 30건과 연결 시작 단계의
  시간 초과 3건이 있었다. 모든 실패를 같은 원인으로 분류하지 않는다.
- 11:26:37 GC 정지 5,593.4ms와 이벤트 루프 지연 5,570.3ms가 함께 관측됐다.
  이 기록이 11:25 실패의 직접 원인이라는 증거는 없다.
- 같은 호스트에서 기존 토큰을 사용한 분봉 조회 3회는 151/44/212ms였다.
  간헐적인 장애와 실시간 경로의 문제를 배제하는 결과는 아니다.
- 모의 입력에서 데이터 콜백 대기가 이미 도착한 REG 응답 처리를 막는 현상,
  구독 미완료인데 connected 상태를 반환하는 현상, ACK 계측에 종료 대기가
  포함되는 현상을 재현했다.

## 구현 순서

1. 실패 관측에 계정, 연결 세대, 실패 단계, 해당 단계 소요 시간을 추가한다.
   기존 session operation과 REST 관측 계약은 유지한다. ACK 대기와 소켓 종료를
   별도로 계측하고 안전한 구조화 정보만 기록한다.
2. 최근 응답뿐 아니라 현재 구독 준비를 확인한 계정만 정상으로 판정한다.
   화면에는 연결 계정 수와 준비 계정 수를 구분하고, 오류 상세와 진단 복사에
   실패 계정과 단계를 표시한다. REST의 과거 관측과 WS 자동 복구 안내를 구분한다.
3. 소켓 수신자는 JSON 식별과 LOGIN/REG/REMOVE/PING 처리를 담당하고,
   순서 보존 데이터 처리는 연결별 작업 하나가 담당한다. 데이터 큐에는 개수와
   용량 상한을 둔다. 포화 시 조용히 데이터를 버리거나 ACK 수신을 대기시키지 않고,
   명시적인 과부하 오류와 카운터를 남기고 해당 연결을 재연결한다.
   세션 종료 시 두 작업과 이전 연결의 대기 데이터를 모두 회수한다.
4. recv의 시간 제한을 asyncio.timeout으로 명시하고 수신 작업 수를 세션 단위로 제한한다.
   실행 서버의 Python 3.14 및 검증 환경 3.12에서는 양수 timeout의 wait_for도
   별도 Task를 만들지 않으므로 이 변경을 GC 원인 해결이나 Task 생성 감소로 주장하지 않는다.
   최대벽 상태 조회에서 이미 존재하는 상태의 임시 객체 생성을 제거한다.
   생성 횟수와 상태 동일성을 검증한다. GC 임계 변경이나 전체 GC 비활성화는 하지 않는다.
5. 실패 재현, 취소/정리/재연결, 데이터 순서와 과부하, wire 계약, 화면 전환을
   검사하고 저장소 필수 검증을 실행한다. 구현 결과와 남은 운영 검증을 이 문서에 기록한다.

기존 ADR-0116의 단일 recv 소유와 ADR-0118의 계정별 구독 정합화를 유지한다.
9월 10일 수신 지연 개선 계획의 계정별 구독 작업과 protocol 2를 재구현하지 않는다.

## 완료 기준

- 느린 데이터 콜백을 보류해도 REG 응답과 PING이 처리된다.
- 데이터 순서가 보존되고 큐 포화, 작업 실패, 취소가 연결 단위로 드러난다.
- 실패 진단이 계정과 단계를 보존하고 종료 대기를 ACK 응답 시간으로 계산하지 않는다.
- 연결된 계정의 구독 미완료가 정상으로 표시되지 않는다. 준비 정보가 없으면 정상으로 추정하지 않는다.
- 수신 프레임 수가 늘어도 작업 수가 늘어나지 않고 기존 상태의 임시 생성이 제거된다.
- 백엔드, 프론트 단위 검사, 타입 검사, 빌드, Playwright E2E를 실행한다.

## 운영 적용과 측정

이 작업트리에서 구현과 검증을 완료한 뒤 실제 서버 적용 여부를 명확히 보고한다.
장중 기존 서버의 자동 재시작이나 같은 앱키의 추가 WS LOGIN은 검증에 사용하지 않는다.
적용 후 같은 종목/창/계정 구성에서 재연결 빈도, 단계별 시간 초과, 데이터 큐 대기와
과부하 카운터, GC 정지, 첫 표시 및 지속 갱신 지연을 비교해야 사용자 증상 개선을
확정할 수 있다. 로컬 테스트 통과만으로 공급자 장애나 GC 정지 전체가 해결됐다고
주장하지 않는다.

## 구현 결과

- 소켓의 단일 reader가 제어 응답을 전달하고, 연결별 consumer 하나가 REAL 데이터를
  순서대로 처리한다. 느린 데이터 콜백이 REG ACK와 PING을 막는 재현을 해소했다.
- 큐 상한은 64메시지와 8MiB의 보수적인 UTF-8 입력 크기다. Python 객체의 실제
  메모리 사용량 상한을 뜻하지 않는다. 큐가 절반 이상 차면 consumer에 실행 기회를
  줘 짧은 입력 집중을 과부하로 오판하지 않는다. 실제 포화 시 세션을 폐기하고
  과부하·미완료 프레임 수를 기록한다. 종료 시 작업을 취소·회수하고 큐를 즉시 비운다.
- 실패 관측과 진단 복사에 계정, 연결 세대, 단계, 단계 소요 시간을 추가했다.
  REG 등 제어 응답 시간과 종료 시간을 분리했고 종료 대기를 2초로 제한했다.
- 최근 수신뿐 아니라 registration_ready를 정상 판정에 반영한다. 화면은 연결과
  구독 준비 수를 분리한다. 내부 데이터 처리 실패는 서버 내부 처리 단계로 안내하고,
  WS 실패는 자동 재연결 후 구독 확인 시 해제된다는 설명을 사용한다.
- 부분 구독 상태에서는 이전 실패 관측을 유지한다. 초기 구독 또는 이후 표적
  재구독·종목 변경으로 현재 구독 준비가 확인된 뒤 해당 계정의 실패를 해제한다.
- 기존 최대벽 상태를 조회할 때 불필요하게 생성하던 임시 상태 객체를 제거했다.
  같은 코드·시장 1,000회 조회에서 상태 객체 한 번 생성과 동일 객체 재사용을 확인했다.

운영 서버 8000은 변경·재시작하지 않았다. 새 테스트 서버는 빈 자격증명과 별도
포트·데이터 경로를 사용했다. 실제 키움 재연결 빈도와 GC 정지 개선 여부는 운영
적용 후 위 측정 항목으로 확인해야 한다.
