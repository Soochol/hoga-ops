# 스크리너 날짜 범위 신고거래량과 과거 일봉 보충 수집

작성일: 2026-09-09
상태: 구현 완료(워크트리). 운영 배포·전 종목 수집은 미실행. 구현·검증 결과는 아래에 기록한다.

## 목표와 완료 예시

사용자가 ‘2019-01-01~2022-12-31 사이에, 그날 기준 2년래 최대거래량을 한 번 이상 기록한 종목’을 검색한다. 필요한 과거 일봉이 없으면 같은 화면에서 수집을 요청하고, 서버 디스크에 저장한 뒤 다시 검색한다. 이후 같은 구간은 저장 데이터로 재사용한다.

데이터 경로는 기존 구조를 유지한다.

```text
조건 입력 → 필요한 이력 검사 → 저장 데이터로 scan
                       ↓ 부족하면 [과거 일봉 수집]
키움 일봉 REST → 검증·보정 계수 확보 → 원주가 Parquet 병합
 → 수정주가 Parquet 재생성·공개 → 보유 범위 재검사 → scan
```

호가·체결·분봉 수집은 필요 없다. OHLCV 일봉만 수집한다. 검색 엔진은 DuckDB-over-Parquet를 유지한다.

## 확인한 현재 구현과 실측

- `hoga/api/screener_runner.py`: scan은 `screener/daily_adjusted.parquet`와 `stocks.parquet`을 읽는다. 장중 basis일 때만 당일 REST overlay를 추가한다.
- `hoga/api/screener_scan.py`: `new_high_vol`은 최근 N개 행 중 당일 포함 M개 행의 최대거래량과 동률 이상인 날을 찾는다. 전체 M개 행이 필요하다. 절대 날짜 범위는 없다.
- `hoga/api/screener_history_backfill.py`: 앞쪽 이력·중간 결손 수집, 배치 병합, 수정주가 재생성, 벤더 관측 이력 기록이 있다. CLI `screener-history-backfill`이 호출하지만 스크리너 화면과 연결되어 있지 않다.
- `hoga/api/trading_days_seed.txt`: 2007년부터 거래일 달력이 있어 이번 2017~2022년 범위를 포함한다.
- 2026-09-09 실행 중 서버의 `/api/live/past-daily-candles`로 삼성전자(005930), SK하이닉스(000660), 현대차(005380)를 조회했다. 각 2017-01-02~2022-12-29, 1,475개 일봉을 반환했다. 연도별 243/244/246/248/248/246개이며 OHLCV 필드 누락·중복 날짜·응답 경고는 없었다. 신규 fetch 응답도 확인했다.
- 실측은 차트용 조회 경로 검증이다. 스크리너 Parquet 저장 완료나 전 종목 제공 보증이 아니다. 응답은 당시 `/tmp/hoga-history-probe/`에 보관했으며 영구 테스트 fixture로 의존하지 않는다.

관련 결정: `docs/adr/0055-today-breakout-distinct-condition-type.md`, `docs/adr/0057-screener-kis-authoritative-factor-store.md`, `docs/adr/0136-kis-removal-kiwoom-full-replacement.md`. 원주가 저장소·계수 기반 파생·검색 구조는 유지한다. 달력 연수 도입은 기존 ‘N/M은 거래일’ 정의의 확장이므로 구현 시 CONTEXT의 별도 기간 단위로 명시한다.

## 검색 의미와 범위

1. 최초 적용 대상은 기존 ‘기간내 신고거래량’이다. 당일 신고거래량·신고가·다른 조건의 의미는 변경하지 않는다.
2. 발생 기간은 시작·종료일 양끝 포함. 미래 종료일, 역전 범위, 유효하지 않은 날짜는 거절한다.
3. 비교 기간은 거래일 수 또는 달력 연수로 명시적으로 선택한다. ‘2년’을 500거래일로 몰래 치환하지 않는다.
4. 거래일 방식은 기존 당일 포함 M개 종목 일봉, 동률 포함 동작을 유지한다. 날짜 범위 모드에서는 필요한 이력의 누락 여부도 검증한다.
5. 달력 2년은 평가일 d에 대해 `(d에서 2년을 뺀 날, d]`로 정의한다. 윤년 2월 29일에서 연수를 뺄 때 해당 연도의 2월 말일로 맞춘다. 경계 정의는 도움말과 테스트에 고정한다.
6. 완전한 비교 이력이 있는 날만 판정한다. 거래량 0만 있는 창은 신규 날짜 범위 모드에서 신고 사건으로 세지 않는다. 기존 최근 N일 조건은 그대로 둔다.
7. 한 조건에서 여러 번 충족하면 가장 최근의 유효 충족일을 대표로 반환한다. 중복 조건은 leaf id별 증거를 따로 보존한다.
8. 다른 조건과의 AND는 기존처럼 종목 집합 교집합이다. 날짜 범위 조건 두 개가 같은 날 성립한다는 뜻이 아니다. 현재가·이동평균 조건은 기존 최신일 기준이며 UI에 이 구분을 안내한다.
9. 대상은 현재 코퍼스·사전필터가 선택한 종목 목록이다. 과거 시점의 상장 종목 전체 복원, 상장폐지 종목 전체 확보, 당시 시가총액·시장 분류 재현은 범위 밖이다.
10. 과거 조건만 있으면 당일 REST overlay를 생략한다. 다른 장중 조건이 함께 있으면 그 조건을 위한 기존 overlay만 유지한다.

## 조건·저장·응답 계약

기존 `new_high_vol` type을 유지하되 이 leaf의 params만 다음 두 형식으로 받는다. 공용 `BreakoutParams`를 무조건 확장해 신고가까지 바꾸지 않는다.

```json
{"lookback":60,"period":250}
```

위 기존 형식은 계속 유효하며 저장본을 강제 변환하지 않는다. 새 날짜 범위 형식의 제안:

```json
{
  "mode":"date_range",
  "start_date":"2019-01-01",
  "end_date":"2022-12-31",
  "record_period":{"unit":"years","value":2}
}
```

- 새 형식의 비교 단위는 `years` 또는 `trading_days`. 명시적 mode와 필수 필드를 검증하고 두 형식의 필드를 혼합한 요청은 거절한다.
- 최근 N일 폼·요약·기존 저장 검색·우측 드로어는 기존 동작을 유지한다. 날짜 모드는 날짜와 단위를 포함한 요약을 제공한다.
- 저장 파일은 새 서버가 기존 v1 저장본을 읽고 보존하는 방향으로 구현한다. 구버전 서버가 새 조건을 읽으면 필드를 무시하거나 파일을 격리할 수 있으므로 구버전으로의 역호환을 주장하지 않는다. 배포 전 저장본 백업, 프론트/서버 동시 배포, 롤백 시 백업 복원을 검증한다.
- 응답에 선택적 `history_coverage`와 leaf id별 `condition_matches`를 추가한다. 기존 `rows`, `price_date`, 정렬·가격 필드의 의미는 유지한다.
- 증거: 충족일, 보정 거래량, 비교 창 최대거래량, 비교 구간, 조건 id. 당일 포함 창에서는 충족일 거래량과 최대값이 같을 수 있음을 그대로 표현한다.
- 커버리지: 대상 수, 완전 평가 수, 이력 부족/벤더 미제공/일시 실패/계수 부족/달력 범위 밖의 수와 종목별 사유. 최종 scan limit와 무관하게 전체 대상에서 계산한다.

## 데이터 부족 판정

새 순수 모듈 `hoga/api/screener_history_coverage.py`를 만들어 scan과 수집 미리보기가 동일한 규칙을 사용하게 한다.

- 연수 모드는 발생 시작일에서 연수를 뺀 날짜까지 읽는다. 2019~2022년·2년 조건은 2017~2022년 이력이 필요하다.
- 거래일 모드는 발생 시작일 이전 M-1개 유효 봉을 확보해야 한다. 거래일 달력으로 초기 요청 범위를 정하되 종목 봉 수가 부족하면 범위를 더 과거로 확장한다. `M × 달력일 근사`로 완료를 선언하지 않는다.
- 최신·최초 날짜만 보지 않고 중간 결손도 검사한다. 달력에 없는 날짜는 휴장일로 판정하지 않고 달력 범위 밖으로 표시한다.
- 종목의 최초 관측일을 실제 상장일로 단정하지 않는다. 전체 2년 이력이 쌓이기 전은 ‘비교 이력 부족’이다. 벤더가 조회한 구간에 행을 주지 않은 사실과 실제 상장일은 별개다.
- 새 날짜 범위 조건은 match/no_match/unknown으로 평가한다. 충분한 창에서 한 번이라도 충족하면 match, 전체 후보일을 충분히 평가하고 미충족이면 no_match, 나머지는 unknown이다. 유효 match가 있어도 일부 이력이 부족하면 부분 평가 표시를 유지한다.
- 거래정지 등으로 예상 거래일의 행이 없으면 임의로 거래량 0을 생성하지 않는다. 공급자 응답으로 원인을 확인하지 못하면 unknown을 유지한다.
- 여러 조건에서 false는 종목을 제외할 수 있지만 unknown은 조건 미충족 건수와 분리한다. 결과 화면에는 ‘확인된 결과’와 미평가 종목 수를 보여준다.
- 코퍼스 변경 버전에 맞춰 커버리지 캐시를 무효화한다. 수집 없이 반복 조회할 때 날짜 인덱스를 매번 전량 재구축하지 않는다.

## 과거 수집기 보완과 저장 정합성

기존 수집기를 재사용하지만 다음 사항을 먼저 보완한다.

### 보정과 벤더 보유 이력

현재 수집기는 수정주가를 가장 오래된 단일 계수로 역보정한다. 기존 문서도 미보유 구간 안의 액면 이벤트가 있으면 재구성 원주가가 부정확할 수 있다고 명시한다. 2017년까지 확장할 때 이를 무검증으로 사용하지 않는다.

- 키움 `adjust=False`와 `adjust=True`의 날짜별 가격·거래량을 분할 구간 표본으로 비교한다. 같은 수정 기준일을 사용한다.
- 장기 구간은 검증된 실제 원주가를 저장하고 기존 계수 생성/갱신 경로를 재사용해 구간별 계수를 확보하는 것을 기본으로 한다. 필요 시 두 응답을 받아도 검색 반복 시에는 다시 호출하지 않는다.
- `derive_adjusted` 결과를 벤더 보정 일봉과 대조한다. 가격뿐 아니라 거래량과 최대거래량 발생일의 일치가 필수다. 표현 가능한 계수가 없거나 불일치하면 해당 종목은 실패 사유를 남기고 완전 평가 대상으로 공개하지 않는다.
- 현재 `backfill_probe.json`의 단일 earliest/빈 응답 기록은 특정 요청의 결과를 전 역사 보유 한계로 오해할 수 있다. 요청 범위·조회 완료 여부·재시도 가능한 실패·확인된 빈 구간을 구분하도록 확장한다. 범위 한 번의 빈 응답으로 종목 전체를 영구 제외하지 않는다.
- 코퍼스에 행 또는 계수가 전혀 없는 종목도 조용히 빠뜨리지 않고 초기 확보 또는 미지원 사유를 반환한다.

### 파일 쓰기와 재시작

- 기존 `daily_unadjusted.parquet`, `factors.parquet`, `daily_adjusted.parquet`을 사용한다. 차트 조회 캐시를 스크리너 저장소로 취급하지 않는다.
- `(code,date)` 기준 멱등 병합. 이미 가진 행은 보충 작업에서 불필요하게 덮어쓰지 않는다.
- 당일 갱신·과거 보충·계수 갱신·CLI가 같은 저장소의 writer 조정을 공유하도록 한다. 파일 교체만 원자적이어서는 동시 read-modify-write 유실을 막을 수 없다. CLI도 참여하는 저장소 단위 프로세스 간 잠금을 사용하고 네트워크 대기 중에는 잡지 않는다.
- 커밋 직전에 최신 파일을 다시 읽어 병합하고 임시 파일을 작성한 뒤 원자적으로 교체한다. raw/factors/adjusted 사이 여러 파일을 하나의 원자 트랜잭션이라고 가정하지 않는다.
- 작업 체크포인트에 파생 필요 상태를 기록한다. adjusted 공개 후에만 해당 버전의 완료 상태를 공개한다. 중단 시에는 마지막 완성 adjusted로 검색하고 미완료 저장은 재시작 때 복구·재파생한다.
- 배치 단위 체크포인트로 재시작 가능하게 한다. 매 종목마다 전체 Parquet를 재생성하지 않고 기존 배치를 기준으로 메모리·재작성 시간을 측정한다. 디스크 공간 부족·쓰기 실패는 완료로 표시하지 않는다.

## API·작업 수명·화면

제안 엔드포인트(구현 시 기존 업데이트 작업과 공통 구성 요소를 재사용):

| API | 역할 |
|---|---|
| `POST /api/screener/history/preview` | conditions+universe로 필요 구간·부족 종목 계산. REST 호출·디스크 쓰기 없음 |
| `POST /api/screener/history/jobs` | 같은 입력을 서버에서 재검사하고 보충 작업 생성. job id 즉시 반환 |
| `GET /api/screener/history/jobs/{id}` | 대기/수집/파생/완료/부분실패/중단 상태와 진행률 |
| `POST /api/screener/history/jobs/{id}/cancel` | 진행 중 요청 이후 안전한 배치 경계에서 중단 |

- 작업은 서버 소유다. 탭 종료·HTTP 연결 종료로 취소하지 않는다. 작업 대상 종목·조건·필요 구간은 시작 시 고정하며 중복 클릭은 같은 진행 작업을 반환한다.
- 기존 `kiwoom_access`/scheduler의 페이지별 background 호출·재시도 규칙을 사용한다. 전 종목별 별도 인증 클라이언트를 만들거나 운영 키를 개발 환경으로 복사하지 않는다.
- 프로세스 재시작 후 영속 작업 메타데이터와 실제 파일을 대조해 중단 상태를 복구한다. 명시적 재개는 남은 구간만 수행하며 이전 실패를 무한 자동 반복하지 않는다.
- 조회는 수집을 자동 시작하지 않는다. 부족 배너에 대상 범위·종목 수와 ‘과거 일봉 수집’ 버튼을 둔다. 수집 완료 시 원래 조건이 그대로일 때만 자동 재조회한다. 조건이 바뀌면 완료 알림과 재조회 버튼을 제공한다.
- 진행률은 종목 완료/전체, 저장 행 수, 실패 수, 수집/파생 단계를 구분한다. REST 호출 완료를 디스크 저장 완료로 표시하지 않는다.
- 우측 드로어도 날짜 조건 실행·부족 안내를 지원한다. 상세 수집 조작은 기존 전체 스크리너 페이지로 연결한다.
- 결과와 CSV에 충족일·거래량 증거를 추가한다. 결과의 현재 가격 날짜와 과거 충족일을 분리한다. 기존 클릭 시 종목 변경은 유지하고 발생일 차트 점프는 별도 후속 범위로 둔다.

- 기존 저장본의 로드/저장/조회 결과가 그대로이고 당일·최근 N일 조건 회귀가 없다.

- 분할 종목에서 디스크 파생 거래량과 벤더 수정 거래량 및 신고 발생일을 대조한다. 표본 API 테스트 성공만으로 이 단계의 성공을 대신하지 않는다.
- 프론트 E2E: 날짜 입력→부족 표시→수집 진행→완료→재조회→충족일 확인, 조건 변경 중 작업 완료, 기존 저장 조건 로드를 검증한다. 벤더 호출은 주입/모킹하고 개발 자격증명은 비운다.
- 대표 코퍼스에서 scan 시간, 최대 메모리, 배치 저장 시간, 추가 디스크 사용량을 측정·기록한다. 전 종목 이력 스캔이 이벤트 루프를 막지 않도록 기존 thread 실행을 유지한다.
- 구현 PR은 저장소의 CLAUDE.md 로컬 필수 검사(백엔드 lint/tests, 프론트 typecheck/tests/build/E2E)를 통과한다. 이 문서만 작성한 단계에서는 실행하지 않는다.

완료 조건: 사용자가 날짜 범위 조건을 저장하고, 부족한 일봉을 화면에서 수집해 디스크에 보존한 뒤, 충분한 데이터에서 확인된 종목·충족일·거래량을 조회할 수 있다. 다시 조회하거나 서버를 재시작해도 수집 결과를 재사용하고 미확인 구간은 명확히 구분된다.


## 구현 결과와 검증 기록 — 2026-09-09

- 날짜 범위 입력·거래일/연수 선택·기존 조건 저장 호환·충족일/거래량 표시·CSV 확장을 구현했다. 수집 상태도 빌더의 스크롤 영역에 포함해 조건이 많아도 접근할 수 있다.

- 신규 날짜 검색은 커버리지 평가의 종목 집합을 기존 scan에 합친다. 기존 최근 N일 SQL은 유지하며, 날짜 조건만 있는 조회는 당일 벤더 overlay를 생략한다.
- 장기 수집은 기존 키움 일봉 어댑터·페이지별 background governor·factor 계산·Parquet 파생을 사용한다. 기존 CLI의 단일 계수 역보정과 probe 형식은 그대로 두고, 화면에서 시작한 수집에는 원주가/수정주가 쌍을 검증하는 별도 조정 모듈을 사용했다. 불확실한 단일 earliest probe를 신규 수집의 전역 보유 한계로 사용하지 않는다.
- 계수 교체가 이후 저장 이력을 훼손하지 않도록 대상 종목의 기존 최초일부터 최근 확정일까지를 함께 검증한다. 16:00 이후에는 당일을 포함하고 기존 디스크 범위도 보존한다. 수집 중 범위가 늘면 잠금을 해제한 뒤 제한적으로 재조회한다. 최초 장기 수집은 단순 결손만 받는 것보다 호출량이 많을 수 있다. 이후 완성 구간 검색/재수집은 REST를 다시 호출하지 않는다. 거래량이 정확히 일치하지 않으면 해당 배치의 저장을 보류하고 사유를 표시한다.
- 20종목 단위로 파일을 파생·저장하며, 기존 당일 갱신·이력 CLI·계수 갱신도 공통 writer 잠금에 참여한다. 완성된 임시 파일을 준비한 후 publication journal을 기록하고 교체한다. 중단 후 다음 writer가 journal을 복구한다. 전원 장애 전체 트랜잭션 보증을 주장하지 않는다.
- 날짜별 누락 판정은 보수적이다. 공급자가 행을 주지 않은 거래정지/상장 전 구간은 0으로 채우지 않고 이력 부족으로 남긴다. 이 구간은 사용자 재수집에도 계속 부분 결과일 수 있다.
- 거래일 창은 예상 거래일의 누락을 숨기지 않도록 달력 기준 N개로 고정했다. 앞쪽으로 더 확장해 중간 결손을 대체하지 않는다. 이는 위 초기 계획의 종목 봉 수 기반 추가 확장 대신 선택한 방식이다.
- 벤더 오류는 요청 구간과 대상 목록이 고정된 작업 기록에 보존한다. 영구적인 벤더 보유 한계 목록은 만들지 않는다. 이후 scan은 공급자의 미제공을 영구 사실로 추정하지 않고 계속 이력 부족으로 표시하며, 사용자가 재시도할 수 있다.
- 보정 계수가 없는 기존 휴리스틱 파생 데이터는 날짜가 충분해도 미확인으로 분류하고 원주가·수정주가 쌍 수집 대상으로 삼는다. 기존 계수 저장소는 현 시스템의 보정 기준으로 유지한다.
