# /live 분봉 과거 팬 로딩 지연 — 병목 실측·확정과 개선 전략

날짜: 2026-07-20 (월, 23:00 장마감 후 실측)
상태: **구현 완료 (2026-07-20 밤)** — 결정은 ADR-0120에 수록.
사용자 선택으로 PR-A는 "키움 백그라운드 워밍 강등"이 아니라 **완전 삭제**로 착지했다.
관련: ADR-0116(키움 브로커 병행), ADR-0105(#574 스텝 폭 5거래일), ADR-0095(분봉
디스크 영속 거부), `docs/superpowers/plans/2026-07-07-live-minute-backfill-measurements.md`

## TL;DR

분봉 차트를 과거로 팬할 때의 지연은 **키움 ka10080 walk-back 프리페치(ADR-0116)가
스텝마다 '오늘'부터 재순회하는 구조** 때문이다. 최근 ~46거래일 구간의 콜드 스텝이
**11~29초**씩 걸리고, 역설적으로 46거래일보다 깊은 과거는 키움을 스킵하고 KIS
병렬로 직행해 **0.3~3.3초**로 훨씬 빠르다. 2026-07-11 실측 당시 지배 병목이던
KIS cold(0.3~1.9s/일)는 이제 2차 요인이다.

## 병목 메커니즘 (3중곱)

`hoga/live/live_candle_backfill.py` `_collect_for_venue` → `_kiwoom_prefetch`:

1. **walk-back은 항상 '지금'에서 시작한다.** ka10080은 cont-yn/next-key 순차
   페이지네이션뿐이라(요청 바디에 시작 날짜 파라미터 없음) 랜덤 액세스가 불가.
   스텝 k의 pending이 오늘로부터 D거래일 뒤면 매번 D×391÷900 ≈ D/2.3 페이지를
   처음부터 다시 삼킨다.
2. **키움 클라이언트 1 req/s 페이싱** (`kiwoom_client.py` `min_interval_s=1.0`,
   전역 락). 페이지당 ~1초 → 스텝 지연 ≈ 거리(거래일)/2.3 초. 실측과 정확히 일치
   (26거래일 → 11~13s).
3. **순회 봉의 ~90%를 폐기한다.** `_kiwoom_prefetch`는 `remaining_set`(이번
   collect의 pending 날짜)에 든 날짜만 `store_past` 하고 나머지 순회 데이터를
   버린다. 그래서 다음 스텝(5거래일 더 과거)은 같은 페이지들을 또 삼킨다.

프론트 settle-loop(`useViewportBackfill.ts`)는 5거래일/스텝 직렬이라 총비용이
**O(D²)**: 46거래일 팬 ≈ Σ(5+10+…+45)/2.3 ≈ 98페이지 ≈ **~98초**.

부차 확인 사항:

- `_KIWOOM_WALKBACK_REACH_DAYS` = 20페이지×900봉÷391봉 = **46거래일**. 이 밖은
  프리페치 스킵 → KIS 병렬(계정×3 슬롯, 15/s×4)이라 빠르다. "가까운 과거가 먼
  과거보다 10~30배 느린" 역전이 사용자 체감의 정체.
- 신규 코드 콜드 로드(최근 5거래일)도 매번 키움 walk 2~3페이지 = **2~3초** 지불.
- `max_fresh_dates_per_collect=12`는 KIS fresh만 제한 — 키움 캐시분은 무관.
- 응답 경고 키는 `data_warnings` (프로브 시 `warnings`로 읽으면 항상 빈 값).
- ADR-0116이 키움우선을 택한 근거는 **콜당 효율(900봉 vs KIS 120봉)과 KIS 유량
  보존**이지 벽시계가 아니었다. 인터랙티브 경로의 벽시계 회귀는 5거래일 직렬
  스텝과의 상호작용에서 발생한 것.

## 개선 전략

### PR-A (최대 지렛대, 백엔드): 인터랙티브 경로 KIS 복귀 + 키움은 백그라운드 워밍으로 강등

- `_collect_for_venue`의 `_kiwoom_prefetch` 인라인 호출 제거 → pending은 곧장
  KIS 병렬(fresh 예산 12 유지). 스텝당 콜드 0.3~3s로 복귀.
- 키움 walk-back은 **fire-and-forget 백그라운드 워밍 태스크**로 이동: 코드의 첫
  collect 후 최근 46거래일 전 구간을 1회 walk, **순회한 완결 날짜 전부**
  `store_past`(폐기 제거, C3 부분-경계일 제외 유지, 오늘 제외, per-code 320일
  쿼터 내 46일이라 여유). 이후 팬 스텝은 대부분 캐시 히트(~20ms).
  - 사실상 ADR-0103이 제거한 선행워밍의 재도입이되, **KIS가 아닌 키움 유휴
    쿼터로** — ADR-0116의 "KIS 유량 보존" 가치를 유지한다.
  - 워밍 단일-flight는 기존 `(venue, code)` 락 재사용. 1 req/s 전역 페이싱은
    백그라운드끼리만 경쟁(인터랙티브 경로가 키움을 안 타므로 무해).
- KIS 쿼터 영향: 워밍이 앞서면 인터랙티브 KIS 콜드는 드묾. 최악(워밍 미완 중
  팬)에도 스텝당 5일×~4콜=20콜, 60/s 대비 미미.
- 예상 효과: 46거래일 팬 ~98s → **3~10s(워밍 미완)** / **~1s(워밍 완료 후)**.
  신규 코드 콜드 로드 2~3s → ~0.5s.

### PR-B (프론트): 예산 배치 스텝 — 직렬 스텝핑(r1) 잔여 해소

- 3b 트리거가 동결한 budget이 2스텝 이상이면 **2스텝(10거래일)을 한 요청으로**
  병합(`nextFrom`을 2스텝만큼 전진). 10거래일 ≤ fresh 예산 12라 한 collect에서
  완결 — 예산 경고 없음. 2026-07-11 실측 근거: 배치가 순차 대비 3.2~5.7×.
- 부수 효과: prepend 커밋 횟수 절반 → 6-pane 풀 setData(r2) 비용도 절반.
- UN venue(키움 무관, 현재 2s/5일)도 이 PR로 개선.

### PR-C (관측): 프리페치·수집 텔레메트리

- `past_candles_collect` 로그에 kiwoom_prefetch 소요·페이지 수·저장 날짜 수 추가,
  `stats_snapshot`에 워밍 진행 상태 노출. HOGA_PERF_DEBUG 없이 INFO 1줄이면
  이번 같은 회귀를 로그만으로 판별 가능.

### 보류 (변경 없음, 판단만 기록)

- **분봉 디스크 영속(ADR-0095 거부 유지)**: 재검토 트리거 중 "`_fresh_past_fetches`
  상시 높음 + UX 불만"이 사실상 발동한 상태. 단 PR-A/B가 착지하면 재시작 후
  콜드도 키움 워밍이 수 분 내 흡수하므로, 착지 후 재평가가 순서.
- **키움 walk 커서 재사용(continuation resume)**: O(D²)→O(D) 대안이지만 PR-A가
  같은 문제를 더 단순하게 흡수 — 복잡도 대비 기각.

## 구현 결과 (2026-07-20 밤)

착지한 것: 키움 분봉 walk-back **완전 삭제** + 분봉 팬 **2스텝 배치 dispatch** +
**느린 collect 상시 WARNING**. 상세 결정·불변식은 ADR-0120.

**A/B 실측** — 같은 종목·같은 날짜를 구(:8000, 키움 경로)와 신(:8001, 워크트리)
