# 분봉 신고거래량 요약과 장중 체결 반영

사용자 요청: 2026-10-20. `최근 5봉 이내 · 100봉 신고거래량`처럼 조건 요약을
읽기 쉽게 바꾸고, 진행 중인 분봉의 기준 도달을 즉시 반영하며 전 시장 가능 여부를 검증한다.

## 적용 범위

- `기간내 신고거래량`: `1분봉 · 최근 5봉 이내 · 100봉 신고거래량`.
  최신 변형은 `1분봉 · 최신 봉 · 100봉 신고거래량`이다. 기간내 신고가도 같은 문장형을 쓴다.
- 후보를 포함한 M봉 최대·동률 인정·양의 거래량이라는 기존 의미와 저장 형식은 유지한다.
- 최근 방식의 분봉 `new_high_vol`·`new_high_vol_today`에 REST로 비교 봉을 준비한다.
  이후 부모 `LiveBuffer`의 KRX 원본 체결 누적거래량으로 진행 중 봉을 갱신한다.
  날짜 범위·완료봉 전용 API·일/주/월·가격 조건은 기존 경로를 사용한다.
- 부모 버퍼를 관찰하므로 운영 기본인 collector process와 inprocess 모두 같은 소비 경로를
  사용한다. 새 브로커 연결이나 구독을 만들지 않는다. hot path에는 REST·디스크·dataframe 연산이 없다.
- 해당 봉의 기준 도달이나 봉 교체가 있을 때 `screener_volume_changed`를 기존 `/api/ws`로
  발행한다. 서버 100ms, 클라이언트 250ms로 모아 페이지와 실행 중 감시 패널을 재조회한다.
  이는 예약 지연이며 전체 응답 시간 보장이 아니다. 정기 15/30초 조회도 유지한다.
  페이지는 사용자가 조회한 조건과 현재 편집 조건이 같을 때 자동 갱신하며 정렬을 보존한다.
- 재조회·탭 복귀·도달 신호가 겹치면 진행 중 요청 뒤 후속 조회 한 번으로 합친다.
  숨긴 탭·장마감·실패 백오프·감시 종료 게이트는 유지한다. 단, 정규장 검증을 통과한
  15:30 종가 체결 신호는 시세의 장마감 위상 전환 뒤에도 마지막 조회를 허용한다.

## 거래량 정합성과 수신 공백

REST 봉과 WS 봉은 합산하지 않는다. REST 준비 시점 이후 관측한 누적거래량 증가분으로
현재 봉을 전진시킨다. REST 요청 중 또는 최초 체결 관측 전의 거래는 정확히 분리할 수
없으므로 이 값은 보수적인 하한이다. 응답 `bar_match.volume_is_lower_bound`와 화면의
`최소 N주`로 구분한다. 이 하한이 확인된 과거 최대 이상이면 도달 사실은 성립한다.

동일 누적거래량의 중복 프레임은 무시한다. 다른 시장·장외·오래된 체결·누적거래량 없는
프레임은 사용하지 않는다. IPC gap·누적값 되감김·15초 초과 공백은 기준점을 다시 잡는다.
분 경계에서 누적 증가분과 관측 체결 수량이 다르면 누락분을 어느 봉에도 임의 배분하지 않는다.
불완전한 봉은 종료 후 비교 최대값으로 쓰지 않고 REST로 확인한다. 지연된 REST 응답은 이미
관측한 도달값을 덮어 지우지 않는다. 누락 때문에 실제 도달보다 늦게 잡히거나 REST 확인까지
평가가 일부 미확인일 수 있으며, 완전한 전 시장 무손실 감지를 주장하지 않는다.

## 전 시장 가능 여부

현재 구성으로 전 시장 동시 실시간 감지는 **지원할 수 없다**.

- 커밋된 마스터 시드 기준 KOSPI 917 + KOSDAQ 1,821 = 주식 2,738개.
  이는 조회 조건으로 선택한 실제 운영 유니버스 숫자와는 다르다.
- 현재 KRX/NXT/통합 동시 구독 정책의 등록 비용은 3,952개다. 계정당 200개,
  업종 예약 66개를 반영한 단순 슬롯 산술은 최소 21계정이다. 가상의 KRX 전용도
  최소 15계정이다. 계정 확대 가능성·벤더 허용 여부를 검증한 수치가 아니다.
- 기존 운영 서버 `/api/live/status`를 읽기 전용으로 확인했다. 설정은 6계정이다.
  장외여서 연결/ready 등록은 0이며 종목 계획값 337개를 실제 체결 수신으로 해석하지 않았다.
  별도 토큰 발급·자격증명 복사·서버 재시작·구독 확대는 하지 않았다.
- 이번 감시 상태는 최대 512개 `(종목, 주기, M, N)`·250,000봉으로 제한한다.
  같은 종목의 다른 조건도 상태 예산을 쓴다. 비활성 상태는 5분 후 만료한다.
- 기존 REST 신규 평가도 한 번 최대 64종목이다. 2,738종목을 30초 간격으로 한 바퀴
  돌면 조회 시간을 제외해도 43회·약 21.5분이다. 최근 5개 1분봉 조건의 전 시장
  누락 없는 감지 수단으로 사용할 수 없다.
- `bar_coverage.realtime`의 `prepared`와 `receiving`을 반환한다. receiving은 요청의
  지원 대상 분봉 거래량 조건 모두에 최근 15초 이내 체결을 받은 종목 수다.
  화면은 `장중 체결 반영 X/Y종목 · 나머지는 분봉 재조회`로 범위를 표시한다.
  거래가 드문 종목의 무수신도 포함하며, 브로커 등록 성공 수나 전체 필터 통과 수가 아니다.

별도 경로로 키움 서버 조건검색 `ka10173`이 있다. [공식 API 목록](https://openapi.kiwoom.com/m/guide/apiguide?dummyVal=0)에
실시간 조건검색이 있으며 [공식 사용안내](https://openapi2.kiwoom.com/intro?dummyVal=0)는
세션당 국내 조건 10개·조건 결과 최대 100종목을 명시한다.
[공식 조건검색 도움말](https://download.kiwoom.com/hero4_help_doc/KiwoomHero4_AdvancedSearch.pdf)에는
신고거래량과 기간 내 신고/신저거래량 항목도 있다. 따라서 전체 체결을 로컬로 받는 방식
밖에 대안이 없다고 단정하지 않는다. 다만 이 앱은 해당 경로를 사용하지 않으며,
`1분봉 · 최근 5봉 이내 · 후보 포함 100봉 · 동률 인정`과 공급자 조건식의 의미 일치,
진행 중 봉 반영·편입/이탈·결과 상한에서의 누락 여부를 실조회로 확인하지 않았다.
이번 작업에서 HTS 조건을 수정하거나 기존 WS 토큰으로 새 연결을 열지는 않았다.

재현 도구: `uv run python tools/measure_screener_volume_runtime.py`.
[측정 원본](../diagnostics/2026-10-20-screener-live-volume/capacity.json)은 합성 체결을
메모리 계산기에 직접 넣은 CPU 처리량이다. 네트워크·collector IPC·전체 검색·브라우저 지연은
포함하지 않는다. 5,000종목 입력 중 감시 예산 밖 체결은 무시하므로 그 처리량을 5,000종목
실시간 처리 성능으로 읽지 않는다. 실장중 공급자 지연과 전 시장 부하는 미검증이다.

## 검증 기록

검증 환경·결과·최종 입력 지문은 [verification.json](../diagnostics/2026-10-20-screener-live-volume/verification.json)에 기록한다.
주요 회귀 검사는 raw 체결 → 부모 버퍼 → 도달 이벤트 → 실제 HTTP 검색 응답,
현재 봉 하한 표기, 분 경계 누락·중복·시장 분리·캐시 역행·예산/만료·앱 종료 정리,
브라우저 페이지/드로어의 즉시 반영과 버스트 조회 합치기를 포함한다.

자동 회귀 검증은 별도 워크트리·무자격 서버로 수행했다. 2026-10-21 사용자 요청으로
PR #2202를 병합하고 고정 기본 체크아웃의 운영 서버에 적용했다. `/health`는
`ed74ebb19`이며 기존 Vite 화면과 단일 워커 reloader를 유지했다. 실장중 collector
process → 부모 버퍼 → WS 신호 → 후속 HTTP 검색도 확인했다. 대상 334종목 중
준비 종목은 첫 조회 64개·후속 128개이며 64개 신규 조회 예산에 따른 초기 준비가
필요하다. 실체결 지연·특정 도달 시점의 정답 비교나 전 시장 검증은 아니다.
앱 프로필·바로가기는 보존했고, UI 도구 부재로 실제 창의 직접 확인은 하지 못했다.
[배포 기록](../diagnostics/2026-10-20-screener-live-volume/deployment.json)을 참고한다.
최종 기준은 `1509d2a04`이고 최초 `d0798a77d` 이후 main의 차트·일봉 이력 보충·
커버리지 사유 개선을 fast-forward로 반영했다. 동일 파일의 충돌은 새 커버리지 필드·
사유별 안내와 체결 수신 범위를 함께 보존하도록 해소했다.
