# 과거 일봉 수집 종료와 저장 실패 정리

## 구현

- 앱 종료 시 해당 데이터 디렉터리의 과거 일봉 수집 작업을 취소·회수한 뒤 벤더 런타임을 종료한다. 종료가 시작되면 새 수집 요청은 503으로 거절한다.
- 스레드로 시작한 검증 데이터 게시와 미완료 게시 복구는 취소로 멈출 수 없으므로 완료까지 기다린다. 수집 작업은 `interrupted`로 기록한다. 실행 전에 취소된 작업도 같은 상태로 남긴다.
- 아직 게시를 시작하지 않은 메모리 배치는 종료 때 추가 조회·게시하지 않는다. 재개할 때 기존 디스크 커버리지를 다시 읽어 부족한 범위를 수집한다. 이미 게시한 데이터는 보존한다.
- 체크포인트 저장 실패는 로그에 남기고 나머지 서버 자원 정리를 계속한다. 디스크 실패 상황에서 상태 영속 성공을 보장하지 않는다. 기존 재시작 시 interrupted 판정 경로를 유지한다.
- 원자 쓰기의 임시 파일 소유·교체·정리를 공통 함수에 모은다. JSON 직렬화, 쓰기/fsync, 파일 교체 실패 시 자신의 임시 파일을 정리한다. 정리 자체가 실패하면 로그에 남기고 최초 저장 예외를 보존한다. Parquet에도 같은 정리 정책을 적용하며 포맷·압축·빈 records 삭제 계약은 유지한다.

## 진행 상태 저장 측정과 결정

임시 디렉터리에서 실제 JobCheckpoint.save를 30회 실행했다. 전체 파일 읽기·검증, 직렬화, fsync, 원자 교체를 포함한다. 로컬 합성 입력이며 운영 디스크·장중 부하 측정은 아니다.

| 종목 수 | 오류 없는 상태 크기 | 중앙값 / 최대 | 모든 종목에 합성 오류 140자 추가 시 중앙값 / 최대 |
|---|---:|---:|---:|
| 100 | 1,859 bytes | 0.08 / 0.30ms | 0.24 / 0.45ms |
| 1,000 | 14,459 bytes | 0.21 / 0.34ms | 2.27 / 4.00ms |
| 4,000 | 56,459 bytes | 0.68 / 0.99ms | 8.43 / 11.03ms |

현재 운영 병목이라는 근거가 부족하므로 진행률 저장을 별도 작업자로 옮기거나 저장 주기를 합치는 변경은 보류한다. 동기 저장은 여전히 이벤트 루프에 있다. 후속으로 실제 디스크 지연과 오류 기록 크기를 측정해 판단한다. 옮길 경우 취소 요청 보존, 단일 작성자, 종료 flush를 함께 설계해야 한다.

## 검증

- 변경 전 JSON/text fsync·교체·직렬화 실패와 정리 실패 로그 테스트 6개 실패 확인.
- 변경 후 기존 원자 쓰기·과거 수집/복구 및 신규 종료 검증 통과.
- 종료 시 수집 취소, 게시 스레드 완료 대기, 실행 전 취소, 다른 데이터 디렉터리 작업 보호, 새 요청 거절, 체크포인트 실패 후 종료 지속을 검증한다.
- 전체 백엔드, 프론트 타입 검사·Vitest·빌드 결과는 PR에 기록한다. 프론트 변경이 없어 E2E 재실행 대상은 아니다.
- 운영 서버 배포·재시작은 포함하지 않는다.
