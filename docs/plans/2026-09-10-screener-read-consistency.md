# 파일 게시와 읽기 캐시 정합성

## 문제와 구현

1. 과거 조건 평가가 새 수정계수와 옛 수정주가 거래량을 함께 읽고도 완료로 판정하는 중간 상태를 재현했다. `evaluate`의 파일 버전 판정과 평가를 공용 `.writer.lock`의 공유 잠금으로 보호한다. 기존 작성자들은 배타 잠금을 사용한다. 미완료 게시 마커가 있으면 공유 잠금을 놓고 기존 복구 경로를 배타 잠금 안에서 실행한 뒤 읽기를 재시도한다. 공유 잠금에서 직접 승격하지 않아 동시 복구자 간 교착을 피한다.
2. 같은 수정 시각·크기를 보존한 원자 교체에서 파일 캐시가 옛 값을 반환했다. `MtimeLruCache`는 device·inode·mtime_ns·ctime_ns·size를 비교하고 읽기 후 다시 확인한다. 읽기 중 바뀌면 최대 세 번 읽고, 계속 변하는 파일은 마지막 읽기 결과를 캐시하지 않고 반환한다.
3. 같은 파일에 동시 읽기 네 개를 실행하니 기존 구현은 파싱을 네 번 했다. 진행 중 로드를 파일 경로별 Future로 공유하도록 바꿨다. 회귀 테스트에서 네 요청의 파싱이 한 번이며 다른 파일은 기다리지 않음을 확인했다. 실패는 대기자에게 전파하고 다음 요청은 재시도할 수 있다. `clear()` 이전에 시작한 로드는 완료돼도 캐시를 다시 채우지 않는다.

## 범위와 제약

- 공유 잠금은 과거 조건의 `screener_history_coverage.evaluate` 경로를 보호한다. 모든 스크리너 쿼리를 하나의 트랜잭션으로 바꾸는 변경은 아니다. 이 경로의 운영 호출자는 기존처럼 스레드에서 실행한다. 잠금 중에는 벤더 조회를 하지 않는다.
- 잠금에 참여하는 작성자에 대해 같은 게시 상태를 읽는다. 외부 프로그램이 잠금 없이 직접 파일을 수정하는 경우의 일관성까지 보장하지 않는다. 동일 스레드의 작성자 잠금 안에서 읽기 잠금을 중첩하면 안 된다.
- 콜드 평가 중에는 작성자가 기다릴 수 있다. 결과 복사(deepcopy)는 잠금 밖에서 수행한다. 별도 버전 디렉터리·포인터 방식은 이번에 도입하지 않는다.
- 파일 캐시는 읽기 전용이며 값은 참조 공유다. 같은 캐시·경로의 로더는 같은 의미여야 하고 같은 경로를 재귀 로드하면 안 된다. max_entries=0 및 파일 stat 실패는 기존처럼 캐시를 우회한다.
- 파일이 계속 바뀌거나 원자 교체 대신 직접 수정된다면 엄밀한 최신 스냅샷을 보장하지 않는다. 불안정한 읽기를 캐시에 고정하지 않고 재시도 횟수를 제한한다.

## 검증

파일 교체·읽기 중 변경·clear 경쟁 테스트 세 개가 변경 전에 실패했다. 변경 후 게시 도중 조회 대기, 중단된 게시 복구, 동일 메타데이터 교체, 읽기 중 교체, clear 경쟁, 동시 로드 공유와 다른 파일 독립성, 실패 전파·재시도, 연속 변경 시 재시도 상한을 검사한다. 신규 8개 및 기존 관련 검사 통과. 전체 백엔드·프런트 타입/Vitest/빌드 결과는 PR에 기록한다.

프론트 변경이 없어 E2E 재실행 대상은 아니다. 운영 서버 배포·재시작은 포함하지 않는다.
