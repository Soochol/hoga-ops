# 토스 묶음 가격정정의 제한된 동시 처리

같은 계좌·종목의 서로 다른 원주문은 최대 2건의 정정 검증·전송을 겹쳐 진행한다.
호가주문은 개별 명령 API를 유지하며, 토스와 구 숫자 계좌 경로에서만 묶음 정정
작업자 2개를 사용한다. 키움·로컬 모의 주문과 기존 취소 정책은 유지한다.

`TradingService`의 정정 슬롯은 같은 TossClient를 쓰는 모든 계좌·종목이 공유한다.
2건은 요청 대기 중 독립 작업 하나를 진행시키는 보수적 자원 한도이며, 토스 TPS에서
도출한 동시성 보장이나 측정한 최적값이 아니다. 클라이언트의 `ORDER`와
`ORDER_HISTORY` 유량 대기·응답 헤더·429 처리는 그대로 적용한다.

## 잠금과 명령 수명

정정은 원주문 잠금 → 정정 슬롯 → 짧은 계좌·종목 잠금 순서로 진입한다. 마지막
잠금에서는 이미 `_commands`가 소유한 정정 task를 해당 종목의 진행 집합에 등록하고
즉시 잠금을 놓는다. 원주문 잠금과 슬롯 안에서 최신 상세 조회·잔량·관측 체결·기존
operation·금액 검사를 수행하고 전송·접수 기록을 마친다.

신규 주문은 계좌·종목 잠금을 유지한 채 등록된 정정 task들을 기다린 뒤 기존 검증과
전송을 수행한다. 새 정정의 등록은 그동안 대기한다. 이 순서는 신규 주문의 결과불명
검사가 아직 실행 중인 명령을 제외하는 기존 규칙을 보존한다. 정정이 `unknown`으로
끝나면 신규 주문은 저장된 결과불명을 확인하고 거절한다.

종목별 집합은 task의 추가 소유자가 아니라 기존 task를 찾는 인덱스다. task가 결과를
저장하고 `_commands`에서 빠진 뒤 동기적으로 제거하며, 완료 경로에서 종목 잠금을
다시 잡지 않는다. 신규 주문의 대기에는 각 task의 `shield`를 사용하여 대기자의 취소가
독립 정정을 취소하지 않게 한다. 슬롯 또는 원주문을 기다리는 미등록 정정은 아직
벤더 검증·전송을 시작하지 않았으므로 신규 주문이 먼저 진입할 수 있다.

취소는 기존대로 같은 원주문의 잠금만 사용한다. 같은 native ID의 정정·취소는 접수
기록까지 서로 배제한다. old→replacement 체인은 임의 root ID로 묶지 않는다. old의
다음 요청은 저장된 operation과 결과불명을 검사하고, replacement에 대한 요청은 그
ID의 최신 편집 가능 상태를 다시 확인한다. ACK가 늦어도 완전한 새 주문 상태를 조회하기
전에는 정정 가능한 것으로 간주하지 않는다.

## 화면과 실패

묶음은 원래 계좌·종목·대상·명령 ID를 캡처하고 창 닫기·종목 전환 뒤에도 그 명령으로
마무리한다. 실패한 하위 요청의 ID와 부분 접수·결과불명·재확인 정책, 한 동작의 접수음
한 번, 계좌별 조회 중단/재개를 유지한다. HTTP ACK만으로 화면의 가격·수량을 완료
처리하지 않으며, 확인된 WS 주문 상태 또는 REST 대조만 사다리에 반영한다.

상세 조회 공유·새 batch API·새 설정은 도입하지 않는다. 개별 주문의 접수·완료 시점과
실패가 다를 수 있고, 원자적 일괄 정정이나 실사용 개선 초수를 보장하지 않는다.
공식 근거는 [토스 API 소개](https://openapi.tossinvest.com/openapi-docs/overview.md)의
Rate Limits와 [공식 OpenAPI](https://openapi.tossinvest.com/openapi-docs/latest/openapi.json)의
단일 주문 정정·상세조회 정의다.

검증은 실제 명령 엔진/저널과 가짜 벤더 HTTP, production 빌드 Chrome의 mock HTTP/WS로
수행한다. 첫 ACK를 보류해도 독립 정정 2건이 진행되고 같은 원주문·신규 주문의 보호가
유지되는지 확인한다. 실전·모의 계좌 API로 한도를 탐색하지 않는다.
