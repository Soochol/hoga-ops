# 스크리너 일봉 스냅샷 재사용

오후장 공략은 분봉 원본·WS 판정을 재사용하더라도 v2 runner가 확정 시각, 표시용 일봉,
일봉 검증 메타데이터를 매번 다시 읽었다. 350종목에서 1,402회 객체 읽기와 전체 JSON
체크섬/확인 표본 검증이 반복됐다. 사용자가 같은 일봉 스냅샷의 검증·표시 자료 재사용과
실제 재조회 속도 확인을 승인했다.

`screener_snapshot_cache`는 data_dir·전체 manifest 내용·처리 종류·종목 집합·조회 날짜/
기간으로 일봉 파생 자료를 구분한다. `_confirmed_at`, `_daily_contract`와 32일 이하의
표시/최근 일봉 `load_series`만 재사용한다. 긴 과거 일봉 범위는 기존 읽기를 유지한다.
WS 분봉·일봉 overlay·순위·제외 목록·최종 조건 판정/결과는 캐시하지 않는다.

검증된 객체와 baseline 파일의 device/inode/크기/mtime/ctime을 기록해 재사용 전에
변경 여부를 확인한다. 파일 교체·삭제·변조·스냅샷/정정/품질 guard/수량 이력 변경은
재검증한다. 준비 중 바뀐 자료와 오류는 정상 캐시에 승격하지 않는다. baseline의 기존
체크섬 검증 캐시도 같은 파일 지문을 사용해 mtime 복원으로 검증을 건너뛰지 못하게 한다.

동일 입력의 동시 요청은 준비를 공유한다. 결과는 프로세스에서 직접 만든 pickle
바이트로만 메모리에 보관하고 호출마다 복원해, 행·set·Pydantic 수량 이력의 변경이
다른 조회나 장중 overlay에 전파되지 않게 한다. 외부 pickle을 읽거나 디스크에 저장하지 않는다.
LRU 128항목, 직렬화 자료·경로 예약 바이트 예산 64MiB, 항목당 8MiB 상한을 적용한다.
서버 재시작/축출/스냅샷 변경 뒤 첫 준비 비용은 남는다. 분봉 캐시의 기존 예산은 별개다.
