# 개발 환경과 Vite 진단

새 워크트리 설치, 서버 기동, `.env` 상속, Vite 캐시 문제를 다룰 때 읽는다.
일반 설치·기동 명령은 [README](../../README.md), 에디터 작업은
[.vscode/tasks.json](../../.vscode/tasks.json)이 기준이다.

## 서버 기동 전

1. 실행 중인 서버의 포트·프로세스·체크아웃을 확인한다. 필요한 서버만 띄우며,
   이미 사용 중인 5173·8000을 비우려고 다른 프로세스를 종료하지 않는다.
2. 워크트리별 포트와 데이터 경로를 정한다. 프론트에서 별도 API에 연결한다면
   런타임 `config.json`과 백엔드의 허용 origin도 맞춘다.
3. 개발 서버는 루프백에 바인딩한다. LAN 노출이 목적일 때만 공개 바인딩을 선택한다.
4. 백엔드 자동 갱신에는 `uvicorn hoga.api.app:default_app --factory`와
   `--reload --reload-dir hoga`를 사용한다. `hoga serve`는 `reload=False`다.
   `--factory`는 앱 팩토리 호출에 필요하고 reload 범위는 프론트 편집으로 인한 재시작을 막는다.
5. 백엔드는 단일 워커를 유지한다. 기동 후 `/health`의 상태·버전·커밋을 확인한다.

## 자격증명과 데이터 가용성

- 개발·워크트리는 무자격으로 실행한다. 실자격증명은 prod에만 둔다.
  같은 키로 별도 프로세스를 띄우면 WS 연결이 충돌하거나 토큰 재발급으로 기존 연결이 멎을 수 있다.
- [hoga/env.py](../../hoga/env.py)는 워크트리 `.env`가 없으면 메인 체크아웃 것을 찾는다.
  상속을 막으려면 **기존 파일이 없는 경우** 워크트리에 빈 `.env`를 둔다.
  기존 `.env`를 덮어쓰지 않는다. 셸에 이미 설정된 값은 빈 파일로 지워지지 않는다.
- E2E는 [playwright.config.ts](../../frontend/playwright.config.ts)의 빈 환경변수로 키를 차단한다.
  `load_dotenv(override=False)`가 환경변수의 존재를 존중하므로 빈 문자열도 상속을 막는다.
  `HOGA_DATA_DIR`만 바꾸는 것으로는 자격증명이 격리되지 않는다.
- 국내 주식 실시간 WS·폴링 REST는 키움, KIS는 옵션 심리 등 파생 경로를 담당한다.
  키가 없는 개발 환경의 실시간·벤더 조회 부재를 인증 장애로 오인하지 않는다.
  분담 근거는 [ADR-0136](../adr/0136-kis-removal-kiwoom-full-replacement.md)에 있다.
- 종목 검색은 커밋된 [마스터 시드](../../hoga/api/kiwoom_master_seed.json),
  거래일 조회는 [정적 달력](../../hoga/api/trading_days_seed.txt)과 오버레이를 이용한다.
  달력 커버리지 밖은 모름이며, 범위 캡처의 뒤쪽 꼬리만 평일 근사와 경고를 사용한다.

## 프론트엔드 의존성

- 새 워크트리의 `frontend/`에서 의존성을 설치한다. `vite: not found`이면 설치 여부부터 확인한다.
- `node_modules`는 워크트리별로 유지한다. 공유 링크는 의존성 갱신을 다른 작업에 전파하고,
  체크아웃 밖의 파일을 Vite가 제공할 때 접근 범위 문제를 만들 수 있다.
- Vite의 HMR을 사용한다. 에디터에서 기동할 때도 `.vscode/tasks.json`의 실제 명령·포트가
  현재 작업 환경에 맞는지 확인한다.

## Invalid hook call / 특정 라우트만 실패할 때

1. 콘솔·네트워크에서 어떤 라우트와 모듈이 실패하는지 기록한다.
   저장된 조회 결과가 없어 문제 컴포넌트 자체가 안 뜬 브라우저는 비교 대상이 아니다.
2. React 중복 로딩 경고와 의존성 청크의 응답·판본을 함께 확인한다.
   청크 파일명이 다르다는 사실만으로 중복 React를 확정하지 않는다.
3. [vite.config.ts](../../frontend/vite.config.ts)의 실제 `cacheDir`을 확인한다.
   현재 값은 `.vite-cache`이므로 dep 캐시는 `frontend/.vite-cache/deps`에 있다.
   같은 디렉터리를 사용하는 Vite 프로세스가 둘인지, 캐시가 언제 갱신됐는지 대조한다.
4. 과거의 `node_modules/.vite` 공유 사고는 #1764에서 캐시 경로를 분리해 막았다.
   **같은 체크아웃에서 같은 캐시를 쓰는 Vite 두 개**는 여전히 충돌할 수 있다.
   당시 원인과 변경 근거는 `vite.config.ts`의 `cacheDir` 주석에 있다.
5. 판본 불일치가 확인되면 자기 작업의 Vite만 정리하고 `--force`로 재기동한다.
   기존 포트·설정·API 연결을 유지한다. 사용자 서버의 재시작이 필요하면 근거를 알린다.

브라우저 저장소 전체 삭제는 이 서버 캐시 문제의 해결책이 아니다. 기존 상태를 보존한 채
같은 origin·종목·설정으로 확인하고, 필요한 경우 별도 프로필과 비교한다.
