# 화이트보드 구현 계획 — 보드 목록 함께

작성일: 2026-10-24 (KST)
상태: 구현·자동 검증 완료. 실제 OS 입력기 후보창/설치 앱 배포 범위는 검증 기록 참조
디자인 기준: 대화에서 사용자가 선택한 미리보기의 **「보드 목록 함께」** 배치

## 1. 목표와 승인된 화면

상단 **캡처** 오른쪽에 **화이트보드**(`/whiteboard`)를 추가한다. 좌측 보드 목록과
중앙 편집 공간을 함께 보여 주고, 여러 차트 이미지·메모·텍스트·도형·화살표를
자유롭게 배치해서 저장하고 다시 편집할 수 있게 만든다.

화면 기준은 다음과 같다.

- 앱 상단: 기존 Ticklane 브랜드와 메뉴를 유지하고 마지막에 화이트보드를 배치한다.
- 좌측: 내 보드, 새 보드, 선택된 보드 강조, 보드별 짧은 보조 정보.
- 중앙 상단: 보드 이름 편집, 저장 상태, 이미지 추가, 내보내기, 새 보드.
- 캔버스 상단: 선택·텍스트·메모·도형·화살표·펜·실행 취소 도구.
- 캔버스: 점 격자, 이미지와 메모를 자유롭게 배치하는 공간.
- 캔버스 하단: 확대/축소와 필요한 상태 안내.
- 앱 우측: 기존 RightRail과 사용자가 열어 둔 패널을 공유한다.

시안의 가상 삼성전자 차트·복기 노트·아이디어·섹터 흐름은 예시 데이터다.
실제 앱 첫 실행에는 빈 보드와 짧은 시작 안내를 제공하며 가상 자료를 사용자 자료로
저장하지 않는다. 이미지만을 위한 기능으로 제한하지 않고 범용 보드로 제공한다.

범용 표 편집기는 후속 범위다. 이번 구현에 필요하지 않은 상시 상태판·패널은 추가하지 않는다.

## 3. 구현 원칙과 먼저 해소할 불확실성

### 편집기 선택

기본 후보는 `@excalidraw/excalidraw`다. 실제 설치할 안정 버전의 React 18 호환성과
공개 API를 확인하고 버전을 고정한다. 프로젝트 전체 React 업그레이드를 전제로 삼지 않는다.

현재 시안은 Excalidraw를 붙인 제품 화면이 아니라 직접 만든 상호작용 목업이다.
따라서 시안과 편집기의 UI 적합성은 **단계 0에서 실제로 검증**한다.

- 공개 API와 공식 스타일 변수로 앱 테마, 도구, 확대/축소, 파일 동작을 연결한다.
- 내부 DOM 변경에 기대어 편집기 기본 UI를 대량으로 숨기거나 private API를 호출하지 않는다.
- 앱 셸·좌측 목록·헤더·색상·배치는 시안을 기준으로 구현한다.
- 캔버스 안 도구/속성 UI의 차이, 한글 글꼴과 입력, 메모의 편집 감각을 실화면으로 비교한다.
- 중요한 배치나 기본 동작을 충족하지 못하면 원인과 대안을 검토한 뒤 엔진을 확정한다.
  차이를 숨긴 채 시안과 동일하다고 보고하지 않는다.
- 메모는 배경 도형과 연결된 텍스트로 구현할 수 있지만, 이동·크기·텍스트 편집·복제·
  삭제·실행 취소에서 하나의 메모처럼 동작하는지를 검증한다.

### 기존 앱과의 경계

- `DESIGN.md`의 현재 테마·폰트·밀도·툴팁·크기 토큰을 따른다. 선택한 배치를 문서화하되
  기존 페이지의 시각 기준을 별도로 변경하지 않는다.
- 편집기와 전용 CSS·폰트는 화이트보드 진입 때만 로드한다. 폰트/자산은 자체 제공하여
  인터넷 연결이 없어도 로컬 서버의 보드를 편집하고 내보낼 수 있게 한다.
- `/live`의 Drawing은 종목·시간·가격 좌표 소유이고, 보드는 자유 좌표 소유다.
  기존 `useDrawingsStore`나 차트 좌표계를 보드 저장소로 재사용하지 않는다.
- 시세 WS 구독이나 차트 데이터 수집을 보드 편집 때문에 새로 만들지 않는다.
- 편집기 데이터는 하나만 정본으로 두고, React/Zustand에 매 프레임 전체 장면을 복제하지 않는다.

## 4. 데이터와 저장 계약

### 소유권

- 정본은 접속한 서버의 `<data_dir>/whiteboards/`에 저장한다. 브라우저와 Electron에서
  같은 서버에 연결하면 같은 보드를 읽는다. 다른 서버의 보드는 서로 섞지 않는다.
- 보드 문서는 보드 ID·이름·스키마 버전·정수 revision·생성/수정 시각·편집기 버전·
  scene·이미지 참조·선택적 차트 출처를 가진다.
- 서버 API 모델과 `frontend/src/api/whiteboards.ts`는 같은 wire 형태로 유지한다.
  편집기 scene은 버전이 있는 payload로 보존하고, 알 수 없는 정상 편집기 필드를
  임의로 제거해서 재편집 데이터를 손상시키지 않는다.
- 마지막 보드·확대/축소·이동 위치 같은 개인 보기 상태는 문서 내용과 구분한다.
  선택 도구·포커스·실행 취소 스택을 서버 문서에 그대로 저장하지 않는다.
- 이름 변경은 문서 revision에 포함한다. 확대/축소만으로 문서 변경·충돌을 만들지 않는다.

### 파일 구조와 무결성

- 보드별 JSON 문서를 정본으로 삼고 이미지 바이너리는 별도 파일로 보관한다.
  목록은 문서 메타데이터에서 복원 가능하게 하며, 목록 캐시가 장면의 정본이 되지 않게 한다.
- 기존 `atomic_write_json`의 원자적 교체 패턴을 활용한다. 문서 저장 중 실패하면
  마지막 정상 문서가 유지되어야 한다. 여러 파일의 원자성을 가정하지 않는다.
- 이미지를 먼저 확정 저장한 뒤 해당 파일을 참조하는 문서를 저장한다.
  참조 대상이 없는 문서를 저장 완료로 처리하지 않는다.
- 이미지 중복은 내용 해시로 줄이고, 원본 파일명을 서버 경로로 사용하지 않는다.
- 삭제 보드는 휴지통 상태로 보관하고 복원한다. 첫 완성 버전에서 영구 삭제/자동 이미지
  청소를 서두르지 않는다. 복제 보드·휴지통·복구 초안에서 쓰는 이미지를 지우지 않는다.
- 구버전 자료는 이관하거나 원본을 보존한 채 안내한다. 기존 preset 저장소의
  구버전 폐기 정책을 사용자 보드에 그대로 적용하지 않는다.

### 자동 저장과 복구

- 권장 시작값: 변경 후 750ms 디바운스, 계속 편집해도 최대 5초 간격으로 저장 시도.
  보드별 저장 요청은 하나씩 직렬화하고 최신 변경을 합쳐 후속 저장한다.
- 매 저장에 `expected_revision`과 재시도 식별자를 전달한다. 서버는 같은 lock 안에서
  revision 확인과 쓰기를 수행한다. 타임아웃 후 재시도로 중복 생성/변경을 만들지 않는다.
- 저장 중 추가 편집이 있으면 이전 응답으로 최신 dirty 상태를 지우지 않는다.
  보드 A의 늦은 응답을 보드 B에 적용하지 않는다.
- IndexedDB에는 서버 식별자·보드 ID·기준 revision과 함께 복구 초안과 미저장 이미지를
  보관한다. 크고 민감한 이미지 자료를 localStorage 문자열로 반복 저장하지 않는다.
- 저장 담당 수명과 페이지 컴포넌트 수명을 분리한다. SPA의 라우트 전환만으로 진행 중인
  저장이나 초안이 사라지지 않게 한다. 보드 선택 중 로딩도 요청 ID로 구분한다.
- 새로고침/창 닫기 시 마지막 네트워크 요청만 믿지 않는다. 서버/초안 확인 전에는
  복구 가능하다고 단정하지 않고, 실제 복구 경로를 테스트한다.
- 저장 상태: `변경됨 → 저장 중 → 저장됨`, 실패·충돌·로컬 초안 실패는 각각 구분한다.
  서버 장애 때는 초안을 유지하며 재시도/편집 파일 백업을 제공한다.
- 복수 탭·Electron 복수 창에서 같은 보드를 편집하면 자동 덮어쓰기를 막는다.
  충돌 시 내 편집을 보존하고 최신본 열기 또는 내 편집을 새 보드로 저장할 수 있게 한다.
- 브라우저 초안 저장은 즉시/무한 보존을 보장하지 않는다. 서버와 브라우저 모두에 아직
  기록되지 않은 변경 또는 저장 용량 부족은 사용자에게 실제 상태대로 알린다.

### 이미지/가져오기 제한

- 첫 지원 포맷: PNG/JPEG/WebP. 파일 크기와 디코딩 후 픽셀 수를 모두 제한한다.
  한도는 대표 차트 이미지 실측 후 확정하고 파일별 실패 이유를 표시한다.
- 큰 이미지는 미리보기/작업용 크기로 줄이는 정책과 원본 보존 여부를 명확히 한다.
  사용자 모르게 작은 글씨를 읽을 수 없는 수준으로 축소하지 않는다.
- 여러 이미지 처리에 순서·중복 방지·부분 실패·취소를 지원한다. 실패한 업로드만 재시도한다.
- `blob:` URL을 영속 참조로 저장하지 않는다. 사용이 끝난 메모리 URL을 해제한다.
- 편집 파일은 이미지까지 포함하는 자체 완결 파일이어야 한다. scene JSON만 내려받고
  이미지는 서버 경로에 남기는 상태를 백업 성공으로 처리하지 않는다.
- 가져오기는 크기·스키마·이미지·참조를 검증한 다음 새 보드로 만든다.
  손상 파일 때문에 열려 있던 보드나 기존 자료를 변경하지 않는다.

## 7. 최종 완료 시나리오

1. 캡처 옆 화이트보드에서 새 보드를 만들고 한글 이름을 입력한다.
2. 파일·드롭·클립보드로 차트 이미지 세 장을 넣고 위치/크기를 조절한다.
3. 메모·텍스트·도형·펜을 추가하고 화살표로 연결한다.
4. 메모 편집·다중 선택·그룹·복제·잠금·삭제·실행 취소/다시 실행을 사용한다.
5. 다른 보드와 라이브 페이지로 이동한 뒤 돌아와 내용과 보드별 보기를 확인한다.
6. 저장 직후 새로고침·서버 재시작·앱 종료 후 다시 열어 이미지/메모를 확인한다.
7. 저장 중 연결을 끊고 편집한 다음 재연결해 초안과 서버 상태를 복구한다.
8. 두 창에서 같은 보드를 수정해 한쪽의 변경이 조용히 사라지지 않는지 확인한다.
9. PNG와 편집 파일을 저장하고 새 프로필에서 편집 파일을 가져온다.
10. 보드를 복제한 뒤 원본을 바꿔 복사본이 유지되는지 확인하고, 삭제 후 복원한다.
11. 실제 차트의 보드에 추가를 사용하고 출처 링크로 돌아간다.
12. 기존 라이브·캡처·저장뷰·드로잉·테마·창 배치의 대표 동작을 확인한다.

앱 종료 직전 또는 프로세스 강제 종료에서 어떤 변경까지 복구되는지 실제 기록으로
구분한다. 아직 내구성 있는 저장에 도달하지 않은 마지막 입력까지 보존한다고 주장하지 않는다.

## 8. 검증과 진행 관리

- 단계 0 → 1 → 2 → 3 → 4 → 5 → 6 → 7 순으로 진행하고 각 단계의 증거와 미해결 사항을 기록한다.
- 조작과 무관한 구현 복제 테스트 대신, 저장 순서·revision 경합·이미지 참조·한글 입력·
  이미지 포함 파일 왕복·실제 포인터 조작과 같은 사용자 결과를 검증한다.
- FE: 타입 검사·관련 단위/컴포넌트 검사·빌드, 편집/레이아웃/드래그 관련 Playwright E2E.
- BE: 관련 저장소/HTTP/파일 실패 검사·wire 계약 검사·Ruff. 최종 범위는 저장소 지침에 따라 정한다.
- 최종 시점에는 최신 main을 반영한 코드의 영향을 확인한다. 통과 기록에는 명령·범위·
  head/base SHA·입력/환경 지문을 남기며, 유효한 동일 입력 결과는 재사용한다.
- E2E는 `workers: 1`, 별도 포트/데이터와 무자격 환경을 사용한다. 사용자 5173/8000 서버를
  종료·재시작하거나 실자격증명을 상속하지 않는다.
- 브라우저 확인은 저장소 `/browse` 경로를 우선한다. 이 환경에는 지정 스킬이 없었으므로
  구현 시 재확인하고, 계속 없으면 사용 가능한 브라우저 도구로 실제 조작 결과를 확인한다.
- 사용자 데스크톱 설치 경로·바로가기·AppArmor 설정은 이번 페이지 추가 때문에 바꾸지 않는다.
  설치/실행 경로 작업이 필요해지면 CLAUDE.md의 고정 설치 경로 규칙을 먼저 적용한다.
- 계획 작성 단계에서는 앱 코드·의존성·서버·실제 사용자 보드를 변경하지 않는다.
