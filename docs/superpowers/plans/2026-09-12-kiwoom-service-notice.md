# 키움 점검 및 연결 상태 표시 계획

## 목표
휴장과 공급사 서비스 상태를 분리하고 모든 페이지에서 점검을 알린다. 공지 근거 없이 연결 실패를 점검으로 단정하지 않는다.

## 구현 순서
1. 서버 서비스 상태 모델: 미설정/연결 확인 중/연결 불가/일부 연결/실시간 연결 정상. 거래 틱 대신 연결과 최근 제어 응답을 사용한다.
2. 전달받은 2026-09-12 08:30–20:00 KST 공지를 등록한다. 출처는 사용자 제공 공지로 명시한다. 추가 공지는 데이터 디렉터리의 `kiwoom-maintenance.json`으로 관리한다.
3. 공지 예정/진행/종료 예정 경과를 서버 시각으로 계산한다. 종료 시각만으로 복구 처리하지 않는다. 종료 이후 모든 계정의 최근 응답이 확인되면 실시간 연결 복구를 기록하며, 재시작 후에도 이전 공지가 재등장하지 않도록 저장한다. REST 전체 복구로 표현하지 않는다.
4. 상단 내비게이션 바로 아래 모든 페이지 공통 배너를 추가한다. 시장 상태는 기존 표시를 유지하고, 키움 영향과 마지막 실시간 수신을 별도로 표시한다. 상태 API 실패 시 캐시를 정상으로 단정하지 않는다.
5. 주말 미연결, 공지 경계, 종료 후 미복구, 실제 연결 복구 및 복구 기록 유지, 서버 상태 조회 실패를 테스트한다.

## 범위
차트 값, 시장 시간, 수집 스케줄, 재시도 정책은 변경하지 않는다. 공지의 홈페이지/HTS/MTS 중단 범위를 REST API 전체 장애로 자동 해석하지 않는다. 공급사 공지 자동 크롤링은 하지 않는다. 데이터 카드별 기존 최신성 표시는 유지하고, 전역 배너에서 마지막 실시간 수신 및 저장 데이터 가능성을 안내한다.

## 공지 운영
`<data_dir>/kiwoom-maintenance.json`이 없으면 이번 사용자 제공 공지를 사용한다. 다음 JSON으로 새 공지를 등록하거나 변경한다(시각은 epoch 밀리초, KST 기준 입력). 공지를 제거하려면 파일 내용으로 `null`을 저장한다. 공지를 새로 발행하거나 기간을 연장할 때는 `id`도 변경한다.

```json
{"id":"kiwoom-20260912","starts_at_ms":1789169400000,"ends_at_ms":1789210800000,"reason":"KRX 애프터마켓 이행 관련 시스템 작업","source":"사용자 제공 키움 공지 · 홈페이지/HTS/MTS 전체 서비스 중단"}
```

`kiwoom-maintenance-recovered.json`은 실시간 복구 확인 기록이다. 정상 연결은 모든 설정 계정이 연결되고 각 계정의 제어 응답이 최근 120초 이내인 경우이며, 공지 해제에는 그 응답이 종료 예정 시각 이후여야 한다. 거래 틱 부재는 휴장 때 정상이므로 사용하지 않는다. 이 기록은 REST 복구 증거가 아니다. 공지 파일 오류는 배너로 알린다.

## 완료 및 검증
- 서버 상태/API 회귀 테스트 17개 통과.
- UI 상태 투영·배너·앱 레이아웃 관련 테스트 46개 통과.
- Playwright: 휴장 상태의 market 상단 배너, 본문과 비중첩, live 페이지 전환 후 유지 통과. 실제 점검 응답을 본뜬 고정 fixture로 검증했다.
- 전체 frontend TypeScript 검사, 변경 파일 ESLint 및 Ruff, diff 공백 검사 통과.
- REST 전체 가용성 측정과 공지 자동 수집은 범위 밖이며, UI도 실시간 연결 복구로만 표현한다.

## 후속: WS·REST 자동 오류 분류
- 실제 키움 REST 호출(토큰 발급 포함)과 WS 연결/로그인 실패를 관측한다. 인증 실패, 호출 제한, 타임아웃, 전송 실패, 서버 오류, 요청 거절, 미분류 오류로 나눈다.
- 인증 서버의 5xx/일시 장애는 앱키 불량으로 표시하지 않는다. HTTP 상태·예외 타입을 사용하며 원문 문구만 보고 점검을 추정하지 않는다.
- 오류는 계정 클라이언트 및 API별로 추적한다. 해당 요청이 성공하면 해제한다. 다른 계정의 성공이나 늦게 끝난 이전 요청으로 지우지 않는다. 사용 중지한 클라이언트는 정리한다.
- API 조회 오류는 WS 연결이 정상이어도 전역 배너에 표시한다. 마지막 실패 시각을 명시하며, 오류 상세에서 안전한 코드만 제공한다. 원문 응답·토큰·요청 본문은 전송하지 않는다.
- 별도 진단용 요청을 발생시키지 않는다. 후속 요청이 없으면 마지막 실패가 계속 표시되며, 서버 재시작 시 관측은 초기화된다. 공지와 실측 오류는 별도로 표시한다.

## 수정: 휴장일 복구 확인
이전 WS 전 계정 복구 조건은 `ws_connection_window`가 닫히는 휴장일/20시 이후에는 충족되지 않는다. 서비스 상태에 `paused`를 추가하여 의도된 연결 대기를 장애 배너로 표시하지 않는다.

점검 종료 예정 시각 이후 상태 폴링에서 FastAPI BackgroundTasks로 조회 전용 `ka10001`(삼성전자 종목정보)을 확인한다. 기존 유량 거버너와 background 우선순위를 사용하며, 진행 중 중복 요청을 차단하고 최소 60초 간격·15초 대기 상한을 적용한다. HTTP 성공뿐 아니라 정상 파싱된 가격 필드가 있는 응답을 확인해야 점검 복구 기록을 저장한다. 이후 상태 폴링(5초)에서 배너가 내려간다. 빈 응답·실패·요청 중 공지 변경은 복구로 처리하지 않는다.

이는 대표 조회 API의 복구 증거이며 전 계정·전체 서비스 정상 보장이 아니다. 다른 API의 오류는 별도로 유지한다. 공지 상태 조회를 하지 않는 동안에는 별도 상시 프로브를 돌리지 않는다.
