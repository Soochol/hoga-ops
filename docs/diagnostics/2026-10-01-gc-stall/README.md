# 키움 실시간 GC 정지 조사

2026년 10월 1일 서버 로그와 분리된 재현 실험으로 조사했다. GC가 실시간 수신을
멈추고 여러 계정의 수신 큐 초과와 재연결로 이어지는 경로는 확인됐다. 큰 수거 대상
객체를 만드는 운영 경로는 아직 확정되지 않았다. Python 3.14.4의 GC 구현과
버전별 의미를 구분하지 않는 앱의 GC 튜닝을 우선 검증할 후보로 좁혔다.

## 운영에서 확인한 사실

대상은 메인 체크아웃의 8000번 서버다. PR 1909의 머지 커밋 `6238a93f8`을
pull한 뒤 12시 24분 24초에 자동 갱신된 프로세스 PID 4047085를 관찰했다.
시간은 모두 KST다. 원본 로그는 `~/.local/share/hoga-ops/logs/hoga.log`다.

| 시각 | GC 정지 | 수거된 객체 | 결과 |
| --- | ---: | ---: | --- |
| 12:30:11 | 1.898초 | 238,974 | 이벤트 루프 지연 1.862초 |
| 12:34:13 | 3.564초 | 502,081 | 이벤트 루프 지연 3.197초 |
| 12:41:35 | 5.460초 | 905,240 | 이벤트 루프 지연 5.305초와 4개 계정 수신 큐 초과 |
| 12:50:26 | 6.339초 | 1,107,156 | 이벤트 루프 정지 관측 |
| 13:01:37 | 7.570초 | 1,343,003 | 4개 계정 수신 큐 초과 |

전부 `gen=1`, `uncollectable=0`이다. 수거되지 못하는 객체가 없다는 사실은 누수
전체를 배제하지 않는다. 반대로 수거 건수가 크다는 사실만으로 영구 누수라고
판정할 수도 없다. GC가 작업한 지점의 `trade_date`, `record`, `_parse_orderbook`
스택은 GC를 유발한 할당 위치이며, 수거 대상의 생성 주체를 입증하지 않는다.

12시 58분경 표시 버퍼는 319종목에 255,002건, 호가는 99,509건이었다. 구독자는
548개였고 버퍼의 종목과 종류별 큐 상한은 360건이다. 프로세스 RSS는 약 12시 50분
1.47GiB에서 12시 58분 1.93GiB로 증가했다. RSS에는 Python 외 할당도 포함되므로
이를 순환 참조 누수의 크기로 해석하지 않는다.

12시 59분 이후 화면 WebSocket의 연결과 종료가 빈번해진 구간도 있다. 그러나
12시 41분의 긴 GC 이전에는 그 연결 폭증이 없어, 최초 GC 문제의 원인으로
단정하지 않았다. 13시 이후의 부하를 비교할 때에는 별도 변수로 취급해야 한다.

## 실행 환경과 GC 설정의 불일치

운영 서버는 `/usr/bin/python3.14`의 Python 3.14.4를 사용한다. 이전 PR의 로컬
검증은 Python 3.12.13에서 실행됐다. `pyproject.toml`은 `>=3.11`을 허용하며
저장소에 `.python-version`이 없어 실행 버전을 고정하지 않는다.

`hoga/gc_tuning.py`는 50,000 / 50 / 50을 설정한다. 운영의 실제 값은
50,000 / 50 / 0이다. Python 3.14.0부터 3.14.4까지는 세 번째 인자를 무시하고,
두 번째 인자는 오래된 객체를 검사하는 속도를 조절한다. 기존 세대별 수집 횟수
기준의 튜닝 근거를 이 구현에 그대로 적용할 수 없다.

Python 공식 문서는 3.14.0부터 3.14.4까지의 incremental GC가 운영 환경의 큰
메모리 압력 보고 때문에 3.14.5에서 3.13의 generational GC로 교체됐다고 설명한다.
이는 실제 서버에 해당하는 버전 위험이다. 이 사실만으로 현재 7.57초 정지의
단독 원인이 입증된 것은 아니다.

- [Python 공식 GC 변경 설명](https://docs.python.org/3.14/whatsnew/3.14.html#garbage-collection)
- [GC 임계값과 세대 동작 변경](https://docs.python.org/3.14/library/gc.html)
- [연관 CPython 이슈](https://github.com/python/cpython/issues/142516)

## 분리된 실험 결과

서버와 다른 프로세스에서 모의 호가 입력을 파싱하고 `LiveStream.on_tick`으로
보관했다. 날짜, 시계, 가격과 잔량은 고정했다. 벤더 호출, 앱 기동, 실제 저장 파일 쓰기는
없다. `writer=None`은 쓰기 경로를 호출하지 않기 때문에 가능한 실험용 값이다.

| 실험 | Python 3.14.4 | Python 3.12.13 |
| --- | ---: | ---: |
| 100종목, 호가 40,000건 입력, 보관 36,000건, 명시적 전체 GC | 258.1ms | 123.3ms |
| 50,000건 입력과 LiveDelivery 전송 및 JSON 직렬화, 보관 36,000건, 전체 GC | 289.1ms | 151.5ms |
| 위 전송 실험을 uvloop 0.22.1로 실행, 전체 GC | 280.9ms | 153.9ms |
| uvloop, 319종목, 180,000건 입력, 보관 114,840건, 튜닝 적용 시 자동 GC 최대 | 139.9ms | 230.57ms |
| 위 319종목 실험 마지막에 실행한 명시적 전체 GC | 1,049.3ms | 392.3ms |

파싱, `trade_date`, 표시 및 피크 처리, 화면 전달 경로의 이 실험에서는 수거할
순환 참조가 0개였다. 실제 로컬 WebSocket으로 20,000건을 전송하고 종료한
실험은 각각 156개와 195개를 수거했다. 운영의 백만 단위 수거는 재현하지 못했다.
초봉 flush의 디스크 쓰기, 실제 TLS 벤더 연결, 모든 조회 경로는 이 실험에 포함되지
않는다. 가격과 시간이 변하는 하루치 피크 상태도 이 입력으로 재현하지 않는다.
작은 재현의 결과로 운영 전체의 누수를 배제하지 않는다.

Python 3.14.4의 기본 임계값 2,000 / 10 / 0으로 같은 319종목 실험을 실행하니
자동 GC는 1,619회, 최대 253.5ms였다. 앱 튜닝 적용 시에는 64회, 최대 139.9ms였다.
명시적 마지막 GC 한 번은 위 자동 횟수에서 제외했다. 임계값을 기본값으로 낮추는
것만으로 개선된다고 주장할 증거는 없다. 전체 GC의 버전 차이도 자동 GC의 모든
정지가 같은 비율로 개선된다는 의미는 아니다.

모의 HTTPX 응답 5,000건은 요청과 응답 및 BoundSyncStream 등을 순환 참조로
남겼다. 각각 80,000개와 105,000개를 수거했다. 이는 일반 라이브러리의 일시적
순환 참조도 수거 대상을 만든다는 증거다. 운영 REST 거버너의 당시 호출 누계는
약 1,349회였고, 이 실험만으로 운영의 백만 단위 수거를 HTTPX에 귀속하지 않았다.

재현 파일은 `harnesses/*.py.txt`에 보관했다. 저장소 루트에서 원하는 가상환경의
Python으로 실행한다. 일반 라이브러리 의존성은 필요하지만 앱의 `.env`를 읽지
않는다. socket 실험만 일시적으로 루프백의 OS 할당 포트를 사용하고 종료한다.

```sh
.venv/bin/python docs/diagnostics/2026-10-01-gc-stall/harnesses/probe_hot_path.py.txt delivery 50000
HOGA_PROBE_AUTO=1 HOGA_PROBE_TUNED=1 HOGA_PROBE_UVLOOP=1 HOGA_PROBE_CODES=319 \
  .venv/bin/python docs/diagnostics/2026-10-01-gc-stall/harnesses/probe_hot_path.py.txt stream 180000
.venv/bin/python docs/diagnostics/2026-10-01-gc-stall/harnesses/probe_httpx.py.txt
.venv/bin/python docs/diagnostics/2026-10-01-gc-stall/harnesses/probe_socket.py.txt
```

## 설계의 영향

키움 reader와 consumer를 나눠도 동일 프로세스의 이벤트 루프에서 돈다. 현재처럼
GC가 이 루프를 멈추면 모든 계정의 제어 응답, REAL 수신, 화면 전달이 함께 멎는다.
따라서 PR 1909의 제어 프레임 분리로 GC 정지 자체가 해결되지는 않는다. 실제 로그는
GC 뒤 큐가 64개 상한에 닿아 재연결하는 경로까지 보여 준다. 상한을 키우는 것은
원인 제거가 아니며, 이후 정상 부하와 최장 프레임 공백에 따른 용량 검증이 필요하다.

## 다음 검증 순서

1. 수정된 GC를 포함하는 Python 3.14.5 이상 환경을 별도로 만들고 현재 3.14.4와
   같은 의존성 및 입력으로 비교한다. 검증 버전과 실제 서비스 버전을 고정한다.
2. 같은 계정 수, 종목 수, 화면 구독 수로 충분히 보관 창을 채우고 운영의
   `gc_pause`, `loop_lag`, RSS, `data_backlog`를 비교한다. 단순 재시작 직후의
   짧은 구간을 해결 증거로 쓰지 않는다. 관측상 이번 정지는 시작 37분 뒤까지
   증가했으므로 장중 부하에서 최소 60분을 비교하는 것이 조사상 권고다.
3. 장 마감 뒤, 객체 조사 옵션을 명시적으로 켠 환경에서 타입별 추적 객체 수를
   확인한다. ADR 0169의 전체 힙 조사 기능은 이 호출 자체가 수 초 멈추므로
   장중에 실행하지 않았다. 가능하면 자연 GC 전후 표와 할당 스택도 비교한다.
4. 생성 주체를 찾은 뒤 해당 경로의 객체 수와 수명을 줄인다. GC 정지가 계속
   수신을 방해하면 수집 프로세스 격리를 별도 설계로 검토한다. 단순히 uvicorn
   워커 수를 늘리면 싱글턴 수집기가 중복 실행되므로 저장소 전제에 맞지 않는다.

첫 조사 때 수정된 Python의 다운로드가 설치된 uv 카탈로그에 없었다. 적용 요청 후
Astral의 공식 다운로드 메타데이터를 지정해 Python 3.14.7을 설치하고
`.python-version`에 고정했다. 기존 서버와 새 환경의 잠금된 라이브러리 버전은 같다.
Python의 외부 디버깅 인터페이스로 어린 세대만
확인하려던 읽기 프로브도 PyRuntime 위치 탐색에서 실패했고 대상 프로세스에서
실행되지 않았다. 운영 전체 힙의 객체 생성 주체와 런타임 교체 후 해결 여부는
미확정이다. GC 임계값은 기존값을 유지한다.

## Python 3.14.7 적용 전 검증

실제 `gc.set_threshold(50000, 50, 50)` 결과는 `(50000, 50, 50)`으로 복원됐다.
319종목 모의 호가 실험은 같은 114,840건을 보관했고 자동 GC 최대 787.61ms,
마지막 전체 GC 1,190.6ms였다. 이 실행은 전체 테스트와 동시에 수행됐으며, 기존
incremental GC와 수집 범위도 다르다. 이 숫자는 속도 개선의 증거가 아니다.
운영 메모리 회수 지연과 긴 정지가 사라지는지는 적용 후 60분 이상 비교해야 한다.

Python 3.14.7에서 전체 백엔드 검증은 5,256건 통과, 기존 실패 4건, skip 2건,
wallclock 제외 13건이다. 실패는 이전 PR 검증 및 기준 코드에서 확인했던
가격 스케일 분류 1건과 오늘 봉 bootstrap 3건으로 동일하다. 전체 Ruff도 기준에
존재하던 연구 스크립트 `summarize.py`의 PLR2004 및 E501 두 건을 보고했다.
런타임 변경을 위해 이 검증 가드를 완화하지 않았다.

기존 3.14.4 리로더에서 새 3.14.7 앱과 그 앱의 3.14.7 워커를 중첩 spawn하는
분리 실험도 통과했다. 실제 적용에서는 새 환경을 먼저 준비하고 기존 환경을
롤백용으로 보관하며, 앱과 워커의 실행 파일 및 `/health` GC 임계를 확인한다.
