# 달력 갱신 오류 7/[1631]

2026-11-02 16:30:42 KST, 새 API가 거래일 오버레이를 갱신하는 중 키움 `ka20006`이
`7: 서비스를 처리하는 중에 오류가 발생했습니다[1631]`을 반환했다. REST 클라이언트는
이 응답을 `KiwoomApiError`로 전달했고, 달력 갱신 loop가 traceback을 기록했다.
재로드의 이전 API 종료는 이미 완료된 뒤였다.

응답으로 확인할 수 있는 최초 원인은 키움의 서비스 처리 실패다. 키움 내부에서
어떤 처리가 실패했는지는 알 수 없다. 요청 형식은 기존 지수 일봉과 동일한
`POST /api/dostk/chart`, `inds_cd=001`, `base_dt=20261102`다. 당시 wire body를
로그에 남기지는 않았으므로 이 필드는 배포 소스에서 복원했다.

조사 중 기존 운영 `/api/market/trade-value?days=1`은 같은 TR·본문으로 현재 날짜의
KOSPI·KOSDAQ 데이터를 정상 제공했다. 이 라우트에는 TTL 캐시가 있으므로 달력
task 자체의 재시도 성공으로 해석하지 않는다. 앞선 10/27·10/29 달력 오류는
IP 미등록 인증 오류 `[8050]`이며 이번 `[1631]`과 구분한다.

우리 코드의 복구 지연도 확인했다. 기본 갱신 주기는 6시간이며 빠른 확인은 평일
16시 이전의 미확인 거래일에만 적용된다. 따라서 16:30의 단발성 서비스 실패 뒤에도
6시간을 기다린다. 시드·기존 오버레이 조회는 계속 가능하지만 커버리지 갱신은 멈춘다.

## 수정과 검증

달력 loop에서 코드 `7`과 상세 `[1631]`을 함께 확인한 경우만 60초부터 재시도한다.
실패가 이어지면 120·240·480·900초로 늘리고 최대 900초를 유지한다. 기존 장 시작
확인·미확인 거래일 주기가 더 짧으면 그 주기를 우선한다. 성공 후에는 실패 횟수를
비우고 정상 주기로 돌아간다. 인증·잘못된 입력·다른 처리 오류는 기존 오류 기록과
주기를 유지하며 토큰을 강제 재발급하지 않는다.

재시도 로그는 API·코드·실패 횟수·다음 대기 시간을, 복구 로그는 실패 횟수를 남긴다.
실제 응답을 받아 오버레이에 반영한 경우에는 추가된 날이 없어도 응답 행 수·최신일·
추가 일수를 기록한다. 따라서 파일이 이미 최신인 정상 응답도 확인할 수 있다.

회귀 테스트의 수정 전 실패는 다음과 같다.

```text
assert [21600.0, 21600.0] == [60, 21600]
At index 0 diff: 21600.0 != 60
```

수정 후에는 단발 실패→성공, 연속 실패의 상한·성공 후 초기화, 인증·입력 오류 제외,
장 시작 확인, 실제 task 취소 시 추가 요청 없음, 실제 REST 파서의 오류→정상 응답과
오버레이 보존·갱신을 검사했다. 집중 검사 144개와 Ruff가 통과했다.
전체 백엔드 결과·입력 지문은 `validation.json`에 기록한다.

로그 원인·현재 상태와 해석 한계는 [incident.json](incident.json)에 보존했다.
