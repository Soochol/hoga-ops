# 분봉 준비 작업의 연속 배정과 후보 우선순위

준비가 끝난 슬롯에 다음 종목을 바로 넣는다. 동시에 준비하는 종목 수는 4개이며,
공용 REST 거버너의 계정별 유량·background 한도와 화면 조회용 슬롯을 유지한다.
3·5·10분봉을 위한 원본은 기존처럼 같은 거래일의 1분봉 한 번이다.
관심종목·히트맵의 전체 구독과 최종 준비 범위도 유지한다.

## 대기와 전체 계산을 분리한다

기존에는 coordinator가 장중 250ms, 장외 1초마다 준비할 종목을 다시 골랐다.
API 응답이 빨라도 비어 있는 준비 슬롯을 다음 점검까지 채우지 않았다.
새 dispatcher는 주기적 품질 검사에서 고른 작업을 최대 512종목 범위의 대기열에 보관한다.
작업 완료 callback은 같은 소유자의 pending 슬롯을 반환하고 대기열에서 다음 작업만 고른다.
품질 검사·전체 알림·구독 동기화·범위 갱신을 callback마다 반복하지 않는다.

대기 작업에는 History 정체성, 취득 시각, 필요 봉 수와 선택 거래일을 붙인다.
배정 직전에 현재 감시 범위·객체 정체성·필요량·거래일·재시도 시각을 확인한다.
종목 제거·조건 변경·세션 전환·이력 교체 뒤의 작업은 버린다.
감시 종료와 읽기 종료 시작은 추가 배정을 막고, 취소된 작업도 자기 슬롯만 반환한다.

## 현재 검색 후보를 먼저 준비한다

결과 조회가 이미 수행하는 순위 평가의 결과를 재사용한다. 추가 순위 API 요청은 없다.
기존 `candidate_codes`가 AND·OR 식을 해석해 실제 필요한 후보를 정한다.
현재 후보 세 종목 뒤에는 일반 종목 한 종목을 준비해 전체 감시 범위가 계속 진행하게 한다.
이미 생긴 이력 손상 복구는 초기 준비보다 먼저 처리한다.

우선순위는 감시별로 보관하며 30초 또는 선택 거래일이 바뀌면 만료된다.
순위 조회 전에는 이전 우선순위를 비우므로 실패·취소가 예전 후보를 계속 우선하지 않는다.
OR 때문에 전체 범위가 필요하면 전체 범위를 후보로 유지한다.
조회 조건의 판정·봉 부족·잠정·충돌·정정 선택과 REST/WS 관측 병합은 변경하지 않는다.

## 실제 개선 전 기준

같은 서버를 기존 코드로 재시작해 메모리 분봉 캐시가 없는 상태에서 감시를 시작했다.
관심종목·히트맵 350종목 중 순위 조건을 통과한 검색 후보는 154종목이다.
첫 응답은 4.903초였고 당시 후보 15종목이 준비됐다. 후보 154종목이 모두 준비된 첫 관측은
시작 후 **95.233초**다. 상태는 약 3초 간격으로 확인했다.

분봉 준비가 끝난 뒤 판정 가능한 종목은 145개, 일치 결과는 4개였다.
나머지 9개는 공급자 표시 가격 미제공으로, 분봉 준비 부족과 구분한다.
health 36회는 모두 200, pong 36회와 감시 삭제 204를 확인했고 점검 오류는 없다.
[개선 전 집계](live-before.json)에 근거가 있다. 이전 실행의 88.095초와 이번 실행을
같은 입력의 반복 수치로 합치지 않는다. 운영 공급자 상태·다른 요청에 따라 달라질 수 있다.
개선 후 운영 측정은 반영 뒤 같은 조건으로 수행하고 PR의 적용 검증에 기록한다.

## 고정 경계의 실행 검증

[실행기](benchmark.py.txt)는 실제 기존·개선 coordinator, loader 준비·병합과 공용
거버너를 실행한다. 외부 연결은 금지하고 API 응답에 가상 시각으로 100ms를 설정했다.
계정은 6개, 감시 350종목, 후보는 코드 순서 뒤쪽 154종목이다. 순위 후보는 시작 250ms 뒤에
전달한다. 두 버전을 5회 교대 실행했다. 가상 시각은 프로그램 배정 효과를 확인하기 위한
모형이며 실제 서버 지연이나 운영 속도 보장이 아니다.

| 가상 시각의 준비 완료 | 기존 | 개선 |
|---|---:|---:|
| 후보 154종목 | 87.10초 | 8.95초 |
| 전체 350종목 | 87.10초 | 14.60초 |
| 분봉 원본 요청 | 350회 | 350회 |
| 최대 동시 준비 | 4개 | 4개 |
| 전체 알림 계산 | 88회 | 15회 |

전체 350종목이 준비됐고 후보 154종목의 6개 분봉 조건 평가가 완전히 같다.
발생 근거와 coverage 전체의 응답 해시는 10회 모두
`0f3df0da875cf0b266af0cc9a4b321df0a70a8e5175ebf4a8f6565e215c93360`이다.
오류는 0건이다. [원시 실행 결과](benchmark-results.json)에 모든 반복을 남겼다.
모형은 API 오류·다른 화면의 동시 요청·실제 네트워크·CPU 경합을 재현하지 않는다.
따라서 위 가상 시각의 단축을 실제 측정값으로 보고하지 않는다.

## 검증과 재현

새 동작 검사는 수정 전 3개 실패·2개 통과였고 수정 후 모두 통과했다.
관련 94개, 스크리너 전체와 공유 분봉 캐시·거버너의 1,797개가 통과했다.
최종 소스의 백엔드 전체는 **8,492개 통과**, 2개 건너뜀, 13개 wallclock 제외다.
전체 실행에는 393.74초가 들었다. Ruff는 전체 추적 소스에서 통과했고 추적되지 않는
`.audit` 조사 도구만 제외했다. [검증 지문](validation-inputs.json.gz)과 압축 로그에 근거가 있다.
프론트·공개 wire 모델·의존성과 잠정·충돌 데이터 정책은 변경하지 않았다.

독립 Astra 검토는 별도 체크아웃에서 기존 34개와 추가 19개 검사를 실행해 확인된 문제 없이
통과했다. [추가 검증 도구](adversarial_cases.py.txt)는 취소·잘못된 대기 작업·scope·day·요구량·
재시도·우선순위 만료·AND/OR·읽기 종료·512종목 한도·객체 참조 해제를 확인한다.
검토자는 애플리케이션 소스를 작성하지 않았다. 모델 구성에 따라 검토자는 Astra 한 명이다.
별도 실행 검증자는 실제 FastAPI 감시 생성·결과·heartbeat·교체·삭제·reload admission을
기존과 개선 버전에서 실행했다. 152종목 원본 이력 요청과 최대 동시 4개를 유지하고,
삼성전자 1개 결과와 30개 발생 근거를 포함한 전체 응답이 같음을 확인했다.
