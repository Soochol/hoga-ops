# 저장 분봉의 저녁 시간축 점검

## 최종 범위

사용자 지시에 따라 **추가 데이터 다운로드·재수집·기존 데이터 보충을 제외**했다.
전체 저장 목록은 읽기 전용으로 검사했다. 이번 변경에는 수집기·파서·WS·데이터
마이그레이션이 없으며, 저장 파일을 고쳐 저녁 캔들을 만드는 작업도 없다.
지시 변경 전 확인용 chart.php 응답은 별도 진단 백업에만 보관했고 앱 데이터에 합치지 않았다.

## 원인과 변경

- `useLiveBundle`이 저장 분봉 모드의 시간축을 정규장으로 제한했다.
  디스크 소스 선택과 표시 세션을 분리하고, 디스크 응답의 날짜별 세션 경계를 우선한다.
  이전 REST 응답의 정규장 경계가 저장 분봉의 저녁 구간을 덮지 않는다.
- 과거 `meta.json`의 정규장 종료 뒤에도 실제 저장 캔들이 있을 수 있다.
  `/api/range?mode=candles`의 표시 종료를 정책 종료와 실제 마지막 캔들 중 늦은 시각으로 정한다.
  공식 정규장 종료 메타데이터를 변경하지 않는다.
- 저장 분봉의 120·240분 집계에서도 기존 저녁 캔들을 보존한다.
  정규장 뱃지 ON이면 저장 1분봉을 먼저 정규장으로 자른 뒤 표시 주기로 집계한다.
  OFF이면 원래 보유한 저녁 분봉이 다시 나타난다. 없는 캔들은 생성하지 않는다.
- 소스 칩 도움말에 보유한 저녁 분봉 표시와 미보유 구간의 빈 표시를 명시했다.
- HogaPlay 자체는 KRX 자료다. 기존 venue별 소스 선택·폴백 정책을 변경하지 않았다.
  KRX·NXT·통합에서 선택된 저장 소스의 경계를 각각 따른다.
- WS 구독·수집·저장 정책은 뱃지와 독립적으로 유지된다.

## 읽기 전용 전수 검사

검사 시점에도 사용자의 캡처 큐가 동작하고 있으므로 목록 수는 이후 늘어날 수 있다.
저장 체결의 가격·수량이 양수인 저녁 시각을 분 단위로 접고, 같은 시각의 저장 분봉
존재 여부를 대조했다. 날짜 하한을 두지 않았다. 체결이 없는 분에 가격을 만들어
넣지 않았으며, 이 검사는 벤더의 과거 보유 여부를 판단하지 않는다.

요약과 표본은 `audit.json`에 보관했다. 전체 항목별 보고서는
`/tmp/hoga-evening-readonly-final.json`, 실행 로그는 `/tmp/hoga-evening-readonly-final.log`다.
전체 보고서의 영구 사본은 `/home/dev/.local/share/hoga-ops/backups/20261016-hogaplay-evening-candles-lb3nu_kc/readonly-audit.json.gz`다.
273개는 파일이 없는 빈 HogaPlay 디렉터리이며 정상 캔들 보유 건으로 세지 않았다.
검사 도구는 결과를 `/tmp`에만 기록했다.

## 검증

- 프론트 관련 단위 테스트 298개 통과.
- 백엔드 관련 테스트 202개 통과. 상세 결과는 `verification.json` 참조.
- Playwright 8개 통과: KRX·NXT·통합에서 저장 모드 ON, 정규장 OFF→ON→OFF,
  1·120·240분 전환, 새로고침 후 저장 모드 재진입, 빈 거래일 유지,
  자동 벤더 보충 미발생, WS 연결·종목 구독 유지, 저녁 보조지표 복원.
  HogaPlay 토글은 기존대로 창의 런타임 상태여서 새로고침 후 직접 다시 켰다.
- 2025년 저녁 및 2026년 19:59·20:00 저장 분봉을 1·60·120·240분으로 검증했다.
  ON/OFF 반복 전후 픽스처 파일 바이트가 동일하다.
- 타입 검사·Vite 빌드·Ruff·diff 공백 검사 통과. ESLint 오류 0개.
- 별도 확장 검사에서 기존 wire 스냅샷 테스트 1개가 실패했다.
  `DailyProgramTradePoint`의 `buy_amount/net_amount/sell_amount`가 기존 스냅샷에 없다.
  이번에 수정하지 않은 main 모델과 main 테스트로 같은 실패를 재현했다.

초기 검증 단계에서는 사용자 개발 서버와 실행 중인 캡처 큐를 재시작하지 않았다.
이후 사용자의 PR 머지·pull·localhost 반영 요청에 따라 적용을 진행하며,
PR 직전 최신 main 검증은 `pr-verification.json`에 별도로 기록했다.
