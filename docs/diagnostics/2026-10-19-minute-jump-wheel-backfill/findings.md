# 분봉 점프 이후 휠 축소와 과거 조회의 표시 범위 보존

2026년 10월 19일. 최초 조사와 수정의 후속 제보는 「분봉으로」의 첫 화면은 정상이며, 마우스 휠로 축소해 과거 데이터를 조회할 때 표시가 다시 깨지는 조건이다.
조사 소스는 `7bcfe1aa2`이며 PR #2098의 첫 화면 수정을 포함한다.

## 재현과 원인

첫 점프 후 휠 축소로 백필을 발생시키고 응답을 보류한 실제 Chrome 테스트에서, 응답 도착 순간 표시 폭과 마지막 봉의 위치가 바뀌는 것을 확인했다.
이 실험에서는 화면 안 봉 수가 2개가 되는 것까지 재현한 것은 아니며, 첫 백필이 사용자의 줌을 덮어쓰는 경로를 확인했다.

| 최초 목적지 봉 수 | 백필 후 전체 봉 | 응답 전 논리 폭 | 응답 후 논리 폭 | 마지막 봉 X 이동 |
| --- | ---: | ---: | ---: | ---: |
| 128 | 1408 | 262.42 | 355.87 | 624.77px → 670.39px |
| 768 | 2560 | 1263.96 | 569.09 | 627.87px → 419.28px |

원인은 `useViewportBackfill`의 `swapPendingRef` 수명이다.

1. 날짜 점프는 `candleSourceKey`를 `vendor|날짜`로 바꿔 소스 재배치 대기를 세운다.
2. 점프는 차트를 새로 만들고 새 차트의 첫 화면은 `LiveChartRoot`가 배치한다.
3. 첫 캔들 커밋에서는 초기 배치가 아직 완료되지 않아 소스 재배치가 `initial_view_pending`으로 보류된다. 다음 동일 캔들 커밋도 `identity_unchanged`로 보류돼 대기가 남는다.
4. 사용자가 휠로 축소하면 과거 조회가 시작된다. 첫 백필이 캔들 개수를 바꾸면 남아 있던 대기가 발화해 `source_swap` 정책으로 화면을 다시 배치한다.
5. 일반 백필의 위치 보존을 덮어쓰므로, 휠로 만든 표시 폭과 봉 위치가 사라진다.

이전 PR은 다른 날짜 번들로 첫 화면을 배치하는 문제를 막았지만 이 대기의 수명까지 바꾸지는 않았다.

## 수정

차트 인스턴스가 바뀌면 이전 인스턴스의 소스 재배치 대기도 해제한다.
새 차트의 최초 배치는 기존 소유자가 그대로 담당하고, 이후 과거 조회는 기존 백필의 위치 보존 경로를 따른다.
소스 키 기억과 캔들 스냅샷은 유지하므로 동일 차트에서 실제 소스를 바꾸는 재배치 정책은 유지된다.

제품 코드 변화는 `useViewportBackfill.ts`의 차트 전환 effect에서 `swapPendingRef.current = false`를 적용하는 한 줄과 관련 주석이다.

## 회귀 검사

- 새 단위 테스트는 차트 없음 → 새 차트 첫 배치 → 첫 백필 순서를 만들며, 수정 전 이전 소스의 재배치가 실행돼 실패했다.
- 새 E2E는 최초 목적지 봉 수 128개와 768개를 각각 검사한다. 실제 마우스 휠로 백필을 시작하고 응답 대기 중 가능한 경우 추가 휠 입력을 넣는다.
- 응답 전후 같은 마지막 봉의 이동이 1px 미만이고, 논리 폭과 봉 간격이 유지되며, 보이는 봉 수가 줄지 않아야 한다.
- 최초 대조 실험에서 수정 후 봉의 X 이동은 부동소수점 오차 수준이고 논리 폭과 봉 간격이 유지됐다. [수정 전 계측](before.json), [수정 후 계측](after.json).
- 관련 6개 단위 파일 504개 및 기존·신규 차트 E2E와 대용량 백필 E2E 11개가 통과했다.
- 변경 파일 ESLint 오류 0개. 제품 파일의 기존 경고 11개는 HEAD와 규칙별 개수가 같다.

테스트는 워크트리 전용 포트 20280과 21280, 무자격 mock API를 사용하며 사용자 서버와 저장소를 초기화하지 않는다.

신규 휠 백필 E2E 2개를 각각 5회 반복해 총 10회 통과했다. 전체 타입 검사와 production build도 통과했다. [반복 결과](repeat.log), [입력 및 검증 기록](validation.json).
