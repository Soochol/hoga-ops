# 분봉 점프 후 왼쪽에 두 봉만 보이는 현상 원인

조사일: 2026-10-18 KST. 제품 소스: `506b67e83`.
사용자가 최근 실행에서도 발생한다고 확인한 제보의 후속 조사다.

현재 코드에서 **정상 응답 128개를 받아도 2개만 왼쪽 끝에 보이는 현상**을 재현했다.
원인은 목적지 데이터를 기다리는 동안 이전 날짜 번들을 유지해, 새 차트가 잘못된 데이터로 초기 표시 범위를 확정하는 것이다.
부분 응답과 호출 제한 경고를 사용하지 않아도 발생한다. 10월 10일의 부분 실패 복구 수정과 구분된다.
실제 제보 세션의 응답을 확보한 것은 아니며, 아래 수치는 격리된 Chrome에서 실제 앱과 mock API로 확인한 값이다.

## 재현 결과

같은 그룹에 일봉과 3분봉 창을 열었다. 10월 1일 기준 분봉 768개가 로드된 뒤 일봉의 9월 29일을 선택하고 실제 「분봉으로」 버튼을 눌렀다.
목적지 응답에는 정상적인 하루 분량을 모사한 130개 원시 봉을 넣고 400ms 지연을 주었다.
마감 동시호가 집계 후 차트 데이터는 128개다. 경고와 HTTP 오류는 없다.

| 조건 | 전체 봉 | 화면 안 봉 | 논리 범위 | 마지막 봉 X | 플롯 폭 |
| --- | ---: | ---: | --- | ---: | ---: |
| 점프 전 | 768 | 300 | 468..848 | 627.87px | 800px |
| 목적지 첫 조회 완료 | 128 | 2 | 126..506 | 2.15px | 800px |

현재 코드의 첫 조회 조건은 **3회 모두** 화면 안 2개로 재현됐다.
대조 조건은 **3회 모두** 화면 안 128개로 정상 표시됐다.
같은 날짜 재점프의 캐시 조건도 별도 1회 정상 표시됐다.
첨부 화면과 마찬가지로 잘못된 범위에서는 봉이 얇고 차트 왼쪽에 몰리며 우측 대부분이 빈다.

## 코드상 발생 경로

1. `frontend/src/live/useTimeframeJump.ts:264`는 점프 날짜를 `asOfDate`로 만들고, `:265`의 `viewSeg`로 차트 재생성을 유발한다.
   `useLiveChartData.ts:172`는 이 날짜를 조회 종료일로 사용한다.
2. `frontend/src/live/useLiveBundle.ts:1462`의 `sourceSwapHold`는 같은 종목과 봉 주기이면 새 쿼리가 로딩되는 동안 이전 `settledChart`를 유지한다.
   **조회 종료일 일치 조건이 없다.** 따라서 실제 소스 토글뿐 아니라 과거 날짜 점프에도 켜진다.
   `:1474`는 목적지 차트에 이전 날짜 번들을 전달한다.
3. `frontend/src/live/LiveChartRoot.tsx:1643`의 최초 범위 설정이 이 이전 번들로 실행되고, `:1673`에서 완료로 기록된다.
   새 목적지의 쿼리는 아직 로딩 중이므로 `initialMinuteHistoryRef`도 생긴다.
4. 목적지 응답이 정상 완료돼도 `needsRecovery`는 blocking 경고가 있을 때만 true가 된다(`:1677`).
   경고가 없는 이번 응답은 복구 대상으로 간주되지 않아 `:1647`의 일회성 가드에서 재배치가 생략된다.
   동시에 `:1057`의 `canReseatAfterSourceSwap`와 `useViewportBackfill.ts:779`는 초기 배치가 소유한 날짜 전환의 소스 재배치를 소비한다.
5. 이전 데이터로 정한 화면 폭이 새 격자에 남는다. 이 실험에서 최종 논리 범위는 `126..506`, 새 데이터는 `0..127`이므로 마지막 2개만 화면 왼쪽에 걸린다.

핵심은 **이전 데이터의 일시적 화면 유지와 새 화면의 초기 배치가 서로 다른 조회에 속한다는 점을 구분하지 않는 것**이다.

## 간헐적으로 발생하는 이유

목적지 데이터가 캐시에 있으면 새 차트가 처음부터 목적지 데이터로 배치돼 정상이다.
캐시가 없고 응답을 기다리면 이전 번들 유지가 켜질 수 있다.
이전 구간과 목적지 구간의 봉 수와 날짜 구성이 다를수록 잘못 계승한 범위가 드러난다.
기존 테스트처럼 두 구간의 봉 수가 비슷하면 이 오류가 가려질 수 있다.
이번 실험에서 같은 날짜로 다시 버튼을 눌렀을 때 정상화된 것은 캐시에 목적지 데이터가 생겼기 때문이다.

## 수정 방향과 대조 실험 범위

새 점프 화면의 최초 배치는 그 목적지에 속한 데이터로만 확정해야 한다.
이전 번들 유지의 조회 정체성에 종료일을 포함하는 것이 이번 경로의 직접적인 수정 지점이다.
대조 실험은 `sourceSwapHold`에 `settledChart.to_date === todayKstYyyymmdd` 한 줄만 추가했다.
[실험용 차이](control.patch)를 보관했으며 제품 소스에서는 되돌렸다.

실제 수정에서는 날짜 변경, 점프 해제, 저장뷰, 정상 소스 토글과 사용자 팬 보존을 함께 검증해야 한다.
모든 데이터 갱신 때 초기 범위를 다시 적용하는 방식은 사용자 조작을 되돌리므로 피한다.
같은 날짜 재점프에서 `historicalFromDate`가 남는 기존 별도 문제는 이번 캐시 재점프 조건에 포함하지 않았다.

## 검증 범위와 재실행

최초 조사에서는 제품 변경 없이 진단 자료만 남겼다. 사용자 서버 5173과 8000은 재시작하지 않았다.
실험은 별도 포트 21988에서 무자격 Vite와 mock API로 실행했다.
기존 `live-viewport-preservation.spec.ts`의 부분 실패 검사는 자동 복구와 드래그 보존 2개가 통과했고, 휠 줌 검사는 입력 후 span이 줄지 않아 재조회 이전 단계에서 실패했다.
이 기존 검사 실패를 이번 재현의 근거나 해결 결과에 포함하지 않았다.

재현 하네스는 현재 버그 상태인 화면 안 2개를 단언한다. 정상 동작을 단언하는 제품 회귀 테스트가 아니다.
제품 수정 이후에는 `JUMP_EXPECT_VISIBLE=128`로 정상 표시를 단언할 수 있다.

```sh
cp docs/diagnostics/2026-10-18-minute-jump-stale-bundle/reproduce.spec.ts.txt frontend/tests/e2e/jump-investigation.spec.ts
cp docs/diagnostics/2026-10-18-minute-jump-stale-bundle/playwright.config.ts.txt frontend/playwright.jump-investigation.config.ts
cd frontend
npx playwright test --config playwright.jump-investigation.config.ts --repeat-each=3 --reporter=list
rm tests/e2e/jump-investigation.spec.ts playwright.jump-investigation.config.ts
```

포트 21988은 실행 전 비어 있어야 하며 설정은 기존 서버 재사용을 금지한다.
캔들 응답, 시계, 화면 크기는 하네스에서 고정한다. 라이브 API나 실제 사용자 저장소를 사용하지 않는다.


## 2026년 10월 19일 후속 수정

사용자 요청에 따라 `useLiveBundle`의 이전 번들 유지에 조회 종료일 일치 조건을 추가했다.
소스 전환 대기뿐 아니라 기존 과거 확장이 진행 중인 홀드에서도 다른 날짜 번들을 새 차트로 전달하지 않는다.
날짜 점프의 상위 effect가 조회 시작일을 초기화하기 전 한 커밋에서도 이전 날짜로 초기 배치를 완료하지 않도록 했다.
동일 날짜의 정상 소스 전환과 백필의 데이터 유지는 유지한다.

제품 회귀 테스트를 추가해 수정 전 실패를 먼저 확인했다.

- 단위 테스트 4개: 벤더 및 저장 데이터, 백필 유무의 조합에서 날짜 점프와 복귀 중 이전 날짜 데이터가 전달되지 않는지 확인한다.
- E2E 2개: 이전 768개에서 목적지 128개 또는 384개로 점프하며, 정상 표시 봉 수와 마지막 봉의 픽셀 위치를 확인한다. 캐시 재점프와 라이브 복귀도 같은 테스트에서 확인한다.
- 수정 전 E2E는 두 경우 모두 화면 안 봉 수가 2여서 실패했다. [수정 전 단위 결과](fix-unit-red.log), [수정 전 브라우저 결과](fix-e2e-red.log).
- 수정 후 관련 6개 파일의 단위 테스트 503개와 기존 및 신규 차트 E2E 8개가 통과했다. 이전 조사에서 실패했던 부분 응답 중 휠 줌 보존 조건도 이번 실행에서는 통과했다.
- 전체 TypeScript 검사와 E2E 준비 단계의 Vite production build가 통과했다. 최종 E2E 대기 조건 강화 이후 E2E TypeScript 검사와 `npm run build`도 다시 통과했다.

현재 제품 테스트는 `frontend/tests/e2e/live-viewport-preservation.spec.ts`가 기준이다.
앞부분에 보관한 진단용 하네스는 수정 전 상태를 단언하므로 제품 수정 검증에는 사용하지 않는다.

최종 브라우저 회귀 2개를 각각 5회 반복해 **10회 모두 통과**했다.
첫 목적지 응답을 보류하는 순서, 캐시가 있는 같은 날짜 재점프, 라이브 복귀를 매번 검증했다.
[기존 및 신규 E2E 8개 결과](fix-e2e-green.log), [최종 10회 반복 결과](fix-e2e-repeat.log).

변경 파일 ESLint는 오류 0개다. `useLiveBundle.ts`의 기존 React hook 경고는 HEAD의 70개에서 53개이며, 두 테스트 파일은 경고 0개다.
제품 코드는 현재 워크트리에 반영했으며 사용자 서버 재시작이나 배포는 수행하지 않았다.

커밋 기준, 실행 명령, 런타임 버전과 입력 SHA-256은 [검증 기록](fix-validation.json)에 남겼다.
