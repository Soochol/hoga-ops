# 수집 IPC 설계 비교 실험 — 2026-10-23

결론은 **독립 수집 상태 채널 + 원본 상태의 변경 지점 기록 + 키별 revision + 종목 내부
분할 복구**를 권고한다. 단순히 JSON 크기 제한을 올리거나, 하루치 배열을 계속 만들어
비교하는 방식은 채택하지 않는다. 이 문서는 제안이며 운영 조립을 교체하지 않았다.

## 실험 범위와 재현

기준 코드는 `bc0e50b7c2fd48d464892cf5200d781665e225c4`와 현재 워크트리의 분할 패치다.
최종 검증 전 최신 main `56ce0b5722b9d76112eb06c072cd7f6d45eba396`을 반영했다.
벤치마크가 읽는 입력 해시가 동일함을 확인해 측정을 재사용하고, 관련 수집·stream·
거래원명 테스트는 합쳐진 코드에서 다시 실행했다.
실제 `TodayAskPeakState`/`TodayBidPeakState.snapshot()`으로 합성 당일 이력을 만든다.
키는 `(Code, venue)`이며 100키가 100개 종목의 KRX 조회에 해당한다. 512키는 추적 상한이다.
벤더 연결·실자격증명·운영 서버 재시작은 사용하지 않았다.

12/100/512키, 30/390분, 변경 없음/일부 변경/전량 변경을 비교했다. 초기 전체 복구,
대기 상태 덮어쓰기, 단일 키의 대형 기록 시퀀스, 실제 socketpair 수신 차단도 시험했다.

## 비교 결과

100키 × 390분, 모든 키의 마지막 분과 최신 극값이 바뀌는 1회 갱신 기준이다.
CPU 열은 원본 snapshot 생성 + 비교/추출 + JSON 인코딩의 중앙값 합이다. 수신 측 적용,
RSS, 벤더 처리 비용은 포함하지 않는다. 변경 지점 기록 비용은 D에 포함했다.

| 후보 | 갱신 전송량 | 생성·비교·인코딩 | 판단 |
|---|---:|---:|---|
| A. 현재 키별 차분 + 여러 키를 묶은 분할 상태 | 11.35MiB | 193.96ms | 크기 초과의 일부를 막지만 큰 전체 상태 비용이 남음 |
| B. 상태 채널 독립 + 키별 전체 이력 | 11.37MiB | 189.85ms | 수신 대기 격리에 유효, 전송량·생성 비용은 유지 |
| C. 상태 독립 + 완성된 배열을 비교한 분별 차분 | 225.88KiB | 210.67ms | 전송량 감소, CPU 증가로 권고하지 않음 |
| D. 상태 독립 + 원본의 변경 분·기록 구간 표시 | 277.05KiB | 4.25ms | 전송량 약 97.6%, 측정 CPU 약 97.8% 감소 |

D는 C보다 scalar/rank 필드를 보수적으로 다시 보내므로 전송량이 조금 크다. 하루치
중간 배열을 만들지 않는 이점이 더 크다. 모든 시각 수치는 이 합성 표본의 로컬 실측이며
실장중 수신 지연 p99를 뜻하지 않는다.

- 1키만 변경: A는 119,322B, D는 2,837B. 공유 snapshot 생성 비용 153.85ms를
  D는 수행하지 않았으며, 변경 추출·인코딩·표시 기록은 약 0.14ms였다.
- 512키 전량 변경: A는 58.13MiB 및 약 958.46ms, D는 1.39MiB 및 약 22.60ms였다.
- 512키 변경 없음: A의 snapshot 생성·비교는 약 794.59ms였다. D의 최대벽 갱신 작업은
  약 0.005ms였다. 일반 수집 상태·revision 요약 전송 비용은 이 수치에 포함하지 않는다.
- 초기 전체 복구의 정보량은 D도 줄이지 못한다. 일반 100키 표본은 약 11.36MiB다.

## 앞선 분할 패치의 미해결 경계

`_offer_all_record()`는 정확한 시간순 누적 최대값을 보존하며 개수를 자르지 않는다.
기존 테스트도 `_TRADED_RECORD_CAP`에서 이 기록을 자르지 않도록 요구한다.
따라서 분별 배열의 길이만으로 키별 응답 크기를 제한할 수 없다.

매도·매수 각각 200,000개의 단조 증가 기록을 가진 한 키에서 현재 `state_frames`가
`collector state peak exceeds byte limit`으로 실패하는 것을 재현했다. 운영 장애 당시
실제 필드별 크기는 미확인이므로 이것을 그 로그의 확정 세부 원인으로 단정하지 않는다.

종목 내부 분할 프로토타입은 같은 전체 이력을 621개 부분, 총 21.77MiB로 전송했다.
단일 payload 최대는 36,812B, 인코딩은 약 1.37초였고 frame 사이에 양보할 수 있다.
반면 마지막 기록 하나씩 추가하는 변경은 양쪽을 합쳐 2,039B, 약 0.10ms였다.
8MiB 초과 단일 키의 전체 복원도 별도 테스트로 원문과 전수 비교했다.

이 프로토타입은 프레임 프로토콜의 타당성을 확인한 것이다. 현재 범용 조립기는 완성된
논리 메시지를 메모리에 만들며 부모도 조각을 모은다. 실제 구현에서는 원본 `Peak`의
일관된 참조를 확보한 뒤 작은 묶음으로 변환하고, 부모의 staging/cache 예산을 별도로
관리해야 한다. 이 부분의 최종 RSS 상한을 검증했다고 주장하지 않는다.

## 상태 채널을 분리할 때 지켜야 할 조건

실제 socketpair에서 최대벽 수신을 멈추고 송신 high watermark를 넘겨 `drain()`을
차단했다. 그동안 별도 채널의 수집 상태 20개를 모두 받았다. 왕복 중앙값은 0.025ms,
최대는 0.128ms였으며 최대벽 송신은 끝까지 차단 상태를 유지했다.

같은 이벤트 루프의 CPU 정지는 별도 소켓만으로 격리되지 않는다. 작은 frame 32개를
보낼 때 `drain()`이 즉시 반환하도록 한 결정적 시험에서는 상태 태스크가 32개 완료
후에 실행됐다. 8개마다 명시적으로 양보하면 8개 시점에 실행됐다. 실제 sender는
frame 수 또는 작업 시간 예산에서 `await asyncio.sleep(0)`으로 양보해야 한다.
원본 이력 전체 생성도 수집 상태 태스크에서 제거해야 한다.

분리 후 수집 상태가 신선하다고 최대벽도 최신이라고 판단해서는 안 된다. 수집 상태에
키별 **원본 revision 요약**을 보내고, 부모는 보유 revision이 기대 revision보다 작으면
그 키의 최대벽을 준비 중으로 취급한다. 미전송 변경이 생겼을 때 revision이 올라야
하므로, 송신 완료 카운터를 요약에 재사용하면 안 된다. 이 조건도 테스트했다.

## 권고 프로토콜과 소유

1. **수집 상태**: 기존 상태 소켓은 계정 수신·완료 카운터, 설정 ACK, 저장 오류, PID,
   epoch, GC, 키별 원본 revision만 전송한다. 최대벽 배열을 만들거나 포함하지 않는다.
   1초 전송과 10초 신선도 판정, 저장 오류·죽은 필수 태스크 판정은 유지한다.
2. **최대벽 전송**: 별도 private socketpair를 사용한다. 공개 포트와 다른 writer는
   만들지 않는다. 화면 체결의 손실 허용 outbox에 섞지 않는다. frame은 최대 256KiB,
   encoded 대기 예산은 기존 8MiB를 상한으로 삼고 sender가 수신 압력만 기다린다.
   수치의 적용은 최대 상태와 부트스트랩 RSS를 추가 측정하며 확정한다.
3. **원본 변경 표시**: 분별 최대벽이 실제 교체된 자리에서 해당 `(키, side, field, 분)`만
   표시한다. scalar/rank는 side 단위로 표시한다. 상태가 바뀌지 않은 Live Tick은 원본
   revision을 올리지 않는다. ingest는 정렬·직렬화·네트워크 대기 없이 O(1) 표시만 한다.
4. **기록 시퀀스**: `all_record`는 단순 append로 가정하지 않는다. 지연 도착이나 seed
   merge로 뒤쪽 기록이 소급 제거될 수 있다. `_offer_all_record`가 바꾼 최소 인덱스부터
   꼬리를 교체하는 splice를 보낸다. 큰 꼬리와 초기 snapshot은 종목 내부에서도 나눈다.
   전송 중/그 뒤 변경의 표시를 분리하고, drain 완료가 더 최신 표시를 지우지 않게 한다.
   프로토타입의 인덱스별 revision 장부는 실구현에서 watermark/세대별 최소 인덱스로
   압축해 정체 시간에 비례하는 작업 큐가 되지 않게 한다.
5. **복구와 적용**: `(epoch, desired_version, key, trading_date/stream_generation,
   base_revision, revision)`으로 한 transaction을 식별한다. 분별 upsert/delete와 기록
   splice를 모아 마지막 부분에서 원자적으로 적용한다. 중간 EOF·혼합 부분은 공개하지
   않는다. 키별 base 불일치는 그 키만 준비 중으로 바꾸고 전체 snapshot을 재조회한다.
6. **초기 조회·RPC**: 초기 조회는 seed 요청과 revision token만 반환하고 큰 이력은
   동일한 최대벽 채널의 분할 transaction으로 보낸다. RPC 응답에 무제한 이력을 넣지
   않는다. 이전 revision의 늦은 전체 응답이 더 최신 차분을 덮지 못하게 한다.
7. **예산과 수명**: 키는 최대 512개, 조회하지 않는 키는 수요/유휴 정책으로 해제한다.
   하나의 최신 대기 상태로 합치고 전송 시작한 transaction은 끝까지 보낸다. 수신 cache와
   staging의 byte/point 예산은 RSS 계측 후 확정한다. 초과 시 해당 조회를 명시적으로
   실패시키며 이력을 자르거나 수집 태스크에 크기 예외를 전파하지 않는다.

키별 복구 대기와 수집 readiness를 구분하는 점은 ADR-0174의 현재 전역 최대벽 gap 실패
동작을 바꾸는 제안이다. 실제 채널 EOF·epoch 불일치·필수 태스크 종료의 fail-closed
정책은 유지한다. 최종 구현 시 ADR-0174를 개정하고 공개 응답을 바꾸는 경우 wire 모델과
프론트 미러를 함께 검증해야 한다. 본 실험은 공개 API를 바꾸지 않았다.

## 구현 순서와 남은 검증

먼저 상태 채널 분리와 **키 내부까지 가능한 분할 seed**를 함께 넣는다. 어느 키의 크기든
수집 상태 생성이 실패하지 않도록 하고, 키별 준비 상태를 연결한다. 이어서 원본 변경
표시를 각 분별 offer, record splice, day extreme, seed merge, 날짜/stream 교체에
연결한다. 프로토타입에 dirty 힌트를 정확히 주면 되는 것과 모든 실제 경로가 빠짐없이
힌트를 주는 것은 다른 검증이다.

구현 후에는 실제 `LiveStream.on_tick`과 seed 재생을 shadow로 함께 실행해 매 단계의
완성 snapshot을 전수 비교해야 한다. 부트스트랩·지연 도착·기록 꼬리 제거·장중 stream
이동·거래일 변경·키 삭제/재구독·이전 RPC·전송 중 덮어쓰기·부모 정지·부분 EOF를 포함한다.
변경 표시의 Live Tick당 추가 비용, 부모/자식 RSS, 자연 GC, 수신→완료 p99도 측정한다.
기존 2,377개 검증을 장중 성능 보증으로 대체하지 않는다.

실험 테스트는 원본 snapshot과의 일치, 변경 후 원복, 늦은 전체 응답, 키별 gap/복구,
이전 epoch/설정 거절, 실제 소켓 차단, 8MiB 초과 단일 키, 기록 소급 제거와 명시적
실행 양보를 검사한다. 재현 코드와 테스트는 `scripts/probe_collector_ipc_design.py`,
`tests/unit/live/test_collector_ipc_design_probe.py`에 있다.
