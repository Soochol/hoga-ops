# 최대벽 후보 정렬 비용 개선

> 아래 수치는 소량 입력 보완 전 측정이다. 이후 변경과 최종 검증은
> [후속 보고서](../2026-10-07-peak-followup/findings.md)를 참고한다.

## 선택한 변경

가격별 또는 (가격, 분봉)별 1위를 고를 때, 해당 그룹의 최대 잔량보다 작은 행을
먼저 제외한다. 남은 동률 후보에는 기존 정렬키(잔량 내림차순, 시각·순번·가격
오름차순)를 그대로 적용한다. 체결된 벽은 체결 필터를 먼저 적용한 뒤 최대 잔량을
구하므로 더 큰 미체결 벽이 체결 후보를 밀어내지 않는다.

적용 함수는 `_peak_bucket_dedup`, `_peak_price_distinct`,
`_peak_touched_distinct` 세 곳이다. 스레드 수·시간 제한·휴식·스케줄 변경은 없다.
출력 의미와 스키마가 같으므로 기존 캐시를 무효화하지 않는다.

## 비교 결과

기준: 병합된 PR #1925(6fc7109c)의 snapshots.py. Polars 32스레드, 양쪽 동일한
진단 DuckDB 4스레드. 실제 데이터 5개 Stock-Date, 각 6회, 실행 순서 교대.

| 합계 | 변경 전 | 변경 후 | 감소율 |
|---|---:|---:|---:|
| 집계 단계 CPU | 60,049 ms | 55,927 ms | 6.9% |
| 집계 단계 완료 시간 | 5,354 ms | 5,060 ms | 5.5% |
| SQL 포함 CPU (독립 재확인) | 59,482 ms | 55,246 ms | 7.1% |
| SQL 포함 완료 시간 (독립 재확인) | 8,070 ms | 7,861 ms | 2.6% |

독립 재확인은 자체 테스트 실행과 겹치지 않게 수행했다. 첫 SQL 포함 측정도
CPU 7.2%, 완료 시간 3.6% 감소였지만, 초반에 짧은 테스트 실행이 겹쳤으므로
최종 판단은 독립 재확인을 기준으로 한다.

SQL 포함 CPU의 표본별 감소율은 삼성전자 11.1%, SK하이닉스 14.2%,
005490 1.0%, 373220 -0.5%, 267260 -4.4%다. 작은 데이터에서는 선행 그룹 집계
비용 때문에 오히려 조금 느려질 수 있다. 모든 데이터가 빨라진다는 주장은 하지 않는다.

분류 조인을 순서 보존 조인으로 바꾸는 다른 후보는 CPU 개선이 1% 미만이라
채택하지 않았다(`order-preserving-join.json`).

## 정확성·검증

- 동일한 SQL 입력 프레임으로 30쌍을 비교해 최대벽 필드 전체 및 대표 행 순서까지
  정확히 동일함을 확인했다. 별도 SQL 실행끼리는 기존의 동률 입력 순서 변동이
  있으므로, 그것을 변경 전후 정확성의 기준으로 쓰지 않았다.
- 새 회귀 테스트 38개: 기존 전체 정렬을 기준으로 12개 시드 × 3가지 후보 선택을
  대조하고, 빈 입력·체결 후보 없음도 확인했다.
- 기존 최대벽·오라클·사전 계산 관련 테스트: 245 통과, 1 건너뜀.
- Ruff와 diff 공백 검사 통과. 전체 백엔드: 5,456 통과, 2 건너뜀,
  wallclock 13개 제외(146.28초).

`benchmark.py`는 기본 모드에서 정확성과 집계 비용을 확인하고 `--full`로 SQL을
포함해 측정한다. 기준 파일 준비 및 실행 방법은 스크립트 머리말에 있다.

## 적용 범위

현재 작업 브랜치 `codex/peak-classifier-order`에만 변경했다. 운영 데이터·캐시 및
실행 중인 서버 설정은 변경하지 않았다. CPU 시간은 전력 사용량이나 온도와 같지
않으며, 적용 후 실제 일일 작업과 발열 효과는 별도로 관측해야 한다.
