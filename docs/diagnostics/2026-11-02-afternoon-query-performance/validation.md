# 오후장 공략 조회 지연 개선

관심종목과 히트맵의 오후장 공략 조건을 빠르게 재조회하면서 같은 자료의 판정을 유지하는 것이 목표다.

## 일봉 준비

같은 불변 스냅샷과 152종목을 사용해 수정 전후를 번갈아 5회씩 실행했다. 일봉 준비 세 단계의 중앙값은 66.378초에서 25.727초로 줄었다. 범위는 수정 전 64.136~71.855초, 수정 후 25.322~28.813초였다. 약 61% 감소이며 전체 HTTP 조회 시간이 아닌 일봉 준비 시간이다.

기존 경로는 확인 시각 계산, 시계열 준비, 일봉 계약 집계에서 같은 관측 자료를 반복해서 디코딩하고 검증했다. 프로파일에서는 JSON 디코딩과 정규화한 원문의 해시 계산이 주요 비용이었다. CPU 시간과 경과 시간이 비슷해 한 코어의 처리량이 제한 요인이었다. 각 측정은 프로파일러 없이 실행했다.

변경 경로는 원문을 검증한 뒤 조건 조회에 필요한 자료를 관측 ID별로 압축해 공유한다. 원문 파일과 공급자 확인 자료는 바꾸지 않는다. 첫 준비의 원문 읽기는 747회에서 251회, 확인 검증은 248회에서 124회로 줄었다. 251개에는 일봉 관측 외의 기준 자료도 포함한다.

모든 실행에서 확인 시각, 152개 시계열의 모든 필드, 이벤트, 실패, 일봉 계약을 형식까지 보존해 비교했다. 전체 결과 지문은 모두 `5003a10b03cce4108ed5b96fad5bd71171ab2d995681bd039c898d841fd0308f`로 같았다. 일봉 준비만 측정하므로 분봉 조건의 이벤트가 비어 있는 것은 이 측정의 범위이며, 전체 검색 결과가 같다는 근거로 사용하지 않는다.

동일한 전체 스냅샷의 재조회는 기존 캐시도 빠르다. 이번 변경은 처음 준비할 때의 중복 작업과 부모 스냅샷만 바뀌었을 때의 재검증을 줄인다. 부모 정보만 바꾼 별도 1회 진단은 2.613초였고, 기준 자료 3개만 다시 읽었으며 일봉 확인 검증은 0회였다. 결과 지문도 같았다.

350종목의 보관량은 56,417,753바이트, 466개 항목이었다. 서로 다른 관측 원문을 한 번씩 읽고 반복 처리에서는 원문 읽기와 확인 검증이 모두 0회였다. 64MiB 전체 한도와 8MiB 개별 항목 한도를 유지한다. 이 수치는 캐시에 보관한 항목의 계산 크기다. 프로세스 전체 RSS나 일시적인 압축 해제 메모리의 상한이 아니다. 전체 시장 2,817종목의 캐시 적중률과 속도는 측정하지 않았다.

32코어 환경에서 관측한 부하는 약 5~6이었다. 실행 중인 사용자 서버를 중단하지 않고 전후를 교대로 실행해 시간에 따른 부하 차이를 줄였다. 측정에 벤더 요청은 없었다. 저장소별 Python 환경과 같은 의존성 잠금 파일을 사용했다.

수정 전은 `a712f83d0c26b86acbb91bbbadc27e6ab36f78aa`, 측정한 일봉 구현은 `f9e869b08265b62f943051be806016d9bf021f85`다. 통합한 `af3972504`는 같은 구현에서 불필요한 설명 주석만 제거한 상태다. 독립 검토에서 원래 후보 ID, 정정 행의 정확한 일치, 원문 확인, 의존 파일 검증과 복사 격리를 확인했다. 별도 여섯 스레드 실험은 각 관측을 한 번씩만 읽고 교착 없이 끝났다.

원시 측정값은 [daily-before-after.jsonl](daily-before-after.jsonl), 입력은 [daily-inputs.json](daily-inputs.json), 부모 변경 진단은 [daily-parent.json](daily-parent.json), 350종목 보관량은 [daily-full-scope.json](daily-full-scope.json)에 있다. 실행한 스크립트 원문은 [benchmark_case.py.txt](benchmark_case.py.txt)와 [benchmark_driver.py.txt](benchmark_driver.py.txt)다. 스크립트가 참조하는 운영 자료는 복제하거나 저장소에 추가하지 않았다. 재현에는 같은 불변 스냅샷을 보관한 로컬 자료와 입력에 기록된 종목 목록이 필요하다.

## 실제 서버의 개선 전 관측

기존 서버에서 저장된 오후장 공략으로 별도 감시 하나를 만들고 결과를 5회 읽었다. 시간은 59.880, 18.127, 20.214, 20.530, 124.449초였다. 대상은 순위 조건에 따라 150~151종목으로 변했다. 완전한 자료를 가진 종목은 0~35종목이었다. 이 실행을 정상적인 전체 판정의 처리량으로 해석하지 않는다.

이 기간에 health 응답 지연과 수집 상태 확인의 일시적인 503이 있었다. 수집 프로세스 재시작은 0회였고 별도 WS의 pong은 45회, 연결 오류는 0회였다. 마지막에는 health가 정상으로 돌아왔다. 검증에서 만든 감시만 삭제했다. [live-before.json](live-before.json)에 응답 시간, 판정 범위, 준비 상태와 연결 관측을 함께 기록했다.

실제 장중 자료는 시간에 따라 변한다. 반영 후 관측은 동일한 저장 조건의 실제 응답성과 준비 범위를 확인하는 용도이며, 전후 검색 종목의 완전한 일치를 주장하는 비교로 사용하지 않는다.

## 분봉 준비와 조회

기존 연속 수집의 한 종목별 1분 자료를 가격 조건과 거래량 조건이 함께 사용한다. 저장된 오후장 공략의 3분, 5분, 10분 신고거래량과 3분, 5분 봉 대비 가격 조건을 같은 수집 소유자가 처리한다. 저장된 F 조건의 3분 설정도 그대로 유지한다.

처음 준비와 연결 누락의 보충은 기존 API 경로를 사용한다. 준비된 당일 자료의 조건 조회는 WS로 갱신한 OHLCV를 읽는다. 한 번의 조회에서 한 종목의 여섯 조건은 같은 고정 관측본을 사용한다. 정상 연결의 조용한 구간에 15초가 지났다는 이유만으로 분봉 API를 다시 호출하지 않는다. 현재 시세 오버레이와 순위의 기존 신선도 계약은 유지하므로 모든 벤더 요청이 없어지는 것은 아니다.

가격이 빠진 체결, 분 중간부터 수신한 불완전한 구간, 연결 세대 변경과 재생 범위 초과를 완전한 OHLC로 표시하지 않는다. 최신 확정 REST 봉이 오래된 재생 자료보다 우선한다. 누락이 있는 종목만 제한된 준비 큐에서 보충한다. 거래가 없는 분을 임의로 만들지 않는다. 장전·휴장일의 직전 거래일 선택과 당일 봉 부족 시 보류하는 규칙도 유지한다.

프로세스 사이의 분봉 전송 형식은 버전 2다. 한 봉은 OHLC, 가격 완전성, 실제 첫 체결과 마지막 체결 시각을 함께 보낸다. 수신부는 묶음 전체를 검사한 뒤 적용한다. 수집기, 인프로세스 경로, 조사 스크립트와 테스트 소비자를 함께 변경했다. 운영 반영은 API와 하위 수집기를 함께 다시 기동하는 기존 전체 reload 경로를 사용한다.

독립 검증자는 격리된 자료에서 실제 HTTP 감시 시작, 조회, heartbeat, 삭제와 실제 runner를 실행했다. 고정 152종목의 일곱 조건 결과를 확인하고 준비·수신·완전 평가가 모두 152임을 검사했다. 16초 뒤에도 분봉 조회 호출은 0회였다. 같은 요청에서 현재 시세 두 묶음과 순위 공급자 경계의 갱신은 따로 기록했다. 별도 5% 가격 조건은 WS 가격 변경으로 HTTP 결과가 0종목에서 1종목으로 바뀌었다. 이는 fixture를 사용하는 기능 검증이며 운영 검색 속도 측정이 아니다.

같은 독립 HTTP 실험을 수정 전 `a712f83d0`에서 실행하면 152종목 준비 뒤에도 결과 조회가 분봉 API 경계에 들어갔다. 검증자가 금지한 벤더 호출 때문에 중단되기 전까지 가격 조건의 분봉 요청 192회가 관측됐다. 이를 전체 요청 수나 성공 처리량으로 해석하지 않는다.

512종목과 종목별 16개의 실제 가격이 있는 재생 봉을 만든 별도 보관량 검사에서 생산자와 복제본이 각각 8,192봉을 보관했다. 8개 전송 묶음의 최대 크기는 137,100바이트로 262,144바이트 한도 안이었다. 재귀적으로 센 두 Python 자료 구조는 약 5.0MB였다. allocator, 전체 RSS와 일시적 전송 버퍼를 포함한 수치는 아니다. 기존 64MiB 감시 허용량에는 추가 보관 봉과 종목별 재생분 예약량을 포함한다. 350종목과 512종목의 79분 요구량이 한도 안에 들어가는 것을 경계 검사로 확인했다. [minute-memory.json](minute-memory.json)에 관측값을 기록했다.

## 대기와 통신 제한

기존 20초 외부 타이머는 동시 실행 슬롯과 API 유량 대기도 포함했다. 앞의 네 요청이 슬롯을 점유한 상태에서 다섯 번째 요청이 벤더에 도착하기 전에 통신 시간 초과로 끝나는 것을 결정적으로 재현했다. 이 타이머를 제거하고 기존 벤더 HTTP의 20초 통신 제한을 유지했다. 큐 대기 취소, 공유 요청의 호출자 취소, 실제 통신 시간 초과와 유량 스케줄링을 함께 검사했다. 제한 시간을 더 큰 값으로 바꾸는 수정은 하지 않았다.

## 검증 범위와 원칙

전체 백엔드 검사에서 8,317개가 통과했고 2개가 건너뛰어졌다. 시간 의존 검사 13개는 제외했다. 장전 주문 BUY와 SELL의 기존 실패 2개는 정확한 기준 커밋 `a712f83d0`에서도 독립 재현했다. 이 작업이 전체 검사를 모두 통과했다고 주장하지 않는다. 기존 실패는 [이슈 2385](https://github.com/Soochol/hoga-ops/issues/2385)에서 관리한다. 후속 작은 변경에는 해당 경로의 검사를 다시 적용한다.

최종 분봉 생명주기 검사 156개와 대기·공유 캐시·통신·조건 평가 검사 171개가 통과했다. Ruff와 diff 검사도 통과했다. [minute-verification.json](minute-verification.json)에 정확한 명령, 검증한 커밋과 입력 해시가 있다. 전체 검사 뒤의 후속 변경은 영향 경로를 다시 검사했으며 재사용 근거도 같은 파일에 적었다. 통합 브랜치가 작업자의 구현과 같은 Python AST를 갖는 것은 [integration-validation.json](integration-validation.json)에서 확인했다. 차이는 중복 모듈 설명과 주석 제거다. 원래 실패와 검사 로그는 압축 파일로 함께 보관한다.

Fix Root Causes는 일봉 원문을 반복 검증하는 지점과 분봉 가격 조건이 별도 API 평가로 빠지는 지점을 고치는 선택에 적용했다. Explain the Number는 성공 응답 시간과 실제 판정 범위를 함께 기록하고, 152종목 전체 결과가 같은지 비교하는 선택에 적용했다. 캐시 적중이나 판정 보류를 전체 계산의 속도 향상으로 해석하지 않는다.

## 최종 리뷰에서 발견한 응답 순서 오류

최초 최종 리뷰는 `83b6da72e`에서 지연된 REST와 WS의 가격 우선순위 오류를 발견해 FAIL로 끝났다. 이때 PR을 draft로 바꾸고 반영을 보류했다. [이슈 2392](https://github.com/Soochol/hoga-ops/issues/2392)에 기록했으며 운영 반영 전에 수정했다.

API 요청 시작은 12:00:20, WS는 12:00:21에 거래량 15·종가 105, REST 응답은 12:00:30에 거래량 20·종가 110인 경우를 재현했다. 요청 시작 시각을 실제 자료의 순서로 비교해 오래된 WS 가격을 완전한 값으로 보존했다. 시가 대비 8% 조건은 완전한 false였지만 REST 자료는 완전한 true를 확인했다. 실제 HTTP 감시 경로에서도 잘못된 0종목 결과를 재현했다.

수정은 같은 원주가 1분봉의 완전한 관측을 거래량과 가격 범위의 일관성으로 비교해 OHLCV 전체를 선택한다. 새 완전 관측은 같은 시가를 유지하고 고가·저가의 범위를 좁히지 않아야 한다. 같은 거래량에서 가격이 다르거나 범위가 충돌하면 보류하고 해당 종목만 보충한다. 분이 닫힌 뒤 오래된 재생 자료가 들어오는 경우도 같은 비교를 적용하며, 확정 REST 봉의 기존 우선순위를 유지한다.

요청 시작 시각과 TTL·과거 조회 기준은 유지한다. API 응답 수신 시각은 별도 내부 필드로 공유 캐시와 차트 공급 경로에 보존한다. 이는 공급자의 체결 시각이 아닌 수신 상한이다. 조회 근거의 시각은 해당 종목의 사용한 자료 묶음을 나타내며, 과거 REST 봉과 현재 WS 봉이 섞이면 현재 봉의 마지막 체결 시각과 다를 수 있다. 사용하지 않은 재생 자료만으로 시각을 앞당기지 않는다. 종목별 사용 관측 시각 목록도 보관 범위에 맞춰 자르고 날짜 전환 때 비운다. 감시 허용량의 봉별 예약은 640바이트로 늘려 같은 기존 총한도 안에서 관리한다.

작업자 소스 `357179a10`은 통합 소스 `590b7efae`와 같다. 수정된 영향 경로 892개와 수집기 28개 검사가 통과했다. 새 독립 Astra 검토는 59개 검사와 일관된 REST/WS 가격 접두 구간·재생 순서 1,296개 조합을 실행하고 PASS를 반환했다. 이전 FAIL의 재현은 이제 true·complete이며 거래량 20·종가 110을 유지한다. 반대 방향으로 WS 거래량이 더 큰 경우는 WS를 보존한다. 원래 152종목 HTTP 검증도 모든 종목의 완전 평가·준비·수신을 유지했다. 한 종목의 WS 가격 변경 뒤 나머지 151종목의 분봉 근거는 같았다.
