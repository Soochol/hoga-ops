# 대신정보통신·레드캡투어 잔여 12개 충돌 검토

2026-10-24 KST. [535개 반영](../2026-10-24-screener-review-535/README.md) 후 남은 대신정보통신
7개·레드캡투어 5개를 검토했다. **12개 모두 가격은 같고 거래량만 다르다. 현재 규칙으로
추가 승인 가능한 것은 0개이며, 운영 정정은 실행하지 않았다.**

수정주가 기준 오류·현재 역산 반올림 수식·분봉의 단순 중간 누적이라는 설명은 이 자료와
맞지 않는다. 일봉/분봉에 포함되는 거래의 범위, 과거 일봉 저장 시점, 사후 정정 중 무엇이
차이를 만들었는지는 아직 입증하지 못했다. 따라서 새 공급자 값이 반복된다는 사실만으로
기존 원본을 잘못된 값이라고 확정하거나 12개를 일괄 승인하지 않았다.

## 추가로 확보한 근거

기존 운영 서버의 소유 클라이언트·거버너를 사용하는 GET **18건**을 실행했다.

- 두 종목 각각 2026-06-08~07-22의 수정 일봉, 3분봉, 60분봉: 6건.
- 충돌 날짜마다 1분봉: 12건. 응답은 모두 `fresh_dates`에 해당 날짜를 표시했다.
- HTTP 오류·응답 경고는 0건이다. 1분봉 12개는 이전 검토 때 보존한 봉·보정계수와도 그대로 같았다.
- 현재 수정 일봉 OHLCV는 앞선 두 독립 수집 회차의 수정 관측과 일치했다. 두 회차의
  **원본** OHLCV와 원문 `trde_qty`도 12개 모두 현재 v2 후보와 동일함을 대조했다.

같은 TR의 여러 해상도는 독립 공급자 셋이 아니다. 그러나 다른 해상도에서도 같은 합계를
얻어 특정 1분 해상도의 집계·일부 행 처리 문제 가능성을 낮춘다. API가 주지 않은 거래 유형이
무엇인지, 원 서버의 `acc_trde_qty`와 개별 봉 합계가 같은지는 이 정규화 응답으로 확인할 수 없다.
현재 API는 `acc_trde_qty`를 내보내지 않는다. 시각 표시 15:35를 실제 수신시각이나 확정 시각으로
해석하지 않았으며, 현재 시장 시간표를 과거 6~7월에 소급하지 않았다.

[NAVER Finance 일봉 게시 자료—레드캡투어](https://api.finance.naver.com/siseJson.naver?symbol=038390&requestType=1&startTime=20260608&endTime=20260722&timeframe=day)와
[대신정보통신](https://api.finance.naver.com/siseJson.naver?symbol=020180&requestType=1&startTime=20260608&endTime=20260722&timeframe=day)도 대조했다.

| 대상 | 다른 게시 경로의 관측 | 복구 검토에서의 의미 |
| --- | --- | --- |
| 레드캡투어 5개 | 전체 OHLCV가 확인 **원본**과 정확히 같음 | 후보 값의 교차 근거 강화. 거래 범위와 기존 값의 발생 원인까지 인증한 것은 아님 |
| 대신정보통신 7개 | OHLC는 병합 후 기준, 거래량은 관측상 `floor(확인 원본량/5)`와 같음 | 수정된 수량을 원수량으로 취급하면 안 됨. 공식 절사·포함 범위 계약을 확인한 것도 아님 |

대신정보통신의 NAVER량을 5배 하면 6/8 **3주**, 6/9 **2주**, 7/10 **2주**, 7/22 **1주**가
확인 원본량보다 적다. 나머지 3개가 우연히 정수로 돌아오더라도 전체의 정확한 원수량 근거로
승격하지 않는다. 이 관측은 기존 설계가 수정량의 역산을 원본량·수량 인증과 구분해야 하는
이유를 다시 보여준다. NAVER와 키움이 서로 다른 게시 경로라는 사실이 기초 거래소 원장이나
수량 이력의 완전한 독립성을 뜻하지도 않는다.

10/21 종료됐지만, 공급자 답변은 공식 Q&A로 문의하라는 안내였다. 집계·확정 규칙에 대한
해결 답변으로 해석하지 않았다. 이번에 외부 문의를 작성하거나 전송하지 않았다.

독립 거래소 원자료도 확인을 시도했지만 KRX 통계 조회는 `400 LOGOUT`, NAVER의 별도
과거 시세 경로들은 409/410을 반환했다. KIND 공개 시세 창은 현재 최근 구간으로, 이번
6~7월 12개를 교차 검증할 날짜 자료가 아니었다. 이들을 성공한 원수량 검증으로 계산하지 않았다.
인증정보를 복사하거나 로그인 제한을 우회하지 않았다.

## 복구 가능 여부와 다음 기준

**현재 즉시 공개할 수 있는 정정: 0/12.** 읽기 전용 `prepare_review`에 실제 분봉 근거를
넣었고 대신정보통신 7개·레드캡투어 5개가 전부 거절됐다. 기존 승인 목록은 그대로였다.
수치가 작다는 이유로 허용오차를 늘리거나 반복 관측만으로 승인하는 규칙을 추가하지 않았다.

복구 후보 자체는 있다. 우선순위와 필요한 자료는 다음과 같다.

1. **레드캡투어 5개 우선 검토**: 두 번의 원본 관측과 다른 게시 경로의 전체 OHLCV가 같아
   후보 값의 근거가 더 강하다. 같은 거래소·세션 범위의 권위 있는 일별 원수량 또는
   공급자의 포함 범위/정정 설명을 추가해 기존량과 차이를 설명한 후 새 검토 계획으로 처리한다.
2. **대신정보통신 7개는 원수량 교차 자료 보강**: 병합 보정된 거래량의 역산을 근거로 쓰지
   않는다. 비수정 일봉 원수량과 거래 유형별 수량을 확보해 확인 후보와 정확히 대조한다.
3. 기존 서버의 소유 클라이언트·거버너에서 **보관 전용 분봉 원문**을 얻는 검토 경로가 필요하다.
   날짜·코드·시장·주기·요청 수정 플래그와 `trde_qty`, `acc_trde_qty`를 함께 고정하고 장전/
   정규장/장후/시간외 및 보고시각의 의미를 확인한다. 기존 관측 재공개나 원본 덮어쓰기는 하지 않는다.
4. 근거가 확보되면 baseline·기존량·후보·독립 원수량·거래 범위·공시 경계를 묶은 별도 규칙으로
   정확히 입증된 날짜만 승인한다. 일부만 입증되면 나머지는 격리 유지한다. 수량 이력 인증은 별개다.

12개가 모두 입증되면 두 종목의 현재 요청 장기 구간은 다른 결측이 없어 준비 완료 대상이
될 수 있다. 이는 향후 조건부 전망이며 이번에 4→6종목으로 전환하거나 결과를 재공개한 것은 아니다.
