# 갱신 자료의 직접 조회와 분봉 계산 재사용

갱신 시 원본을 검증해 공개한 일봉 자료를 첫 조회부터 사용한다. 원본 후보와 확정·잠정·충돌,
원주가 수집 가드, 정정 선택, 수량 근거는 그대로 유지한다. 오래된 스냅샷이나 손상된 파생
자료는 기존 원본 전체 검증으로 돌아간다. 원본 자체가 바뀌거나 손상되면 결과를 거부한다.
설계와 로컬 준비 방법은 [공개 계약](../../plans/2026-11-02-screener-ready-query-publication.md)에 있다.

## 새 프로세스의 첫 HTTP 조회

동일한 실제 일봉 복사본과 152종목으로 각 버전을 번갈아 5회 실행했다. 매 실행은 새 Python
프로세스다. 준비된 분봉과 순위·현재가는 고정한 외부 경계 자료이며 네트워크 연결을 금지했다.
실제 FastAPI 감시 생성과 결과 라우트, ContinuousMonitors, 스크리너 평가·직렬화를 실행했다.
시장은 2026-11-02 12:40:20 KST로 고정했다. 분봉 준비는 타이머 밖에서 끝냈다.

| 범위 | 기존 중앙값과 범위 | 개선 중앙값과 범위 |
|---|---:|---:|
| 첫 결과 HTTP GET | 27.360초 (27.120–28.007) | 4.181초 (4.003–4.787) |
| 다시 읽은 원본 관측 JSON | 248개 | 0개 |
| 전체 조건 평가 가능 | 152/152종목 | 152/152종목 |
| 일치 결과 | 삼성전자 1종목 | 삼성전자 1종목 |

10회 모두 오류 0건이다. 전체 응답에서 공개 스냅샷 ID만 제외한 직렬화 해시가 같다.
표시 가격·거래대금·조건별 사건·보류 사유·확정 정보·분봉 수집 상태도 비교에 포함했다.
상승하는 삼성전자 분봉과 나머지 평탄한 분봉은 조건 평가와 결과 행이 실제로 실행됐음을 확인한다.
분봉 초기 준비 외 결과 조회 중 분봉 API 호출은 없다. 프로세스 캐시는 비었지만 OS 파일 캐시는
초기화하지 않았다. 공유 호스트의 브라우저와 사용자 서버를 유지했으며 32논리 CPU에서 측정했다.
CPU 시간과 경과 시간이 거의 같아 주된 제한은 한 프로세스의 자료 변환 비용이다.

기존 측정 버전은 `6c5d84198a3a2681f93ca7f844b823e4f3f492ab`, 개선 버전은
`7f2d73d1ec3719d7af6dcdfcbd91679300da718e`다. 이후 main의 달력 갱신 복구 변경을 합친
`0866e57cb54a9e440bbd1e7ce75090363fffd376`도 독립 검증자가 같은 HTTP 응답 해시와
152종목 평가, 원본 JSON 0개를 확인했다. 독립 단일 실행 시간은 반복 비교 수치에 합치지 않았다.

[원시 측정값](fresh-process-results.json), [실제 HTTP 실행기](first_query_case.py.txt),
[교대 실행기](compare_first_query.py.txt), [자료 복사 도구](clone_corpus.py.txt)에 근거와 경계가 있다.
재현하려면 원래 불변 스냅샷과 시장 자료를 보관한 로컬 환경이 필요하다. 운영 원본은 저장소에
추가하지 않았다. 준비된 같은 자식 스냅샷을 두 버전이 읽으며 기존 버전은 추가 필드를 무시한다.
고정 시계의 11월 2일은 복사본의 가변 달력 오버레이에만 추가했다. 원본과 불변 기준 달력은 그대로다.

## 공개 준비 비용과 남은 조회 비용

선택한 152종목 중 기존 v2 관측이 있는 124종목을 로컬에서 한 번 준비했다. 원본 파일 합계는
2,008,511,304바이트, 조회 본문 합계는 압축 17,644,888바이트와 해제 123,515,871바이트다.
최대 한 본문은 압축 165,812바이트, 해제 1,098,809바이트로 제한 안에 있다. 초과 종목은 없다.
이 준비에는 24.510초가 들었고 첫 조회 비교에 포함하지 않았다. 공급자 API는 호출하지 않았다.
수치와 종목별 크기는 [준비 보고서](preparation.json)에 있다. 향후 관측 공개는 이 준비를 공개
단계에서 수행하며, 기존 자료는 선택 범위를 명시해 한 번 준비한다.

별도 [프로파일](calendar-profile.txt)은 남은 초기 표시 자료 준비에서 압축 본문의 JSON 해제,
행 스키마 확인, 가격·날짜 요약 처리가 대부분임을 보인다. 프로파일의 4.724초는 계측 오버헤드가
포함돼 반복 비교 수치와 더하거나 직접 비교하지 않는다. 최초 공급자 분봉 준비 대기는 이 비용과
별개다. 실제 서버 재시작과 현재 공급자 상태에서의 검증은 아래 운영 반영 후 확인에 있다.

## 분봉

하나의 결과 조회 안에서 불변 분봉 스냅샷의 3·5·10분 집계를 한 번씩 계산해 재사용한다.
조건별 봉 수와 하한·열린 봉·손상·수집 상태 확인은 그대로 적용한다. 같은 시간봉을 쓰는 여러
조건이 있어도 이미 만든 집계를 복사해 사용한다. 캐시는 해당 조회가 끝나면 해제된다.
초기 API 준비·누락 보충, WS 수집, 가변 History 갱신, 구독 범위와 동시 호출 수는 바꾸지 않았다.

실제 구현의 독립된 분봉 평가 비교는 각 5회 교대 실행이다. 준비·HTTP·일봉·순위는 제외했다.

| 준비된 입력 | 기존 중앙값 (범위), ms | 개선 중앙값 (범위), ms |
|---|---:|---:|
| 150종목, 변경 없는 버전 | 451.6 (393.2–639.4) | 132.9 (116.7–141.7) |
| 150종목, 버전 변경 | 937.3 (776.2–1046.0) | 541.3 (322.4–558.8) |
| 152종목, 버전 변경 | 1036.2 (811.4–1174.9) | 555.5 (305.4–566.7) |

모든 전체 평가·사건 응답이 같고 평가·준비·수신 수가 종목 수와 같다. 결과 중 공급자 분봉 요청은
0개다. 별도 계측에서 150종목 버전 변경 시 집계는 5,400회에서 450회로 줄었다. 추가 객체 그래프는
약 2.44MB이며 RSS 수치가 아니다. 실제 틱 빈도와 결과 사건 수에 따라 절감 폭은 달라진다.
[원시 측정과 소스 지문](minute-results.json), [실행기](minute_benchmark.py.txt)에 근거가 있다.
보고서의 head는 커밋 전 측정 당시 base를 표시하므로 소스 지문을 기준으로 확인했다.
두 production 모듈과 분봉 평가 모듈의 SHA-256은 최종 통합 소스와 같다.
분봉 실행기는 `.audit/minute-read-aggregation/` 아래의 `base_continuous.py`와 `base_bars.py`를
읽는다. 재현 시 함께 저장한 `minute_base_continuous.py.txt`와 `minute_base_bars.py.txt`를
그 이름으로 복사하고 실행기를 같은 디렉터리의 `benchmark.py`로 실행한다.

여전히 느릴 수 있는 부분은 감시 시작 시 여러 종목의 API 준비 대기와, 많은 종목이 동시에
바뀔 때의 배경 알림 계산이다. 이번 조회 내 재사용은 이 두 경로를 변경하지 않는다. 조사에서
350종목을 동시에 변경한 인위적 알림은 약 0.26초였으나, 실제 틱당 변경 종목 수를 측정하지
않았으므로 운영 비용으로 일반화하지 않는다. 준비 순서 변경과 배경 계산 최적화는 별도 근거가 필요하다.

## 정확성과 회귀 검증

원본 관측·후보, 헤더와 본문의 읽기 전후 파일 정체성, 체크섬, 크기·해제 한도와 형식 버전을
검사한다. 같은 크기와 복원된 mtime으로 원본을 바꿔도 ctime을 포함한 수신증이 변한다.
읽기 종료까지 원본이 바뀌면 거부한다. 파생 자료가 없거나 깨진 경우에만 검증된 원본으로 돌아간다.
기존 원본 파일을 덮어써서 복구하거나 잠정 자료를 확정으로 올리지 않는다.

독립 검토에서 최종 행 해제 뒤 원본 변경 검사가 빠진 공용 reader 경계를 발견했다. 네 가지
새 검사는 수정 전 모두 실패했고 수정 후 모두 통과했다. 차가운·따뜻한 캐시와 준비·기존 형식을
각각 확인했다. 전체 라우트의 바깥 캐시는 이미 변경을 거부했지만 공용 reader도 같은 계약을 갖게 했다.

일봉 구현의 백엔드 전체 검사는 8,424개 통과, 2개 건너뜀, 13개 wallclock 제외다.
파서·관측별 재사용 변경 뒤 관련 1,731개, 최신 main과 분봉을 합친 뒤 관련 1,826개,
최종 해제 검사와 달력 변경 뒤 관련 111개가 통과했다. 기존 전체 검사와 통합 입력 차이는
[검증 지문](validation-inputs.json.gz), [원래 전체 지문](full-backend-inputs.json.gz),
[검증 기록](daily-owner-validation.json)에 있다. 최종 통합 소스에서 백엔드 전체를 다시 실행해 **8,487개 통과**, 2개 건너뜀,
13개 wallclock 제외를 확인했다. 실행 시간은 392.14초이며
[전체 로그](integrated-full-backend.log.gz)에 남겼다. 이 최종 검사는 앞선 부분 재사용 판단도 포함한다.
Ruff는 추적 소스 전체에서 통과했다. 루트의 추적되지 않는 `.audit` 임시 조사 파일만 제외했다.

독립 검증자는 자기 체크아웃에서 실제 공개 후 새 프로세스의 전체 스크리너를 실행했다.
정상·미확정·충돌·잠정·commit_pending·정정 선택의 7개 사례가 기존 원본 조회와 같았다.
원본 JSON을 열지 못하게 하는 audit hook, 본문 손실 후 검증 경로, 원본 손상 거부도 확인했다.
실제 운영 재시작과 공급자 준비 시간은 이 격리 검증이 증명하지 않는다.

## 운영 반영 후 확인

PR #2396을 머지하고 기본 체크아웃에 pull했다. 서버가 `6b23591d8`로 한 번 재시작한 뒤
첫 감시 결과 HTTP 응답은 **4.905초**였다. 당시 검색 후보 154종목 중 분봉 준비가 끝난 것은
15종목이었다. 후보 154종목의 분봉 준비가 모두 끝난 시점은 감시 시작 후 **88.095초**였다.
첫 응답 시간과 전체 API 준비 시간을 합쳐 설명하지 않는다.

후속 감시의 반복 조회는 별도 기록이다. 마지막 응답에서 분봉은 154종목 모두 준비됐고,
153종목은 판정 가능했으며 일치 결과는 4종목이었다. 나머지 1종목 `069540`은 공급자 표시
가격 미제공으로 보류됐다. KRX 정규장 종료 뒤의 검사이므로 수신 중 0종목은 정상이다.
[원시 집계](live-results.json)와 [서버 단계 로그](live-phases.log)에 근거가 있다.

기존 관심종목·히트맵 350종목 중 v2 관측 233종목을 로컬에서 한 번 준비했다. 원본 합계는
3,578,854,412바이트, 조회 본문은 압축 31,058,952바이트와 해제 219,584,668바이트다.
준비에는 40.161초가 들었고 공급자 호출은 없다. 원래 핀한 스냅샷은 그대로이며 새로운
스냅샷의 의미 있는 필드는 이전과 같다. 조회용 참조와 parent만 추가됐다.
사용자 체크아웃의 기존 수정·미추적 파일 39개와 stash 14개의 내용·순서도 그대로다.

처음 상태 점검기는 WS 메시지를 소비하지 않아 클라이언트 수신 큐가 찼다. 이 점검기의 pong
시간 초과는 서버 장애 통계로 사용하지 않았다. 별도 로컬 WS 서버에서 64개 프레임을 보내면
읽지 않는 클라이언트만 pong을 받지 못하고, 메시지를 소비하면 즉시 받는 현상을 재현했다.
점검기를 수정한 뒤 약 36초 동안 실제 서버에서 health 12회 모두 200, pong 12회와 WS 프레임
수신을 확인했으며 오류는 없었다. 두 점검은 각각 만든 감시만 삭제했다.
