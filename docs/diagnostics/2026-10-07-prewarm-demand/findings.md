# 사전 계산과 실제 요청의 관계 조사

## 확인한 사실

- PR #1926은 `7f1d4dcb485fdf463a7e853fadef0420043ec049`로 병합했고
  `/home/dev/code/hoga-ops` main에 fast-forward pull했다. 기존 로컬 파일 두 개의
  SHA-256은 pull 전후 동일하다.
- 기존 prewarm은 유효한 캐시를 건너뛰며, 관심종목 우선·최근 날짜순이다.
  기본 대상 소스는 hogaplay와 kiwoom_live 둘 다다. 따라서 원본 소스별로 실제
  수요를 구분해야 한다. 한쪽만 조회한다고 확인되기 전에는 다른 쪽이 낭비라고
  단정하거나 계산 대상을 제거하지 않는다.
- 기존 `hoga.log`에는 10월 1일·2일·6일 성공 집계가 각각 2,000건으로 기록돼 있다.
  소요 시간은 각각 2,071.1 / 1,912.9 / 2,245.4초다. 실패·스킵과 분리된 건수다.
  이는 성공한 Stock-Date/source 번들 빌드 건수이며 순수 계산 CPU 시간이 아니다.
- 일반 성공 요청은 기본 설정에서 전수 기록하지 않는다. request_timing은 느린
  요청·5xx 또는 PERF_DEBUG가 켜진 요청만 기록한다. 이 로그로 조회율을 계산하면
  빠른 캐시 적중 요청을 빠뜨리므로 잘못된 결론이 된다.
- 새 계측 형식으로 기존 현재 로그를 읽은 `baseline.json`은 이벤트 0개,
  demand_rate=null이다. **사용률 0%라는 뜻이 아니라 기록이 없다는 뜻**이다.

## 추가한 계측

- 사전 계산의 두 빌더가 성공한 뒤 warm 이벤트를 하나 기록한다. dry-run,
  이미 warm인 스킵, 메타 검사 실패, 계산 예외는 분모에 넣지 않는다.
- API `/range`가 만든 정상 번들에 대해 demand 이벤트를 요청당 하나 기록한다.
  source는 선호 설정이 아닌 실제로 선택된 source를 사용한다.
- 데이터 루트·종목·날짜·source·venue·지표 종류(peak/depth)를 담는다.
  부모와 compute worker는 PID가 달라도 같은 데이터 루트로 결합한다.
  테스트용 데이터 루트는 별도로 분리된다.
- 과거 날짜만 세며 hoga/candles 모드, cutoff 전용 요청, 꺼진 지표는 제외한다.
  내부 진단·백필 도구는 기본적으로 기록하지 않는다. API가 내부 인자로 명시적으로
  기록을 활성화하며 HTTP 쿼리나 응답 필드를 추가하지 않는다.
- 기존 INFO 회전 로그를 사용한다. 매 요청의 원본·캐시 재검사, 폴링, 추가 스레드,
  영구 접근 기록 DB는 도입하지 않았다. 로그 직렬화·쓰기에 작은 추가 비용은 있다.

## 집계 방법과 해석

`tools/report_prewarm_usage.py`에 데이터 루트 및 보존된 로그 파일 전체를 넘긴다.
예시(저장소 루트):

```sh
PYTHONPATH=. .venv/bin/python tools/report_prewarm_usage.py \
  --data-dir /home/dev/.local/share/hoga-ops/data --window-hours 24 \
  /home/dev/.local/share/hoga-ops/logs/hoga.log*
```

기본 관찰 창은 계산 완료 이후 24시간이다. 관찰 종료는 입력 이벤트의 최신 시각을
사용한다. 충분한 기간이 지나지 않은 계산은 요청이 있었어도 pending으로 분리해
성숙 표본의 조회율을 부풀리지 않는다. 로그 입력 순서는 무관하며 중복 이벤트를
제거한다. 같은 날짜를 다시 계산한 것은 별도 빌드로 센다.

이 비율은 **warm 번들 뒤에 같은 종류의 API 수요가 하나라도 발생한 비율**이다.
실제 캐시 적중·최신 generation 일치·브라우저 표시·절약된 CPU 시간을 뜻하지 않는다.
특히 일부 지표만 누락되어 실행된 prewarm도 번들 하나로 센다. 보존 로그가 중간에
유실됐거나 회전 삭제됐다면 낮은 비율을 정책 변경의 증거로 사용해서는 안 된다.

관찰 뒤에는 source별 수요 비율을 먼저 비교하고, 낮은 쪽을 줄였을 때 콜드 요청
지연이 얼마나 늘어나는지 함께 확인한다. 24시간 미관측을 영구 미사용으로 보지 않으며
더 긴 보존 기간을 확보하면 `--window-hours 168`로 7일 창도 비교할 수 있다.

## 상태

계측 및 보고 도구는 `codex/prewarm-usage-measurement` 작업 브랜치에 구현했다.
이 후속 계측은 아직 사용자 서버에 반영하지 않았다. 따라서 실제 조회율·낭비율은
현재 산출할 수 없으며, 데이터가 쌓이기 전에 계산 정책을 변경하지 않았다.
검증 완료: Ruff 및 diff 공백 검사 통과. 전체 백엔드 5,573 통과, 2 건너뜀,
wallclock 13개 제외, 기존 경고 35개(145.60초). API wire 계약 검사도 포함한다.
