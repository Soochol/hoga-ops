# 일반 자동 갱신의 잠정·확정·재대조·격리 검증

2026-10-24. [설계와 동작 계약](../../plans/2026-10-24-screener-automatic-daily-ingest.md).
기존 데이터·저장 조건을 보존하며 구현과 기본 체크아웃 반영을 완료했다.
최초 전체 공급자 재대조는 기존 22시 스케줄에 맡긴다. 이번 검증에서 4,404종목을 실제 증권사에
일괄 요청한 것은 아니다. 아래 부하 수치는 운영 데이터 복사본과 명시적인 모의 미래 봉으로 측정했다.

## 반영 내용

- 당일 원주가 일봉은 잠정 원장에 보존한다. 해당 날짜 22시 이후의 관측과 다음 날짜 독립 관측이
  정확히 일치한 없는 날짜만 추가한다. 금요일 관측은 토요일에도 재대조한다.
- 종목별 정기 요청 한 번에서 최근 5거래일을 검사한다. 마감 이후 불일치, 기존 저장값의 수정,
  잘못된 OHLCV는 원본을 덮어쓰지 않고 격리한다. 1주 차이도 자동 허용하지 않는다.
- 원주가 수량·금액과 독립 확인된 공급자 수정 OHLC를 분리한다. 거래량만의 충돌로 가격 조건을
  무효화하지 않으며 수량 이력 인증·기존 v2 정정 규칙은 확장하지 않는다.
- 검색은 조건별 필요 날짜에만 가드를 적용한다. OR의 정상 조건과 명시적인 당일 장중 오버레이를
  유지한다. 저장된 조건식·유니버스·제외 설정을 자동 수정하지 않는다.
- 상태 응답과 기존 갱신 표시에서 확정·잠정·격리·확인 실패를 구분한다. 추가 행이 없어도
  격리 상태가 달라질 수 있으므로 지난 검색 결과에 재조회 필요 표시를 한다.
- 오늘의 달력 범위가 아직 확보되지 않았더라도 22시에는 확인된 과거 날짜만 재검사한다.
  확인되지 않은 오늘이나 휴장일 봉을 새로 추정하지 않는다.

운영 비교의 네 종목은 `000120`, `003240`, `013030`, `900310`이다. 1,000봉 원본 수량 창은
완전하지만 해당 날짜가 신고거래량 조건에 부합하지 않아 결과 행은 0개였다. 주식 수 이력에
근거가 없으므로 보정 수량 창은 계속 미완전하다. 가격 조건은 기존 25개 결과를 유지했다.

직렬화 비교는 새로 추가된 완전한 `daily_coverage`를 별도 확인하고, 기존 비교기의 실행 시각
필드만 정규화했다. 운영 HTTP 비교는 실행 ID와 조회 시각만 제외하며 원 응답을 함께 보존했다.
이전 코드의 실행은 이전 코드가 운영 중일 때 정확 재실행했고, 최종 실행은 최종 코드 지문과
일치함을 확인했다. 이전 스냅샷과 실행 결과의 GET은 바뀌지 않았다.

재발 방지 테스트에는 잠정 값 수렴, 다음 날짜 확인, 1주 수정, 마감 후 변경의 지속 격리,
원본/후보·요청 코드·날짜·수량 불일치, 잘못된 원본 봉, 대량 0거래량 차단, 누락 날짜,
재시도 예산, 중단 후 응답 재사용, 저장 실패 후 재개, 동시 writer 충돌, 동시성 3개,
페이지 예산, 배경 거버너, 토요일 트리거, 장중 오버레이, OR 조건, 독립 수정주가와 원주가
충돌 분리, HTTP 상태·검색 필드 보존, 달력 미확인 시 과거 날짜만 계획하는 경우가 포함된다.

## 부하 실측

측정 대상은 로스터 **4,404종목**, 최근 5거래일이다. 기존 운영 파일을 복사하고 네트워크 대신
저장값 재생과 모의 미래 봉을 사용했다. 수치는 **독립 검증 프로세스 전체**이며 기존 업데이터
대비 추가분이나 전체 PC 사용량으로 해석하지 않는다. 실제 공급자 대기·속도 제한은 제외한다.

| 단계 | 논리 조회 | 로컬 처리 시간 | 프로세스 CPU 시간 | 누적 최대 RSS |
|---|---:|---:|---:|---:|
| 최초 최근 구간 대조 | 4,404 | 약 4~6초 | 약 6~8초 | 약 0.5GB |
| 정상 당일 잠정 수집 | 4,404 | 4.02초 | 5.57초 | 약 0.6GB |
| 다음 날짜 확인·확정분 추가 | 4,404 | 7.39초 | 10.30초 | 917MiB, 약 0.9GB |

전체 과거 파일을 메모리에 합치던 초안은 최대 **4,587MiB**였다. 이를 **65,536행씩 복사**하고
새 날짜만 계산하도록 바꿔 같은 시나리오의 최대 메모리를 약 80% 줄였다. 기존 행 값은 전부
동일하다. 최종 측정의 최대 이벤트 루프 지연은 약 165ms였으며, 부하가 전혀 없다는 의미는 아니다.

완료 뒤 스케줄러의 작은 상태 파일 확인은 1,000회 평균 **0.051ms**였다. 확인된 1,000거래일
구간·4,404종목의 가용성 검사만 측정하면 최초 약 113ms, 캐시 후 약 23~70ms였다.
전체 검색 실행 시간과 구별한다.

증거 gzip의 실데이터는 하루 약 1.7MB였지만 작은 파일의 디스크 할당과 체크포인트를 포함하면
지속 보관량은 약 **32~35MB/실행일**이다. 최근 원장은 약 8~13MB였다. 원본 증거를 보존하므로
장기 사용 시 저장량이 누적된다. 기존 대형 parquet 두 개의 교체·journal 복사 I/O도 남는다.

평시에는 5일을 각각 조회하지 않고 한 응답에서 처리한다. 기존 background 우선순위를 유지하고
동시 조회 3개, 조회당 최대 2페이지, 하루 2회 시도, 실패 후 30분 간격으로 제한한다.
성공한 종목 응답은 같은 날 재사용한다. 과거 누락분의 최초 확인에만 두 번째 조회를 사용한다.
금요일의 다음 날짜 확인을 위한 토요일 전체 요청은 기존 거래일 전용 갱신 대비 추가 비용이다.
`provider_pages`는 수신 완료 표본의 페이지 수이며 전송 계층 내부 재시도 횟수와 같지 않다.
모의 입력에서 497~500종목은 최근 날짜가 부족했다. 이는 실제 신규 증권사 오류 수가 아니다.

기본 체크아웃 `/home/dev/code/hoga-ops`에 이번 기능의 18개 파일만 반영했다. 병행 main 갱신의

확인하고 사용자의 명시적 승인을 받아 **8000 백엔드만** 기존 고정 실행기로 다시 실행했다.

## 증거 재검증

```bash
python docs/diagnostics/2026-10-24-screener-auto-ingest/verify.py
```

[evidence.json.gz](evidence.json.gz)에 전후 검색 응답·고정 스냅샷·실행·모의 부하 결과가 들어 있다.
`recorded-scripts/`는 당시 실행한 진단 스크립트이며 경로가 검증용 `/tmp`와 운영 데이터의
읽기 위치에 고정돼 있다. 운영에 그대로 실행하는 복구 도구로 사용하지 않는다.
`verify.py`는 보존한 증거를 읽기만 하며 공급자 요청·운영 데이터 쓰기를 하지 않는다.
