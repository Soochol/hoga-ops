# 조건검색 자동 준비와 갱신 최적화 제안

2026-11-01 KST. 사용자 요청: 갱신을 빠르게 하고, 조건검색에서 별도 준비 버튼이나
체크 없이 사용할 수 있는 설계를 테스트로 검토한다. **제안이며 제품 동작은 변경하지 않았다.**

## 권고

**사용자는 조회/시작만 누른다. 서버가 필요한 입력을 계획하고, 기존 관측을 재사용하며,
부족한 입력만 준비하고, 판정 가능한 결과를 자동으로 갱신한다.**

일반 갱신의 동시 종목 수 3은 우선 유지한다. 새 기준 준비의 순차 실행을 최대 4개
준비 작업으로 바꾸되 기존 전역 background 실행 한도 4와 앱키·TR·공용 읽기 제한을
그대로 따른다. 일반 갱신과 검색 준비에 별도 거버너나 별도 자격증명을 만들지 않는다.

새 구현의 중심은 **서버가 소유하는 공통 준비 작업 관리자**다. 현재 일반 갱신·v2 준비·
명시적 복구를 하나의 무차별 수집 함수로 합치지 않고, 요청 공유·계획·진행·재개와
수집 원본의 재사용을 공통화한다. 각 경로의 확정 및 계산 계약은 유지한다.

### 유량 제한을 유지한 병렬 비교

`probe.py`가 **실제 KiwoomCapacityScheduler**를 사용하고 전송만 sleep 기반으로 대체했다.
유량은 기본 5 × headroom 0.8/앱키/TR, background 상한 4를 그대로 적용했다.
현재 서버의 다른 화면 요청·실제 HTTP·토큰·공용 읽기 예산은 모사하지 않았다.
따라서 아래 결과를 실제 서버의 배속 또는 완료 시간으로 예측할 수 없다.

24종목 × 종목당 순차 2요청, 가상 앱키 4개, 각 3회 중앙값:

| 요청당 모의 지연 | 종목 작업 1개 | 3개 | 4개 | 6개 |
|---|---:|---:|---:|---:|
| 80ms | 3.860초 | 2.920초 | 2.841초 | 2.844초 |
| 200ms | 9.625초 | 3.317초 | 2.962초 | 2.961초 |

- 순차 → 4개는 이 실험에서 약 1.36~3.25배다.
- 6개로 늘려도 기존 background 한도 4 때문에 추가 이득이 없다.
- 앱키 1개 대조군은 순차 5.850초, 동시 작업 4개 5.857초로 차이가 없다.
  API 제한에 막힌 경우 동시성 증가는 해결책이 아니다.

일반 갱신에 가까운 **48종목 × 1요청, 가상 앱키 6개**, 각 3회 중앙값:

| 요청당 모의 지연 | 현재 3개 | 후보 4개 | 판단 |
|---|---:|---:|---|
| 80ms | 1.916초 | 1.918초 | 개선 없음 |
| 200ms | 3.211초 | 2.461초 | 약 23% 단축 |

일반 갱신의 3 → 4 확대는 첫 변경으로 채택하지 않는다. 운영의 대기/응답/저장 비중을
먼저 계측하고, foreground 지연과 오류율까지 비교한 뒤 별도 변경으로 판단한다.
현행 동시 종목 예산 3은 기존 자동 갱신 설계에 명시돼 있다.

두 소비자가 동일한 관측을 동시에 요구하는 구성에서 호출자별 키는 전송 48회,

포괄하는 신규 공통 요청 계약은 구현 단계의 별도 회귀 검사가 필요하다.

### 일괄 공개 비교

임시 디렉터리의 48종목 × 700일, 로스터 4,412종목. 실제 immutable 객체·writer lock·
atomic pointer·fsync를 사용했다. 새 일괄 공개 함수는 이 실험 파일 안의 **프로토타입**이다.
최초 baseline 복사와 네트워크는 시간에서 제외했다. 각 3회 중앙값:

| 공개 단위 | 공개 횟수 | 저장 구간 |
|---|---:|---:|
| 현재 종목별 | 48회 | 633ms |
| 8종목 | 6회 | 365ms |
| 24종목 | 2회 | 342ms |

8종목 묶음은 이 구간에서 약 42% 단축했다. 24종목 묶음의 추가 이득은 작고,
결과를 공개하기까지 기다리는 종목 수가 늘어난다. **첫 결과 즉시 공개, 이후 최대
8종목 또는 250ms 중 먼저 도달한 시점**을 초기 후보로 권고한다. 250ms 및 첫 결과
공개 지연은 아직 통합 프로토타입으로 측정하지 않은 조정값이다.

공개 후 manifest의 관측·로스터·달력·기준선/수정 기준이 동일함을 비교했다
(공개 이력을 나타내는 parent와 snapshot ID는 다를 수 있다). 원본 parquet 해시 보존,
포인터 공개 전 장애에서 이전 스냅샷 유지, 원본 충돌 격리, 수정 기준 변경 시

취소 중 batch flush, 다른 writer와의 경쟁까지 갖춘 제품 구현은 아직 아니다.

## 제안하는 사용 흐름

1. 조건을 편집하는 동안에는 수집을 시작하지 않는다.
2. **조회/시작**하면 서버가 조건식에서 실제 참조하는 leaf와 선택 종목 범위를 확정한다.
3. 저장된 입력으로 바로 평가 가능한 경우 기존 scan을 수행한다. 공급자 호출은 0회다.
4. 필요한 입력만 부족하면 서버가 준비 작업을 시작/공유한다. 다른 창에서 같은 범위를
   요구하면 진행 중 작업에 합류하고, 새로고침 후에도 작업 id로 상태를 복구한다.
5. 평가 가능한 종목부터 결과를 표시한다. 대상 총수와 평가 완료·준비 중·검증 대기·
   최종 미제공 수를 함께 표시하며, 일부 결과를 전 시장의 완료 결과로 표현하지 않는다.
6. 준비 완료 시 결과를 자동 갱신한다. 전체 순위 조건은 고정된 전체 모집단의 순위를
   사용하며 준비된 일부 종목 안에서 재순위화하지 않는다.

기존 ‘새 기준 일봉 준비’와 사용자가 선택해야 하는 준비 체크를 제거한다.
종료된 다른 조건의 전역 history job을 현재 검색의 상태처럼 붙이지 않는다.
판정 불가를 ‘조건 불충족’ 또는 ‘검색 결과 0’으로 합치지 않는다. 예:

> 일치 18종목 · 평가 완료 720/800 · 데이터 준비 중 75 · 검증 대기 5

검증 대기 5종목은 준비가 끝나도 별도로 남을 수 있다. 사용자가 내부 데이터 기준을
선택해야만 진행할 수 있게 만들지 않는다. 상세는 필요한 경우 펼쳐 본다.

## 서버 설계

### 입력 요구사항과 준비 상태를 한곳에서 계산

각 leaf가 요구하는 가격·원본 수량·실제/추정 거래대금·수량 사건 근거·날짜/주기 범위를
계획한다. 가격 조건에 수량 증거 부재를 전파하지 않는다. `preview`, `_prepared`, scan이
각자 다른 기준으로 준비 여부를 판단하지 않도록 현재 evaluation 계약을 공유한다.

상태는 적어도 아래처럼 나눈다. 이름은 API 구현 시 Pydantic/TypeScript에 함께 선언한다.

| 상태 | 자동 처리 |
|---|---|
| 준비 완료 | 즉시 평가, 네트워크 없음 |
| 수집 가능한 누락 | 필요한 원본/수정 가격·기간만 계획하여 수집 |
| 잠정/독립 확인 대기 | 적절한 확인 시각까지 대기, 같은 응답을 재확인으로 세지 않음 |
| 공급자 일시 실패 | 기존 횟수·시간 예산 안에서 재시도 |
| 검증 근거 부족/충돌 | 이유를 유지, 재다운로드만으로 해결하려는 반복을 중지 |
| 확인된 상장 전/종료 후/정지·제공 한계 | 근거를 표시, 가짜 봉이나 0거래량을 만들지 않음 |

거래량 기본 기준을 raw 또는 1배로 몰래 바꾸지 않는다. 기존 저장 조건의 legacy 정책과
발생 제외는 유지한다. 자동 준비는 정책 이관·공급자 정정 승인과 다른 작업이다.

### 저장된 관측을 공유하고 수집 완료 지점에서 재개

서버의 한 준비 작업 관리자에서 일반 갱신·활성 검색·정기 작업의 수요를 합친다.
조정 여부, 공급자/TR, 종목·시장, 공급자 기준 날짜/수정 기준, 커서, 응답 계약 버전,
관측 회차를 포함한 키로 동일 요청만 공유한다. 응답 범위는 각 소비자가 검증 후 잘라 쓴다.

실행 중 요청 공유와 완료 응답의 영속 재사용은 분리한다. 실행 중 future 공유는 현재
거버너 기능을 재사용하고, 완료 응답은 기존 복구의 불변 staging/checkpoint 방식을
활용한다. 성공 응답은 공개 전에 기록해 프로세스 재시작·공개 실패 시 재다운로드하지 않는다.
일반 갱신 원장의 다음 날 확인은 시각과 회차가 다른 새 관측이어야 한다.

같은 기준일의 검증된 완료 구간만 재사용한다. 수정 기준이 바뀐 가격에 새 날짜만
붙이는 방식이나 이전 날 가격을 현재 기준이라고 재표시하는 방식은 사용하지 않는다.
새 기준의 전체 필요 구간을 다시 받아야 하는 경우는 계획에 남긴다. 기존 원주가 관측을
가격과 별도로 재사용할 수 있는지도 검증한 뒤 원본 요청을 생략한다.

### 병렬 수집과 단일 공개

새 기준 준비 작업은 최대 4개, 실제 HTTP는 **기존 전역 거버너**를 통과한다.
일반 갱신·다른 검색과 실행 한도를 합산하며, 전체 과거 요청을 `user_visible`로 올려
차트 조회를 밀어내지 않는다. 진행 중 검색의 준비와 정기 확인 작업은 작은 단위로
번갈아 처리해 어느 한쪽의 큰 작업이 큐를 독점하지 않게 한다.

확정된 응답을 writer 하나가 작은 묶음으로 공개한다. 각 묶음은 현재 manifest를 잠금
안에서 다시 읽어 병합하고, 네트워크 중에는 writer lock을 잡지 않는다. 객체는 각각
fsync하고 마지막에 완성된 manifest와 포인터를 원자 공개한다. 체크포인트 역시
완료/취소 경계를 지킨다. 오류 때 이전 완성 스냅샷과 staging을 남긴다.

### 검색 실행과 단순 조회를 분리

새 실행 API 후보는 `POST /api/screener/runs`다. 요청 즉시 실행 id·상태·사용 가능한
결과를 돌려주고, `GET /api/screener/runs/{id}`로 진행과 결과 revision을 조회한다.
현재 `/scan`의 조회 전용 동작은 유지한다. 자동 수집을 기존의 모든 `/scan` 호출에
암묵적으로 붙이면 폴링·조건 편집·저장 결과 재현에도 수집이 생겨 범위가 커진다.

실행은 조건·정책·종목 모집단·달력·마스터·제외·평가 시각·수정 기준일을 고정한다.
각 결과 revision은 실제 사용한 manifest를 가리킨다. 준비가 진행되는 동안 새로
추가된 입력을 반영하더라도 다른 기준일·모집단의 행을 합치지 않는다. 한 사용자가
중지해도 다른 창/정기 갱신이 필요한 공통 요청은 취소하지 않는다.
기존 스냅샷 재현 요청은 자동 준비/최신화 경로에 넣지 않는다.

결과 평가·화면 알림은 공개 한 번마다 전체 재실행하지 않는다. 바뀐 종목의 평가를
묶어서 반영하고, 기본 UI 통지는 약 1초 단위 후보로 둔다. AND/OR·제외·정렬·limit와
전체 순위 의미를 유지하며 마지막에 동일 고정 문맥의 전체 평가와 대조한다.

## 선택하지 않은 대안

| 대안 | 이유 |
|---|---|
| 버튼만 숨기고 브라우저 effect에서 기존 수집 실행 | 창/재접속/폴링 간 공유·재개·예산·차단 사유를 해결하지 못함 |
| 조회할 때마다 전 시장 과거 전량 수집 | 필요한 범위보다 과도하고 이미 완료한 작업을 반복함 |
| 모든 갱신의 동시성/거버너 제한부터 확대 | 빠른 응답 구간에서 이득이 없고 chart 자원 경합이 늘 수 있음 |
| 수정 가격·원본·수량 근거를 하나의 준비 완료 플래그로 처리 | 가격은 가능한데 수량 근거가 없는 정상 상태를 표현하지 못함 |
| 공급자 정정/수량 보정을 자동 추정하여 성공 처리 | 기존 관측 보존 및 ADR-0057 개정의 계산 기준 분리와 충돌함 |

## 적용 순서와 남은 검증

1. **자동 준비의 상태/실행 계약**: 버튼 제거, 클릭 한 번, 준비/검증 대기 분리,
   실행 중복 합류, 재접속 복구. 기존 수집기와 evaluator를 먼저 재사용한다.
2. **요청 공유와 영속 staging**: 동일 공급자 응답만 공유하고 중단 후 이어받는다.
3. **새 기준 준비 병렬화와 일괄 공개**: 한도 4/묶음 8을 초기 후보로 적용한다.
4. **운영 계측 후 일반 갱신 조정**: queue/HTTP/파싱/검증/저장/첫 결과/최종 완료,
   호출·재사용·재시도 수와 foreground p95·오류율을 비교한다. 효과가 확인될 때만
   기존 일반 갱신 동시 종목 예산을 개정한다.

구현 후에는 다음을 새 통합/E2E 검사로 검증해야 한다. 아래 항목을 이번 실험에서
모두 통과한 것으로 해석하지 않는다.

- 조회 한 번으로 준비/결과 표시, 브라우저 새로고침·두 창 동시 시작·조건 변경 시
  이전 실행 응답 무시, 다른 조건의 과거 작업 표시 제거.
- 실제 공급자 요청 파라미터와 공용 읽기 예산을 포함한 공유 키 차이 검사:
  원주가/수정주가, 기준일, 시장, 커서, 독립 확인 회차는 서로 섞이지 않음.
- 두 소비자 중 하나의 취소·서버 재시작·기준일 변경·기존 writer의 동시 갱신·
  staging 후 장애·batch 공개 중 취소·디스크 부족에서 데이터/진행 상태 보존.
- 가격/거래량/금액, D/W/M, 분봉/랭킹/총잔량 조건의 경로 분리, AND/OR·미참조 leaf·
  순위/limit·제외 의미와 최종 전체 결과 동등성.
- 사용자의 실제 앱에서 빠른 응답/느린 응답/공급자 장애 구간을 관측하고 일반 갱신의
  전체 완료 및 화면 조회 p95를 함께 비교. 외부 요청 실험은 별도 운영 검증 단계다.

기존 ADR-0136/0138의 단일 거버너·우선순위·앱키별 제한과 ADR-0057 개정의
가격/수량 분리는 유지한다. 현재의 ‘명시적 새 기준 준비’는 검색 실행에 포함하도록
사용 흐름을 개정하는 제안이다. 명시적 정정 승인·정책 전환의 계약은 개정 대상이 아니다.

구현 후의 동작과 검증 결과는 [구현 문서](../../plans/2026-11-01-screener-auto-preparation-implementation.md)에 별도로 기록한다. 아래 한계는 이 선행 실험 시점의 범위다.

## 한계

이번에는 운영 갱신을 새로 실행하지 않았고 실제 벤더를 대상으로 속도/429/foreground
경합을 측정하지 않았다. 최종 제품 UI나 공통 작업 관리자도 아직 구현하지 않았다.
측정치는 제한된 모의 전송/합성 저장 입력에서의 후보 비교다. 그러므로 전체 갱신이
몇 배 빨라진다거나 이 구성이 모든 환경에서 최적이라는 결론은 내리지 않는다.
