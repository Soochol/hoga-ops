# 0102 — 500종목 10초 호가 수집: 계정별 예산 + 동시성 계정 비례 + 4번째 앱키

**Status:** accepted (2026-07-10)

**Related:**
- ADR-0100 (KIS REST 앱키별 독립 토큰버킷) — 이 목표의 필수 전제. 계정별 15/s 버킷이 없으면 예산이 전역 15/s에 갇혀 500@10초 불가.
- ADR-0098 (REST 호가 전용 + rest30 동시 디스패치) — 종목당 1콜(호가) + 동시 디스패치 골격. 예산 산식(15/s=30초당 450콜)의 계정 배수 확장.
- ADR-0097 (히트맵 종목 rest30 REST-전용 합류) — 500종목이 kis_api_targets에 들어오는 경로.
- ADR-0101 (WS 등록 상한 41 + 슬롯 13종목) — 상위 ~13×계정 종목은 WS 실시간, 나머지는 REST rest30.
- `hoga/live/storage_runtime.py` `_rest30_concurrency` — 구현점.

## Context

목표: 히트맵+관심종목 ~500종목의 호가(orderbook)를 **10초마다 수집→표시+저장**. 히트맵은 상한 없는
사용자 큐레이션 보드(ADR-0068)라 500종목이 `kis_api_targets`로 자연 유입되고, rest30 recorder가 저장
(JSONL)과 표시(LiveBuffer publish)를 동시에 담당한다(ADR-0098). 종목당 호가 1콜(FHKST01010200).

**산식**: 500종목 × 1콜 / 10초 = **50콜/s 필요**. KIS REST 유량은 앱키별 독립 ~15/s(실측 2026-07-10,
ADR-0100), 앱키당 실효 goodput ~13.4/s(15/s 페이싱에 ~10% EGW). 따라서:

| 앱키 수 | 예산(goodput) | 500콜 사이클 | 10초 경계 정렬 실효 주기 |
|---|---|---|---|
| 3 | ~40/s | ~12.5초 | ~20초 (미달) |
| **4** | ~53/s | ~9.4초 | **10초 정착** |
| 5 | ~67/s | ~7.5초 | 여유 있는 10초 |

사이클을 10초 아래로 넣어야 벽시계 경계 스케줄링(`rest30_recorder._next_delay_s`)이 매 10초에 걸린다
(사이클 > interval이면 다음 경계로 밀려 ~20초 실효). 즉 **4번째 앱키가 최소 조건**이다.

**동시성 재검토(중요)**: rest30 `concurrency=10`은 단일 15/s 버킷 포화값(in-flight ≈ rate×latency ≈ 8,
ADR-0098)이다. 버킷이 앱키별 독립(ADR-0100)이 되면 aggregate 예산(~15/s×계정수)을 채우려면 in-flight도
계정 수에 비례해야 한다 — concurrency=10 고정이면 4앱키 예산(~53/s)의 절반도 못 쓴다(10 in-flight ÷
~0.5s latency ≈ 20/s에서 막힘). 백필 동시성(ADR-0100 후속)과 같은 논리.

## Decision

1. **rest30 concurrency를 계정 수 비례로** (`storage_runtime._rest30_concurrency`): 계정당 10, 상한 48.
   1계정 10 → 3계정 30 → 4계정 40. 4번째 앱키를 넣으면 자동으로 40이 돼 별도 config 변경 불요. 실제
   콜레이트는 계정별 버킷이 클램프하므로 과플러딩 없다.

2. **4번째 앱키(KIS_APP_KEY_4) 프로비저닝은 운영 단계** — 코드는 `configured_account_ids`로 자동 수용
   (WS 4연결·스케줄러 워커·rest30 동시성·버킷 전부 계정 수에 자동 연동). 프로비저닝 자체는 사용자 결정.

3. **티어링은 도입하지 않는다** — 4앱키로 500 전량 10초가 되므로 핫/콜드 분리(ADR-0098 비범위)가 불필요.
   4앱키를 못 구하면 티어링이 대안이나, 본 ADR은 4앱키 경로를 채택한다.

## Consequences

- 4앱키 + concurrency=40에서 500종목 호가가 ~9.4초 사이클 → 10초 경계 정착. 저장(JSONL→Today Promotion)
  과 표시(SSE)가 그 밀도로 갱신. 히트맵 표시가 10초 해상도.
- 3앱키만 있으면 concurrency=30에서 ~12.5초 사이클 → ~20초 실효(현재 500종목의 ~40초보다 2배 개선이나
  10초 미달). 4번째 앱키가 10초의 결정적 조건.
- concurrency는 계정 수에 자동 연동 — 앱키 추가/제거 시 재튜닝 불요.

## 검증됨 / 잔여 리스크

- **4번째 앱키 독립성 = 확인됨(2026-07-10).** KIS_APP_KEY_4 프로비저닝 후 지속 부하 재실측: 4앱키 각
  15/s(합산 60/s)×120초 → 성공 **53.2/s, EGW 10.1% 평탄(12창)**, 배율 **4.05x**. 3앱키 3.03x → 4앱키
  4.05x 선형 유지 = 4번째도 독립 ~15/s. 명의당 앱키수/명의 단위 상한 없음(4까지). 500÷53.2 = **9.4초/
  사이클**로 산식 확증.
- **일일 누적 쿼터 미검증(ADR-0100 상속).** 500종목×10초 = ~432만콜/일(8.5시간) 수준. 일일 상한이
  있으면 장중 후반 소진 가능 — 장중 실가동으로 확인.
- **사이클 시간은 관측으로 확정.** latency(~0.5s 역산)·EGW율에 따라 실사이클이 산식과 다를 수 있다.
  `/api/live/status`의 `kis_api_last_cycle_ms`가 < 10000이어야 10초 정착. 초과 시 5번째 앱키 또는 티어링.
- **재발 신호(ADR-0100)**: `rate_limit_failovers`↑ / cooldowns 상시 non-empty / EGW 9% 이탈 상승 →
  4앱키가 독립이 아니라는 신호. 그 경우 `_SHARED_BUCKET_KEY` 롤백 + 티어링으로 선회.

## 비범위

핫/콜드 티어링(4앱키 실패 시 대안), 히트맵 종목 수 상한(현재 무제한 — 500 초과 시 별도 정책), 표시
경로 최적화(SSE fan-out), rest_poller user_visible 승격.
