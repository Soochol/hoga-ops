# 0138 — 키움 REST 유량은 앱키별로도 독립이다

- ADR-0137 — 에러 처리 전략. 이 ADR 의 계정 선택이 `penalize` 를 failover 신호로 재사용한다.
- [#1015](https://github.com/Soochol/hoga-ops/issues/1015) — TR별 유량 실증. **앱키 축은 보지 않았다** — 그 공백이 이 ADR 이 메우는 자리다.
- ADR-0100 — KIS 앱키별 유량 재측정. 같은 질문을 다른 벤더에 물었던 선례.

## Context

### ADR-0136 이 삭제한 것과, 그 근거의 공백

ADR-0136 은 KIS 스케줄러(303줄)에서 계정 차원을 통째로 걷어냈다 — 계정 풀 선택·health/failover·`cooldown_scope`. 근거는 한 문장이었다:

> 키움 유량이 TR별이라 계정을 고를 이유가 없다.

TR별인 것은 맞다. `#1015` 가 실증했다 — `ka10080` 을 429 까지 밀어붙인 **직후 대기 없이** `ka10081` 을 호출하니 통과했다. 하지만 그 실험은 **하나의 앱키 안에서** TR 을 바꿔본 것이다. "다른 앱키로 같은 TR 을 호출하면?" 은 묻지 않았다.

ADR-0136 자신이 이 공백을 알고 있었다:

> **(거부) 앱키 증설** — 예산이 열위가 아니라 개선이므로 필요가 실증되면 그때. 대가는 **앱키당 유량 독립 여부가 미검증으로 남는 것**.

즉 미검증 항목이 삭제 결정의 근거로 쓰였다. "TR별이다" 에서 "그러므로 앱키는 무관하다" 로 넘어가는 자리에 실측이 없었다.

### 필요의 실증 — 전체 시장 장중 스캔

ADR-0137 이 스크리너 장중 오버레이의 청킹을 거버너 위로 올리면서, 전체 시장 4,295종목 스캔이 처음으로 **성공**했다. 다만 10.8초가 걸린다. 43콜 ÷ (5 req/s × 0.8 헤드룸) = 10.75초 — 이론값과 정확히 일치하는, 유량이 정한 하한이다.

ADR-0136 이 말한 "필요가 실증되면" 이 이것이다.

### 실측 — 앱키 축도 독립이다

`#1015` 의 실험을 앱키 축으로 그대로 돌렸다:

```
앱키0: 8번째 콜에서 429 (유량=5, API ID=ka10095)
앱키1: 대기 없이 즉시 통과 ✅ rows=3
```

그리고 전체 시장 유니버스(43청크)를 구성별로 처리한 결과 — 각 키가 자기 스케줄러(즉 `(앱키, TR)` 버킷)를 갖는 형태로:

| 앱키 | 소요 | 처리량 | 429 | 배수 |
|---:|---:|---:|---:|---:|
| 1개 | 10.31초 | 4.17 콜/초 | 0 | 1.00× |
| 2개 | 5.28초 | 8.14 콜/초 | 0 | 1.95× |
| 4개 | **2.34초** | 18.4 콜/초 | 0 | **4.41×** |

4키는 3회 반복해 2.33 / 2.34 / 2.34초로 일관했고 매번 43청크 전량 성공했다. 1키의 4.17 콜/초가 헤드룸 이론값 4.0 과 거의 정확히 맞는다는 점이 이 측정을 신뢰할 근거다 — 계산이 맞아떨어지는 구성에서 키만 늘렸더니 배수가 그대로 따라왔다.

**유량은 `(앱키 × TR)` 별이다.**

## Decision

### 큐는 하나, 버킷만 쪼갠다

계정마다 스케줄러를 두는 형태(측정에 쓴 구성)를 **제품에 넣지 않는다.** 거버너가 가진 네 기계 — 우선순위·중복제거·승격·양보 — 는 전부 전역이어야 의미가 있다. 스케줄러를 N개로 쪼개면 관심종목 시세(`user_visible`)가 계정0 큐에, 백필이 계정1 큐에 있을 때 **양보가 작동하지 않고**, 같은 `key` 가 두 계정에서 동시에 나가 **중복제거가 깨진다**.

```
큐(우선순위·중복제거·승격·양보)          ← 하나로 유지
   └─ 버킷 dict[(account_id, api_id)]    ← 여기만 N배로 쪼갬
```

### 계정 선택은 "가장 빨리 열리는 계정"

`_TokenBucket` 이 이미 들고 있는 `_next_at` 을 `available_at()` 으로 노출하고 최소값을 고른다.

**이 한 줄이 failover 를 공짜로 만든다.** 429 를 맞은 계정은 `penalize()` 가 `_next_at` 을 뒤로 밀어 두므로 자연히 선택에서 빠지고, 회복되면 스스로 돌아온다. ADR-0136 이 걷어낸 KIS 식 health check·failover 상태 기계를 **되살리지 않는다** — 그 삭제는 여전히 옳았다.

라운드로빈은 막힌 계정에도 순서대로 보내므로 쓰지 않는다.

### 클라이언트를 늦게 바인딩한다

계정을 거버너가 고르므로 클라이언트도 거버너가 주입한다. 기존 시그니처가 이미 이걸 지원했다 — `fetch_fn` 이 클라이언트를 인자로 받는 형태였다:

```python
call=lambda picked: fetch_fn(picked if picked is not None else client)
```

`run_with_capacity(..., client=...)` 의 `client` 는 **풀이 비었을 때만 쓰이는 폴백**으로 의미가 바뀐다. 호출자 코드는 그대로 두되, "넘긴 클라이언트가 항상 쓰인다" 는 가정은 더 이상 성립하지 않는다.

`ensure_rest_client(data_dir, account_id)` 도 계정별 싱글턴이 된다. 이전 판은 전역 `_client` 하나라 **`account_id` 를 받고도 무시**했다.

### N=1 로 자연히 축퇴한다

`configured_account_ids()` 가 앱키 개수를 센다 — `[]` 면 휴면(ADR-0134 dev 무자격), `[0]` 이면 버킷이 하나뿐이라 현행과 동일하다. 키가 4개인 것은 이 개발 환경의 사정이지 코드의 전제가 아니다. 테스트가 이 축퇴를 봉인한다.

### 관측

`snapshot()` 에 `accounts` 와 `calls_by_account` 를 낸다. 쏠림이 보이지 않으면 앱키를 늘려도 배수가 안 나는 것을 알아챌 수 없다.

## Consequences

**얻는 것.** 전체 시장 장중 스캔 10.8초 → 약 2.3초. 같은 이득이 `ka10095` 에 국한되지 않는다 — 백필·순위·지수 등 모든 TR 이 같은 배수를 받는다. failover 가 상태 기계 없이 따라온다.

**비용.** 버킷 수가 계정 배수만큼 는다(메모리는 무시할 수준). 호출자가 넘긴 클라이언트가 실제로 쓰인다는 보장이 사라져, 클라이언트를 `fetch_fn` 밖에서 직접 쓰는 코드는 거버너를 우회하게 된다 — `trading_days.py` 가 그런 지점이라 후속 정리 대상이다.

**위험 집중.** 같은 앱키 4개를 WS 도 쓴다. 프로토콜과 유량은 분리돼 있지만 **한 앱키가 벤더 측에서 정지되면 그 계정의 WS 와 REST 가 함께 죽는다.**

## 미확인으로 남기는 것

- **계정 합산 상한** — 4키 18.4 콜/초에서 429 가 0건이었으니 관측되지 않았다. 8키 이상에서도 선형인지는 모른다. 앱키를 더 늘릴 일이 생기면 그때 다시 잰다.
- **TR 마다 다른 유량** — `유량=5` 는 `ka10080`·`ka10095` 에서만 확인했다. `tr_rates` 오버라이드는 그대로 열어둔다(ADR-0136 Trigger).
