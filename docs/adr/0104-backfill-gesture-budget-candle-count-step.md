# 0104 — /live 백필: 제스처 예산(트리거 동결·무조건 완주) + 스텝 캔들 50개 통일

**Status:** accepted (2026-07-11)

**Related:**
- ADR-0103 — 선행 워밍 + read-ahead 제거 (이 ADR이 드러낸 문제를 마무리)
- ADR-0090 (superseded) — 3거래일 스텝("latency cap")의 출처

## Context

분봉에서 마우스 줌인·아웃을 반복하면, 차트가 꽉 차 보이는데도 과거 데이터
fetch가 이어지고 왼쪽에 캔들이 대량으로 쌓이는 현상이 보고됐다. /browse
재현·계측(2026-07-11)으로 메커니즘을 확정했다:

- 줌아웃은 우측 끝 고정으로 왼쪽으로만 확장되며, 그 한계는 화면 용량
  (`차트폭 ÷ minBarSpacing 0.5px`)이다 — 휠 몇 노치가 수개월치 빈공간을 한
  번에 열 수 있다.
- settle-loop(useViewportBackfill 3a)는 매 스텝 완료 시 **뷰포트를 다시
  측정**해 빈공간이 남아있는 한 계속 걸었다. 실측: 30m 줌아웃 15노치(1.5초
  입력) → 무입력 12초간 fetch 15연발, `historicalFromDate` 3개월 확장, 캔들
  65→1,211개.
- 배압(PR #533)은 정상이었다 — 배압은 "동시에 몇 개"(항상 1)를 통제할 뿐,
  "총 몇 번"은 빈공간 크기가 결정했고 그 총량 통제층이 존재하지 않았다.
- fill 도중의 추가 인터랙션이 재측정에 반영돼 목표가 계속 자라는 것도 확인.

기각된 대안들(순서대로 검토·폐기):
- **휠 줌아웃 좌단 벽**(`computeWheelOutcome` minFrom, 한때 구현 후 제거):
  입력별 클램프는 입력 열거가 필요한 두더지잡기(드래그·핀치·복원 미커버).
- **범용 뷰포트 좌단 벽**(빈공간 ≤ 1스텝으로 뷰포트 자체를 교정): 모든 입력을
  커버하지만 줌아웃이 "50캔들 도착할 때마다 한 뼘씩"의 톱니 UX가 됨.
- **minBarSpacing 상향**(수요 천장): 한 줄로 최대 빈공간을 제한하지만
  줌아웃 도달 범위 자체를 줄인다. 사용자가 줌 범위 보존을 선택해 제거.

## Decision

**제스처 예산**: 트리거 순간의 필요량을 동결하고, fill은 그 예산만큼
무조건 완주한다. 진행 중에는 뷰포트를 다시 측정하지 않는다.

1. **스텝 = 캔들 50개** (`STEP_CANDLE_TARGET`, 전 타임프레임 공통).
   분봉은 거래일 환산(1m~5m=1일 floor, 10m/15m=2일, 30m=4일) + **주말 스킵
   날짜 걷기**(`subtractWeekdaysKst`) — 좁은 스텝이 토·일만 덮는 빈 왕복을
   호출 전에 결정론적으로 제거한다(공휴일은 프론트 미지 정보라 남지만 기존
   홀리데이 진행 처리로 흡수). D/W/M은 캘린더 환산(70/350/1,550일).
2. **예산 산정**: 트리거(3b) 순간 `ceil(빈공간 바 수 ÷ 스텝당 실제 봉 수)`
   (`fillBudgetSteps`). 분모는 `STEP_CANDLE_TARGET`이 아니라 거래일 ceil이
   반영된 실제 봉 수(`stepCandlesEstimate`; 1m=390, 30m=52, D=50) — 아니면
   1m 예산이 ~8배 과다해진다. MAX_FILL_STEPS(60)로 캡.
3. **무조건 완주, 재측정 없음**: settle-loop(3a)는 활성 fill의 예산만
   소진한다. fill 도중의 줌인·줌아웃·팬은 이번 fill을 늘리지도 줄이지도
   못한다(추가 호출 0) — 활성 fill 중 3b는 새 트리거를 거부해 예산 덮어쓰기를
   막고, fill 상태는 실제 dispatch 직전에만 동결한다(반려된 이벤트가 유령
   활성 fill을 남기면 falling edge가 없어 영구 잠금되므로). 도중에 생긴 새
   빈공간은 완료 후 다음 뷰포트 이벤트의 새 예산으로 배치 처리된다.
4. **coverage_gap fill**: 목표(트리거 순간의 viewport 좌단 날짜)를 동결하고
   요청 창이 거기 닿을 때까지 걷는다(예산은 백스톱). left_pan과 동일하게
   fill 중 재측정 없음.

종료 조건은 예산 소진·250일 클램프·coverage 목표 도달·종목/타임프레임
전환뿐이다. "빈공간이 남았는가"는 더 이상 종료 조건이 아니다 — 조기 종료
(줌인 시 중단)도 의도적으로 없앴다: 받은 캔들은 병합 캐시에 남아 재줌아웃
시 즉답이므로, "사용자가 한 번 요청한 과거는 마저 채워둔다"가 더 예측
가능하다(사용자 결정).

## Consequences

- 재현 시나리오 재실행(동일 30m 줌아웃 15노치): 예전 15연발·3개월·무한
  재측정 → **트리거 `logicalFrom:-284` → 예산 6스텝 → 정확히 6 fetch →
  2초 만에 stop, 이후 완전 침묵**(/browse 실측, perf 로그 확인).
- 총 호출량 = 사용자가 실제로 연 빈공간에 비례(스텝 단위 ceil). 화면
  용량만큼의 첫 풀 줌아웃은 여전히 그만큼(와이드 모니터 30m ~40여 스텝,
  MAX_FILL_STEPS 캡)을 1회 완주하지만, 같은 구간의 반복 줌인아웃은 호출
  0이다(창 단조 + 병합 캐시).
- 연휴 스텝(캔들 0개)도 예산 1을 소모하므로 fill이 빈공간을 약간 남기고
  끝날 수 있다 — 다음 뷰포트 이벤트의 새 예산(1~2스텝)이 회수(자가 치유).
- 되돌림/조정 손잡이: `STEP_CANDLE_TARGET`(스텝·예산 분모 공유),
  MAX_FILL_STEPS(제스처당 상한). 첫 풀 줌아웃 비용이 문제로 실측되면
  minBarSpacing 상향(수요 천장)을 재검토한다.
