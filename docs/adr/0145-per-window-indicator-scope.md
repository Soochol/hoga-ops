# 0145 — 창별 지표 분리는 opt-in, 내용물은 전역 저장소에 둔다

**Status:** accepted (2026-08-14)

**Amends:** #712 의 "지표는 앱 전역 1세트" 결정. 그 결정을 뒤집는 것이 아니라
**기본값으로 강등**한다 — 전역 공용이 기본이고, 사용자가 명시적으로 분리한 창만 갈린다.

**Related:**
- #712 — 창 소유 지표를 전역 1세트로 되돌린 작업(`indicatorsWindowMigration.ts` 가 그 잔재).
- ADR-0072 — 한 지표의 prefs 가 `livePage`·`chartPrefs` 두 store 에 나뉜다는 결정.
- ADR-0114 §3 — pane 순서는 전역 1세트.
- ADR-0119 — 멀티창 워크스페이스와 창-스코프 뷰 컨텍스트.
- `frontend/src/state/indicatorSettingsV2.ts` (`byWindow`), `frontend/src/live/workspace/windowView.ts`.

## Decision

지표 설정에 **창 축**을 하나 더 준다. 저장 모델은 `live.indicators.v2` 안에서 확장한다:

```
{ paneOrder, paneStretch,
  byTimeframe: { minute|D|W|M: sparse diff },        // 공용 — 기본
  byWindow: { "live:<id>"|"study:<id>": {같은 4버킷} } // 분리된 창만 등장
}
```

1. **기본은 연동.** `byWindow` 에 엔트리가 없으면 공용 세트를 읽는다 = 종전 동작. 저장값
   마이그레이션이 없고, 필드를 버리면 전부 연동으로 돌아온다.
2. **멤버십은 키의 존재.** 값이 `{}` 여도 분리다(공장값 상태에서 분리하면 복사할 diff 가
   없다). 정규화는 `byTimeframe` 과 달리 **빈 엔트리를 걷어내지 않는다**.
3. **내용물은 전역 localStorage 에 남는다.** 창이 갖는 것은 스코프 키뿐이다.
4. **분리는 무손실, 복귀는 파괴적.** 분리는 현재 유효 설정을 복사하므로 화면이 안 바뀐다.
   복귀는 그 창의 오버라이드를 버리므로 2단계 확인을 거친다.
5. **`chartPrefs` 의 indicator-modal 키도 같은 축으로 갈린다**(ADR-0072 의 두 store 가
   한 드로어에 함께 뜨므로). 멤버십의 SSOT 는 `livePage.indicatorsByWindow` 이고
   `chartPrefs.indicatorModalByWindow` 는 그 미러다 — 분리·복귀·회수는 항상 동반 호출.
6. **레이아웃(pane 순서·크기)과 프리셋은 공용 유지.** 프리셋은 "모든 창의 기본 구성" 을
   갈아끼우는 물건이고, 분리는 사용자가 그 창을 기본에서 뺀 상태다.
7. **스코프 회수는 창 닫기·레이아웃 프리셋 적용에서만.**

## Context — 왜 #712 의 재발이 아닌가

#712 는 창 소유 지표를 되돌렸다. 그 사고의 원인은 창-스코프라는 **개념**이 아니라
**설정의 내용물을 창 스냅샷에 담은 것**이었다: 워크스페이스(`live.workspace.v1`)는 탭별
sessionStorage 라, 새 브라우저 탭에서 지표가 공장값으로 리셋됐고 탭마다 구성이 갈렸다.

여기서는 내용물이 전역 localStorage 에 남는다. 따라서:

- 크로스탭 동기화(`subscribeToIndicatorsStorage`)가 **분리된 창까지 그대로 덮는다.**
- 새 탭에서도 같은 분리 상태가 재현된다(창 id 가 워크스페이스 시드로 함께 넘어온다).
- 워크스페이스 스냅샷 스키마는 무변경 — `ChartWindowConfig` 는 여전히 봉만 갖는다.

즉 재발 여부를 가르는 것은 "창별인가" 가 아니라 **"설정이 어느 저장소에 사는가"** 다.

## Why opt-in (창마다 항상 독립이 아니라)

창은 자주 열고 닫는다. 항상 독립이면 새 창을 열 때마다 지표를 처음부터 켜야 하고, 그건
멀티창의 주 용도(같은 종목을 여러 봉으로 나란히 보기)에 마찰만 더한다. opt-in 은 기본
동작이 종전과 **완전히 같다**는 성질도 덤으로 준다 — 마이그레이션도, 기존 사용자의
화면 변화도 없다.

## Alternatives considered

### A. 페이지별 분리(`/live` ↔ `/study` 두 세트) — 기각
가장 작은 변경이지만 요구가 "창" 이었다. 같은 페이지에서 두 창을 다르게 보려는 요구를
전혀 해결하지 못한다. 창 축이 있으면 페이지별은 그 특수 경우로 표현된다.

### B. 명명 프로파일(창이 프로파일을 **참조**) — 유예
"기본 / 스캘핑 / 일봉" 같은 이름 붙은 세트를 만들고 창이 그중 하나를 가리키는 모델.
창이 사라져도 설정이 남고 여러 창이 한 세트를 공유할 수 있어 상위 호환이지만, 프로파일
CRUD·이름·삭제 시 참조 처리 같은 관리 UI 가 통째로 따라온다. 요구는 "창마다 따로" 였고,
프로파일은 **분리된 창 설정에 이름을 붙인 것**이라 나중에 이 모델 위에 얹을 수 있다.

### C. 창 스냅샷에 설정을 되돌려 놓기 — 기각
#712 를 그대로 재현한다. 위 Context 참조.

## Consequences

**Positive:** 소비자 39개 파일 무변경(`useWindowIndicators`/`useWindowIndicator`/
`useIndicatorActions` 세 훅이 유일한 절단면). 되돌리기가 싸다 — 정규화에서 `byWindow` 를
버리면 끝. 기본 동작 무변경이라 마이그레이션 없음.

**Negative / watch:**

- **번들 요청은 "요청 축" 이 갈릴 때만 는다.** 쿼리 키에 실리는 것은 지표 설정 전체가
  아니라 `studyReferenceQuerySettings` 의 **8개 필드뿐**이다(askPeak·bidPeak·
  brokerLateEntry·tradeVolumePoc·depthHeatmap·volumeDistribution 계열). 그래서 분리된
  창이라도 그 8개가 공용과 같으면 키가 같아 **캐시를 그대로 공유한다** — MA 기간·색·
  pane 토글을 아무리 달리해도 요청은 늘지 않는다. 증가분은 "분리 창 수" 가 아니라
  **"그 8개를 실제로 다르게 켠 창 수"** 이고, 그건 사용자가 명시적으로 요구한 것
  자체다. 이 목록에 필드를 추가하면 그때 창별 요청 분기가 넓어진다는 점만 기억할 것.
- **비활성 탭 워밍(`useWarmStudyReferenceTabQueries`)은 공용 세트로 근사한다** — 탭에는
  창이 없기 때문이다. 분리 창을 활성화하면 그 창 키로 한 번 더 받는다.
- **두 store 의 멤버십이 어긋나면 절반만 분리된 드로어가 된다.** 동반 호출이 그 유일한
  방어이므로, `indicatorModalByWindow` 를 직접 만지는 코드를 새로 만들지 말 것.
- **같은 창 id 가 두 브라우저 탭에 살아 있으면 GC 가 과하게 걷을 수 있다.** 워크스페이스는
  탭별이지만 공유 시드에서 복제되므로 두 탭이 같은 창 id 를 가질 수 있고, 그때 탭 A 에서
  그 창을 닫으면 전역 `byWindow` 에서 회수되어 **탭 B 의 같은 창이 조용히 재연동**된다.
  "워크스페이스는 탭별, 스코프 키는 전역" 이라는 이 모델에 내재한 비대칭이고, 회수를
  포기하면 대신 영구 누수가 남는다. 빈도가 낮아 감수한 트레이드오프이지 미구현이 아니다 —
  이걸 고치려면 스코프 키에 탭 식별자를 넣어야 하는데, 그러면 새 탭에서 분리 상태가
  재현되지 않아 #712 의 증상으로 되돌아간다.
- **재검토 트리거**: 분리한 창이 흔해져 "이 창들이 같은 설정을 쓰게" 하고 싶어지면 그때가
  대안 B(명명 프로파일)의 시점이다.
