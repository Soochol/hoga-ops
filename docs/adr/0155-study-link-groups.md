# 0155 — `/study` 링크 그룹 (그룹 → 저장뷰)

**Status:** accepted (2026-08-21) — **ADR-0149 를 부분 supersede.**

## 무엇을 뒤집고 무엇을 남기는가

ADR-0149 는 `/study` 의 저장뷰 탭을 없애며 **"한 번에 하나"** 를 본문에 못박았다. 이 ADR
은 **그 하나만** 뒤집는다: 한 페이지 안에서 저장뷰를 여럿 볼 수 있고, 그 축은 탭이
아니라 **창의 링크 그룹**이다.

**무효가 되는 것** (ADR-0149 안에서):

- §Decision 2 의 "활성 저장뷰의 새 집은 `state/studyActiveView.ts`, 영속 키
  `study.activeView.v1`". 그 스토어와 모듈은 삭제됐다. 키는 **승계 전용**으로 남는다.
- "`/study` 는 이제 저장뷰를 하나만 연다" 를 전제로 한 서술 — 특히
  `useStudyRangeCacheEviction` 의 보존 집합이 "활성 종목 하나" 라는 부분.

**그대로 남는 것** (ADR-0149 의 `Status` 를 `accepted` 로 두는 이유다):

- **탭 스트립은 돌아오지 않는다.** 세로 공간 상시 점유 대비 이득이 낮다는 ADR-0113·0149
  의 판정은 유효하다. 그룹은 창 타이틀바의 **16px 뱃지**라 새로 먹는 세로 공간이 0이다.
- `[`/`]` 탭 순환, `disposition`("새 탭으로 열기"), 탭별 봉·뷰포트, 비활성 탭 프리페치
  훅 — 전부 되살아나지 않는다(§4).
- §7 의 `?view=` 딥링크가 저장뷰 전환의 정식 경로라는 것.
- 봉의 소유자는 차트 창이라는 것(#1326). 그룹이 생겨도 갈리지 않는다 — 한 그룹에 봉이
  다른 차트 창 둘을 두는 것이 이 페이지의 원래 용도다(#801).

**ADR-0152(창별 지표 세트)와는 직교한다.** 같은 날 머지됐고 둘 다 "창이 무엇을
소유하는가" 를 늘리지만 축이 다르다 — 저기는 **지표**(창이 스코프 키를 갖는다),
여기는 **저장뷰**(창이 그룹 번호를 갖고 그룹이 뷰를 갖는다). 창 하나에 둘 다 붙고
서로를 읽지 않는다.

## Context — 왜 지금인가

두 갈래가 만났다.

**하나.** `/live` 는 #711 부터 링크 그룹을 갖는다: 창은 콘텐츠를 직접 들지 않고 **번호**만
들며, 번호→종목(`groupSymbols`)이 SSOT 다. 같은 번호를 단 창들은 종목이 함께 바뀌고,
창을 닫아도 종목은 남는다. `/study` 만 이 제스처가 없어 두 페이지의 근육 기억이 갈렸다.

**둘.** `/study` 코드가 이 분기점을 **미리 적어 뒀다**. `studyWindowWorkspace.ts` 의
`getWorkareaCode` 주석:

> 창 id 는 쓰지 않는다: 차트 창이 여러 개여도 전부 활성 저장뷰에 묶여 있어 종목이
> 하나이기 때문이다. **창별 저장뷰(창마다 다른 종목)를 허용하는 날** "이 창은 어느
> 뷰인가" 가 생기고, 그때 창별로 갈라진다.

어댑터 계약(`WindowWorkspaceAdapter.getWorkareaCode(windowId)`)이 이미 창 id 를 받고
있었으므로, 이 축을 켜는 데 seam 변경이 필요 없었다.

## Decision

**1. 창은 `group: GroupId`(1..10)를 갖고, 그룹 → 저장뷰 맵(`groupViews`)이 SSOT 다.**

`/live` 와 다른 것은 번호가 가리키는 **대상**뿐이다:

| | `/live` | `/study` |
|---|---|---|
| 그룹 → | 종목(`groupSymbols`) | **저장뷰**(`groupViews`) |
| 영속 키 | `live.workspace.v1` | `study.workspace.v1` |

종목이 아니라 저장뷰인 이유: 복기 쿼리는 종목만으로 서지 않는다. **어느 날 · 어느
구간**까지가 쿼리 키이고, 저장뷰가 그 셋을 한 덩어리로 들고 있다.

**2. 번호 자체는 페이지 중립 leaf `workspace/groupId` 가 소유한다.**

범위(1..10)·판별자·팔레트 목록. `state/workspace.ts`(=/live 스토어)에 두고 `/study` 가
가져다 쓰면 **`/study` 를 여는 것만으로 `/live` 워크스페이스가 하이드레이션돼
`live.workspace.v1` 에 시드를 쓴다** — 안 만진 페이지의 저장값이 바뀌는 종류의 조용한
사고다. 뱃지·팔레트 컴포넌트(`workspace/GroupBadge`)도 같은 이유로 공유한다.

**"live 와 study 는 별도 창번호를 관리한다"** 는 요건은 이 배치에서 구조적으로 충족된다 —
공유하는 것은 타입과 마크업뿐이고 상태는 서로 다른 스토어·다른 키에 산다.

**3. `study.activeView.v1` → `groupViews[1]` 로 1회 승계한다. 사슬은 두 홉이다**
(`study.tabs.v1` → `study.activeView.v1` → 여기).

ADR-0149 §3 의 비대칭이 여기서도 그대로 성립한다: `/study` 에는 `live.page.v1` 같은
이중화가 없어 "마지막으로 보던 뷰" 의 집이 이 키들뿐이다. 끊으면 기존 사용자의 첫
진입이 빈 화면이다. **두 홉을 한 함수에 둔다** — ADR-0149 가 4일 전이라 첫 홉을 이미
마친 사용자와 아직 안 마친 사용자가 동시에 존재한다.

그룹 1 인 것은 임의가 아니다: 기존 저장분의 창은 관대 파싱 폴백으로 전부 그룹 1 이
되므로, 승계 직후 화면이 **승계 전과 같다**.

**승계했다는 이유만으로 굳히지는 않는다.** 차트 설정 시드와 갈리는 지점이다 — 저쪽은
살아 있는 키라 굳히지 않으면 사용자가 창에서 바꾼 봉을 매 방문이 덮지만, `study.activeView.v1`
은 이제 **쓰는 사람이 없어** 재읽기가 멱등이다. 반면 하이드레이션이 쓰기를 하면 *"새 탭은
열기만 해서는 아무것도 안 쓴다"* 는 탭 격리 계약이 깨진다. 옛 키는 지우지 않는다.

**4. ADR-0149 가 지운 축들 중 무엇이 그룹 단위로 되살아나는가 — 판정**

| 지운 것 | 그룹 축에서 | 이유 |
|---|---|---|
| 뷰포트 캡처·복원 | **부활 안 함** | 그룹은 상시 공존이라 "이탈 → 복귀" 라는 사건이 없다. 복원 사슬은 `bandViewport ?? savedViewport` 그대로 |
| 비활성 탭 프리페치 | **부활 안 함** | 그룹은 전부 활성이다. 프리페치가 아니라 그냥 fetch |
| 캐시 축출의 탭 축 | **부활함** | 보존 집합이 "어느 그룹이든 지금 보는 종목 전부". `useQueries` 옵저버가 `type:'inactive'` 가드를 떠받치는 구조는 그대로 |
| 라우트 sync 가드 3개 | **그대로** | `?view=` 는 **활성 그룹만** 갈아탄다(§5) |
| 탭별 봉 | **부활 안 함** | 봉의 소유자는 창이다(#1326) |

**5. `?view=` 딥링크는 활성 그룹에만 꽂힌다.** 활성 그룹 = 포커스 창의 그룹이고,
`/live` 처럼 **저장하지 않는다**(포커스에서 파생 — 두 번째 진실을 만들지 않는다).
딥링크는 "지금 보고 있는 자리를 이걸로" 라는 뜻이지 모든 그룹을 갈아치우라는 뜻이
아니다. 드로어 행 클릭도 같은 규칙이다.

**6. 프리셋은 `groupViews` 를 담지 않는다.** `/live` 가 `groupSymbols` 를 빼는 것과 같은
규율이다 — 배치를 불러오는 것만으로 보던 복기뷰가 바뀌면 안 된다. 그룹 **번호**는 배치의
일부라 남고, 그 번호가 어느 뷰인지는 프리셋 밖의 현재 상태가 정한다.

배제는 **타입이 강제한다**: `snapshotStudyWorkspace()` 가
`StudyWorkspaceSnapshot`(= `Persisted` − `groupViews`)를 반환한다. `StudyLayoutPresetPayload`
가 구조적 부분집합이라 `Persisted` 를 그대로 넘겨도 컴파일은 통과하므로(변수 대입에는
excess property check 가 안 걸린다), 좁은 타입을 경유하는 것이 유일한 방어다.

**7. 페이지 게이트가 창으로 내려온다.** "저장뷰를 선택하세요" 는 그동안 페이지 전체의 빈
상태였다. 그룹이 여럿이면 그 게이트가 못 산다 — 빈 그룹의 창을 클릭했다는 이유만으로 다른
그룹에서 보던 복기뷰가 통째로 사라진다. 그래서:

- 페이지 빈 상태 = **어느 그룹에도 뷰가 없을 때**
- 그룹별 안내 = 창 안의 `viewMissing` (로딩과 **구분한다** — 뷰가 없으면 쿼리가 아예 안
  걸리므로 로딩 문구는 영영 끝나지 않는 거짓말이다)
- 로딩·에러 게이트는 **활성 그룹에 뷰가 있을 때만** 판정한다(그룹 도입 전에는 빈-상태
  게이트가 그걸 보장했다 — 그 불변식을 명시로 되살린 것)

**8. 데이터 창은 자기 그룹의 포커스 차트 창 번들을 먹는다.** 한 그룹에 봉이 다른 차트가
둘이면 그중 포커스된 쪽이다. 그룹을 무시하고 전역 포커스 차트를 먹이면 그룹 2 의 10호가에
그룹 1 의 데이터가 뜬다. 메모 창도 자기 그룹의 저장뷰에 쓴다.

## Consequences

- **얻는 것**: 복기뷰 두 개를 나란히 놓고 비교할 수 있다(ADR-0149 이후 브라우저 탭
  두 개가 유일한 방법이었고, 그건 창 배치를 공유하지 못한다). `/live` 와 제스처가 같아진다.
- **비용**: `/study` 상태의 축이 하나 늘었다. "활성 저장뷰" 를 읽던 자리가 전부 "**어느**
  그룹의" 를 물어야 한다 — 그 질문을 안 하고 지나가면 조용히 옆 그룹 값을 쓴다.
  `StudyItemCtx` 를 전부 `windowId => 값` 함수로 바꾼 것이 그 질문을 타입으로 강제한다.
- **되돌리려면**: `groupViews` 를 `{1: …}` 로 고정하고 뱃지를 숨기면 ADR-0149 상태와
  동치다. 창의 `group` 필드는 관대 파싱이라 남아 있어도 무해하다.
- **아직 안 한 것**: 관심종목/스크리너 행을 창에 떨구는 entryDrag 정밀 드롭은 `/study` 에
  여전히 없다(`/live` 에만 있다). 그룹이 생겼으므로 이제 "떨군 창의 그룹" 이라는 답이
  가능해졌지만, 저장뷰는 종목이 아니라 구간이라 드롭으로 만들 수 없다 — 별도 결정이다.
