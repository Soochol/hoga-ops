# 0104 — /live 백필: 휠 줌아웃 좌단 벽 + 스텝을 캔들 100개로 통일

**Status:** accepted (2026-07-11)

**Related:**
- ADR-0103 — 선행 워밍 + read-ahead 제거 (이 ADR이 드러낸 문제를 마무리)
- ADR-0090 (superseded) — 3거래일 스텝("latency cap")의 출처

## Context

분봉에서 마우스 줌인·아웃을 반복하면, 차트가 꽉 차 보이는데도 과거 데이터
fetch가 이어지고 왼쪽에 캔들이 대량으로 쌓이는 현상이 보고됐다. /browse
재현·계측(2026-07-11)으로 메커니즘을 확정했다:

- /live의 휠 줌은 자체 구현(`useWheelInteractions` → `computeWheelOutcome`)
  이고, 줌아웃은 우측 끝(라이브 엣지/뷰포트 우단) 고정으로 **왼쪽으로만**
  확장된다. 보이는 스팬이 로드된 봉 수를 넘는 순간 좌단 논리 인덱스가 음수
  = 빈공간이 생긴다.
- 줌아웃 한계는 `차트폭 ÷ minBarSpacing(0.5px)` = **화면 용량**이다. 좁은
  창(674px)도 1,347바 — 30분봉 기준 ~103거래일. 휠 몇 노치가 "수개월치
  빈공간"을 한 번에 열 수 있다.
- 백필 settle-loop(useViewportBackfill 3a)는 "빈공간이 남아있는 한" 스텝을
  계속 밟는다. 실측: 30m에서 줌아웃 15노치(1.5초 입력) → **무입력 12초간
  fetch 15연발**, `historicalFromDate` 20260626→20260412(약 3개월), 캔들
  65→1,211개. 요청은 배압으로 직렬(동시 1개)이지만, 빈공간 자체가 상시
  수요로 작동해 스텝이 재생산된다(이벤트 큐잉 아님 — PR #533의 배압은 정상
  작동 중이었다).
- ADR-0103으로 워밍이 사라지기 전에는 이 연쇄 대부분이 백엔드 캐시 히트라
  눈에 띄지 않았다. 워밍 제거가 옳았기에 수요 폭주의 근원이 드러난 것.

근본 문제: **수요의 단위가 사용자 입력량이 아니라 화면 크기다.** 팬(드래그)은
움직인 만큼만 빈공간이 생기는 입력-선형이지만, 줌은 지수적(factor=exp)이라
휠 1노치가 화면 용량 전체를 수요화할 수 있다.

## Decision

두 가지를 함께 적용한다. 핵심 불변식: **"줌아웃이 여는 빈공간은 항상 fetch
1스텝으로 채워진다."**

1. **휠 줌아웃 좌단 벽** — `computeWheelOutcome`에 `minFrom`(= −스텝 봉 수)
   클램프를 추가한다. 줌(plain·ctrl 둘 다)은 데이터 좌단 밖으로
   `STEP_CANDLE_TARGET`(100)바까지만 빈공간을 열 수 있다. 앵커 비율 보존
   방식(기존 maxSpan 플로어 클램프와 동일 기법)이라 커서 아래 바가 밀리지
   않고, 현재 from이 이미 벽보다 왼쪽이면 그 값이 벽이 된다(스냅 점프 없는
   단조 가드). shift+휠 팬과 드래그 팬은 입력-선형이라 벽을 두지 않는다.
   과거를 더 보려면 휠을 더 굴리면 된다 — 굴린 만큼 1스텝씩 채워지는
   의도-비례 fetch가 된다.

2. **스텝을 캔들 100개로 통일** — 기존 스텝(분봉 3거래일 / D 250봉 /
   W·M 120봉)을 `STEP_CANDLE_TARGET = 100`캔들 하나로 통일한다.
   - 분봉: 거래일 환산(`stepTradingDays`, 1m·3m=1일 floor, 5m=2, 10m=3,
     15m=4, 30m=8) + **주말 스킵 날짜 걷기**(`subtractWeekdaysKst`). 스텝이
     좁아지며 생기는 토·일-전용 빈 왕복을 호출 전에 결정론적으로 제거한다.
     공휴일은 프론트가 모르는 정보(백엔드 KIS 캘린더 소유)라 남는데, 빈
     청크여도 진행 루프가 base를 밀어 다음 스텝을 밟는 기존 처리로 흡수된다.
   - D/W/M: 캘린더일 환산(D=140, W=700, M=3100일). D의 "한 팬에 1년(350일)"
     one-shot은 폐기 — 줌 벽이 있으면 어차피 100바씩만 열린다.
   - 스텝 단위를 기간이 아니라 캔들 수로 잡는 이유: 뷰포트·빈공간·줌 벽이
     전부 바 단위이므로, 수요와 공급의 단위를 맞추면 스텝이 타임프레임과
     무관하게 화면의 일정 비율이 된다(1거래일 고정안은 30m 13봉 vs 1m 390봉
     으로 30배 편차 + 깊은 팬 왕복 3배 증가라 기각).

## Alternatives considered

- **제스처당 자동 연쇄 N청크 상한**: 증상 완화일 뿐 — 줌인아웃 반복 시
  제스처마다 N청크씩 여전히 래칫하고, "제스처" 판정도 모호. 기각.
- **줌아웃발 빈공간을 수요로 안 침**: 줌아웃으로 과거를 보는 UX가 죽고 빈
  영역이 영구히 남는다. 기각.
- **hydrate 클램프(persist된 깊은 창의 리로드 재fetch 차단)**: 조사 결과
  불필요 — 탭 영속이 `historicalFromDate: null`로 저장하고 마운트 시 탭
  투영이 페이지 값을 덮어써서, 리로드 폭풍 경로가 애초에 없다.

## Consequences

- 재현 시나리오 재실행(동일 30m 줌아웃 15노치): fetch 15연발·3개월 →
  **fetch 1회·8거래일, 즉시 stop**. perf 로그의 `logicalFrom: -100`이 벽
  작동을 확인.
- 깊은 과거 탐색은 휠을 굴린 만큼 진행된다(노치 배치당 1스텝). 수개월
  단위 히스토리 탐색은 /study의 몫이라는 기존 분업과 일치.
- 팬(드래그)의 settle-loop 연쇄는 유지된다 — 드래그 거리만큼의 빈공간은
  정당한 수요다. MAX_FILL_STEPS(60)·250일 클램프 백스톱 불변.
- `STEP_CANDLE_TARGET` 하나가 fetch 폭과 줌 벽을 동시에 지배한다 — 조정 시
  두 쪽이 자동으로 함께 움직인다.
