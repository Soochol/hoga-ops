# ADR-0120 — 키움 분봉 walk-back 제거, 과거 팬은 KIS 날짜병렬 + 배치 스텝

- 상태: Accepted (2026-07-20)
- 관련: ADR-0116(키움 WS 병행 브로커 — 본 ADR이 그 "REST 분담" 절을 부분 폐기),
  ADR-0105(#574 스텝 폭 5거래일), ADR-0100(KIS 계정별 병렬 슬롯),
  ADR-0091(#452 fresh 예산 12), ADR-0095(분봉 디스크 영속 거부 — 유지)
- 플랜/실측: `docs/plans/2026-07-20-live-minute-past-pan-kiwoom-walkback-strategy.md`

## 맥락

ADR-0116(2026-07-16)은 과거 분봉 딥 백필을 키움 `ka10080`으로 이관했다. 근거는
**콜당 효율**(900봉/콜 vs KIS 120봉/콜 = 7.5배)과 그로 인한 **KIS 유량 보존**이었고,
구조는 키움우선 → KIS폴백 사다리(ADR-0109 문법)였다.

2026-07-20 밤 콜드 실측에서 `/live` 분봉 과거 팬이 스텝당 11~29초로 나타났다.
지평선(46거래일) 밖 구간은 오히려 0.3~3.3초였다 — **가까운 과거가 먼 과거보다
10~30배 느린 역전**이 사용자 체감의 정체였다.

## 문제 — 왜 콜당 효율이 벽시계 회귀가 됐나

세 성질이 곱해진다:

1. **랜덤 액세스 불가.** `ka10080`은 시작 날짜 파라미터가 없고 `cont-yn`/`next-key`
   순차 페이지네이션만 있다. 특정 과거 구간에 닿으려면 **매 요청마다 '오늘'부터**
   D/2.3 페이지를 다시 걸어야 한다(D = 거리, 거래일).
2. **직렬 강제 + 1 req/s.** 다음 페이지 키가 이전 응답에서 나오므로 병렬화가
   불가능하고, 키움 TR 유량(실측 1/s)에 맞춘 페이싱이 페이지당 1초를 더한다.
   → 스텝 지연 ≈ D/2.3 초(실측: 26거래일 → 11~13초).
3. **순회분 폐기.** 프리페치가 이번 요청의 pending 날짜만 저장하고 나머지 순회
   봉을 버려, 다음 스텝이 같은 페이지를 다시 삼킨다.

프론트 settle-loop가 5거래일씩 **직렬**이므로 총비용은 O(D²)가 된다(46거래일 팬
≈ 98초). 반면 KIS 경로는 날짜 단위 랜덤 액세스가 되므로 미캐시 날짜를 계정 슬롯에
**병렬 분산**한다(ADR-0100) — 콜 수는 많지만 벽시계는 max(날짜)에 가깝다.

즉 ADR-0116의 근거(콜당 효율)는 여전히 참이지만, **처리량과 지연·접근 패턴은 다른
축**이었다. 인터랙티브 팬이 요구하는 것은 처리량이 아니라 낮은 지연과 랜덤 액세스다.

## 결정

1. **키움 분봉 walk-back을 완전히 제거한다.** `kiwoom_client.py`(ka10080 어댑터),
   `kiwoom_runtime.ensure_minute_client`, `LiveMinuteCandleBackfill`의
   `_kiwoom_prefetch`·`kiwoom_source`·`KiwoomMinuteFetcher` 포트, 전용 테스트 2파일을
   삭제한다. 과거 분봉은 **전량 KIS 날짜병렬**로 돌아간다.
   - ADR-0116의 "REST 분담 = 과거 분봉 딥 백필만 키움 이관" 절은 폐기된다. 나머지
     (WS 전담 = 키움, 그 외 REST 전량 KIS)는 그대로 유효하다.
   - 키움 자격증명·토큰 provider(`kiwoom_runtime`)는 WS(`kiwoom_session`)가 계속
     쓰므로 남는다. 키움의 **REST 소비자는 이제 없다**.
2. **분봉 좌측 팬은 dispatch당 최대 2스텝을 묶는다**(`MAX_BATCH_STEPS_PER_DISPATCH`).
   settle-loop가 직렬이라 왕복 횟수가 곧 지연인데, 백엔드는 날짜를 병렬 처리하므로
   한 요청의 날짜 수를 늘려도 벽시계가 거의 안 는다(배치 3.2~5.7× 실측 2026-07-11).
   prepend 커밋도 절반이라 render 측 비용도 함께 준다.
3. **느린 collect는 상시 WARNING 1줄**(`_SLOW_COLLECT_WARN_MS=5000`). 기존 collect
   로그가 `HOGA_PERF_DEBUG` 전용이라 이번 회귀가 나흘간 로그에 흔적을 안 남겼다.

### 배치 상한이 2인 이유 (3-상수 불변식)

2스텝 = 10평일 = **14캘린더일** ≤ `PAST_CHUNK_CALENDAR_DAYS`(15) → 요청이 항상
청크 1개로 나가고, 10거래일 ≤ `max_fresh_dates_per_collect`(12) →
`fetch_budget_exhausted` 유예 없이 한 collect에서 완결된다. 3스텝(15평일 =
21캘린더일)은 두 제약을 **동시에** 깨서 청크 분할 + 예산 유예로 오히려 느려진다.
세 상수는 서로 다른 파일이 소유하므로 `liveDateTime.test.ts`가 이 관계를 못박는다.

`coverage_gap` fill은 배치하지 않는다(항상 1스텝) — 종료 조건이 예산이 아니라 날짜
수렴이라, 묶으면 viewport가 보지도 않는 과거까지 지표 창이 넓어져 #582(wide-range)
재발이다.

## 결과

- 최근 46거래일 구간 콜드 팬: 스텝당 11~29초 → **0.3~3.3초**(지평선 밖에서 이미
  관측되던 값). 왕복 횟수 절반으로 딥 팬 총시간은 추가로 ~2배 단축.
- 신규 종목 콜드 로드에서 매번 지불하던 키움 walk 2~3초가 사라진다.
- **부수 정합 개선**: 키움은 정규장(09:00–15:30) 밖 `15:35` 봉을 하루 1개씩 얹어
  주고 있었다(A/B 실측 001680 20260612: 키움 381봉 09:00~15:35 vs KIS 380봉
  09:00~15:30). KIS 복귀로 이 봉이 사라지며, `TRADING_MINUTES_PER_DAY=390`
  (09:00–15:30)을 전제하는 세션 모델·스텝 산식과 다시 일치한다. 정규장 데이터
  손실은 없다.
- KIS 쿼터 지출은 늘어난다(46거래일 기준 20콜 → ~184콜). 15/s × 4계정 = 60/s 예산과
  재시도·쿨다운(ADR-0050/0091)이 이미 이 부하를 전제로 설계돼 있고, 딥 팬은 상시가
  아니라 간헐적 인터랙션이라 수용한다. **장중 EGW00201 율(#608 집계)을 한 번
  관찰해 확인한다** — 이것이 본 결정의 유일한 열린 리스크다.
- 코드 순감: -430줄(어댑터 162 + 프리페치 56 + 테스트 ~210).

## 대안 (기각)

- **키움 walk 커서 재사용(continuation resume)**: 세션당 커서를 캐시해 O(D²)→O(D).
  1 req/s 직렬 제약이 남아 스텝당 수 초는 그대로고, 커서 무효화·부분일 경계 처리가
  복잡하다. 삭제가 같은 문제를 더 단순하게 해소한다.
- **키움을 백그라운드 워밍으로 강등**(순회분 전량 저장). KIS 쿼터를 아끼면서 웜
  캐시도 얻는 안이지만, 어댑터를 유지하는 복잡도 + 워밍 진행 상태 관리가 붙는다.
  쿼터가 실제로 문제가 되면 이 ADR을 되돌려 재도입한다(아래 트리거).
- **분봉 디스크 영속**(ADR-0095 되돌리기): 재검토 트리거가 근접했으나, 본 변경이
  재시작 후 콜드도 0.3~3.3초로 되돌리므로 선행 조건이 약해졌다. 유지.

## 재검토 트리거

① 장중 딥 팬 시 EGW00201 율이 유의하게 상승하고 다른 KIS 소비자(스크리너·일봉·
지수)가 체감 열화 ② `live.past_candles.slow_collect` WARNING이 상시 발생
③ KIS 계정 수를 줄여야 하는 상황. 충족 시 "키움 백그라운드 워밍"(위 대안 2)을
재도입한다 — 삭제된 어댑터는 git 이력(본 커밋 이전)에서 복원 가능하다.
