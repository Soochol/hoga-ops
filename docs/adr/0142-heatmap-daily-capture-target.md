# 0142 — 히트맵을 일일 캡처 대상으로, catch-up 은 당일치기로

**Status:** accepted (2026-08-07)

**Amends:**
- **ADR-0068**(히트맵 독립 스토어) — "히트맵은 캡처를 구동하지 않는다" 는 전제를 **뒤집는다**.
  독립성(별도 파일·별도 락·별도 CRUD)은 그대로다. 뒤집히는 건 캡처 대상 여부뿐이다.
- **ADR-0034**(일일 스케줄러 · catch-up) — 적재 집합이 관심종목에서 **관심종목 ∪ 히트맵**
  으로 넓어지고, catch-up 의 백필 범위가 **등록일~오늘 전 구간에서 오늘 하루로 좁아진다.**

**Unchanged:** ADR-0065(스토어 손상 처리 규율) · ADR-0112(히트맵 v3 폴더 필수) ·
ADR-0132(다중 그룹 등록) · ADR-0042(fail_streak) · ADR-0116/0118(키움 WS 저장셋).

**결정 출처:** 사용자 확정 2026-08-07. 두 선택지("그룹별 토글" vs "전체 자동")를 비용 실측과
함께 제시했고 **전체 자동, 토글 없음**이 선택됐다. catch-up 은 **당일치기**로, 그리고 같은
결정을 **관심종목에도 소급**하도록 지시받았다.

---

## Context

히트맵 종목에는 자동 캡처가 없었다. ADR-0068 이 히트맵을 "모니터링 보드이지 캡처 대상이
아니다" 로 정의했고, 그래서 `HeatmapEntry` 에는 캡처 마커 필드 자체가 없었다. 사용자는
히트맵 종목도 관심종목처럼 매일 자동 수집되기를 원했다.

### 실측 비용 (사용자 데이터, 2026-08-07)

| 항목 | 값 |
|---|---|
| 히트맵 | 40그룹 / **271종목** (관심종목 25) |
| 1종목·1일 raw | 약 150MB (`raw/20260806` = 25종목 3.7GB) |
| 271종목 하루치 | **약 35GB** (`raw/20260803` 에 248종목 수집한 실측이 35GB) |
| 큐 소진 | 271 × 90초 ÷ 동시성 3 = **약 2.3시간** (17:00 → 19:20경) |
| 디스크 | 여유 446GB · 현재 raw 104GB · 보존 기본 3일 |

시간은 문제가 아니다. 디스크는 보존이 정상 작동하면 ~105GB 로 안정되지만, prune 기본 게이트는
`COMPLETE` 만 지우므로 미완결 캡처가 섞이면 회수되지 않는다(#998 에서 351GB 가 그렇게 묶였다).

## Decision

### 1. 히트맵 = 일일 캡처 대상 (그룹 토글 없음)

17:00 KST 일일 런이 **관심종목 ∪ 히트맵**을 적재한다. 순서는 관심종목 먼저, 코드 단위 dedup.

- **순서가 계약인 이유**: 큐는 FIFO 이고 hogaplay 업스트림 보유가 ~18시간이다. 271종목이면
  소진에 ~2.3시간이 걸리므로 뒤로 밀린 종목일수록 유실 위험이 크다. 사용자가 실제로 매매를
  보는 관심종목이 앞에 서야 한다. 라이브 저장셋 우선순위(`coverage.plan_storage_targets`)와
  같은 순서다.
- **dedup 이 필요한 이유**: 두 목록은 겹치고, 히트맵 entry 는 `(folder_id, code)` 라 한 종목이
  여러 그룹에 있을 수 있다. 큐도 같은 `(code,date)` 를 deduped 로 되돌리지만 그건 큐의 방어이지
  계획의 정확성이 아니다 — dedup 없이는 "N종목 적재" 로그가 실제 종목 수와 어긋난다.
- **그룹별 on/off 토글은 두지 않는다**(사용자 결정). 등록 = 캡처 대상이다. 되돌리려면 히트맵에서
  뺀다. 폴더의 `capture_enabled` 는 **읽지 않는다** — 그 플래그는 관심종목에서도 hogaplay 캡처가
  아니라 실시간 WS 저장셋을 고르는 값이다(`capture_ordered_codes`). 이름이 오해를 부르지만
  의미를 바꾸는 것은 이 ADR 의 범위가 아니다.

### 2. 마커는 code 키 사이드 테이블 (entry 아님)

`heatmap.json` v4 에 `capture_markers: {code → YYYYMMDD}` 를 둔다. `entries` 는 손대지 않는다.

**근거**: 히트맵 entry 의 identity 는 `(folder_id, code)` 다(ADR-0132 다중 그룹 등록). 마커를
entry 에 얹으면 한 종목이 3개 그룹에 등록됐을 때 마커가 **3벌로 갈라지는데**, 정작 그 마커가
가리키는 캡처는 `(code, date)` 하나뿐이다. 어느 값이 진실인지 말할 수 없는 상태가 구조적으로
생긴다. code 로 키잉하는 것만이 추적 대상과 모양이 맞는 유일한 형태다.

`registered_at_kst_date` 대응물은 **두지 않는다.** 관심종목이 그 필드를 가진 유일한 이유가
catch-up 백필의 floor 였고, catch-up 은 §3 으로 당일치기가 됐다. 마커 부재 = 수집 이력 없음이며,
이는 새로 추가한 종목에 대해 UI 가 보여줘야 할 바로 그 의미다.

**마커 생명주기**:
- 전진: 캡처 finalize 훅이 `bump_last_success`(전진 전용). 관심종목·히트맵 **양쪽**을 올린다 —
  한 종목이 두 목록에 있을 수 있고 디스크 Stock-Date 는 하나이기 때문이다. 두 스토어는 락이
  다르고 종목이 한쪽에만 있을 수도 있어 **예외 경계를 각각** 둔다.
- 시드: 종목이 히트맵에 **처음** 등록될 때 `latest_complete_date` 로 디스크에서 시드한다.
  이미 캡처가 있는 종목이 "미수집" 으로 보이지 않게 한다.
- 정리: `save_document` 한 곳에서 고아 마커를 prune 한다. 종목을 빼는 명령이 넷
  (`remove_entry`·`remove_entries`·`delete_folder`·`move_entries`)이라 각 명령에 정리 코드를
  넣으면 하나만 빠뜨려도 유령 마커가 남는다. 쓰기 경로 단일 지점에 두면 명령들은 `entries` 만
  건드리면 되고 정리는 구조적으로 따라온다.
- **`set_last_success`(역행 가능) 는 두지 않는다.** 호출할 catch-up 이 없다. 히트맵 마커는
  "마지막으로 성공한 캡처" 이지 "지금 디스크에 있는 것" 이 아니다 — 보존 prune 이 마커를 뒤로
  되돌리면 안 된다. 디스크 잔존 여부는 보관함의 질문이다.

**손상 처리**: 형식이 깨진 마커 행은 **드롭하고 로그**한다(`_clean_markers`). `model_validate`
까지 보내면 마커 한 줄 때문에 문서 전체가 corrupt 백업 경로로 가서 40그룹 271등록이 날아간다.
마커는 디스크에서 재계산 가능하고 그룹 구성은 아니다 — 복구 가능한 것을 지키려고 복구 불가능한
것을 버리는 것은 정확히 거꾸로다(ADR-0065 rule 1 의 우선순위를 이 자리에 적용).

**v3→v4 마이그레이션은 순수 필드 추가**다. 디스크를 훑어 마커를 시드하지 않는다 — 그렇게 하면
load 마다 271회 stat 이 붙는다. 마커 부재가 이미 옳은 의미라 backfill 이 필요 없다.

### 3. catch-up 은 당일치기 (관심종목 포함)

`catchup_one_entry` 의 적재 대상을 "등록일/마커 다음날 ~ 오늘의 모든 거래일" 에서 **오늘 하루**
로 좁힌다. 마커를 디스크와 맞추는 reconcile(Step 1)은 **유지한다** — 결손 표시가 디스크와
어긋나지 않으려면 필요하다.

**두 가지 이유**:
1. hogaplay 업스트림 보유가 ~18시간이라 예전 walk-back 이 만들던 날짜는 **대부분 이미 받을 수
   없는 날짜**였다. 실패할 수밖에 없는 작업을 큐에 넣고 그 날짜들에 fail_streak 를 태웠다.
2. 히트맵 271종목이 같은 경로를 타면 첫 런에서 큐가 수천 건이 된다. 90초/건이면 자신이 쫓는
   보존 창 안에 소진이 불가능하다.

과거 결손은 **수집 다이얼로그**의 몫이다(명시적 구간 + coverage preview 선행).

히트맵에는 catch-up 라우트를 **만들지 않는다**. 당일치기라면 17:00 런이 이미 그 일을 하므로
행별 "오늘 수집" 버튼은 스케줄러와 경주할 뿐이다.

### 4. 결손 표시

- wire: `HeatmapResponse.capture_markers`(code 키 맵) + `next_run_at_ms`. 후자는 관심종목
  라우트와 **같은 함수**(`scheduler.next_run_at_ms`)에서 나온다 — 하나의 일일 런이 두 목록을
  적재하는데 두 화면이 다른 시각을 말하면 그 자체가 버그다.
- 기준일은 **마커의 최댓값**이지 달력이 아니다. 히트맵 전 종목은 같은 런에서 함께 적재되므로
  정상이면 마커가 한 날짜로 수렴하고, 그보다 뒤처진 종목이 곧 결손이다. 달력(마지막 거래일)을
  기준으로 삼으면 **장중에는 오늘 런이 아직 안 돌아 271개 전부가 "미수집"** 이 된다 — 정보가
  아니라 소음이다.
- 표시는 **그룹 헤더의 '미수집 N' 칩 + 행 툴팁**이다. 히트맵 행은 밀도가 1차 정책이라
  (`HeatmapRow` 주석) 271행 × 날짜 배지를 담을 칼럼이 없다. 결손 행은 종목명을 `--error` 로
  낮춘다(DESIGN.md 색 규율에서 캡처 성공/실패는 상태 semantic 이며 시세 적/청과 다른 축이다).
  결손이 0이면 칩을 **그리지 않는다** — 정상은 침묵한다.

## Consequences

- **디스크가 하루 ~35GB 늘어난다.** 보존 3일이면 ~105GB 정상 상태. 미완결 캡처가 쌓이면 회수되지
  않으므로(#998), 여유가 줄면 `HOGA_PRUNE_CONFIRMED_GAPS=1` 을 켜는 것이 첫 대응이다.
- **큐가 17:00 부터 ~2.3시간 점유된다.** 그 사이 수동 수집은 뒤에 선다.
- 관심종목의 과거 결손 자동 백필이 **사라진다.** 오프라인이 길었던 뒤 복귀해도 스케줄러는 오늘만
  넣는다 — 과거는 수집 다이얼로그로 명시 수집한다. `registered_at_kst_date` 는 디스크·모델에
  남지만 더 이상 floor 로 읽히지 않는다(등록일 표시 용도).
- ADR-0068 의 "캡처 무구동" 전제를 인용하는 문서·주석은 이 ADR 을 함께 읽어야 한다.
