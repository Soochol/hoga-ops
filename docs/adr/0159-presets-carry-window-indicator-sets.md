# 0159 — 레이아웃 프리셋은 창별 지표 세트를 함께 담는다

**Status:** accepted (2026-08-24)

**Amends:**
- [ADR-0152](0152-per-window-indicator-sets.md) 결정 4 — "내용물은 전역 localStorage 에
  남고 창이 갖는 것은 키뿐이다. **워크스페이스 스냅샷 스키마는 무변경**". 앞 문장은
  그대로 유효하고, 뒷 문장이 **프리셋 payload 에 한해** 풀린다. 스토어의
  `WorkspaceWindow` 와 탭 sessionStorage 는 여전히 지표를 모른다.
- [ADR-0119](0119-live-multi-window-workspace.md) PR-E 의 "프리셋 = 창·배치".

**Related:**
- #712 — 창 소유 지표를 되돌린 작업. 그 사고의 원인은 창-스코프가 아니라 **내용물을
  탭별 sessionStorage 에 담은 것**이었다(ADR-0145·0152 가 같은 판정).
- ADR-0072 — 한 지표의 prefs 가 `livePage`·`chartPrefs` 두 store 에 나뉜다.
- `frontend/src/live/presets/layoutPresetSnapshot.ts`,
  `frontend/src/state/indicatorScopeGc.ts`.

## Decision

1. **프리셋 payload 의 차트 창 원소가 지표 세트를 싣는다** — `indicators`(livePage 의
   `byWindow` 엔트리)와 `indicatorModal`(chartPrefs 미러). 두 키는 **쌍으로** 움직인다.
2. **캡처는 빈 세트도 담는다.** 멤버십은 키의 존재이므로(ADR-0152 결정 6), 공장값
   상태의 창은 `{}` 가 정상값이다. 빈 것을 생략하면 적용 시 마운트 시드가 **페이지
   세트**를 복사해, 저장한 것과 다른 화면이 된다.
3. **적용은 스냅샷 적용 뒤에, 스토어의 창 목록을 순회해서 한다**(payload 순회 아님).
   이유는 아래 Context.
4. **복원은 무조건 덮어쓴다**(시드의 멱등 건너뜀과 다르다). 프리셋 적용은 "비었으면
   채우기" 가 아니라 "저장된 값으로 교체" 다 — rect 와 같은 대우다.
5. **백엔드·wire 계약은 무변경이고 `schema_version` 도 3 그대로다.** 서버 payload 는
   `windows: list[dict[str, Any]]` 라 새 키를 그대로 통과시킨다.
6. **하위호환은 키의 부재로 판정한다.** 두 지표 키가 모두 없는 창 원소는 이 기능
   이전에 저장된 프리셋이고, 그 창은 종전대로 마운트 시드가 채운다.
7. **종목·창 핀은 여전히 담지 않는다.** 이 ADR 은 그 결정을 건드리지 않는다.

## Context

### 무엇이 고장나 있었는가

프리셋 payload 는 창 id 를 담고, 창별 지표는 그 id 에 매달려 전역 저장소에 산다.
그래서 지표는 **우연히 반쯤** 따라왔다 — 그리고 프리셋의 주 용도에서 정확히 실패했다:

| 시나리오 | 종전 | 이유 |
|---|---|---|
| 창을 옮기고 같은 프리셋 재적용 | 유지 | `before == after` id → 회수 없음 |
| A 적용 → B 적용 → A 재적용 | **리셋** | B 적용 때 A 의 창 id 가 회수됨 |
| "기본 배치로 초기화" | **리셋** | `defaultWindows()` 가 새 id 를 발급 |
| 다른 기기에서 적용 | **리셋** | 프리셋은 서버 파일, `byWindow` 는 localStorage |

즉 종전 동작은 "유지" 도 "교체" 도 아닌 **"리셋"** 이었고, 1행 때문에 빠른 수동
테스트로는 멀쩡해 보였다.

### 왜 종목과 반대 판정인가

프리셋에서 종목을 뺀 근거는 "배치를 바꾸려고 누른 프리셋이 **보던 것**까지 갈아치우면
손해" 였다. 지표는 그 "보던 것" 이 아니라 **작업 환경**이다 — 어느 종목을 보든 스캘핑
구성은 스캘핑 구성이다. 그래서 배치와 함께 움직이는 쪽이 프리셋의 쓸모에 맞고,
사용자가 이 변경을 요청한 동기도 그것이었다.

대가는 명시한다: **프리셋 적용은 현재 창들의 지표 조정을 덮어쓴다.** 설계상 그렇게
되는 것이지 결함이 아니다.

### 왜 #712 의 재발이 아닌가

#712 의 원인은 창-스코프라는 개념이 아니라 **내용물이 탭별 sessionStorage 에 앉은
것**이었다. 여기서 바뀌는 것은 **서버에 저장되는 프리셋 payload** 뿐이다:

- 스토어의 `WorkspaceWindow` 타입은 무변경 → `persistFromState` 가 쓰는 탭
  sessionStorage 에 지표가 들어가지 않는다.
- 지표의 SSOT 는 여전히 전역 `live.indicators.v2` 다. 프리셋은 그 값을 **복사해
  나르는 매체**이지 저장소가 아니다.
- 적용 경로의 `readWindow` 는 **화이트리스트**라 payload 의 지표 키를 애초에 읽지
  못한다. 즉 스토어 오염이 타입이 아니라 **파서 모양**으로 막혀 있다.

이 셋이 유지되는 한 재발 경로가 없다. 셋 중 하나라도 바꾸려는 변경은 #712 를 다시
읽고 오라는 뜻이다.

### 왜 payload 가 아니라 적용 후 스토어 창을 순회하는가

`readWindow` 가 거부한 창(손상된 rect·공장 기본 폴백)은 스토어에 없다. payload 를
순회해 심으면 **어떤 창도 가진 적 없는 스코프 키**가 남고, 회수는 `before` 에 있던
id 만 걷으므로 그 키에 영원히 닿지 못한다. 상한이 64 인 전역 맵에서 영구 고아는
"시드가 조용히 거부되는" 상태로 이어진다 — ADR-0152 가 경고한 "절반만 동작" 서명이다.

### 왜 스냅샷 적용 **뒤**인가

먼저 심으면 옛 창들이 아직 맵에 남아 있어 상한에 걸릴 수 있고, 시드·복원은 상한에서
**조용히 포기**한다. 스냅샷 적용이 사라진 창을 회수한 뒤라야 자리가 난다.

### 왜 덮어쓰기인가

시드 의미(이미 있으면 no-op)를 쓰면, 프리셋의 창이 지금 화면에 살아 있는 경우 —
위 표의 1행, 종전에 유일하게 동작하던 경로 — 엔트리가 이미 있으므로 **저장된 지표가
영영 적용되지 않는다.** "지표를 만지고 → 같은 프리셋 재적용 → 저장 값으로 되돌아온다"
가 이 기능의 인수 조건이다.

## Alternatives considered

### A. 현상 유지 — 기각
위 표의 세 행이 남는다. 특히 크로스기기는 원리적으로 해결 불가다(지표가 로컬에만 있음).

### B. GC 를 프리셋이 참조하는 id 에 대해 유예 — 기각
창 닫기 회수를 프리셋 목록과 대조해 미루는 방식. 크로스기기가 그대로 깨지고, 고아가
`INDICATOR_WINDOW_SCOPE_LIMIT` 에 쌓이면 시드가 조용히 거부된다. 증상을 미룰 뿐이다.

### C. 명명 프로파일(창이 이름 붙은 세트를 참조) — 유예
ADR-0145·0152 가 두 번 유예한 상위 호환 모델. CRUD·삭제 시 참조 처리 UI 가 통째로
따라오고, 이 축 **위에** 얹을 수 있다.

### D. 최상위 payload 키(`indicatorsByWindow`)로 넣기 — 기각
창 원소 안에 넣는 것과 표현력이 같은데, 백엔드 모델 필드 + wire 스냅샷 + 프론트 미러가
전부 따라온다(ADR-0004 의 4층 가드). 창에 매달린 값을 창 원소에 두는 것이 자연스럽고,
`readWindow` 화이트리스트라는 기존 방어선도 그 자리에서만 작동한다.

## Consequences

**Positive:** 백엔드·wire 계약·저장 스키마 전부 무변경. 되돌리기가 싸다 — 캡처에서
지표를 안 얹으면 옛 payload 는 키 부재로 읽혀 종전 동작이 된다. 지표 소비자는 무변경
(절단면은 캡처·적용 두 함수와 스토어 액션 하나씩).

**Negative / watch:**

- **프리셋 적용이 현재 창들의 지표를 덮어쓴다.** 의도된 동작이고 UI 문구가 이를
  알린다("적용 시 창 배치·지표가 교체됩니다"). 되돌릴 실행취소는 없다.
- **payload 가 커진다.** sparse diff 라 공장값 사용자는 `{}` 에 가깝지만, 지표를 많이
  켠 창이 여럿이면 프리셋 하나가 수십 KB 가 될 수 있다. 서버가 통째로 읽고 쓰는
  파일이므로 창 수가 실사용 범위를 넘으면 다시 볼 것.
- **두 store 를 쌍으로 실어야 한다.** 한쪽만 실리면 같은 드로어에서 절반은 프리셋 값,
  절반은 옛 값이 된다. 캡처·복원 모두 없는 쪽을 `{}` 로 채워 멤버십이 갈리지 않게 한다.
- **상한에 닿은 사용자는 부분 복원된다.** 새 엔트리만 상한을 보므로 기존 창 덮어쓰기는
  항상 성공하지만, 창이 64 개를 넘으면 나머지는 페이지 세트로 열린다(조용하다).
- **`schema_version` 을 올리면 프리셋이 전멸한다** — 스토어의 stale 버전 가드가 파일을
  빈 목록으로 대체한다. 이 확장은 v3 안에서 양방향 호환이므로 올릴 이유가 없다.
- **재검토 트리거**: 여러 창·여러 프리셋이 같은 지표 구성을 공유하게 하고 싶어질 때 —
  그때가 대안 C(명명 프로파일)의 시점이다.
