# 0116 — 키움 WS 병행 도입: 고정 역할 공존으로 실시간 커버리지 76→876종목

**2026-10-02 표시 보관량 보완:** `LiveBuffer`는 기존 시간·deque 상한에 더해 전체
250,000개 항목과 추정 payload 512MiB 예산을 적용한다. 환경변수는
`HOGA_LIVE_BUFFER_MAX_ENTRIES` / `HOGA_LIVE_BUFFER_MAX_BYTES`다. 조회 subscriber가
없는 stream을 먼저, 그다음 마지막 publish가 오래된 stream부터 FIFO로 축출한다.
예산 포화 시 최소 시간 보존 규칙의 **명시적 예외**로 화면 이력을 줄인다.
`/api/live/series.buffer_history_truncated`와 창의 안내가 이를 드러낸다.
해당 code가 Live Set에서 제거되기 전에는 축소 이력 표시를 유지한다.

마지막 호가 sidecar(Code×venue 최신 1개), subscriber 전달, 원본 LiveWriter 입력과
기존 JSONL→promote→parquet 저장 계약은 표시 축출에서 제외한다. 최신값은 Live Set
제거 때만 함께 지운다. 추정 예산은 payload의 도달 가능한 알려진 container 크기이며
allocator·sidecar·작업 임시값을 포함한 전체 RSS 상한이 아니다. 기존 초봉 cell 상한,
조회 캐시 LRU·bar 상한과 subscriber/outbox 상한도 유지한다. 추가로 오늘 지표 TTL
캐시에 전체 512개·추정 값 128MiB LRU 예산을 적용하며 큰 값은 캐시하지 않고 재계산한다.
키·bookkeeping과 opaque 객체 내부는 byte 추정에서 제외되므로 호스트 RSS와 함께 본다.

기본 예산은 기존 243/800종목 메모리 실측과 packed 호가 구조를 바탕으로 둔 안전핀이다.
운영 크기별 유지 가능한 표시 창과 부모·compute/promote 자식의 합산 메모리는 별도
검증하며, 작은 합성 재생의 안정화를 장중 최고부하 해결로 확대하지 않는다.

**Status:** proposed (2026-07-16) — **"REST 분담" 절은 ADR-0120(2026-07-20)에 이어 ADR-0136(2026-08-04)으로 최종 폐기** — REST 도 키움이 됐다
(과거 분봉 딥 백필의 키움 이관을 되돌리고 전량 KIS 날짜병렬로 복귀. 콜당 효율은
참이었으나 `ka10080`의 랜덤 액세스 불가 + 1 req/s 직렬이 인터랙티브 팬에서 스텝당
11~29초 회귀를 냈다). WS 전담·역할 공존 등 나머지 결정은 유효하다.

## Context

`/live` 실시간 시세는 전량 KIS에 강결합돼 있다. 수집 클라이언트(`Kis*`)는 브로커 추상화가
없고, 소스 다형성은 저장·조회 read-path(`hoga/api/sources.py`)에만 존재한다.

WS 실시간 커버리지가 병목이다. KIS WS는 연결당 등록 상한 39(하드 41), 종목당 2 TR
(호가+체결)이라 계좌당 19종목, 4앱키 = **76종목**뿐이다. 나머지(히트맵 등 ~500종목)는
REST 10초 폴링(rest30, ADR-0102)으로 덮여 push가 아니다.

키움증권 REST API를 실계좌 4앱키로 실측(2026-07-16)한 결과, WS 용량이 KIS의 10배 이상이다:

| 항목 | 실측값 |
|---|---|
| WS 등록 상한 | 연결당 총 **200종목** (grp_no 늘려도 총합 200 불변) |
| 카운트 단위 | **종목당 1건, 타입 무관** (`0B`+`0D` 쌍 등록해도 200종목) |
| 앱키당 세션 | **1개** — 동일 앱키 2번째 LOGIN이 기존을 킥(close 1000) |
| 앱키 간 독립 | 확정 — 4앱키 동시 각 200, disjoint 800종목 동시 수신 |
| REG 유량 | ~5 REG/s per 연결 (배치 50종목/REG로 회피) |
| NXT | `_NX` 접미 코드로 수신 확정 |
| 분봉 REST | 900봉/콜 (KIS 120봉/콜) |
| REST 유량 | TR당 ~1/s (폴링 엔진 불가) |

커뮤니티 통설("97건, 종목×타입당 카운트")은 실측으로 반증됐다.

## Decision

키움을 **평행 수집 스택**으로 신설하고, KIS와 **고정 역할 공존**한다. 동적 샤딩(한
universe를 두 브로커에 섞기)이 아니라 소유권을 고정한다 — 한 종목의 실시간 소유자는 항상
하나다.

**WS 분담**
- 관심종목(76) = KIS WS (venue 스왑·유실 사다리 검증 자산 유지)
- 히트맵(≤800) = 키움 WS (`0B`+`0D`, 슬롯당 200×4)
- 그 외 열람 종목 = 키움 온디맨드 WS (표시 전용, writer 금지)

**REST 분담** — ⚠️ **ADR-0120으로 폐기(2026-07-20): 키움 REST 소비자는 이제 없다.**
- ~~과거 분봉 딥 백필만 키움 이관(900봉/콜, 키움우선→KIS폴백).~~ 되돌림 — `ka10080`은
  시작 날짜 파라미터가 없어 매 요청이 '오늘'부터 재순회하고(1 req/s 직렬), 프론트
  직렬 스텝과 곱해져 O(D²)가 됐다. 전량 KIS 날짜병렬로 복귀(ADR-0120).
- 나머지 REST(일봉·스크리너 배치·거래원·프로그램·지수·투자자·캘린더·토큰) 전부 KIS
  잔류 — 상시·대량은 KIS 유량(15/s×4)이 강점, 키움 1/s는 퇴보. **이 판단은 결과적으로
  분봉 백필에도 적용됐어야 했다**(ADR-0120 회고).

**장애·용량 대응** = 키움 계좌 추가(WS). rest30 폴백 열화 정책은 만들지 않는다. 브로커
전체 장애는 계정 수와 무관(운명 공동체)함을 인지하고 수용한다. rest30·2s 폴러 코드는
삭제하지 않고 휴면(대상 빈 집합 = 호출 0).

**아키텍처 = Ports & Adapters.** 포트 = `WsTick` + `LiveStream.on_tick`(소스 무관 단일
진입점). 코어(표시·저장·지표)는 브로커를 모른다. 지금(N=2)은 **Adapter만**
(`kiwoom_frames`); `LiveCollector` Protocol + waterfall 배분은 3번째 증권사 때 추출한다
(Rule of Three). 상속 베이스(Template Method) 금지 — 킥 vs 거부, 배치 REG vs 개별 TR로
골격이 다르다.

**지금 지킬 규율**: (1) `kis_*`↔`kiwoom_*` 상호 import 금지 (2) 공유 코드에 브로커 분기
금지, 주입만 (3) 관측성 shape 통일 (4) `WsTick` 계약 테스트 공용화.

## Consequences

- WS push 커버리지 76 → 876종목(3.5배 이상). 히트맵이 10초 폴링에서 틱 push로.
- rest30 상시 부하(최대 ~50콜/s) 소멸 → KIS REST 예산이 백필·폴백으로 해방.
- 키움 클라이언트 신설(수집·인증·슬롯 층). 소비 경계·저장 태깅은 재사용.
- 킥 의미론이 KIS(거부)와 달라 이중 기동 가드가 필수. 76→876 틱 볼륨 ~10배 →
  0D 파싱은 필요 FID만, 계측 첫날부터.
- 미해결: 정규장 `_AL`이 KRX·NXT를 한 스트림으로 주면 UN 통합을 키움 1슬롯으로 해결
  가능 — "NXT=KIS 전담"이 재평가된다(후속 ADR).

## 2026-10-01 개정: reader/consumer 양보 예산과 큐 장애 증거

REAL을 순서대로 처리하는 consumer와 PING/REG를 처리하는 reader는 각각 독립적인
`LoopWorkBudget`을 유지한다. 기존 공유 시각은 `sleep(0)` **전**에 갱신돼, 다른
태스크를 기다린 시간이 다음 양보 판단에 들어갔다. CPU 경쟁 아래에서 consumer가
작업을 거의 하지 않고 다시 양보하는 증폭을 오프라인에서 재현했다.

예산은 생성 시 현재 시각으로 시작하고 명시적 양보 **복귀 후** 갱신한다. 루프 회전
표식은 예산당 최대 하나의 `call_soon` 핸들이다. 콜백/큐가 이미 suspend했다면 다음
체크포인트에서 새 작업 구간을 시작한다. 프레임마다 태스크를 만들지 않으며 취소 시
핸들을 해제한다. reader의 큐 압력에 따른 양보와 제어 응답 경로는 유지한다.

이것은 협력적 wall-time 예산이다. 한 파싱/콜백의 CPU 작업을 선점하지 않고, 콜백
내부의 마지막 await 이후 작업 시간도 따로 계측하지 않는다. 모든 부하에서 1ms 정지
상한이나 무손실을 보장하지 않는다. 입력이 처리 능력을 넘으면 기존 128 메시지/8MiB
상한으로 세션을 종료하고 손실을 명시적으로 집계한다.

큐 초과 시 기존 로그에 payload 없는 `evidence` JSON을 붙인다. PID, commit, live
시작 시각, 연결 세대/세션 시작, 수신·완료 프레임률, 처리 중 프레임 경과, 실패 당시
rolling 대기·dispatch 통계, 양보 횟수/대기, GC 카운터를 보존한다. 프레임률의 단위는
REAL 프레임이며 raw 행 수와 파싱 후 완료 틱 수를 혼동하지 않는다. CPU 증분은
**프로세스 전체 및 이벤트 루프 스레드 전체**이고 특정 계정/태스크 CPU가 아니다.
샘플은 초당 최대 하나, 12개로 제한하며 보통 최근 약 10초를 비교한다. 절전 등으로
간격이 벌어지면 실제 `window_ms`로 해석한다. 실패 시 전체 힙 스캔은 하지 않는다.
GC 경고에도 PID를 넣어 여러 프로세스가 공유한 로그를 구분한다.

## 2026-10-02 개정: 제어 실패의 세션 종료 소유권

외부 Live Set 변경의 제어 요청이 실패하면 연결 표시 변경만으로 종료하지 않는다.
구독 태스크는 세션별 종료 신호를 보내고, `run()`의 세션 소유자가 reader/consumer
취소·join, waiter·큐 정리, transport 종료를 완료한 뒤 재연결한다. 구독 lock 안에서
소유자의 정리를 기다리지 않으며, retiring 세션은 제어 송신·후속 Live Tick 전달에
재사용하지 않는다. 최신 desired 종목은 새 세션에서 다시 등록한다.

close의 앱 제한은 라이브러리 자체 제한보다 길게 두고, 실패·취소 시 native adapter의
abort와 `wait_closed()`로 종료를 확인한다. 종료를 증명할 수 없는 custom adapter는
자동 대체하지 않는다. 시간 제한은 협력적이며 GC·동기 작업을 선점하지 않는다.
제어 실패 시점의 안전한 관측을 즉시 기록하고 최근 최대 32개의 요청/ACK 사건을
PID·연결 세대·세션 시작·runtime context와 함께 남긴다.
