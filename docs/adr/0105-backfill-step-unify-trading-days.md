# 0105 — /live 백필: 스텝 커널 단일화(분봉 1→5거래일, 전 타임프레임 STEP_TRADING_DAYS)

**Status:** accepted (2026-07-11)

**Related:**
- ADR-0104 — 제스처 예산 + 스텝 캔들 50개 통일 (이 ADR이 분봉 스텝 폭을 부분 개정)
- ADR-0103 — 선행 워밍 + read-ahead 제거 (이 ADR이 재노출한 콜드를 완화)
- ADR-0100 — KIS REST 앱키별 유량 독립 + past-candles 계정 비례 동시성(9~12슬롯)

## Context

통합(UN) venue·1분봉에서 과거로 팬하면, 지표를 전부 꺼도 캔들 로딩이 하루당
1.5~2.5초(최악 13.4초)씩 걸린다는 보고. /browse E2E + curl 백투백 실측
(2026-07-11)으로 병목을 확정했다:

- 과거 분봉은 메모리 온리 캐시(ADR-0095)라 첫 방문 날짜는 항상 KIS 콜드 fetch.
- UN 하루(08:00~20:00) = KIS 120행/콜 제한으로 **6~9페이지 순차**(앵커 워크백이
  직전 응답에 의존해 페이지 병렬화 불가). KRX 하루(390분)는 4페이지.
- **프론트 settle-loop가 분봉 스텝 = 1거래일씩 순차 요청**(ADR-0104: 스텝 캔들
  50개 → 1m은 최소 1거래일로 floor). 그 결과 백엔드의 날짜-병렬 슬롯
  (계정×3 = 9~12, ADR-0100)을 **1개만** 사용.
- 실증: UN 10거래일 = 순차 스텝 15~25초 vs 한 요청(백엔드 병렬) 5.0초.
  KRX 재검증도 5×단일일 4457ms vs 1×5일배치 1287ms = **3.2~5.7배**.

즉 병목의 곱셈 항은 "KIS 콜드"가 아니라 "1거래일 순차 스텝이 백엔드 병렬성을
봉인한 것"이다. 스텝 폭만 키우면 기존 직렬 루프가 요청당 백엔드 병렬 배치를
탄다(백엔드 무변경).

기각된 대안:
- **램프업(1스텝 1일 → 2스텝+ 15일)**: 첫 커밋을 빠르게 하려는 장치. 그러나
  5거래일 배치도 백엔드 병렬이라 첫 커밋 대기가 "가장 느린 하루 하나" ≈
  1.5~2.5초로, 1일 스텝과 대등. 장치가 무료로 불필요해져 기각(상태만 추가).
- **15캘린더일 균일**: 첫 커밋이 ~5초로 늘어남(스텝이 넓어 첫 배치가 큼).
- **5캘린더일 균일**: 주말 위치에 따라 산출량이 거래일 3~4일로 출렁이고,
  캘린더/거래일 단위 혼용이 남음. 거래일 단위가 주식 데이터의 자연 단위.

## Decision

**백필 스텝 커널을 전 타임프레임 단일 통화(거래일) + 단일 테이블 + 주말 스킵
단일 경로로 통일**한다. 분봉 스텝을 1거래일 → 5거래일로 확대한다.

1. **`STEP_TRADING_DAYS: Record<LiveTimeframe, number>`** 단일 소스:
   `{1m~30m: 5, D: 50, W: 250, M: 1050}`. D/W/M 값은 캔들
   `STEP_CANDLE_TARGET(50)`개에서 유도(D=50거래일, W=50주×5, M=50개월×21)해
   "한 스텝 ≈ 50캔들" 불변식(ADR-0104)을 코드로 드러낸다.
2. **`stepBackFrom`은 전 타임프레임이 `subtractWeekdaysKst`(주말 스킵) 단일
   경로**를 쓴다. ADR-0104의 분봉/캘린더 분기를 제거. 근거: 거래일이 주식
   데이터의 자연 단위(일봉은 거래일에만 존재)라 스텝당 캔들 산출량이 주말
   위치와 무관하게 일정(1m = 5×390 = 1,950봉 고정). D=50평일=70캘린더일,
   W=250평일=350캘린더일로 기존 ADR-0104 캘린더 스텝과 **정확히 동치**(회귀
   없음, 테이블 테스트로 증명). M=1050평일≈1470캘린더일(기존 1550의 의도된
   근사; M 딥팬은 드물고 차트는 존재하는 캔들만 표시).
3. **예산 산정 갱신**: `stepCandlesEstimate`가 `STEP_TRADING_DAYS[tf] × 봉/거래일`
   (1m=1950, 5m=390, 30m=65, D/W/M=50). `fillBudgetSteps` 식은 무변경(분모만
   갱신). MAX_FILL_STEPS(60) 캡 유지.
4. **삭제**: `stepTradingDays`(거래일 ceil), `stepChunkDays`(캘린더 환산).
   `STEP_CANDLE_TARGET`은 D/W/M 유도·예산 상수로 존치.

스텝(5거래일 ≈ 7~9캘린더일)은 청크 캡 `PAST_CHUNK_CALENDAR_DAYS=15`·백엔드
신선날짜 예산 `max_fresh_dates_per_collect=12`보다 작아, 스텝당 past-candles
요청은 항상 청크 1개로 완결된다(예산 경고 없음).

## Consequences

- E2E 재측정(/browse, 워크트리 :5174, 통합 1m 콜드 딥팬): 각 백필 스텝이
  `from=20260629&to=20260703`, `from=20260622&to=20260628`(각 5거래일 = 7캘린더일)를
  **한 요청**으로 발사 — 옛 코드라면 각 5개의 단일일 요청. 백엔드 날짜-병렬
  슬롯이 스텝당 5일을 동시 처리해 콜드 딥팬 총시간이 순차 대비 3~5배 단축.
- 첫 커밋 대기는 5거래일 배치의 병렬성 덕에 ~1.5~2.5초로 1일 스텝과 대등
  (첫 화면에 5일치가 한꺼번에 등장). 딥팬은 5거래일마다 점진 커밋.
- 부수 이득: 스텝(5일) < 청크 캡(15일)이라 스텝당 요청이 항상 1개 → 딥
  워크백의 placeholder 체인 단절 경로를 밟지 않아 `isExtending` 파생이 단순.
- 트레이드오프: 스텝당 요청 폭이 커져 스텝당 KIS 콜 수가 늘지만(5일 ≈ 30~45콜),
  청크 캡·계정 예산 안이라 EGW00201 위험은 청크 단위로 격리. 백엔드 유량 정책·
  쿨다운·WS 슬롯은 무변경.
- 되돌림/조정 손잡이: `STEP_TRADING_DAYS['1m'~'30m']`(현재 5)을 낮추면 스텝당
  병렬 슬롯 사용이 줄고 총시간이 늘며, 높이면(≤11거래일) 청크 캡까지 병렬성을
  더 쓴다. 첫 커밋 지연이 문제로 실측되면 이 값이 단일 손잡이.
