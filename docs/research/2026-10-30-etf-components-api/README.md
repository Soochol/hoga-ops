# 선정 ETF 구성종목 API 자동 수집 가능 여부

2026년 10월 30일, 선정 ETF 38개의 최신 구성종목을 같은 JSON 조회 경로로 자동 조회할 수 있음을 실제 호출로 확인했다. API 키·로그인·증권사 자격증명 없이 38개 모두 HTTP 200과 구성 목록을 반환했다. 이는 현재 시점의 기술적 조회 가능성 검증이며, 정기 수집 서비스나 브레스 계산 기능을 설치한 결과는 아니다.

## 확인 결과

| 검사 | 결과 |
|---|---|
| 선정 목록과 조회 대상 일치 | 38개 전부 일치 |
| HTTP 200과 비어 있지 않은 JSON 목록 | 38개 전부 통과 |
| ETF Code가 모든 응답 행에 일치 | 38개 전부 통과 |
| 종목 Code 이름 비중 기준일 제공 | 38개 전부 확인 |
| 선언한 구성 항목 수와 실제 행 수 | 38개 전부 일치 |
| 각 ETF 내 단일 기준일 | 38개 전부 2026년 10월 30일 |
| 전체 응답 행 | 795개 |
| 국내 증권 Code와 KR7 ISIN 형태의 행 | 757개 등록 행. ETF 간 중복 포함 |
| 그 밖의 행 | 원화현금 38개 |
| 비중 합계 범위 | ETF별 99.70%에서 99.96% |
| 음수 비중 항목 | 은행·헬스케어·태양광 ESS ETF의 현금 항목 3개 |
| 운용사 직접 JSON 표본 대조 | 3개 ETF의 주식 Code와 CU 수량 일치 |

`componentCount`와 행 수의 일치는 공급자가 선언한 목록이 응답에서 잘리지 않았다는 검사다. 운용사의 실제 전체 보유자산과 동일하다는 인증은 아니다. 현금·다른 펀드·파생 여부와 실제 국내 보통주 여부는 종목 마스터로 별도 확인해야 한다. 757개를 고유 종목 수로 해석하지 않는다.

## 공통 조회 경로와 필드

```text
GET https://stock.naver.com/api/domestic/detail/{ETF_CODE}/ETFComponent
```

[실제 확인한 반도체 ETF 조회 경로](https://stock.naver.com/api/domestic/detail/091160/ETFComponent)

| JSON 필드 | 의미와 처리 |
|---|---|
| `itemCode` | 조회한 ETF Code. 요청 Code와 행별 대조 |
| `componentItemCode` | 구성 종목의 Code. 문자열과 선행 0·영문을 유지 |
| `componentIsinCode` | 구성 자산의 ISIN. 현금과 증권 식별에 활용 |
| `componentName` | 구성 자산 이름 |
| `weight` | 공급자가 제공한 비중 문자열. 소수 정밀도를 보존 |
| `referenceDate` | 구성 기준일. API를 호출한 시각과 구분 |
| `componentCount` | 서비스가 선언한 구성 항목 수. 현금 포함 응답 행 수와 대조 |
| `cuUnitQuantity` | 설정단위 CU 기준 수량. 개인 보유수량이나 전체 펀드 수량으로 사용하지 않음 |
| `evalAmount` | 해당 구성 항목의 평가금액 원본값 |

종목 이름이나 검색어를 조합할 필요 없이 기존 ETF Code로 요청할 수 있다. 응답은 상위 10개에 제한되지 않았다. 예를 들어 KODEX 바이오는 현금 포함 51행, TIGER 의료기기는 50행이었다. 이번 검증은 최신 구성만 대상으로 했으며, 과거 날짜 선택 API·과거 전 기간 보유 이력·장기 호출 한도·계약상 가용성은 검증하지 않았다.

이 경로는 별도의 공식 OpenAPI 계약을 확인한 경로가 아니다. 웹 조회 경로의 변경·차단·응답 지연을 처리하는 설계가 필요하다. 기존 성공 스냅샷을 덮어쓰기 전에 Code·기준일·건수·필수 필드를 검증하고, 실패·빈 응답을 정상 편출로 처리하지 않는다.

## 운용사 직접 API 대조

공통 조회만으로 판정하지 않도록 서로 다른 운용사 3개의 동일 기준일 JSON을 실제 호출했다. 해당 3개는 구성 주식 Code 집합과 CU 수량이 모두 일치했다. 나머지 35개의 운용사 원본 대조까지 완료한 것은 아니다.

| ETF | 운용사 직접 경로 | 확인 |
|---|---|---|
| KODEX 반도체 091160 | `/api/v1/kodex/product/2ETF07.do`의 `pdf` | 22행과 기준일 제공. 주식 21개 Code·CU 수량 일치 |
| SOL 조선TOP3플러스 466920 | `/api/fund/pdfList?fund_cd=211028&work_dt=20261030` | 14행과 기준일 제공. 주식 13개 Code·CU 수량 일치 |
| PLUS K방산 449450 | `/api/v1/product/pdf/list?n=006192&page=0&d=20261030&pageSize=100` | 전체 11행. `totalElements=11`, 마지막 페이지 확인. 주식 10개 Code·CU 수량 일치 |

출처: [KODEX 직접 JSON](https://m.samsungfund.com/api/v1/kodex/product/2ETF07.do), [SOL 직접 JSON](https://www.soletf.com/api/fund/pdfList?fund_cd=211028&work_dt=20261030), [PLUS 직접 JSON](https://www.plusetf.co.kr/api/v1/product/pdf/list?n=006192&page=0&d=20261030&pageSize=100).

비중은 Code나 CU 수량과 구분해서 읽어야 한다. KODEX 화면은 현금성 자산·예금을 제외한 비중을 사용하므로 현금을 포함한 공급자 비중과 바로 대조하면 다르게 나온다. PLUS 원본은 소수 넷째 자리까지, 공통 조회는 소수 둘째 자리까지 제공했고, SOL에서도 표시 정밀도에 따른 0.01%p 차이가 있었다. 공통 조회 비중의 합계가 100%에 못 미치는 원인을 전 ETF에 대해 확정하지 않았으므로, 부족분을 현금이나 누락 종목으로 추정하거나 100%로 정규화하지 않는다. KODEX 은행의 현금 비중은 -0.20%, TIGER 헬스케어는 -0.16%, PLUS 태양광&ESS는 -0.06%였다. 원인을 확인하지 않은 채 0으로 바꾸지 않고, 주식 편입 여부와 현금 비중을 별도로 처리한다.

`PDF`는 이 맥락에서 Portfolio Deposit File이라는 자산 구성내역이다. 문서 파일 형식 PDF만을 뜻하지 않는다. 구성 바스켓과 실제 운용 보유내역이 항상 일치한다고 가정하지 않는다.

HANARO는 구성내역 화면·날짜 선택·엑셀 다운로드 조작을 확인했지만 직접 데이터 API는 호출하지 않았다. TIGER의 직접 운용사 API도 이번 대조에 포함하지 않았다. RISE 직접 페이지는 TLS 호스트명 검증에서 실패해 해당 경로의 검증을 중단했으며 TLS 검증을 끄지 않았다. 이들 ETF도 네이버 공통 API의 38개 전수 조회에는 포함돼 성공했다.

## 증권사 공식 API 검토

한국투자증권은 [공식 예제](https://github.com/koreainvestment/open-trading-api/blob/main/examples_llm/etfetn/inquire_component_stock_price/inquire_component_stock_price.py)에 ETF 구성종목시세 API를 제공한다.

- 경로: `/uapi/etfetn/v1/quotations/inquire-component-stock-price`
- TR: `FHKST121600C0`
- 요청: `FID_COND_MRKT_DIV_CODE=J`, `FID_INPUT_ISCD=ETF Code`, `FID_COND_SCR_DIV_CODE=11216`
- 응답: ETF 정보 `output1`, 구성종목 `output2`

이 경로는 문서 존재만 확인했고 실자격으로 호출하지 않았다. 따라서 38개 커버리지·구성 기준일·응답 상한은 미검증이다. 저장소 ADR-0136은 KIS 사용을 제한하므로 새 런타임 의존성으로 추가하는 결정과도 별개다.

키움 [공식 스펙](https://github.com/Kiwoom-Securities/Kiwoom-REST-API/blob/main/kiwoom/_data/kiwoom_api_spec.json)의 현재 ETF 분류 9개 API에서는 구성종목 목록을 찾지 못했다. `ka40002`는 ETF 자체의 이름·기초지수·과세유형 등이고, `ka90002`는 키움 테마의 구성종목이므로 ETF 바스켓으로 대체하지 않는다. 이 판단은 확인한 스펙의 범위이며 모든 향후 API의 부재를 뜻하지 않는다.

## 프로젝트 적용 판단

최신 구성 목록의 자동 수집은 현재 38개 모두 기술적으로 가능하다. 첫 구현에서는 공통 경로로 기준일별 응답을 보존하고, 운용사 직접 경로는 대조·복구 수단으로 확장하는 방식이 가능하다. 종목당 한 표의 브레스는 편입 종목 집합을 사용하고, 비중 가중 지표는 출처별 분모와 정밀도를 따로 정의해야 한다.

정기 실행을 붙이기 전에는 38개 운용사 원본 대조, 종목 마스터에 의한 자산 유형 확인, 날짜별 변경 감시와 실패 복구를 구현해야 한다. 현재 검증은 조회 가능성을 확인한 연구용 스냅샷이며 정기 실행·자동 주문·앱 데이터 갱신을 추가하지 않았다.

## 증거 파일과 검증

| 파일 | 내용 |
|---|---|
| `probe-results.json` | 38개별 URL·HTTP 상태·기준일·건수·비중 합계·응답 해시 |
| `responses/*.json` | 공통 API 38개의 실제 응답 바이트 |
| `issuer-probes.json` | 운용사 3개 표본 대조와 미검증 경로 |
| `issuer-responses/*.json` | 운용사 표본 응답. KODEX는 구성내역과 상품 정보만 추출 |
| `broker-api-review.json` | 증권사 공식 스펙 검토. 실호출과 구분 |
| `probe_components.py` | 자격증명 없는 직렬 조회 도구. 호출 시작 간격 최소 0.5초 |
| `validation.json` | 오프라인 재검사·입력과 출력 해시·스크립트 검사 결과 |

`probe_components.py`는 현재 공개 응답을 조회하며, 기존 응답이 있으면 덮어쓰지 않고 중단한다. 새 조회는 `--output-dir`로 별도 디렉터리를 지정한다. 운영 수집기로 등록된 도구가 아니다.
