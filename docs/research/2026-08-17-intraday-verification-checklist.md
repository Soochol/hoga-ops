## 0. 공통 전제 — 이걸 안 맞추면 8개가 전부 공허하게 통과한다

| # | 전제 | 확인 명령 |
|---|---|---|
| 0-1 | **거래일**이고 장중(09:00–15:30 KST) — 시계만 보면 안 된다, 아래 0-C | `TZ=Asia/Seoul date` + 0-C |
| 0-2 | :5173 이 **Vite dev 서버** (프로덕션 빌드엔 DEV 전역이 없다) | `curl -s localhost:5173/src/live/incrementalPeakWallSource.ts \| head -1` → `"DEV": true` 치환이 보임 |

**0-A. 실제 서빙 PID를 먼저 잡는다.** `uvicorn --reload` 는 부모/자식 구조라 로그의 `pid=` 는
**자식**이다. 부모 PID로 grep 하면 0줄이 나오고 그걸 통과로 오독한다.

```bash
ss -ltnp | grep ':8000 ' | grep -o 'pid=[0-9]*' | cut -d= -f2 | sort -u
```

**0-B. 라이브 스트림이 실제로 흐르는지 먼저 판별한다.** 무자격이면 `ob` 가 0건이고,
항목 1·7·8 이 **무측정을 통과로 위장**한다.

```bash
curl -s "http://127.0.0.1:8000/api/live/series?code=005930&date=$(TZ=Asia/Seoul date +%Y%m%d)&venue=KRX" | python3 -c 'import json,sys; d=json.load(sys.stdin); s=d.get("snapshots",[]); print("snapshots:", len(s))'
```

`snapshots: 0` 이면 여기서 멈춘다. 0 이 아니면 그 값이 **항목 8의 눈금**이 된다(하드캡 360).

**0-C. 「연결됨」과 「틱이 온다」는 다른 사실이다 — 이걸 구별하는 것이 0-1 의 실체다.**

WS 가 붙어 있고 구독이 acked 이고 프레임이 매초 들어와도, **휴장이면 틱은 0건**이다.
판별식은 `last_tick_ms` 다(`last_recv_ms` 가 아니다 — 그건 하트비트로도 갱신된다).

```bash
curl -s 'http://127.0.0.1:8000/api/live/status' | python3 -c '
import json,sys
kw=json.load(sys.stdin)["kiwoom"]
print("connected_accounts:", kw.get("connected_accounts"), "/ subscribed:", kw.get("subscribed_count"))
print("last_tick_ms:", kw.get("last_tick_ms"), "  <-- None 이면 틱 0건")
print("per-account last_tick_ms:", [a.get("last_tick_ms") for a in kw.get("accounts", [])])
'
```

지수 시세로 교차 확인한다 — 장이 열렸으면 가격이 있다:

```bash
curl -s 'http://127.0.0.1:8000/api/live/index-quotes' | head -c 300
```

> **실사용 기록 (2026-08-17 13:47 KST, 이 문서의 첫 적용).**
> 시계상 장중이었고 0-1 을 통과했으나 **0-B 에서 `snapshots: 0` 으로 걸렸다.** 원인은 휴장이다:
> WS 5계좌 전부 `connected`, 297 구독 `acked`, `kicked_by_peer: false`, `last_recv_ms` 1초 전인데
> **전 계좌 `last_tick_ms = null`**, `/api/live/series` 는 빈 배열, `ask_peak_today: null`,
> 지수 시세는 `t_ms` 만 있고 **가격이 없다**. 거래일 오버레이
> (`~/.local/share/hoga-ops/data/calendar/trading_days.txt`)도 **2026-08-14(금)에서 멈춰 있다**.
> 토큰 킥(#1088)이 아니고(8005 로그 0건, `kicked_by_peer: false`) 병행 e2e 탓도 아니다.
> **2026-08-17 이 공휴일(휴장)임은 사용자가 확인했다.** 위 신호들은 전부 그 결과다.
>
> 운영상 결론은 사유와 무관하다: **틱이 0건이면 항목 1·3·7·8 은 성립하지 않는다.**
> 그래서 0-C 의 판별식은 「휴일인가」가 아니라 **「틱이 오는가」** 다 — 달력을 몰라도,
> 임시 휴장·시스템 장애·자격증명 문제처럼 **사유가 무엇이든** 같은 신호로 걸린다.
>
> **이 문서의 0-B 가드가 첫 실사용에서 위양성을 막았다.** 그대로 진행했다면 항목 7 의
> `total: 0` 과 항목 8 의 「가볍다」를 **무측정 상태에서 통과로 기록**했을 것이다.

## 1. 지표 ON 에서 최대벽·매물대가 그려지는가 (#1345)

**왜.** #1345 는 토글 OFF 일 때 `live.ob`/`live.trade` 대신 빈 배열을 넘긴다. OFF 쪽 이득은
이미 얻었고 남은 위험은 **반대 방향** — 켰는데도 안 그려지는 것. 이 실패는 **조용하다**:
그려지는 것이 전부 canvas primitive 라 **DOM·레전드에 흔적이 없다.**

**전제.** 차트 창이 **주식**(지수는 토글 자체가 없음) + **분봉**(D/W/M 이면 안 그려지는 게 정상).
세 지표의 공장 기본값은 **전부 OFF** — 처음에 안 보이는 건 버그가 아니다.

**재현.**
1. 차트 창 **헤더 오른쪽**의 「보조지표」 버튼(`data-testid="live-indicators-button"`). 전역 툴바가
   아니라 **창 헤더**다 — 드로어는 그 버튼을 누른 창을 편집한다.
2. 「10호가 지표」 그룹 → **「당일 최대벽」** 행 오른쪽 체크 아이콘(`aria-label="당일 최대벽"`).
   이 하나가 매도·매수를 **함께** 켠다.
3. 같은 그룹 **「당일 최대 매물대」** 도 켠다.
4. 배선부터 확인: `JSON.parse(localStorage['live.indicators.v2']).byTimeframe.minute`

**통과 기준.**
- 저장: `askPeakEnabled`·`bidPeakEnabled`·`tradeVolumePocEnabled` 세 키가 `minute` 안에 **존재**
  (sparse 저장이라 공장값과 같으면 안 적힌다 → true 만 나타남).
- 화면: 캔들 pane 에 **거래일마다 수평 세그먼트**. 매도 파랑 `#1D4ED8`(두께 2), 매수 빨강
  `#DC2626`(2), 미체결 주황 `#F97316`(1), **보이는 영역 최대 1개는 노랑 `#EAB308`(3)**.
  각 선 오른쪽 끝에 **잔량 칩**. 매물대는 같은 pane 의 가로 밴드(보라 알파 0.12).
- 매물대가 어두우면 상세 패널에서 **투명도를 40%** 로 올려 확인 후 되돌린다.

> ⚠ **파랑이 0 이어도 실패가 아니다.** 보이는 영역 최대 1개 세그먼트는 새 선이 아니라
> **기존 선을 노랑으로 재색칠**하는 것이라, 하루만 보고 있으면 파랑이 통째로 노랑에 흡수된다.

**실패 의미.**
- 저장이 비었다 → 토글 클릭이 안 먹은 것(#1345 회귀 아님). 상세 패널의 `settings-toggle-*` 는
  **행 wrapper 의 testId** 라 스크립트로 그걸 누르면 무동작이다.
- 저장은 true 인데 안 그려진다 → **셋 다** 안 나오면 `cb.segments` 가 빈 것(= `/api/range` 문제).
  캔들·세그먼트는 정상인데 **벽만** 없으면 **#1345 회귀 본체**. 판별식은 네트워크 —
  `ask_peaks_enabled=true` 요청이 나갔는가(나갔으면 fetch 게이트만 켜진 비대칭).

## 2. 창 여러 개에서 드래그가 가벼워졌는가 (#1348)

**왜.** `rectOf` 가 호출마다 새 rect 객체를 내서, 드래그에 **참여하지 않는** 창까지
pointermove(≈60Hz)마다 재렌더됐다. `/live` 에서 그 서브트리는
`ChartWindowInner → useLiveChartData → LiveChartRoot` 라 창 수에 비례한다.

**전제.**
- 드래그 대상 창을 **먼저 클릭해 포커스**시킨 뒤 드래그 — 안 그러면 pointerdown 의
  `focusWindow` 가 zOrder 를 바꿔 **1회짜리 전 창 재렌더**가 결과에 섞인다.
- 링크 그룹 팔레트는 **닫고** 시작(`onDragStart` 가 닫으면서 `itemCtx` 신원이 1회 바뀐다).

**재현.** 창을 6개로 늘리고, **차트가 아닌 창**(예: 프로그램 창)을 끌면서 Performance 녹화.

**통과 기준 (가장 강한 판별식).**
> `pointermove` **Event task 의 자손으로** `ChartWindowInner`/`LiveChartRoot`/`useLiveChartData`
> 프레임이 **0건**. 그 task 안엔 `WorkspaceCanvasCore → computeMove → 드래그한 창 하나`만 보여야 한다.

⚠ 장중엔 WS 틱이 **별도 task**에서 `LiveChartRoot` 를 계속 돌린다. 판정 문구는
"프로파일에 `LiveChartRoot` 가 없다" 가 **아니라** "**`pointermove` task 밑에** 없다" 이다.
이 구별을 놓치면 정상을 실패로 읽는다.

**보조 정량.** 창 6개의 프레임 `p95` 가 창 2개와 **같은 급**. 핵심은 절대값이 아니라 **기울기** —
창 수를 3배로 늘렸는데 비례해 늘지 않는 것이 통과다.

## 3. 콜드 종목 첫 방문에 「지표 불러오는 중…」이 뜨는가 (#1348)

**왜.** 홀드 게이트는 `!isHogaLoading && !isSidecarLoading` 인데 문구 게이트는 `isHogaLoading`
만 봤다. 그 차집합이 **커버는 떠 있고 글자는 없는** 구간이고, 사이드카는 호가보다 두 자릿수
느리다(감사 실측 콜드 4.68s, 한 달 창 11.7s).

**전제.** `/live` 차트 창 **한정**(`/study` 는 이 프롭을 안 넘긴다). **지수 창은 제외**(강제 차단).
분봉 + 사이드카 지표 1개 이상 ON(또는 같은 그룹에 매물대·프로그램 창이 열림) + 캐시 콜드.

**재현.** 오늘 한 번도 안 본 종목을 고르고, 전환 직후를 관찰.

**통과 기준.**
- 커버(`chart-reveal-cover`)가 `opacity: 1` 인 동안 `hoga-loading-note` 가 보이고 텍스트가
  정확히 `지표 불러오는 중…`.
- Network 에 `mode=sidecar` 요청 1건, 그 완료 시각 ≈ 문구 사라지는 시각.
- **음성 대조군**: `D` 봉에서는 문구가 뜨지 않고 `mode=sidecar` 요청도 없다.

**실패 의미.** 커버는 뜨는데 문구가 없다 → #1348 회귀. 커버 자체가 안 뜨면 캐시가 웜이라
구간이 없는 것(88ms — 눈에 안 띈다). 공장 기본값 사용자는 **애초에 발생하지 않는다.**

## 4. `/api/live/status` 카나리아 — slow-log 에 0줄인가 (#1350)

**왜.** 루프 기아가 남아 있으면 **무관한 라우트**가 느려진다. 이 라우트는 원리적으로 2초를
넘을 일이 없어 카나리아로 쓸 수 있다.

**⚠ 전제가 이 항목의 절반이다.** 브라우저에 `/heatmap`(또는 관심종목)이 **열려 있어야** 296종목
`/api/live/quotes` 가 돌고, 그래야 #1350 이 고친 경로가 실행된다. 안 열려 있으면 카나리아가
**공허하게 초록**이다.

```bash
PID=$(ss -ltnp | grep ':8000 ' | grep -o 'pid=[0-9]*' | cut -d= -f2 | sort -u | head -1)
grep "$(TZ=Asia/Seoul date +%Y-%m-%d)" ~/.local/share/hoga-ops/logs/hoga.log \
  | grep "pid=$PID" | grep 'path=/api/live/status' | grep 'slow=1'
```

**통과: 출력 0줄.**

**red-check 먼저.** 위 grep 이 정말 무언가를 잡는지 확인하려면 `path=/api/live/status` 를
`path=/api/range` 로 바꿔 본다 — 비장중에도 다수 잡힌다(실측 최대 19,914.8ms). 0줄이면
로그 회전(10MB × 5)으로 밀린 것이지 통과가 아니다.

> **이 카나리아의 한계.** 0줄은 **「2초급 기아 없음」만** 말한다. 250ms~2초 구간은 원리적으로
> 못 본다 — 그건 항목 6이 본다.

> **덮이지 않는 절반.** `/api/live/tab-metrics` 는 **프론트 호출자가 0건**이다(전수 grep 확인).
> 즉 브라우저 트래픽은 `/api/live/quotes` 만 태우고, #1350 이 고친 두 라우트 중 **절반은 이
> 카나리아로 확인되지 않는다.**

## 5. 아침 첫 시세 폴링에 콜드 폭발이 없는가 (#1350)

**왜.** 기준가 캐시 키가 `(code, today)` 라 **KST 날짜가 바뀌면 전 종목 캐시가 무효화**된다.
종전엔 그 첫 폴링이 296종목 × 종목당 쿼리 1건 ≈ **1.9초** 동안 루프를 멈췄다.

**⚠ 오늘(08-17) 아침 첫 폴은 이미 지나갔고 사후 검증이 불가능하다** — `HOGA_PERF_DEBUG` 가
꺼져 있고 2000ms 임계에도 안 걸렸다. 다만 **09:51:22 에 서버가 재시작**돼 캐시가 한 번 더
콜드가 됐으므로, 그 시각 근처 로그가 대체 표본이 될 수 있다.

**재현(내일 아침 또는 서버 재시작 직후).** `/heatmap` 을 연 상태에서 `body_bytes` 가 가장 큰
`/api/live/quotes` 계열의 **첫 줄 duration_ms** 를 뒤 3~5줄과 비교한다.
(쿼리 문자열로는 계열을 못 고른다 — 로그가 200자에서 자른다.)

**통과 기준.** 첫 줄이 뒤 줄 대비 **1.5~2.5초급 초과를 보이지 않을 것.**
수백 ms 더 큰 것은 **정상**이다 — DuckDB 인스턴스가 이 parquet 을 처음 만지는 메타데이터
파싱(오늘 실측 콜드 248.2ms vs 웜 25.6ms) + 벤더 첫 호출.

**대조용 실측(오늘, 실코퍼스 133.9MB / 실히트맵 296코드).** 배치 1쿼리 콜드 **248.2ms** ·
웜 **25.6ms**. 종전 종목별 경로는 30코드 194.9ms → 296 환산 **약 1,923ms**.

## 6. `hoga_perf loop_lag` 가 조용한가 (#1354)

**왜.** 경보가 흔하면 사용자가 무시하기 시작하고, 그러면 장치가 죽는다. "조용한가" 가
인수 조건인 이유다.

**전제.** 프로브가 실제로 등록됐는지 먼저:

```bash
curl -s 'http://127.0.0.1:8000/health?deep=1' | python3 -c 'import json,sys; print([t for t in json.load(sys.stdin).get("supervised_tasks",[]) if t["name"]=="loop-lag-probe"])'
```

→ `[{'name': 'loop-lag-probe', 'running': True, 'state': 'running'}]` (오늘 실측 확인)

행이 **없으면**(dead 가 아니라 부재) 프로브가 등록조차 안 된 것이라 아래 grep 의 0건은
아무 의미가 없다.

```bash
grep "$(TZ=Asia/Seoul date +%Y-%m-%d)" ~/.local/share/hoga-ops/logs/hoga.log | grep 'hoga_perf loop_lag'
```

**통과 기준 — 오늘 실측에서 끌어낸 기준선:**

| 상태 | 실측 | 판정 |
|---|---|---|

## 7. 폴백 카운터 — 「0에 머무는가」는 **틀린 기준이다** (#1357)

**왜.** #1357 의 슬라이딩 축출은 판정이 모호해지는 입력에서 전량 재소비로 **폴백**한다.
폴백은 **결과가 옳으므로 완벽하게 조용하다** — 실데이터가 t_ms 중복을 자주 만들면 이
최적화가 프로덕션에서 통째로 무효인데 아무도 모른다.

```js
window.__peakWallFallbacks?.() ?? 'MISSING'
```

**전제.** DEV 빌드 + `/live` 로드 + **분봉 + 최대벽 토글 ON**.
⚠ 토글이 꺼져 있으면 `obLength` 가 0에 머물러 폴백이 **원리적으로 한 번도 안 세어진다** —
그 상태의 0은 "잘 돈다"가 아니라 **"코드가 한 번도 안 돌았다"** 는 뜻이다.

**통과 기준은 세 갈래다.** `{ total, byReason: { "buffer-replaced", "t-ms-collision", "touch-out-of-order" } }`

| 구간 | 기준 |
|---|---|
| **red-check** (종목을 한 번 바꿔 본다) | `buffer-replaced` 델타 **> 0** — 안 오르면 카운터가 안 물린 것이고 **이후의 0은 아무것도 증명하지 않는다** |
| **정지 구간** (15분 방치, 아무것도 안 건드림) | 세 사유 **전부 델타 0** |
| **세션 전체** | `t-ms-collision` · `touch-out-of-order` **누적 0** ← **이 둘이 진짜 판별식** |

> 제가 앞서 "0에 머무는가"라고 한 것은 **부정확했다.** `buffer-replaced` 는 종목 전환·봉 전환·
> 토글 OFF 마다 **정상적으로** 오르므로 절대량에 의미가 없다.

**`undefined` 는 실패가 아니라 세 번째 상태다** — `/live` 가 아니거나 프로덕션 빌드다.

**실패 의미.**
- `t-ms-collision > 0`: 서로 다른 ob 스냅샷이 같은 `price:t_ms` 를 만들었다. **한 번 뜨는 것과
  계속 오르는 것은 다른 사실** — sticky 는 누적 상태에만 걸려 충돌 쌍이 15분 창을 벗어나면
  슬라이딩이 저절로 재개된다. **계속 오르면** 키 설계를 바꿔야 한다(t_ms 대신 스냅샷 순번).
- `touch-out-of-order > 0`: 체결 틱이 시간 역순으로 도착했다. 키움 WS 프레임 순서 또는
  `item.t_ms` 부재 시 폴백 규칙이 원인 후보.
- 정지 구간에 `buffer-replaced` 가 오른다: 조작이 없었는데 tail 참조가 사라졌다.
  후보 — 탭 백그라운드 중 버퍼 슬라이드, `/api/live/series` 재hydrate, venue 자동 전환.

## 8. 15분 이상 열어 둬도 가벼운가 (#1357)

**왜.** 종전 증상은 **"열어 둘수록 무거워지고 새로고침하면 한동안 괜찮다"** 였다. 프론트 버퍼가
15분 창을 다 채워 **앞을 자르기 시작한 순간부터** 매 flush(150ms)마다 창 전체를 재소비했다.

**전제.** 항목 7이 **먼저** 통과해야 한다 — 폴백이 걸리면 개선분이 0이라 항목 8도 안 좋아진다.
그리고 **활발한 종목**으로 잴 것(1 ob/s 구간은 수정 전에도 12.5ms/flush 라 판별력이 없다).

**재현.**
1. 활발한 종목 + 분봉 + 최대벽 ON. 30초 안정 후 `__peakWallFallbacks()` **T0 기록**.
2. **15분 방치** — 새로고침·종목 전환·venue 전환·토글을 **하지 않는다**(전부 정당한 폴백을 만든다).
3. 델타 확인 + 30초 간격으로 두 번 더 읽어 증가하지 않는지.
4. Performance 10초 녹화(크로스헤어 좌우 + 팬/줌) → Bottom-Up 에서 `consumeOb`·`accumulate`·
   `classify` self time. dev 서버는 원본 ESM 이라 함수명이 그대로 보인다.
5. **교대 대조**: 그 직후 새로고침하고 30초 안에 같은 동작 반복.

**통과 기준.**
- **핵심**: `total` 의 15분 델타 = **0**.
- 10초 녹화에서 세 함수 self time 합계가 **수십 ms 급**(1% 미만). 150ms 주기로 반복되는
  long task 가 **없다**. (수정 후 벤치 상한 눈금: 18,000 버퍼 × 3.42ms × 67 flush ≈ 230ms)
- **정성**: 20분째 체감이 **새로고침 직후와 구별되지 않는다** ← 종전 판별식의 역방향 확인.

**눈금.** 0-B 의 `snapshots` 값(하드캡 360)과 span 으로 ob/s 를 구해 감사 표의 어느 행인지 본다:

| 15분 버퍼 | 수정 전 flush 당 |
|---:|---:|
| 900 | 12.5 ms |
| 1,800 | 18.9 ms |
| 4,500 | 54.4 ms |
| 9,000 | 124.8 ms |
| 18,000 | 309.8 ms |

**수백 급이면 절감량이 작아 4·5단계 체감 차이가 미미한 것이 정상이다.**

| **키움 WS 틱 수신이 이벤트 루프 위에서 동기 처리** | ✅ **`active+gil`** |

`_dispatch`(`kiwoom_ws_client.py:453-457`)가 파싱된 틱마다 `await self._on_tick(tick)` 을
**순차로** 부르고, `on_tick` 은 `async def` 지만 본문이 **순수 동기 CPU 작업**이다 —
`_ingest_ask_peak` · `_ingest_bid_peak` · 10레벨 × 2 순회 · `_is_continuous_book` ·
`monitor.ingest_orderbook`. 297종목 구독에 종목당 16 ob/s 면 개장 직후 초당 수천 틱이
이 경로를 지난다.

### 증거 셋이 서로를 지지한다

1. 덤프의 `active+gil` 이 정확히 그 스택
2. loop_lag 가 **09시 162건**으로 개장 직후(틱 유량 최대)에 집중
3. `to_thread` 워커 전부 idle → GIL 경합 후보에서 배제

### 왜 감사가 못 봤나

감사 레인 C 는 **라우트**를 훑었다(88곳의 `to_thread` 규율 확인). **WS 수신 경로는 라우트가
아니라 후보에 오르지도 않았다.** 그래서 "진짜 병목은 `to_thread` 안쪽" 이라는 레인 C 의
결론도 이 자리는 못 봤다. **#1354 의 프로브가 없었으면 지금도 몰랐을 자리다.**

### 남은 것

- **통계 확인**: 단일 샘플이다. 발화가 몰리는 개장 직후에
  `py-spy record --pid <PID> -d 30 -o /tmp/hoga-gil.svg --idle` 로 상위 보유자를 확정할 것.
- **수정은 설계가 먼저다.** 선택지가 여럿이고(배칭 / 집계만 `to_thread` / 틱 스로틀 /
  시그널 모니터 분리), 실시간 수집 경로는 이 앱의 심장이라 **장중 변경은 금물**이다.
- 이 발견은 **이번 세션 PR 과 무관**하다 — 손대지 않은 경로이고 프로브가 드러냈을 뿐이다.
