# 과거 스크롤 최대벽 표시 지연 개선

기준 커밋: `2f4c71818`. 측정일: 2026-09-06~07. 사용자 보고는 과거 구간에서
캔들보다 최대벽 표시가 늦게 채워지는 현상이다.

## 확인한 병목

실행 중인 서버에 삼성전자 20260824~20260828, KRX 1분봉을 요청했다.
최대벽 측정에서는 다른 sidecar 지표를 껐다. 이는 HTTP 응답 시간이며
스크롤 입력부터 브라우저 페인트까지의 시간은 아니다.

| 소스 | 캔들 | 최대벽 첫 요청 | 최대벽 재요청 |
| --- | ---: | ---: | ---: |
| 기본 kiwoom_live | 123ms | 546ms | 149ms |
| hogaplay 지정 | 138ms | 1,680ms | 301ms |

당시 저장된 1분 `ask_peak` 캐시 21,685개 중 v12 20,563개, v14 19개,
v15 1,103개였다. 약 95%가 현재 v15와 달라 재계산 대상이었다.
9/5 봉별 계열 추가에 따른 버전 변경은 필요한 무효화이므로 되돌리지 않는다.

## 변경

- `peak_prewarm.prewarm`: 관심종목을 먼저 처리하고 각 그룹 안에서는 최신 날짜부터
  계산한다. 관심종목을 채운 뒤 남은 예산은 나머지 종목에 쓴다. 날짜·종목 필터,
  오늘 제외, 기존 계산 건수 상한은 유지한다. 일일 스케줄러와 CLI가 같은 정책을 쓴다.
- `_peak_scalar`: 최대 잔량 후보를 먼저 추려 동률 후보만 정렬한다.
- `_peak_bar_max_sequence`: 봉별 최대 잔량을 집계해 추린 뒤 동률 후보만 정렬한다.
  순위 키 `qty DESC, intra_ms ASC, seq ASC, price ASC`와 동일분 터치 판정은 유지한다.
- `usePeakWallRender`: 봉별 모드에서 세 계열의 계단용 세그먼트 계산을 생략한다.
  캔들 오버레이는 계속 계산하며, 계단 모드로 돌아가면 계단 입력을 다시 계산한다.

반환값과 캐시 스키마가 같으므로 캐시 버전을 올리지 않는다.

## 알고리즘 비교

같은 프로세스에서 기준 커밋의 두 함수와 변경 함수를 교대로 교체해 실제
`query_day_ask_bid_peak_dual_with_rep`를 실행했다. 각 조합의 첫 실행을 제외한
5회 중앙값이다. 순서는 매 회 뒤집었다. 원본 parquet을 계산하는 경로이며,
최대벽 결과 캐시는 사용하지 않았다. 소스는 hogaplay, 해상도는 1분이다.

| 날짜 / 종목 | 기존 | 변경 | 감소 |
| --- | ---: | ---: | ---: |
| 20260623 / 000660 | 391.7ms | 342.9ms | 12.5% |
| 20260904 / 005930 | 596.0ms | 546.8ms | 8.3% |
| 20260904 / 287840 | 164.1ms | 139.0ms | 15.3% |

모든 반복에서 매도·매수 반환 객체가 기존과 같았다. rep 행도 중복 수를 포함한
전체 값이 같았다. 같은 스냅샷의 여러 가격 행 순서는 원래부터 고정되어 있지 않으므로
rep 배열은 멀티셋으로 대조했다. 일자별 서버 부하에 따른 변동이 있어 이 수치는
브라우저 표시 속도의 개선율을 보장하지 않는다.

## 검증

- 수정 전 관심종목 우선순위 테스트와 봉별 모드의 계단 생략 테스트가 각각 실패함을 확인.
- 수정 후 관련 백엔드 300개 통과, 실데이터 선택 실행 테스트 1개 생략,
  wallclock 테스트 1개 제외. 독립적인 단순 구현과 비교하는 최대벽 oracle 포함.
- 프론트 전체 Vitest, 앱·테스트·E2E TypeScript 검사, Vite 빌드 통과.
- 저장소 전체 Ruff 통과.

## 공유 저장소의 캐시 갱신

기존 배치 상한 2,000건으로 실제 `prewarm`을 실행했다. 범위는 KRX의 hogaplay와
kiwoom_live이며, 관심종목 87개를 우선 처리했다. 421.7초 동안 2,000개
(종목·날짜·소스) 캐시를 새로 채웠고 748개는 이미 유효해 건너뛰었다.
실패는 0건이었다. 다음 대상에서 상한에 도달해 중단했으므로 전체 과거 구간이
모두 채워진 것은 아니다. 남은 구간은 이후 배치 또는 최초 조회에서 채운다.

공유 저장소의 갱신된 캐시는 실행 중인 서버도 사용할 수 있다.
