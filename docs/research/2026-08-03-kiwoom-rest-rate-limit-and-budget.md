# 키움 REST 유량 실측과 백필 예산 — 유량은 **TR별 5 req/s**

- 티켓: [#1015](https://github.com/Soochol/hoga-ops/issues/1015) (지도 [#1005](https://github.com/Soochol/hoga-ops/issues/1005))
- 조사일: 2026-08-03 · 실계좌 프로브(`scripts/probe_kiwoom_rest_tr.py`)
- 성격: 실측 + 예산 계산. 메커니즘은 [#1011](https://github.com/Soochol/hoga-ops/issues/1011) 이 확정했고 **이 문서는 수치와 그로 인한 교정**을 담는다.

## 한 줄 결론

**유량 = TR(API ID) 당 5 req/s.** 벤더가 429 응답에 수치를 직접 적어 보낸다. **TR 간에는 독립**이라 한 TR 이 한도에 걸려도 다른 TR 은 즉시 통과한다.

귀결: **분봉 팬이 20~50배 빨라진다**(회귀가 아니라 개선). 그리고 #1011 이 정한 거버너 단위 "앱키당 워커" 는 **TR별 버킷**으로 교정된다.

---

## 1. 상한 — 벤더가 알려준다

점진 탐색(첫 에러에서 중단):

| 페이싱 | 실효 속도 | 결과 |
|---|---|---|
| 0.3 s | ~3.3 req/s | 10페이지 에러 0 · 지연 30~172 ms |
| 0.15 s | ~6.7 req/s | 12페이지 에러 0 · 지연 22~116 ms |
| 0.05 s | ~20 req/s | 12페이지 에러 0 · 지연 27~70 ms |
| **0 s** | 무제한(직렬 왕복) | **8~11페이지째 HTTP 429** |

```
HTTP 429
{"return_code":5,
 "return_msg":"허용된 요청 개수를 초과하였습니다
   [1700:허용된 API 요청 개수를 초과하였습니다. 유량=5, API ID=ka10080]"}
```

**`유량=5` 와 `API ID=ka10080` 이 응답에 그대로 들어 있다.** 상한을 추정할 필요가 없다.

> 페이싱을 걸었을 때 20 req/s 로 계산되는데도 통과한 것은 요청이 **직렬 왕복**이라 실제 발사 속도가 `1/(pace+latency)` 이기 때문이다. 0.05 s + 40 ms ≈ 11 req/s 로 보이지만 버킷은 초 단위 윈도로 재므로 버스트가 5를 넘지 않는 구간이 있었다. **정확한 상한은 벤더가 준 `5` 를 쓴다.**

## 2. TR 간 독립 — 실증

`ka10080` 을 429 까지 밀어붙인 **직후, 대기 없이** 다른 TR 을 호출했다:

```
ka10080: page 11: HTTP 429 ... 유량=5, API ID=ka10080
    ↓ 즉시
ka10081: ✔ return_code=0, rows=600, 47.3 ms
```

**유량은 TR(API ID)별로 독립이다.** 12개 TR 을 쓰면 창구가 12개인 셈이다.

## 3. 실패 형태 — **HTTP 레벨이다, `return_code` 봉투가 아니다**

이건 seam 설계에 직접 영향을 준다. 다른 모든 오류(경로 불일치 `1504`, 필수 파라미터 `1511`, 인증 누락 `1513`)는 **HTTP 200 + `return_code != 0`** 으로 온다. 유량 초과만 **HTTP 429** 다.

조사 중 실제로 이 함정을 밟았다 — 프로브가 `return_code` 만 보고 요약해서, 429 로 중단된 것을 "8페이지에서 커서가 끝났다" 로 잘못 읽었다. **에러 분류기는 HTTP status 와 `return_code` 두 축을 모두 봐야 한다**(#1011 에러 모델).

## 4. 예산 재계산

측정값: 분봉 900행/페이지(#1008) · 일봉 600행/페이지 · 유량 TR당 5 req/s.

| 작업 | 계산 | 결과 |
|---|---|---|
| 분봉 팬 1스텝(5거래일) | 5 × 390분 ÷ 900 ≈ 3콜 ÷ 5/s | **0.6 초** |
| 46거래일 팬 전체 | 46 × 390 ÷ 900 ≈ 20콜 ÷ 5/s | **4 초** |
| 스크리너 일봉 백필 | 2,718종목 × 2벌(수정/원) × 1콜(600행 = 2.4년) ÷ 5/s | **≈18 분** |

**ADR-0120 실측 대조**: 분봉 팬 스텝당 11~29초 · 46거래일 팬 98초. → **20~50배 개선.**

두 요인이 곱해진다:
1. `base_dt` 랜덤 액세스로 **순회 자체가 사라진다**(#1008) — O(D²) → 목표 구간 직접 조회
2. 유량이 1 req/s(ADR-0120 의 보수 페이싱)가 아니라 **5 req/s**

즉 지도가 우려하던 "성능 회귀를 얼마나 감수할 것인가"(#1012)는 **회귀가 아니라 개선**으로 뒤집힌다.

## 5. #1011 거버너 단위 교정

#1011 은 **"단일 우선순위 큐 + 앱키당 워커"** 로 정했다. 실측이 단위를 바꾼다:

| | #1011 결정 | 교정 |
|---|---|---|
| 유량 버킷 단위 | 앱키당 | **TR(API ID)당 5 req/s** |
| 병렬도 | 앱키 수 | **동시에 쓰는 TR 수** (앱키 1개 기준) |

**큐·우선순위·중복제거 구조는 그대로 유효하다** — 바뀌는 것은 "무엇이 게이트인가" 뿐이다. 워커가 몇이든 **TR별 토큰 버킷**이 발사를 막는다.

앱키 축은 사라지지 않는다. 앱키가 늘면 버킷 키가 `(앱키, TR)` 이 될 수 있으나 **앱키당 독립 여부는 미검증**이다(아래).

## 6. 결정 — 앱키 증설하지 않는다 (사용자 확정 2026-08-03)

TR당 5 req/s 로 계산한 예산이 현행 대비 **열위가 아니라 개선**이므로 지금 증설하지 않는다. 필요가 실증되면 그때 늘린다 — #989 가 dev 키에 쓴 것과 같은 문법이다.

**대가**: 앱키당 유량 독립 여부가 미검증으로 남는다. 앱키가 1개뿐이라 실험 자체가 불가능했다.

## 7. 만석 정책

WS 의 "만석 = 신규 차단 + 알림"(#685)과 달리 REST 는 **큐에서 대기시키면 된다** — 429 는 영구 거절이 아니라 초 단위 백오프로 해소된다. 벤더가 `유량=5` 를 알려주므로 버킷을 정확히 맞추면 429 자체를 거의 만들지 않는다.

429 를 만났을 때의 거동(백오프 폭·재시도 횟수·`user_visible` 우선 양보)은 #1011 의 `error_policy` 재사용 결정에 따라 기존 정책 기계에 태운다.

## 미측정 · 유의

- **앱키당 독립 여부** — 앱키 1개라 실험 불가. 증설 시 최우선 확인 항목.
- **`유량=5` 가 모든 TR 에 동일한지** — `ka10080` 응답에서만 확인했다. TR 마다 다를 수 있다(순위·마스터처럼 무거운 TR 은 더 낮을 가능성).
- **버킷 윈도의 정확한 형태**(고정 1초 vs 슬라이딩)를 재지 않았다. 보수적으로 5 req/s 페이싱을 쓰면 무관하다.
- 스크리너 백필 예산은 **1콜/종목(600행=2.4년)** 가정이다. 실제 요구 기간이 더 길면 콜 수가 비례한다.
- KIS 측 비교 수치는 ADR-0120 의 실측을 인용한 것이고 이번에 재측정하지 않았다.
