# /live 분봉 cold 로딩 — 우선순위별 후속 검증

2026-09-07. [최초 조사](./2026-09-07-live-minute-cold-load.md)의 5개 우선순위를 검증했다.
제품 코드는 변경하지 않았다. 아래 수치는 실측, 격리 실험, 모의 입력 검증을 구분해서 읽어야 한다.

## 판정

| 우선순위 | 검증 결과 | 다음 개선 판단 |
|---|---|---|
| 1. 키움 수집 내부 | 연결을 재사용해도 응답 본문 수신 중 약 1초 공백이 발생한다. 수신 TCP out-of-order 카운터도 증가했다. | 외부 응답 수신 경로의 지연이 확인됐다. 원래 서버의 8초를 단계별로 완전히 분해한 것은 아니다. worker 증설이나 keepalive 비활성화는 근거가 없다. |
| 2. 오늘 봉 우선 | 오늘만 조회할 때 수정계수 조회 2회를 생략한 후보가 6개 조건에서 전체 응답과 일치했다. | 오늘 전용 bootstrap을 먼저 제공하는 개선 근거가 있다. 과거와 오늘을 한 응답으로 묶으면 순서만 바꿔도 첫 표시가 빨라지지는 않는다. |
| 3. 보조지표 요청 분리 | 과거·오늘·venue·결측 조건 15개에서 분리 후 병합 결과가 기존과 일치했다. | 최대벽·히트맵·프로그램 등을 캔들과 겹쳐 계산할 수 있다. 격리 실험상 효과가 있으나 실제 UI 개선율은 미측정이다. |
| 4. 지표 계산/캐시 | 5일 최대벽 1,967→26ms, 히트맵 811→94ms로 기존 디스크 캐시가 효과적이다. SQL 변경 후보는 성능이 불안정했다. | cold 결과를 언제 준비하고 유지하는지 검토하는 것이 먼저다. 일괄 SQL 변경은 보류한다. |
| 5. 응답량 | 사이드카 약 2.24MB 중 히트맵이 약 87.5%. localhost 본문 수신은 0.75–1.61ms다. | 현재 환경의 수초 지연을 지배하지 않는다. 압축 재도입은 우선순위가 낮다. |

## 조건과 범위

- 실행 서버는 기존 localhost:5173 / :8000을 유지했다. 서버 재시작, 운영 캐시 삭제,
  계정 토큰 발급/갱신, 네트워크 설정 변경은 하지 않았다.
- 서버 기준은 `341bd3ed5` / `0.12.43.0`, 분석 워크트리는 `c32ed4e2b`다.
  두 버전의 관련 분봉·지표 경로가 같은 것은 최초 조사에서 확인했다.
- 외부 호출 실험은 기존 캐시 토큰을 읽는 별도 프로세스에서 실제 REST client와 수집기를 사용했다.
  토큰 발급이나 무효화를 할 수 없는 provider로 제한했다. 결과에는 토큰과 응답 원문이 없다.
- 외부 API 부하를 제한하려고 격리 scheduler를 worker 1, rate 1/s로 설정했다.
  headroom을 포함한 페이싱은 약 1.25초 간격이다. **실행 서버의 scheduler 설정을 재현한 것이
  아니므로 이 실험의 전체 시간을 원래 서버의 큐 대기 시간으로 해석하면 안 된다.**
- 지표 cold는 결과 캐시가 없는 상태다. OS 페이지 캐시는 비우지 않았다.
  별도 임시 루트에서 원본 parquet를 참조하고 임시 결과 캐시를 사용했다.
- SQL 후보 비교는 각 조건에서 실행 순서를 번갈아 3회 측정한 중앙값이다.
  나머지 표본 수는 아래 및 JSON에 명시했다. 통계적 p95나 일반적인 개선율을 추정하지 않는다.

## 1. 키움 HTTP 수신 지연을 분리해 확인

실제 cold 수집에서 호출은 수정계수 `ka10081` 2회 → 과거 `ka10080` 3페이지
(09/04, 09/02, 08/31) → 오늘 `ka10080` 1회 순서였다. 총 6회다.

| 표본 | cold 수집 전체¹ | 실제 HTTP 호출 시간, 순서대로 | 같은 수집기 warm |
|---|---:|---|---:|
| 삼성전자, keepalive 90초 | 5,718ms | 1,629 / 186 / 75 / 59 / 76 / 139ms | 7.05ms, 외부 호출 0 |
| 현대차, 같은 연결 풀 재사용 | 6,440ms | 51 / 38 / 48 / 44 / 40 / 1,387ms | 5.90ms, 외부 호출 0 |
| 삼성전자, keepalive 0초 | 16,539ms | 3,698 / 7,652 / 1,729 / 1,338 / 1,365 / 724ms | 7.89ms, 외부 호출 0 |

¹ 의도적으로 느리게 설정한 격리 페이싱을 포함한다.

삼성전자 첫 수정계수 호출은 TCP 연결 20ms, TLS 71ms, 응답 헤더 대기 28ms였지만
**본문 수신이 1,485ms**였다. 현대차 오늘 분봉은 새 TLS 연결 없이 헤더가 25ms에 도착한 뒤
**본문 수신에 1,357ms**가 걸렸다. keepalive를 껐을 때는 본문 6,506ms,
TLS 약 1,067–1,085ms 표본도 관측했다.

keepalive 0초 비교는 순차 소표본이므로 90초 대비 인과적 개선율을 계산할 수 없다.
다만 연결 재사용을 없애서 해결된다는 가설을 지지하지 않는다. 재사용 중에도 수신 지연이
발생하므로 keepalive 만료 시간만 늘려 해결할 수 있다고 단정할 수도 없다.

추가로 같은 삼성전자 오늘 분봉 요청을 4회 반복했다. 모두 900행 / 176,510 bytes였다.
HTTP stream의 chunk 시간과 Linux `TCP_INFO`를 계측했다.

| 순서 | HTTP 전체 | 본문 수신 | chunk 사이 최대 공백 | 수신 out-of-order 증가 | 연결 |
|---|---:|---:|---:|---:|---|
| 1 | 722ms | 161ms | 104ms | 36 | 새 연결 |
| 2 | 1,669ms | 1,638ms | 1,139ms | 73 | 재사용 |
| 3 | 2,036ms | 917ms | 160ms | 46 | 재사용 |
| 4 | 1,515ms | 1,421ms | 1,049ms | 39 | 재사용 |

RTT 추정치는 약 12.4–12.5ms였다. 커널 구조체 offset은 로컬 Linux 헤더로 별도 검증했다.
로컬 송신 `total_retrans=0`은 상대 서버의 재전송이 없었다는 뜻이 아니다.

**확인된 것:** 큐를 빠져나와 HTTP 응답을 받는 단계에서 지연이 실제로 발생한다.
연결 재사용 중에도 본문 도착이 중단되는 구간이 있고 순서가 뒤바뀐 수신이 관측된다.
**미확정:** 패킷 손실 여부, 지연 발생 hop, Wi-Fi/외부 경로/상대 서버 중 원인,
원래 8초 요청에서 각 원인의 비중. out-of-order와 지연의 동시 관측만으로 단일 원인을 확정하지 않는다.

다음 검증은 실제 요청의 단계별 timing을 지속 기록하고, 동일 요청을 다른 네트워크 경로와
비교하는 것이다. 현재 증거만으로 worker나 계정 수를 늘리는 조치는 정당화되지 않는다.

## 2. 오늘 전용 조회에서 수정계수 2콜을 줄일 수 있는지

실제 `collect_minute`를 호출하되 vendor 응답만 모의 입력으로 바꿨다.
과거 날짜 수정계수는 0.5, 오늘은 1.0인 입력을 사용했다.
KRX/NXT/UN 각각에 오늘 캐시 hit/miss를 조합해 **6개 비교 조건**을 확인했다.
수정계수 캐시는 모든 조건에서 cold다.

| 오늘 캔들 캐시 | 현재 외부 호출 | 오늘 전용 수정계수 생략 후보 | 전체 응답 비교 |
|---|---|---|---|
| miss | 수정계수 2 + 분봉 1 | 분봉 1 | 3 venue 모두 동일 |
| hit | 수정계수 2 | 0 | 3 venue 모두 동일 |

캔들뿐 아니라 `adjust_factors`, 세션 등 전체 `model_dump()`를 비교했다.
따라서 **`from == to == 실제 today`인 요청에 한정해 2콜 제거 가능성을 확인했다.**
과거가 섞인 요청에서 수정계수를 생략하는 근거는 아니다. 캐시된 과거 봉도 기업행동에 따른
수정계수 확인이 필요하다. 모의 입력 1봉 검증이므로 날짜 전환·오류·다중 봉 정합성까지
회귀 검증을 마친 구현으로 간주하지 않는다.

현재 `/past-candles`는 과거와 오늘 수집을 모두 끝낸 뒤 응답한다.
오늘을 내부에서 먼저 수집하는 변경만으로 첫 화면 표시가 빨라지지 않는다.
개선하려면 오늘 seed와 과거 bootstrap 응답/상태를 분리하거나 점진적으로 전달해야 한다.
WS tail 15분만으로 오늘 전체 OHLCV와 누락 구간을 대체할 수는 없다.

증거: [today.json](./2026-09-07-live-minute-followup-evidence/today.json).

## 3. 캔들 가격 범위가 필요한 지표만 늦게 요청하기

기존 사이드카 한 묶음을 다음처럼 나눠 실제 builder로 검증했다.

- 즉시 계산: 최대벽, 히트맵, 프로그램, 거래원 지표.
- 캔들 가격 범위 이후 계산: 매물대 분포, 체결량 POC.
- 즉시 계산 응답에 늦게 계산한 `volume_distributions`, `trade_volume_pocs`를 병합했다.

과거 5일, 1분봉, KRX의 3종목에서 **원래 응답의 최상위 22개 필드가 모두 동일**했다.
별도로 오늘 parquet를 고정 복사한 입력에서 KRX/NXT/UN × 오늘 단독/과거 결측 포함 ×
가격 범위 제공/생략의 **12개 조건도 동일**했다. 오늘 입력에는 실제 히트맵 226–260개
포인트가 있으며 빈 응답끼리만 비교한 것은 아니다. 오늘 경계 실험의 프로그램 데이터는 비어 있다.

성능 실험에서는 캔들 준비 시간을 **1,400ms로 모의**하고 즉시 계산과 겹쳤다.

| 종목 | 기존 builder 실측 | 기존 완료 예상¹ | 분리 완료 실측² | 조건부 단축률 |
|---|---:|---:|---:|---:|
| 삼성전자 | 3,085ms | 4,485ms | 2,531ms | 43.6% |
| SK하이닉스 | 3,011ms | 4,411ms | 2,593ms | 41.2% |
| 인투셀 | 1,080ms | 2,480ms | 1,465ms | 40.9% |

¹ 기존 builder 실측 + 모의 캔들 대기 1,400ms를 합한 예상값.
² 모의 대기와 두 builder를 겹쳐 실행한 격리 프로세스 전체 시간.

**실제 `/live` UI가 41–44% 빨라졌다는 측정은 아니다.** API 큐, 추가 HTTP 왕복,
React commit, 차트 공개 게이트는 이 실험에 없다. 가격 의존성이 없는 큰 계산을 앞당길
효과가 있다는 근거다. UI에 적용할 때는 query key·취소·각 요청 오류·청크 커버리지 병합을
검증해야 한다. 오늘 경계 12개 실험은 고정 snapshot의 결과 비교용이며 성능 비교용이 아니다.

증거: [split.json](./2026-09-07-live-minute-followup-evidence/split.json),
[split-edge.json](./2026-09-07-live-minute-followup-evidence/split-edge.json).

## 4. 최대벽·히트맵 계산과 캐시

삼성전자 09/04 하루 최대벽 cold 752ms 중 parquet 조회·호가 레벨 펼치기·Polars 변환을
포함하는 `_read_peak_wall_frames`가 374ms, 분류가 74ms였다. 최대벽 계산은 이미 Polars를
사용한다. Python 행 반복문 하나를 제거하는 유형의 문제로 볼 근거는 없다.
같은 날 히트맵 cold 188ms 중 버킷 집계 query는 119ms였다.
측정 wrapper 사이에는 중첩이 있으므로 함수별 시간을 모두 더해서 총 시간으로 삼으면 안 된다.

레벨을 펼치는 `UNION ALL`을 zipped `UNNEST`로 바꾼 후보도 별도 query wrapper로 실험했다.
3종목 × 1분/5분 × 최대벽/히트맵, 각 3회 중앙값이다.
삼성전자 1분 최대벽은 **714→1,053ms로 악화**, 5분은 569→506ms로 개선됐다.
다른 종목도 작은 개선과 악화가 섞였다. 히트맵은 약간 개선된 조건이 있지만 일관되지 않았다.
최대벽 ask/bid 결과는 같고 대표 행은 중복 수를 포함해 같은 구성이었으나 내부 목록 순서가 달랐다.
따라서 전체 결과의 엄격한 동일성은 실패했다. 일괄 적용할 후보로 채택하지 않는다.

기존 디스크 캐시를 유지한 채 엔진만 다시 만들어 cold와 비교했다.
삼성전자 5일, 결과 `model_dump()` 시간을 포함한다.

| 지표 | 결과 캐시 없음 | 새 엔진 + 디스크 hit | 같은 엔진 메모리 hit |
|---|---:|---:|---:|
| 최대벽 | 1,967ms | 26ms | 9ms |
| 히트맵 | 811ms | 94ms | 37ms |

모든 응답은 동일했다. 기존 캐시가 효과적으로 cold 계산을 피한다.
따라서 완료된 데이터의 캐시 준비 시점과 무효화 빈도를 검토하는 것이 새 캐시나 일괄 SQL
재작성보다 우선이다. **실행 서버의 캐시 miss 빈도 자체는 이번에 계측하지 않았다.**

증거: [compute.json](./2026-09-07-live-minute-followup-evidence/compute.json),
[unpivot.json](./2026-09-07-live-minute-followup-evidence/unpivot.json),
[cache.json](./2026-09-07-live-minute-followup-evidence/cache.json).

## 5. 큰 응답과 불필요해 보이는 요청

실행 서버에서 삼성전자 과거 5일 사이드카를 3회 조회했다.
2,236,259 bytes 중 히트맵 필드가 1,957,328 bytes로 약 87.5%였다.
하지만 localhost에서 헤더 수신 이후 본문 읽기는 **0.75–1.61ms**,
Python JSON 파싱은 **29–35ms**였다. 파싱 수치는 브라우저 측정값이 아니다.
헤더까지는 168–411ms이며 여기에 서버 처리와 스케줄링 등이 포함된다.

호가 range는 449,935 bytes, 본문 읽기 0.31–0.57ms였다.
기본 MA/거래량 화면에서도 이 요청이 존재하지만 세션·커버리지 등에도 쓰이므로 pane만
보고 무조건 끌 수 있는 요청은 아니다. 현재 수초 지연에서 우선순위는 낮다.

[ADR-0154](../adr/0154-drop-http-response-compression.md)는 localhost 전송 이득보다
압축 CPU 비용이 커서 gzip을 제거한 결정을 기록한다. 이번 측정도 압축 재도입을 뒷받침하지 않는다.
원격 클라이언트 네트워크에서의 영향은 별도로 측정해야 한다.

증거: [payload.json](./2026-09-07-live-minute-followup-evidence/payload.json).
