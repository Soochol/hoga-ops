# 패턴 검색의 주봉·월봉 확장 — 검토

**작성:** 2026-09-02 · **상태:** 검토 완료 · **구현 미착수** · **대상:** 우측 레일 「패턴」 패널

대상은 ADR-0166(#1689~#1699 및 후속)이 만든 봉 패턴 검색이다. 현재 엔진은 일봉 전용이고
`PatternSearchRequest` 에 timeframe 축이 **없다**. ADR-0166 의 v1 비목표에 「분봉/주봉/월봉」이
남아 있으므로 이 검토는 그 비목표의 **부분 뒤집기 제안**이다.

수치는 전부 실측이다 — 일봉 코퍼스에서 주봉·월봉을 파생해 **기존 엔진에 그대로 태워서**
얻었다(재현 절차는 §⑦). 커널을 고치지 않고도 「그 코퍼스에서 이 기능이 어떻게 동작하는가」를
잴 수 있다는 것이 이 검토가 성립한 이유다.

> **§① 의 결함은 확장과 별개로 고쳤다 — PR #1715.** 아래 서술은 그 수정 **이전** 상태를
> 기록한 것이고, 확장을 착수할 때 같은 함정을 다시 만들지 않기 위해 남긴다.

## 판정 요약

| | 주봉 | 월봉 |
|---|---|---|
| 변별력(1위 − 100위, 중앙값) | **+0.052** (일봉 +0.028) | +0.038 |
| history 검색 시간 (L=7) | 257ms (일봉 777ms) | 144ms |
| 코퍼스 상주 | 145MB (일봉 682MB) | 34MB |
| 파생 시간 | 0.29s | 0.18s |
| 공장값(1년·forward 20봉)에서 | 동작 | **결과가 통째로 빈다** |

- **주봉은 성립한다.** 변별력이 일봉보다 낫고 — 후보창이 5배 적은데도 그렇다 — 비용은 1/3 ·
  메모리는 1/5 다. 다만 공장 기간(1년)에서는 후보창이 32,662 뿐이라 분포 눈금이 얇다(아래 (e)).
- **월봉은 조건부다.** 변별력 자체는 문제가 아니다(정정 — 아래 ⑤). 걸리는 것은 **공장값 조합에서
  후보가 0** 이고, `mid` 프리셋의 60개월 워밍업이 모집단을 2,691 → 1,625 로 깎는다는 점이다.
  별도 공장값·경고 없이 내면 «빈 화면» 이 기본이 된다.
- **선행 조건이 있다.** 아래 결함 ①은 확장 여부와 무관하게 지금 존재하며, 확장의 전제이기도 하다.

## ① 지금 있는 결함 — W/M 차트에서 그은 구간이 «일봉» 으로 해석된다

`ChartWindow.tsx:363` 의 게이트가 `isMinuteTimeframe(view.timeframe)` 만 본다. 바로 위 주석은
「**일봉일 때만 만든다**」 라고 적혀 있으나 코드는 주봉·월봉을 통과시킨다. 통과 뒤:

- `savedRangeCandles` 는 `aggregateCalendar` 를 지난 **집계 봉**이라 `patternSeedFromRange` 의
  봉 수 검증(5~30)이 **주/월 개수**로 세어져 통과한다.
- 서버로 가는 것은 `from`/`to` **날짜**뿐이고, `_resolve_window` 는 그 구간을 **일봉 봉수**로 센다.

실측(삼성전자, 미완성 마지막 버킷 제외). 드래그가 어디서 놓이느냐에 따라 일봉 봉수는 몇 개
움직이므로 아래 값은 대표치다:

| 화면에서 그은 것 | 서버가 답하는 질문 | 사용자가 보는 것 |
|---|---|---|
| 주봉 5개 | 일봉 **~20봉** 패턴 | 정상적인 결과 (1위 갤럭시아머니트리 0.738) |
| 주봉 7개 | 일봉 **~29봉** 패턴 | 정상적인 결과 (1위 코미코 0.571) |
| 주봉 10개 | 상한 30봉 초과 | **빈 결과, 원인 표시 없음** |
| 월봉 5개·7개 | 상한 초과 | **빈 결과, 원인 표시 없음** |

앞의 두 줄이 더 나쁘다 — 화면이 그럴듯한 답을 내므로 사용자가 **틀린 질문의 답을 옳은 답으로
읽는다**. 속성 패널의 「125봉 — 패턴 검색은 5~30봉이다」 안내도 주 개수를 세므로 침묵한다.

**수정은 한 줄**이고 확장 결정과 독립적이라 PR #1715 가 이것만 고쳤다 — 판정을
`isPatternSearchableTimeframe`(`tf === 'D'`) 한 곳에 모으고 `patternSeedFromRange` 가
timeframe 을 **값으로** 받게 했다.

⚠ **이 유형은 회귀 테스트가 원리적으로 없다.** 주봉·월봉은 게이트가 쓰일 때부터 있었고
늘어난 것은 코드도 timeframe 도 아니라 **그 질문이 구별하지 못하는 경우의 비중**뿐이다.
여집합(`!isMinute`)으로 물은 게이트는 새 멤버를 자동으로 통과시키면서 타입·테스트·주석
어디에도 흔적을 남기지 않는다 — **허용 집합을 직접 쓰는 것**이 유일한 방어다.

## ② 곁가지 결함 — `corr` 이 1 을 넘는다 (현행 일봉 프로덕션, 원인 확정)

상관계수는 1 을 넘을 수 없는데 넘는다. `ma_preset` 과 무관하다(아래는 전부 `ma=off`).

**원인은 확정됐다** — 완전 정지 구간이 평탄 가드를 통과하고, cumsum 분산이 파국적 상쇄로
참값보다 작게 나와 나눗셈이 점수를 부풀린다. 문제 창을 직접 재면:

```
에이전트AI(060900) 2015-07-09~07-17  corr=1.250   (참값 0.652)
   sd  2-pass 1.999e-07 · cumsum(_win_sd) 1.043e-07 · 비 0.52
   종가 215639 로 7봉 내내 동일 · 일 변동폭 0.000%
```

`_FLAT_SD = 1e-9` 가 낮다. 처방은 커널 재작성이 아니라 **그 상수 + 2-pass 검산**이다.

⚠ **새 값을 짐작으로 정하지 말 것.** 「로그가격 1틱 ≈ 1e-4」는 25만원대 종목의 수치이고,
싼 종목은 로그 공간에서 틱이 1e-3 이상이라 **종목마다 다르다**. 코퍼스의 **실제 최소 비영
창 sd 분포를 재서** 정지 구간과 살아 있는 저가주를 가르는 자리를 찾아야 한다 — 1e-6 은
무난해 보이지만 1e-4 는 멀쩡한 창을 지울 수 있다.

**차단 주체 정정.** 처음에 「기간 조건이 가린다」고 적었으나 교차 실측은 그렇지 않다 —
8종목 × 100행 = 800행 기준:

| | tv=0 | tv=50억 |
|---|---|---|
| 전 기간 | 일봉 1 · 주봉 3 · 월봉 0 | **0 · 0 · 0** |
| 최근 5년 | **0 · 0 · 0** | 0 · 0 · 0 |

즉 막는 것은 **거래대금 필터**이고 기간도 (5년까지는) 함께 막는다. 공장값이 50억이라 기본
경로에서는 보이지 않는다. 다만 조건 칩이 **「거래대금 무관」(0)을 실제로 제공하므로**
(`PatternConditionChips.tsx:83`) UI 에서 도달 가능하다 — 재현 조건은 「거래대금 무관 + 기간 전체」다.

⚠ 이 관찰은 메모리의 「중심화로 corr>1 을 고쳤다」 기록에 대한 **정정**이다. 계열 중심화는
계열 간 상쇄를 없앴을 뿐, 창 단위 상쇄는 남아 있다.

## ③ 아키텍처 — 서버 파생이 유일한 답

종목 주봉·월봉을 주는 벤더 경로가 **없다**(키움 W/M TR 은 `kiwoom_index_rest.py` 의 **지수** 전용).
따라서 `daily_adjusted.parquet` 에서 서버가 파생한다. 그 파생 규칙은 프론트
`calendarBucketKey`(`aggregateCandles.ts:93`)와 **같아야** 한다 — ADR-0166 이 내세운
「화면의 봉과 검색 대상이 같은 데이터」 가 그것으로만 유지된다.

- 주 = 그 날이 속한 주의 **월요일** 날짜를 키로. `dt.truncate("1w")` 에 맡기지 말고
  `date − (weekday − 1)` 로 명시할 것.
- 월 = 달력 월. 시간대는 parquet 의 `date` 가 이미 KST 달력 날짜라 변환이 없다.
- **정제(`_sanitized`)를 먼저, 집계를 나중에.** 순서가 바뀌면 버려야 할 행이 그 주의 고가·저가를
  오염시키고, 집계 후 OHLC 정합성은 구성상 보장된다.
- 경계 픽스처는 `aggregateCandles.test.ts:214~288`(일요일·월요일 케이스)을 백엔드로 옮겨 대조.

파생 결과: 주봉 1,903,052행 / 월봉 443,170행 (일봉 8,942,793행의 21% · 5%), 4,330종목 동일.

## ④ 결정해야 할 함정 — 전부 실데이터에 이미 있다

**(a) 미완성 마지막 버킷 — 결과의 절반이 갈린다.**
코퍼스 마지막 날짜가 2026-09-01(월)이라 마지막 주봉은 2거래일, 마지막 월봉은 1거래일이다
(전 종목 4,288/4,288 이 미완성). 포함/제외로 `now` top20 을 비교하면:

| 종목 | top20 겹침 | 1위 corr | 1위 종목 |
|---|---|---|---|
| 005930 | 16/20 | 0.961 → 0.941 | 다름 |
| 000660 | 15/20 | 0.953 → 0.958 | 다름 |
| 035420 | 11/20 | 0.864 → 0.919 | 다름 |
| 051910 | 10/20 | 0.979 → 0.961 | 같음 |

화면이 그 봉을 그리므로 `now` 는 포함하는 쪽이 일관되지만, **모든 매치의 마지막 봉이 같은
방식으로 왜곡**된다. 어느 쪽을 고르든 패널이 그 사실을 말해야 한다(「이번 주 2일치 포함」).

**(b) 월요일 휴일 오프바이원 — 주봉의 7.6%.**
프론트 `aggregateCalendar` 의 `t_ms` 는 그 버킷의 **첫 거래일**이고(`aggregateCandles.ts:107`
주석이 그 이유를 적는다 — Gap 에 떨어지지 않게), 서버 파생 키는 **월요일**이다. 월요일이
휴일이면 둘이 갈린다. 전체 주봉 144,233/1,903,052 = **7.6%**, 삼성전자만 6.4%이고 최근
사례가 2026-08-17·05-25·03-02 다. 요청의 날짜를 **버킷 키로 정규화한 뒤** 비교해야 하며,
월요일 휴일 픽스처가 필요하다.

**(c) 생존 판정이 깨진다.** `search_now` 는 `c.dates[e-1] != c.last_date` 로 「지금이 있는가」를
본다. 파생 `date` 를 **첫 거래일**로 잡으면 월~수 정지한 종목의 그 주 값이 목요일이 되어
`last_date`(월요일)와 달라져 «상장폐지» 취급된다. 위 (b)의 처방(키 = 월요일)이 이것도 막는다.

**(d) 날짜 변환은 «양방향»이다 — (b)와 한 항목이다.** 들어올 때는 요청 날짜를 버킷 키로
정규화해야 하고((b)), **나갈 때는 그 반대**다: `PatternMatchRow.from_date/to_date` 와
`PatternQueryWindow` 가 버킷 키(월요일, 때로 휴일)를 그대로 실으면 **차트에 그 날 캔들이 없어**
착지 밴드가 아무 데도 걸리지 않는다. `from_date` 는 그 버킷의 **첫 거래일**, `to_date` 는
**마지막 거래일**이어야 한다. 따라서 코퍼스가 날짜 배열을 **셋**(키·첫날·끝날) 들고 있어야 한다.

**(e) 공장 기간이 짧은 봉을 전제한다 — 월봉은 비고 주봉은 얇다.** `since` = 1년(월봉 12봉) 이고 `forward_days` = 20 **봉**
(월봉 20개월)이라 후보가 0 이다. 실제로 `ma` 3종 전부 「결과 없음」이 나왔다. `forward_days` 는
필드명·라벨이 「일」인데 코드는 **봉**을 센다(`min_after`). 공장값과 라벨이 timeframe 별로 갈려야 한다.

주봉은 비지는 않으나 **분포 눈금이 얇다**: 공장 기간 1년의 후보창이 일봉 121,920 vs 주봉
**32,662** 라 p99.99 가 표본 **3.3개** 위에 서 있다(일봉은 12.2개). 3년이면 141,478 / 14.1개다.
행마다 그리는 분포 스트립이 그 눈금을 쓰므로 **주봉 공장 기간은 3년 이상**을 권한다.

**(f) `min_tv_eok` 의 뜻이 바뀐다.** 코퍼스가 `평균가 × 거래량` 으로 tv 를 만드는데 집계 봉의
volume 은 **합**이다. 2026년 실측 중앙값은 일봉 4.8억 vs 주봉 23.0억 = **4.8배** — 「50억 이상」이
주봉에선 실질 일 10억이 된다. 버킷 tv 를 **일평균**으로 두면 임계값의 뜻이 보존된다.

**(g) 이평 프리셋의 의미.** `paneSpecsForTimeframe('D') === ('W')` 이므로 차트도 봉 단위로 MA5/20 을
그린다 — 매칭을 봉 단위로 두는 것이 화면과 일치한다. 다만 「단기 5·20」이 주봉에선 5주·20주임을
라벨이 말해야 한다. 월봉 `mid`(20·60)는 60개월 워밍업이라 모집단이 2,691 → **1,625** 로 떨어진다.

**(h) 착지가 D 로 강제된다.** `PatternDrawer.tsx:445` 가 `setChartTimeframe(landing, 'D')` 이고
`savedTimeframe: 'D'`(124행), 이력 확장은 `subtractDaysKst(..., CONTEXT_DAYS)` 로 **일 단위**다
(#1697·#1704 가 세운 계약). W/M 매치는 그 timeframe 으로 착지해야 하고 확장도 버킷 단위여야 한다.

**(i) 캐시 정책과 워커 메모리.** 캐시는 `(경로, mtime)` 키로 **항상 1개만** 유지한다. timeframe 이
셋이 되면 번갈아 쓸 때마다 재빌드(일봉 **1.9s**)가 나거나, 셋 다 상주해야 한다. 상주 실측은
일봉 682MB + 주봉 145MB + 월봉 34MB = 861MB 이고, 엔진은 컴퓨트 워커 프로세스에서 돈다
(`compute_jobs.py:170`, 기본 워커 2~3) → **프로세스당** 그 값이다. 현행 2.0GB 대비 +540MB.

**(j) 저장 wire.** `timeframe` 필드를 더하고 **부재 = `"D"`** 로 읽어야 기존 저장이 산다(#1711 의
「부재는 공장값을 따른다」와 같은 규칙). ADR-0004 4층: `PatternTimeframe` Literal ↔ 프론트 union 을
`WIRE_ENUM_MIRRORS` 에 **손으로** 등록하고 `EXPECTED_REST_WIRE_FIELDS` 갱신.

## ⑤ 실측 원표

`ma=off`, L=7, `min_tv_eok=0`, 전 기간. `corr>1` 오염 행 제외, 8종목.

| | 코퍼스 | 빌드 | now | history | 후보창 | p50 | p99.99 | 1위−p99.99 | **1위−100위** |
|---|---|---|---|---|---|---|---|---|---|
| 일봉 | 8.94M봉 682MB | 1.91s | 57ms | 777ms | 7,385,384 | +0.306 | 0.870 | +0.038 | +0.028 |
| 주봉 | 1.90M봉 145MB | 0.27s | 53ms | 257ms | 1,514,581 | +0.368 | 0.861 | +0.053 | **+0.052** |
| 월봉 | 0.44M봉 34MB | 0.12s | 57ms | 144ms | 298,980 | +0.221 | 0.937 | +0.025 | +0.038 |

⚠ **두 자를 함께 봐야 한다 — 앞의 자는 코퍼스 크기에 오염된다.** 메모리가 쓰던 「1위 − p99.99」는
**같은 코퍼스 안에서 봉수를 고르려고** 만든 자다. 후보창 수가 24배 차이 나는 세 코퍼스를 그
자로 비교하면, N 이 클수록 최댓값이 꼬리 더 안쪽까지 들어가므로 **일봉이 부풀고 월봉이 눌린다**.
순위 간격(1위−100위)은 그 편향에 **훨씬 덜** 흔들린다 — 없는 것은 아니다(고정 순위 간격도
표본 수에 얼마간 의존한다).

그렇게 재면 판정이 바뀐다: **주봉이 두 자 모두에서 1위**이고(후보창이 5배 적은데도),
월봉은 뒤의 자에서 일봉을 앞선다(+0.038 vs +0.028). 첫 초안의 「월봉 변별력은 일봉의 절반」은
**철회한다** — 그것은 N 교란이었다. 다만 **확립된 것은 「두 자가 서로 다른 답을 낸다」까지**이고,
그 자리에 「월봉이 일봉보다 낫다」를 놓으면 같은 과오를 반대 방향으로 반복하는 것이다. 월봉을 조건부로 두는 근거는 변별력이 아니라 (e)의 공장값
공백과 (g)의 워밍업 손실이다. (100위까지 오염 없이 채운 종목만 셌으므로 n 은 일봉 7 · 주봉 5 ·
월봉 8 로 고르지 않다 — 표본이 작다는 점은 감안할 것.)

`now` top6 이 timeframe 마다 갈린다(삼성전자 기준): 일봉은 SK하이닉스·한솔테크닉스…,
주봉은 삼성전자우·삼성물산…, 월봉은 SK하이닉스·삼성생명·삼성물산…. 긴 봉일수록 계열·대형주가
올라온다 — 「다른 질문」이라는 근거이자 기능의 값어치다.

## ⑦ 재현

측정 스크립트는 커밋하지 않았다(일회성 탐침). 다시 재려면 아래로 충분하다 — **코퍼스를
파생해 `screener/daily_adjusted.parquet` 레이아웃으로 쓰고 그 디렉터리를 `load_corpus` 에
주면 기존 엔진이 그대로 돈다.** 원본은 읽기만 한다.

```python
import polars as pl
from hoga.config import resolve_data_dir
from hoga.api.screener_pattern import _sanitized

df = _sanitized(resolve_data_dir() / "screener" / "daily_adjusted.parquet")  # ★ 정제 먼저
key = (pl.col("date") - pl.duration(days=pl.col("date").dt.weekday() - 1)   # 주 = 월요일
       if tf == "W" else pl.col("date").dt.truncate("1mo"))
agg = (df.with_columns(key.alias("bkey"))
         .group_by(["code", "bkey"], maintain_order=True)
         .agg(pl.col("open").first(), pl.col("high").max(), pl.col("low").min(),
              pl.col("close").last(), pl.col("volume").sum(),
              pl.col("date").first().alias("first_day"),   # ← §④(d) 의 날짜 배열
              pl.col("date").last().alias("last_day"), pl.len().alias("days"))
         .rename({"bkey": "date"}).sort(["code", "date"]))
# <out>/screener/daily_adjusted.parquet 로 쓰고 stocks.parquet 을 곁에 복사한 뒤:
#   screener_pattern.reset_cache(); screener_pattern.run_pattern_search(Path("<out>"), req)
```

⚠ 캐시는 `(경로, mtime)` 키라 디렉터리를 바꾸면 자연히 갈리지만, **항상 1개만** 유지하므로
timeframe 을 번갈아 재려면 `reset_cache()` 없이도 매번 재빌드가 난다(일봉 1.9s). 한 코퍼스의

「1위」가 되어 어느 자로 재든 무의미해진다.
