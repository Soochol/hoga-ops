# /live 분봉 캔들·보조지표 cold 로딩 병목 조사

2026-09-07 12:26–12:34 KST 실측. 제품 코드는 변경하지 않았다.

## 결론

**이번에 재현한 8~10초 지연의 주 병목은 서버의 키움 분봉 수집 경로다.**
캔들 응답을 기다리는 프론트 게이트 때문에 호가비·총잔량·체결강도 pane도 함께 늦게 보인다.
매물대를 켜면 사이드카 요청 자체가 캔들 응답 뒤에 시작되어 지연이 더해진다.
별개로, 지표 캐시까지 없는 경우에는 **최대벽과 호가 잔량 히트맵의 최초 계산**이 무겁다.

이번 표본에서 브라우저 투영·Canvas 작업이나 JSON 파싱이 수초 지연을 지배한다는 증거는 없었다.
다만 키움 수집 내부의 **HTTP 왕복 / 토큰 버킷 대기 / 수정계수 조회별 시간**은 기존 관측값으로
완전히 분리되지 않는다. “키움 서버 응답만 8초”라고 단정하지 않는다.

## 측정 조건

- 브라우저·HTTP: 실행 중인 localhost:5173 / :8000. `/health`는 `341bd3ed5`, `0.12.43.0`.
- 소스 분석·격리 프로파일: 이 워크트리 `c32ed4e2b`. 런타임 이후 세 커밋은 일봉 cold-start,
  WS 정리, Vite 캐시 개선이다. 분봉 수집·사이드카 게이트와 여기서 측정한 지표 빌더는 동일하다.
- 브라우저: gstack browse, KRX, 1분봉, 20260831–20260907. 새 종목의 `fresh_dates`로
  **실제 분봉 캐시 미스**를 확인했다. 서버를 재시작하거나 운영 캐시를 지우지 않았다.
- 지표 프로파일: 삼성전자 20260831–20260904, 5거래일, `source_pref=hogaplay`.
  임시 데이터 루트에서 원본 parquet만 참조하고, 지표 결과 캐시는 새 임시 디렉터리에 생성했다.
  각 설정에서 cold 후 같은 엔진으로 warm 호출. 전체 실험을 두 번 수행했다.
- OS 페이지 캐시는 비우지 않았다. 지표 cold는 **계산 결과의 메모리·디스크 캐시가 없는 상태**다.
  브라우저 cold와 지표 cold의 수치를 하나의 동일 실험처럼 합산하면 안 된다.
- 브라우저 측정은 이미 로드된 앱에서 종목 전환을 수행했다. 최초 JS 다운로드 비용은 제외한다.

## 1. 실제 사용자 경로: 분봉 수집이 임계 경로

| 종목 / 설정 | 분봉 요청 시간 | 호가 range 완료 시점¹ | 차트 공개 시점¹ | 사이드카 마지막 응답¹ |
|---|---:|---:|---:|---:|
| 삼성전자 / 기본 MA·거래량 | 8.027초 | 개별 요청 212 / 123ms² | 미계측 | 비활성 |
| SK하이닉스 / MA·거래량·총잔량 | 8.765초 | 0.319초 | 8.899초 | 비활성 |
| 인투셀 / 아래 지표 활성 | 1.402초 | 0.420초 | 2.180초 | 3.245초 |
| 현대차 / 아래 지표 활성 | 8.531초 | 0.333초 | 9.320초 | 9.992초 |
| 인투셀 재방문 / 동일 지표 | 0.115초 | 브라우저 캐시 재사용 | 0.250초 | 브라우저 캐시 재사용 |

¹ 종목 전환 호출을 0으로 한 시간. “차트 공개”는 `chart-reveal-cover`의 opacity가 0으로
바뀐 시점이며, 160ms fade의 종료나 모든 pane의 최종 paint 시점은 아니다.
² 삼성전자는 최초 browse network로 관측했고 절대 시작 타임라인은 따로 계측하지 않았다.

지표 활성 실험은 MA·거래량·총잔량·호가비·체결강도·연속체결 매물대·최대 매물대·최대벽·
호가 히트맵·프로그램 순매수다. 요청 파라미터는 증거 JSON에 있다. 외국인·기관 및 일봉 MA의
별도 cold 경로는 이번 실험 대상이 아니다. 별도 일봉 요청은 활성 실시간 창의 다른 소비자도 낸다.

삼성전자 같은 범위를 직후 curl로 다시 읽으면 **16.292ms / 220,708 bytes**였다.
서버 로그의 해당 `slow_collect`는 **7,980ms**, `pending_dates=5`, `fresh_dates=6`,
`deferred_dates=0`, `rate_limited=False`였다. 전체 8,027ms 중 99.4%가 서버 내부 수집 시간이다.
현대차도 `slow_collect=8,498ms`로 브라우저 요청 8,531ms와 일치한다.

수집 경로는 다음과 같이 순차 실행된다.

```text
_collect_for_venue
  → 수정계수 확보: cold이면 ka10081 수정/원주가 2회 순차
  → 캐시 없는 과거 날짜: ka10080 페이지 순차 walk-back
  → 오늘 캐시 miss: 오늘 ka10080 별도 조회
  → 캔들 묶음 응답
```

- `hoga/live/live_candle_backfill.py:418`: 수정계수를 캐시 읽기보다 먼저 확보한다.
- `hoga/live/kiwoom_adjust_factors.py:204`: 수정/원주가 2콜을 순차 호출한다.
- `hoga/live/kiwoom_minute_candles.py:313`: 페이지 결과의 최古 날짜를 다음 커서로 삼는다.
  최古 날짜는 불완전할 수 있어 다음 페이지로 온전하게 받아야 한다. 날짜별 무조건 병렬화는
  중복 조회와 완결성 문제를 만든다.
- `hoga/live/live_candle_backfill.py:487`: 과거 walk 후 오늘 캐시를 확인하고 필요하면 추가 조회한다.
- `hoga/live/past_candles_cache.py:64`: 오늘 TTL은 60초. 과거 캔들은 메모리 전용이다.
  재시작·축출·새 종목/해상도에서 cold가 다시 생긴다.

**공용 큐의 지속적인 포화는 이번 재현에서 관측하지 못했다.** 현대차 실험과 겹치는 18초 동안
약 300ms마다 status를 조회했으며 queued는 전부 0, inflight 최대 3, worker는 4였다.
status 응답은 최대 37ms였다. 단, dequeue 뒤의 토큰 버킷 대기는 queued에 포함되지 않으므로
이 결과만으로 모든 페이싱 대기를 배제할 수는 없다. 당시 캐시 통계의 과거 eviction은 0이었다.

서버 로그에는 과거 `pending_dates=0`인데 오늘 1일만 받으며 5~13초 걸린 사례와
`ka10080 ReadTimeout`도 있었다. 과거 일수를 줄이는 것만으로 모든 지연이 해결되지는 않는다.

## 2. 지표가 같이 늦어지는 프론트 의존성

`frontend/src/live/useLiveBundle.ts:991`의 hoga 요청은 캔들과 **병렬로** 시작한다.
실제로 SK하이닉스의 호가 데이터는 0.319초에 준비됐지만 캔들은 8.791초에 도착했다.
`useLiveBundle.ts:1466`은 cold 캔들 대기 중 호가 시리즈를 빈 배열로 보류한다.
캔들보다 호가 시리즈를 먼저 넣었을 때 공유 시간축 변경으로 차트가 깨지던 문제를 막는 장치다.
게이트만 제거하는 수정은 부적절하다.

반면 `useLiveBundle.ts:955` 및 `:1013`의 매물대 가격 범위 대기는 **사이드카 묶음 전체**를 막는다.
매물대와 무관한 최대벽·히트맵·프로그램까지 같은 요청에 묶여 기다린다.

현대차 실측 타임라인:

```text
0.037초  캔들 / hoga 요청 시작
0.333초  hoga의 두 청크 응답 완료
8.568초  캔들 응답 JSON 수신 완료
8.616초  sidecar 첫 요청 시작
9.320초  차트 공개: sidecar 대기 상한 도달
9.696초  sidecar 첫 청크 완료
9.992초  sidecar 다음 청크 완료
```

`LiveChartRoot.tsx:268`의 사이드카 대기 상한은 **700ms**다. 이것은 전체 로딩 700ms 제한이
아니라 **캔들과 hoga가 준비된 뒤 남은 사이드카 대기**에만 적용된다(`:1130`).
따라서 느린 분봉 수집 8.5초를 줄이지 않으며, pane들의 최종 데이터 준비도 보장하지 않는다.
range의 최신 구간 → 이전 구간 청크 조회도 순차로 이어진다.

## 3. 지표 계산 자체의 cold 비용

5거래일 격리 캐시 프로파일 두 번째 실행. 단위 ms, HTTP 전송 제외.

| 요청 설정 | cold 빌드 | warm 빌드 | 비압축 JSON 크기 |
|---|---:|---:|---:|
| 저장된 캔들만 | 121 | 38 | 206KB |
| hoga: 호가비·총잔량·체결강도 | 327 | 13 | 450KB |
| 최대벽만, 매수·매도 양쪽 | **1,539** | 35 | 68KB |
| 호가 히트맵만 | **716** | 12 | **1.96MB** |
| 최대 매물대만 | 350 | 29 | 1.9KB |
| 연속체결 매물대만 | 309 | 18 | 6.1KB |
| 사이드카 전체³ | **3,055** | 43 | **2.24MB** |

³ 위 다섯 종류와 신규 거래원·프로그램을 포함한다. 매물대 bin=15, 신규 거래원 시작=09:00.
이 설정은 UI 실험의 bin=10 / 신규 거래원 off와 다르다. 결과 크기의 단위는 decimal이다.

첫 실행도 최대벽 1,592ms, 히트맵 783ms, 전체 2,991ms로 같은 우선순위를 보였다.

- 최대벽: `_prefetch_peak_caches`가 3 worker로 먼저 완료일을 계산하고 본문이 캐시를 읽는다.
  **이미 병렬화되어 있다.** 하위 builder 누적 시간은 병렬 구간 때문에 전체 wall time보다
  클 수 있으므로 서로 합산해 요청 시간을 추정하면 안 된다.
- 히트맵: `build_depth_heatmap_slice`가 날짜별 원시 집계와 결과 캐시 저장을 수행한다.
  캐시 후 계산은 작아도 close / 최대 총잔량 순간 / 가격별 최대 세 소스의 큰 응답은 남는다.
- 매물대/POC: 표의 시간에는 공통 연속거래 종료 경계·가격 범위 조회도 포함된다.
  각 표 행은 독립적으로 cold를 만들었으므로 이들을 단순 합산하면 공통 비용을 중복 계산한다.
- 전체 사이드카 JSON 직렬화는 별도 약 9~13ms. FastAPI 응답 모델 처리·전송·브라우저 계산은 제외했다.

## 4. 우선순위와 후속 검증

1. **키움 수집 경로의 세부 타이밍부터 분리한다.** 요청별 수정계수 hit/miss, 페이지 수,
   enqueue→실행, token acquire, 실제 HTTP 시간을 기록해야 8초의 정확한 내부 원인을 가를 수 있다.
   현재 증거로 worker/계정 수만 늘리는 결정을 정당화할 수 없다.
2. **오늘/최근 봉을 먼저 제공하는 로딩 경로를 검토한다.** 현재는 과거 walk 뒤에 오늘을 받는다.
   서버가 이미 가진 today/WS 데이터 재사용과 첫 화면에 필요한 범위 우선 반환이 대상이다.
   수정계수·venue·공유 시간축의 정합성을 유지해야 한다.
3. **가격 범위가 필요한 매물대만 분리한다.** 최대벽·히트맵·프로그램은 캔들 완료 전부터
   계산할 수 있다. 현재 waterfall을 겹치게 만드는 개선이며, 캐시 키와 청크 커버리지 검증이 필요하다.
4. **지표 cold 계산은 최대벽 → 히트맵 순으로 본다.** 기존 병렬화·1분 결과 캐시를 중복 구현하지
   말고 실제 cold 계산/캐시 무효화 빈도를 줄일 방법을 검토한다. 데이터 소스 변경이나 캔들 디스크
   캐시 추가는 기존 정책을 바꾸는 별도 설계다.
5. 히트맵 응답량과 hoga 비활성 pane의 불필요한 요청은 후순위다. 기본 MA·거래량만 있어도
   hoga 요청이 나가는 것은 확인했지만, 이번 8초 지연의 주원인은 아니다.

브라우저에는 현대차·인투셀 측정 중 50ms 이상 long task가 없었고, SK하이닉스는 캔들
도착 직후 50ms 하나였다. 여기서 `response.json()`의 await 시간에는 body 수신 및 스케줄링도
포함되므로 증거 파일의 `parse`를 순수 JSON CPU 시간으로 읽으면 안 된다.
긴 기간·여러 차트·다른 지표 설정에서 렌더링 병목이 없다는 일반적 결론은 내리지 않는다.

## 증거와 재현

[측정 JSON 디렉터리](./2026-09-07-live-minute-cold-evidence/)에 요청별 시작·응답·JSON 완료,
차트 공개 시점, long task, 격리 캐시 builder 시간, 공용 scheduler 표본을 보존했다.

실제로 실행한 재현 명령:

```bash
# 실행 중인 서버의 분봉 요청. 이미 warm이면 cold를 재현하지 않는 것이 정상이다.
curl -s -o /tmp/minute-cold-response.json \
  -w '%{time_total}s %{size_download} bytes\n' \
  'http://127.0.0.1:8000/api/live/past-candles?code=005930&from=20260831&to=20260907&venue=KRX&bucket_ms=60000'
# 관측: 0.016292s 220708 bytes (직전 cold 8.027초 후 재조회)

# 같은 머신의 조사용 harness. 런타임 제품 파일에 계측 코드를 추가하지 않았다.
PYTHONPATH="$PWD" /home/dev/code/hoga-ops/.venv/bin/python /tmp/minute-cold-5056-profile.py
/home/dev/.claude/skills/gstack/browse/dist/browse eval /tmp/minute-cold-5056-browser-third.js
```

조사용 Python harness는 임시 루트의 parquet·프로그램 데이터 링크와 임시 지표 캐시를 쓰고
`build_range_bundle`의 slice builder를 시간 측정 wrapper로 감싼다. temporary directory는 종료 시
정리됐다. 브라우저 harness는 종목 전환 후 20초간 fetch·cover·long task를 관측하고 wrapper와
observer를 해제한다. 성능 실측 및 코드 조사만 수행했으며 수정·전체 테스트·배포는 하지 않았다.
