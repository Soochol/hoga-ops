# 히트맵 1분 캐시 재사용

완료일의 요청 해상도 캐시가 없고 1분 캐시가 이미 있을 때, 1분 대표들을 큰 봉으로 합친다. 1분 캐시가 없는 첫 조회는 요청 해상도로 직접 계산한다. 오늘은 기존 TTL 경로를 유지한다. 출력 필드와 close/최대 총잔량/가격별 최대의 세 소스는 그대로다.

총잔량 최대 대표는 20개 수량의 합으로 순위를 복원한다. 최대 합이 같으면 `(ask_p1, ask_q1, bid_p1, bid_q1, …, ask_p10, ask_q10, bid_p10, bid_q10)` tuple의 큰 값을 선택한다. 직접 SQL도 같은 규칙이다. 마지막 대표는 시각, 같은 시각이면 레벨 tuple로 고른다. 이전 SQL은 이 동률 대표를 명시하지 않았으므로 **동률 사례의 대표 레벨은 바뀔 수 있다**. depth kind 버전만 8→9로 올려 구 대표가 파생에 섞이지 않게 했다. 다른 지표 캐시는 무효화하지 않는다.

가격별 최대는 각 가격의 최대 수량을 합치고 ask 오름차순/bid 내림차순을 유지한다. 시간은 KST 자정 기준으로 묶어 7분처럼 UTC epoch 정렬과 다른 경우도 정확하다. 입력은 기존 캐시의 불변 객체로 취급한다.

## 실데이터 계산 측정

3종 원본 parquet를 사용했다. 워밍업 후 5회 중앙값, 직접 조회는 실제 build_depth_heatmap_slice(cache=None)의 SQL+모델 변환, 파생은 이미 준비된 1분 모델의 reaggregate_depth_heatmap이다. HTTP/JSON/Canvas 시간과 1분 캐시 읽기 비용은 아래 표에 포함하지 않는다. 세 종목 × 5/7/15분 전부 직접 결과와 파생 결과가 완전히 일치했다.

| 종목/날짜 | 봉 | 직접(ms) | 1분 모델 파생(ms) |
|---|---:|---:|---:|
| 000660/20260623 | 5분 | 48.205 | 2.423 |
| 000660/20260623 | 15분 | 47.440 | 2.728 |
| 005930/20260904 | 5분 | 87.250 | 3.510 |
| 005930/20260904 | 15분 | 80.490 | 1.471 |
| 287840/20260904 | 5분 | 33.914 | 3.653 |
| 287840/20260904 | 15분 | 25.772 | 3.478 |

전체 원시 수치와 재현 Python을 인접 파일에 보존했다. 프로젝트 루트에서 `PYTHONPATH=.`와 프로젝트 Python으로 실행한다. 원본 데이터가 있어야 하며 사용자 서버와 벤더 자격증명을 사용하지 않는다.

## 선택 소스만 응답하는 변경의 판단

세 소스 전체와 close만 남긴 동일 모델 JSON의 크기는 각각 428,789→112,148 / 390,882→131,344 / 302,471→97,946바이트였다. raw payload 절감은 분명하다. 비교용 gzip 크기도 JSON에 있지만 **현재 서버는 압축하지 않는다**(ADR-0154); 압축 수치를 실제 응답량으로 해석하지 않는다.

이번에는 선택 응답을 구현하지 않았다. 현재 프론트는 세 소스가 모두 존재한다는 계약으로 즉시 토글하며, 소스를 빠뜨리면 새 요청의 로딩·오래된 응답 차단·query key·레전드 상태를 함께 바꿔야 한다. 실제 원격 네트워크와 토글 빈도/지연의 비교는 아직 없다. 계획의 조건에 따라 세 소스 즉시 전환을 유지하고 계산 캐시 재사용을 적용한다. 원격 대용량 기간의 payload가 다음 병목으로 확인되면 별도 UI/API 작업으로 진행할 수 있다.

## 회귀 검증

- 직접 SQL↔파생의 전체 wire 비교: 3/5/7/15분, 동률·동일 시각·빈 구간·세션 상하한·장중 VI.
- 원시 입력 순서를 뒤집어도 동률 결과가 같고, 기존 1분 모델/배열을 수정하지 않는다.
- 실제 builder: 1분 캐시가 있으면 원시 스캔 0회, 없으면 요청 봉 조회 1회(1분 강제 생성 없음).
- 구버전 8 캐시로는 파생하지 않고 새 직접 조회를 수행한다.

## 디스크 읽기·결과 저장을 포함한 builder 측정

별도 임시 디렉터리에서 매번 새 PastIndicatorsCache를 생성해 5분 조회를 5회 측정했다. 기준은 1분/5분 캐시가 모두 없는 경우이며, 비교군은 디스크에만 1분 캐시가 있는 경우다. 둘 다 5분 결과 저장까지 포함하고, 1분 캐시를 미리 만드는 비용은 제외한다. 후자는 실제로 `get_depth`가 JSON을 읽고 모델을 복원한 뒤 파생하는 경로다. 캐시 파일 생성은 테스트 전용 임시 디렉터리에서 수행했다.

| 종목/날짜 | base 없음 중앙값(ms) | disk 1m base 중앙값(ms) |
|---|---:|---:|
| 000660/20260623 | 71.072 | 31.992 |
| 005930/20260904 | 76.470 | 29.493 |
| 287840/20260904 | 35.763 | 29.743 |

각 결과는 동일했다. 디스크 파싱·쓰기 때문에 순수 파생 1.5~3.8ms가 builder 전체 시간은 아니다. 거래가 적은 날짜의 이득은 작다. 인접 depth-disk-performance.json 및 depth-disk-benchmark.py.txt에 원시 결과와 재현 코드를 보존했다.
