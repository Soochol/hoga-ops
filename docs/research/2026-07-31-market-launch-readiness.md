# 시장 출시(다중 사용자) 준비도 분석 — 한계점과 방안

2026-07-31. 질문: **현재의 hoga-ops 를 상용 서비스로 시장에 내놓아 여러 사람이 동시에
사용하게 되면 어떤 한계가 있고, 각각 어떤 방안이 있는가.**

분석 방법: 코드베이스·ADR·실측 기록을 6개 관점(아키텍처, 보안·멀티테넌시, 외부
의존성·법적 리스크, 데이터 계층, 운영, 제품·프론트엔드)에서 병렬 검토한 뒤 누락
점검(금융규제·정확성 책임·라이선스·배포 경로)을 추가로 수행했다. 모든 항목은 실제
파일·ADR 근거를 갖는다 — 추측 항목은 없다.

## 결론 요약 (TL;DR)

hoga-ops 는 **명시적으로 기록된 단일 사용자 로컬 도구**다(ADR-0036, README "Access
model"). 다중 사용자 상용화의 장애물은 버그가 아니라 **설계 전제 그 자체**이며, 크게
세 겹이다:

1. **사업·법적 전제가 없다 (기술 이전의 문제).** KRX 시세 재배포 라이선스 부재,
   hogaplay 비공식 스크래핑 의존, 개인 명의 증권사 앱키의 대리 사용, 유사투자자문업
   규제 미검토. 이 층이 해결되지 않으면 코드 품질과 무관하게 출시 자체가 불가하다.
2. **멀티테넌시가 0 이다.** 인증·사용자 개념·데이터 격리·사용량 제한·감사 로그가
   전부 없다. 이는 실수가 아니라 ADR-0036 이 채택한 결정이고, 같은 ADR 이 "Multi-user
   배포 검토" 를 supersede 트리거로 스스로 명시해 두었다.
3. **수평 확장 경로가 봉인되어 있다.** 단일 프로세스 인메모리 상태, data_dir flock
   단일 소유자(ADR-0094), 프로세스-로컬 KIS 토큰버킷, 로컬 파일시스템 단일 저장소.
   인스턴스를 늘리면 상태 불일치이거나(이벤트 유실) 유해하다(쿼터 2배 소모).

긍정적 측면: 이 프로젝트의 ADR 들은 단일 사용자 전제를 무의식적 가정이 아니라
**명시적 결정 + 재검토 트리거**로 기록해 두었다(ADR-0036 Trigger Conditions,
ADR-0053/0088/0095 Future signals). 상용화 검토 시 이 트리거 목록이 그대로 작업
백로그가 되며, 실측 수치(KIS 15/s, WS 41등록, DuckDB 87GB OOM, raw 704GB 사고)가
ADR 에 남아 있어 전환 비용 산정을 다른 프로젝트보다 정확히 할 수 있다.

## 0. 전제 — 현재 설계가 명시하는 것

- **인증 없음이 의도된 결정**: README "This API has no authentication. That is a
  deliberate, recorded decision (ADR-0036)". 보안 경계는 loopback 바인딩 하나
  (`hoga/cli.py` `host="127.0.0.1"` 하드코딩, `--host` 옵션 미노출).
- **`origin_guard.py` 는 인증이 아니다**: 브라우저 CSRF 만 막고 curl·스크립트는
  설계상 통과. 허용 origin 도 dev 포트(`localhost:5173/5174`) 하드코딩.
- **리소스 캡의 의도적 부재**: ADR-0036 — retry MAX_ATTEMPTS 없음, enqueue batch cap
  없음("19000101..20991231 → ~30k QueueItem"). 근거가 전부 "단일 사용자 로컬
  배포에서 누가 그런 입력을 하겠는가".
- **한 data_dir 당 쓰기 가능한 백엔드는 1개**: ADR-0094 flock. 비소유 인스턴스는
  읽기 전용 + 뮤테이션 503. "NFS 는 범위 밖" 명시.

## 1. 사업·법적 전제 (출시 가능성 자체) — 최우선 해결 대상

### 1-1. KRX 시세 재배포 라이선스 부재 [critical]

제품 전체가 KRX 10호가/체결/거래원 데이터를 최종 사용자에게 표시·저장·리플레이하는
구조인데, 데이터 출처가 전부 개인용 채널(개인 hogaplay 세션, 개인 KIS/키움 앱키)이다.
저장소 전체에 시세 이용·재배포 계약 문서는 0건. 개인이 본인 명의 키로 본인이 보는
것은 "개인 이용"이지만, 서버가 수집한 시세를 불특정 다수에게 유상 표시하는 순간
**재배포(redistribution)**가 되어 코스콤/KRX 시세분배 계약이 필요하다. KIS·키움
Open API 약관도 제3자 제공·재판매를 허용하지 않는다.

- **단기**: 출시 전 법률 검토 선행. 파일럿은 BYOK(사용자 본인 API 키 연동)로 한정해
  "각자 자기 키로 자기 화면의 시세 수신" 구조로 재배포 논점 최소화. 운영자 키로
  수집한 데이터를 타 사용자에게 보여주는 경로(공유 캐시 팬아웃 포함)는 차단.
- **장기**: 코스콤/KRX 정식 시세분배 계약 → 벤더 피드 1회 수신 → 멀티테넌트 팬아웃.
  지연시세(20분) 상품은 라이선스 조건이 달라 무료 티어 전략으로 병행 검토.

### 1-2. hogaplay 비공식 스크래핑 의존 [critical]

`hoga/collector/client.py` — Chrome UA 위장 + 로그인 세션 쿠키 복사(`.cookie`)로
first.php 를 순회 수집. 계약·API 없는 업스트림(ADR-0021)이고, 쿠키 만료 시 수집 풀
전체 정지 + 수동 갱신(무인 운영 불가). 상용 데이터 공급망으로 삼으면 약관 위반이
거의 확실하고, hogaplay 가 쿠키 무효화·IP 차단·포맷 변경만 해도 파이프라인이
즉사한다. **업스트림 보존 ~18h** 제약은 SLA 정의 자체를 불가능하게 한다(캡처 실패가
18시간 내 복구되지 않으면 전 사용자 공통의 영구 데이터 홀 → 환불/보상 이슈).

- **단기**: 상용 빌드에서 hogaplay 경로 제거 또는 운영자 전용 오프라인 도구로 격리.
  공백은 이미 있는 자체 실시간 수집(kiwoom_live 캔들 합성 ADR-0125, kis_api 복구
  ADR-0109)으로 메우는 방향을 기본값으로 승격.
- **장기**: 장중 실시간 자체 수집 + 자체 다년 아카이브로 "사후 18h 창 스크래핑"
  카테고리 자체를 제거. 또는 코스콤 데이터몰 등 정식 과거 틱 데이터 벤더 계약.

### 1-3. 개인 증권계좌 앱키의 서버 대리 사용 [critical]

계정 모델이 (운영자 1인) × (앱키 0..N)이고 테넌트 개념이 없다(`kis_runtime.py` 의
정수 id 싱글톤 dict). 두 갈래 모두 문제: (a) 운영자 키 공용 — 개인용으로 발급된
실전투자 앱키로 불특정 다수 서비스는 약관 위반 + 키 정지 시 전 사용자 동시 장애.
(b) BYOK 수탁 — 타인의 증권계좌 앱키/시크릿을 서버가 보관하게 되는데 현재는 .env
평문 + 로컬 디스크 토큰 캐시라 암호화 보관·접근 통제·감사가 전무하고, 전자금융·
개인정보 규제 검토가 필요한 다른 리스크 등급이 된다.

- **단기**: (1) 키가 서버에 오지 않는 형태 — 현 구조를 데스크톱/셀프호스트 상품으로
  포장 — 우선 검토. (2) 호스팅형 BYOK 는 KMS/vault 암호화 + 테넌트 격리 + 감사부터.
- **장기**: 증권사 정식 제휴(법인/핀테크 채널) 또는 사용자 동의 기반 위임 토큰 모델.
  시세 공급은 벤더 계약으로 분리해 사용자 키는 계좌 고유 기능에만.

### 1-4. 자본시장법상 유사투자자문업 리스크 [high]

시그널 알림(`signal_alert_monitor.py` 총잔량 급증·매도총잔량 갱신), 스크리너
돌파/신고가 조건검색, 투자자 동향 추정 표시는 불특정 다수 유상 제공 시
**유사투자자문업 신고 대상 여부**가 정면으로 걸린다(미신고 영업은 형사처벌 대상).
면책 고지·투자권유 아님 표시·이용약관이 저장소 전체에 없다.

- **단기**: 법률 검토로 서비스 정의 확정. 1차 출시에서 시그널·스크리너를 제외하거나
  "데이터 표시(시세 단말)" 수준으로 한정 + 전 화면 면책 고지·약관·위험고지.
- **장기**: 유사투자자문업 신고 후 합법적 신호 제공, 또는 데이터 단말 포지셔닝.
  표현 컴플라이언스 리뷰 절차 + 약관·개인정보 처리방침 등 법무 문서 체계.

### 1-5. 파생·추정·합성 값의 정확성 책임 [high]

거래대금이 근사식(`(O+H+L+C)/4 × volume`)이고, 투자자 추정치는 장중 가집계·잠정이며,
kiwoom_live 1분봉은 WS 틱 '합성'(ADR-0125 스스로 화질 차이 기록), 같은 (code,date)
캔들이 소스 사다리(ADR-0121/0124) 구성에 따라 달라진다. 단일 사용자에게는 ADR 로
트레이드오프를 알고 감수하는 합리적 설계지만, 유료 고객에게는 "서비스가 보증하는
값"으로 읽혀 투자 손실 분쟁으로 직결된다. UI 면책·방법론 고지는 전무.

- **단기**: 파생·추정·합성 값 전부에 정의·한계 고지(근사식 툴팁, 추정/잠정 배지),
  백엔드 `data_warnings` 를 사용자 표면으로, 약관에 정확성 비보증 조항.
- **장기**: 지표 방법론 문서 공개, 소스별 품질 등급 표기, KIS 공식값 주기 대사
  (reconciliation), 정정 공지 절차 등 데이터 품질 거버넌스.

### 1-6. 데이터 출처·라이선스 컴플라이언스 [medium]

- 스크리너 일봉 코퍼스의 깊은 역사 구간은 dev-tradingview DB 1회 시드가 유일
  원천(ADR-0057)인데 수집 경로·이용 조건 기록이 없다 → 상용 상품에 출처 불명
  데이터가 섞인다. 시드 유래 구간 재시드 또는 제거 + provenance 메타데이터 도입.
- lightweight-charts(TradingView, Apache-2.0)의 attribution 고지가 없고, 저장소
  LICENSE/NOTICE 파일·CI 라이선스 스캔도 없다. 개인 도구는 "배포"가 아니라 의무가
  발동하지 않지만 상용 웹 서비스는 고지 의무가 생긴다. → attribution UI +
  THIRD-PARTY-NOTICES 생성 + CI 라이선스 게이트.

## 2. 인증·멀티테넌시 부재

### 2-1. 인증·인가 전면 부재 + 파괴적 엔드포인트 노출 [critical]

비-loopback 바인딩 순간, 포트에 닿는 누구나 자격증명 없이: 캡처 큐 전량 취소
(`POST /cancel-all` — 장중이면 오전 데이터 영구 소실), 라이브 수집 중단
(`POST /api/live/control` stop), 저장뷰·프리셋·관심종목 삭제(DELETE 계열 ~54개
상태변경 라우트), catchup 대량 스크래핑 유발이 가능하다. 파라미터 없는 상태변경
라우트 6건은 form POST 만으로 도달(origin_guard docstring 실측).

- **단기**: 리버스 프록시(TLS + OAuth 프록시) + 파괴적 라우트에 admin 토큰 +
  감사 로그 + soft-delete. WS 핸드셰이크에도 세션 검사(ADR-0053 이 이미 예고).
- **장기**: FastAPI Depends 전역 인증(라우터 빌더 패턴이라 주입 지점은 명확 — 산정:
  수 주) + 리소스 소유권 모델 + 시스템 동작(수집 start/stop)은 운영자 권한 분리.
  ADR-0036 공식 supersede ADR 작성이 선행 조건.

### 2-2. 사용자 데이터 격리 전무 [critical]

watchlist.json, heatmap.json, screener/saves.json, study_views/, layout preset,
live_settings.json 이 전부 **data_dir 당 단일 파일 + user_id 개념 없음**. 두 번째
사용자가 접속하는 순간 전원이 같은 관심종목·저장뷰·프리셋을 읽고 덮어쓰고 지운다.
watchlist 는 캡처 대상 선정의 입력(ADR-0079)이라 한 사용자의 상태 변경이 전체 수집
파이프라인을 바꾼다. 파일 손상 시 "빈 문서로 리셋" 정책(versioned_json_file)은
상용에선 전 사용자 상태 동시 소실이다.

- **단기**: 스토어가 전부 `data_dir` 인자를 받는 얇은 구조라
  `users/{user_id}/` 네임스페이스 삽입으로 파일 단위 격리(변경 범위가 경로 함수에
  국한 — 좋은 밑그림).
- **장기**: 사용자 상태를 Postgres(user_id FK + row-level 인가)로 이전. 시세
  데이터(parquet)는 사용자 무관 공용 코퍼스로 공유 유지 — **이 이원 분리가 작업량을
  크게 줄이는 핵심 설계 판단**이다.

### 2-3. 프론트엔드 상태의 절반이 브라우저 localStorage [critical]

지표 셋업 전체(`live.indicators.v2` + `hoga.chart.prefs.v1`), 워크스페이스 창 배치,
테마, 드로잉 기본값 등 30개+ 키가 브라우저 프로필 귀속. PC 교체·캐시 삭제 시 분석
셋업이 통째로 증발하고, 서버 저장(watchlist·프리셋)과 반쪽씩 갈라진 split-brain
경험이 된다.

- **단기**: 프로필 export/import(JSON). 키가 전부 버전드(.v1/.v2)이고 zustand
  persist 퍼널이 단일 창구라 스냅샷 비용이 낮다.
- **장기**: 계정 도입 후 `GET/PUT /api/profile` 서버 저장으로 이전. 기존
  PresetStore(낙관적 동시성 `expected_updated_at_ms`)를 user-scoped 로 일반화.

### 2-4. 감사 로그·rate limit·사용량 제한 부재 [high]

행위자 식별이 원리적으로 불가능(인증이 없으므로), rate limit 미들웨어 없음,
ADR-0036 의 무상한 enqueue/retry 와 결합하면 익명 클라이언트가 30k 아이템 enqueue·
고비용 /api/range 버스트로 전체 서비스를 DoS 할 수 있다(ADR-0085 실측: 병렬 몇
개로 87GB OOM).

- **단기**: per-IP rate limit(프록시) + enqueue batch cap·MAX_ATTEMPTS 즉시
  도입(ADR-0036 supersede — ADR 이 예약해 둔 작업) + 상태변경 공통 감사 로그.
- **장기**: 사용자/플랜별 쿼터 시스템(API 호출·캡처 잡·쿼리 비용) + admission
  control + append-only 감사 저장소.

## 3. 업스트림 용량·쿼터 — 산식이 "계정 수"의 함수이지 "사용자 수"의 함수가 아님

실측된 물리 상한(전부 ADR 에 기록):

| 자원 | 상한 | 근거 |
| --- | --- | --- |
| KIS REST | 앱키당 ~15/s (goodput ~13.4/s) | ADR-0100 실측 |
| KIS WS | 연결당 등록 41 하드상한 → 계정당 13종목 | ADR-0101 실측 (현재는 ADR-0118 로 키움 WS 전담) |
| 키움 WS | 앱키당 200종목, 앱키당 세션 1개(2세션 상호 킥) | coverage.py, kiwoom_ws_client.py 실측 |
| 온디맨드 실시간 풀 | 124 고정, 만석 시 신규 차단 | ADR-0118 |
| KIS 일일 누적 쿼터 | **미검증** (현재 ~432만 콜/일 사용) | ADR-0102 |

동시 사용자 10명이 서로 다른 종목을 보기만 해도 실시간 슬롯이 뷰 전환 경쟁으로
스래싱되고, 한 사용자의 5년치 backfill 이 다른 모두의 오늘자 캡처를 굶긴다(공정성
차원이 스케줄러에 없음 — user_visible/background 2계층뿐). ADR-0036 이 정확히 이
시나리오("한 사용자의 무제한 retry 가 다른 사용자의 quota 를 갉아먹는")를 supersede
트리거로 명시했다.

추가로 **"보기"와 "수집하기"가 결합**되어 있다: WS 뷰 구독이 수집 슬롯을 직접
점유하고(`ws.py` → `lifecycle.on_view_subscribe`), 누구든 `/api/live/control` stop
으로 전체 수집을 죽일 수 있다. 뷰어가 곧 수집 오퍼레이터인 설계다.

- **단기**: 테넌트별 rate limit + fair queuing 을 KisCapacityScheduler 큐 rank 에
  추가(ADR-0082 구조 위에 한 차원 증설). 같은 종목을 보는 N명은 콜 1회가 되도록
  request-key coalescing 을 사용자 차원으로 확장. 수집 대상은 서비스가 정한 고정
  유니버스로 운영하고 뷰 구독은 재배포만 담당하게 분리. live/control 은 관리자
  권한으로. 일일 쿼터 소진 실측을 최우선 운영 과제로.
- **장기**: 수집 플레인·서빙 플레인 완전 분리 — 수집 데몬은 유니버스 기반 독립
  운영(1회 수신), 서빙 계층이 전 사용자에게 팬아웃하는 1:N 모델. 이 구조에서만
  사용자 수와 업스트림 콜 수가 디커플링된다(단, 1:N 재배포는 §1-1 라이선스 선행).

## 4. 아키텍처 — 수평 확장을 막는 지점 전수 목록

`uvicorn --workers 4` 조차 즉시 깨지는 구조다. 차단 지점 12개:

1. `hoga/cli.py` — 단일 워커·host 하드코딩.
2. `captures.py` — 캡처 큐 전체(_queue/_active/_done/_fail_streaks)가 모듈 전역
   인메모리. `_done` 은 "무한히 자란다"(주석).
3. `queue_ownership.py` + ADR-0094 — 로컬 FS flock 단일 소유자, NFS 범위 밖.
4. `events.py` EventBus + `ws.py` — in-process asyncio.Queue pub-sub. 워커 A 의
   이벤트가 워커 B 의 WS 클라이언트에 전달 안 됨. 느린 구독자 프레임 drop
   (maxsize 64/2048) → "어떤 사용자 화면만 멎는" 비결정 장애.
5. `lifecycle.py` — 라이브 스트림 상태·LiveBuffer 프로세스 전역(800종목 최악
   ~3.7GiB, "메모리는 종목 수의 선형 함수" — 미결 리뷰 Major).
6. `kis_runtime.py` — KIS 토큰버킷이 프로세스 전역 dict. 인스턴스 2개면 합산
   송신률이 앱키 한도 2배 초과 → EGW00201 폭증(ADR-0100 이 실측한 실패 모드).
7. ADR-0082 — capacity scheduler 가 "process-local per data_dir".
8. `scheduler.py` + lifespan — daily-loop·프로모터·워치독이 프로세스마다 무조건
   기동, 리더 선출 없음(scheduler_state.json 은 원자적 선점 아님).
9. `today_ttl_cache.py`·`slice_coalescer.py` — TTL 캐시·single-flight 프로세스
   로컬 → 인스턴스 수만큼 중복 계산.
10. ADR-0095 — KIS 분봉 캐시 memory-only → 인스턴스마다 쿼터 중복 소모. (같은
    ADR 이 "멀티 인스턴스가 되면 재검토" 트리거와 Reversal 설계를 이미 준비해 둠.)
11. 로컬 FS data_dir 단일 트리 + atomic rename/mtime 검증 — 공유 스토리지 일관성
    미설계. 라이브 수집·Today Promotion 은 flock 보호 범위 **밖**이라 이중 기동 시
    last-writer-wins 로 값이 요동.
12. `queries.py` — QueryEngine 이 프로세스 수명 공유 `:memory:` DuckDB.

**DuckDB 메모리**: ADR-0085 실사고 — anon-rss 87~90GB, 하루 3회 OOM-kill, 스필
356GB. 완화(v2.1: 쿼리 0.53s/450MB) 후 동시성 가드를 은퇴시켰는데 그 근거("동시
peak 계산 수는 동시 /api/range 요청 수로 자연 상한")가 **사용자 1인의 탭 수
가정**이다. 동시 12건 실측 +5.5GB → 동시 100건이면 수십 GB. single-flight 는 동일
키만 접으므로 사용자마다 다른 종목·날짜면 전혀 접히지 않는다. OOM 시 수집까지 동반
사망(같은 프로세스) — 첫 붕괴 지점이다.

- **단기**: 역할 분리 — 수집(라이브 스트림·캡처 워커·스케줄러)을 별도 프로세스로
  추출, API 는 읽기 전용 복수 기동(ADR-0094 read-only boot 재활용). heavy-query
  전역 세마포어 재도입(이번엔 "멀티유저 메모리 예산" 근거). WS 이벤트 채널에
  사용자/토픽 필터.
- **장기**: 상태의 외부화 — 캡처 큐 → 외부 작업 큐(Postgres/Redis), EventBus·틱
  fan-out → Redis pub/sub·NATS + WS 게이트웨이, 캐시·single-flight → 공유
  캐시/분산 lock, 지표는 수집 완료 시 선계산(materialized)으로 전환. 그 위에서
  stateless API 워커 N + 수집 데몬 1(리더 선출)의 표준 토폴로지.

## 5. 데이터 계층

- **로컬 디스크가 유일한 DB** (`atomic_write.py` 주석 그대로). 성격이 다른 3종
  (불변 시장 데이터 / 가변 사용자 상태 / 재구축 가능 캐시)이 한 트리에 공존해
  계층별 보존·복제 정책을 따로 적용할 수 없다.
- **백업·DR 전무**: parquet 이 유일 사본, raw 는 3일·JSONL 아카이브는 7일 후 자동
  삭제, 업스트림 재수집 창 ~18h → **소실 = 영구 소실**. 디스크 100% 실사고 이력
  (raw 704GB, ADR-0075). promoted parquet 과 kis-past-indicators 는 프루닝 없이
  무한 증가.
- **용량 산정**: 유동성 상위 종목 snapshots ~5.7MB/일 실측 → 전 종목(~2,700)
  수렴 시 수십 GB/일, 연 수 TB. 핫/콜드 계층 개념 없음.
- **완결성 메타데이터가 파일 존재·mtime·벽시계 기반** — 분산 스토리지에서 캐시
  무효화·DiskState 분류가 오작동할 설계.

권고 구조 (기존 레이아웃이 이전에 유리하다):

1. **시장 데이터(공유가 정답)**: `parquet/{date}/{code}/{source}`(ADR-0037)가 Hive
   파티셔닝에 1:1 매핑 → S3 + DuckDB httpfs 쿼리 노드, 장기적으로 Iceberg/Delta
   또는 ClickHouse. 사용자별 복제는 절대 금지(쿼터·용량 양쪽에서 유일하게 스케일
   되는 형태가 공유 수집이다).
2. **사용자 상태(분리가 정답)**: 단기 `users/{user_id}/` 네임스페이스, 장기
   Postgres. 기존 schema_version 전진 마이그레이션 관행(ADR-0065/0070)을 이식.
3. **캐시(재구축 가능)**: 인스턴스 로컬 메모리 위에 공유 티어(Redis + object
   storage). "과거=불변/오늘=TTL" 이원 계약(ADR-0092)은 그대로 유효.
4. **백업 즉시**: 장 마감 promote 완료 시점 오프사이트 증분 백업(restic/rclone)
   + 월 1회 복원 리허설 + 백업 미확인 시 prune 보류.

## 6. 운영·신뢰성

- **SPOF**: 프로세스 1개가 API·수집·큐·스케줄러 겸업. 장중 사망 = 전 사용자 서비스
  중단 + 복구 불가 데이터 결손(~18h 창). 배포물은 systemd **user** 유닛 1개가 전부
  (Dockerfile·compose·k8s 없음). 저장은 10초 주기 flush 라 사망 시 최대 10초분 +
  이후 전 구간 소실.
- **배경 태스크 자동 복구 부재**(ADR-0088 의도적): today-promoter 침묵 사망 = 전
  사용자 당일 승격 정지, 새벽 사망은 신고까지 방치. `/health?deep=1` 이 503 을 내게
  만들어져 있으나 **그 503 에 반응하는 감독 주체가 배선되어 있지 않다** — 신호는
  있는데 액추에이터가 없다.
- **관측성 부재**: 메트릭·트레이싱·경보 의존성 0건. 로그는 로컬 RotatingFileHandler.
  경보 채널이 "화면 앞의 사용자"(토스트). ADR-0064 실사고(폴러 침묵 사망을 저녁에
  데이터 구멍으로 발견)가 정확히 이 부재의 비용.
- **CD·롤백·무중단 배포 부재**: CI 는 상용 수준에 근접(typecheck 3-project + 테스트
  7천+ 건 + e2e 게이트)하지만 그 뒤가 없다. 설정 변경조차 재시작 필요(ADR-0082/
  0100), 마이그레이션은 부팅 블로킹 원샷, blue-green 은 flock 구조상 불가.
- **프론트엔드 프로덕션 서빙 경로 자체가 없다**: dist 를 소비하는 배포 경로 부재,
  API base 가 정적 `public/config.json` 의 localhost:8000 고정.

단계별 운영 스택 (순서 논리: 관측 없이 분리하면 장애를 못 보고, 분리 없이 멀티 AZ 는
성립하지 않으며, 라이선스 없이 1:N 재배포는 법적 리스크다):

| 단계 | 기간 | 내용 |
| --- | --- | --- |
| Phase 0 | 수 주 | systemd system 유닛 승격 + deep-health 기반 자동 재시작 배선(코드 무수정, timer 1개) + 외부 업타임 프로브·경보 + 일일 오프사이트 백업 + 배포 윈도 정책(장전/장후) |
| Phase 1 | 1~2개월 | Prometheus/Grafana 계측(request_timing·KIS 스케줄러 snapshot), 중앙 로그, 장중 온콜, per-tenant rate limit·enqueue cap(ADR-0036 supersede), KIS 일일 쿼터 실측 |
| Phase 2 | 3~6개월 | 수집기/API 프로세스 분리, 컨테이너화, CD + 스모크 게이트, single-tenant-per-process 샤딩으로 초기 유료 사용자 수용 |
| Phase 3 | 6개월+ | 상태 외부화(object storage + 외부 큐 + pub/sub 팬아웃), k8s 멀티 AZ, 수집 1:N 재배포 모델(시세 라이선스 선행), SLO/error budget 운영 |

## 7. 제품·프론트엔드

- **온보딩이 개발자 전용**: pip install·`.cookie` 생성·`.env` 편집·systemd 설정이

  장기: SaaS 온보딩 퍼널 또는 데스크톱 패키징(Tauri 등).
- **에러 UX 가 운영자 어휘**: UI 에러가 `.env`/`.cookie` 파일 편집을 지시
  (`upstream-hints.tsx`). 에러 분류 체계 자체는 잘 설계되어 있어 문구·액션 계층만
  교체하면 된다. → "사용자 조치 가능 / 서비스 장애 / 플랜 한도" 3계층 에러 정책.
- **데스크톱 전용**: 최소 1026×702px, 창 드래그·hover 기반 인터랙션이 마우스 전제.
  한국 리테일 주 사용 환경은 MTS(모바일) — 모바일 제품은 사실상 신규 제품 1개
  분량임을 로드맵에 반영. 단기는 읽기 중심 모바일 요약 뷰 + 데스크톱 전용 명시.
- **결제·플랜·미터링 인프라 0건**: 자연스러운 과금 축은 이미 물리 상한과 일치한다 —
  실시간 슬롯 수(계정당 13종목), 히스토리 보관 기간(HOGA_RETENTION_DAYS 사용자별화),
  동시 캡처 수(HOGA_MAX_CONCURRENT 사용자별화).
- **i18n 부재 [low]**: 한국 시장 우선이면 현상 유지 + `lang="ko"` 수정. 신규
  컴포넌트부터 문자열 분리 컨벤션화로 부채 증가만 멈춘다.

- **10명**: KIS/키움 실시간 슬롯 경쟁(계정당 13종목)과 사용자 간 간섭이 먼저
  무너진다 — 뷰 구독 스래싱, kiwoom_full_house, 누구든 수집 stop 가능(인증 부재).

## 9. 권장 진행 순서 (종합)

1. **법무 게이트 (다른 모든 것에 선행)**: 시세 재배포·유사투자자문·개인 API 키
   약관 검토로 **출시 형태 결정** — (a) 셀프호스트/데스크톱 상품(키가 서버에 안 옴,
   현 구조 최대 재활용), (b) BYOK 호스팅(중간), (c) 정식 라이선스 SaaS(최대 투자).
2. **ADR-0036 supersede**: enqueue cap·MAX_ATTEMPTS·rate limit — ADR 이 스스로
   예약해 둔 작업이고 코드 변경량이 작다.
3. **인증 + 사용자 네임스페이스**: FastAPI Depends 전역 주입(수 주) +
   `users/{user_id}/` 파일 격리(경로 함수 국한) → 클로즈드 베타 가능 상태.
4. **수집/서빙 분리 + Phase 0-1 운영 스택**: SPOF 해소와 관측이 유료화의 전제.
5. **상태 외부화 재아키텍처(Phase 2-3)**: 유료 사용자 증가 추세가 확인된 뒤에.
   그 전에 하면 과투자, 그 후에 하면 늦다 — 트리거는 "단일 인스턴스 자원 상한의
   실측 접근"으로 정의해 둘 것.

셀프호스트/데스크톱 경로 (a)는 과소평가하지 말 것: 인증·멀티테넌시·라이선스·수평
확장 문제의 대부분이 "사용자 머신 = 단일 사용자"로 환원되어 현 아키텍처를 거의
그대로 상품화할 수 있다. 호스팅 SaaS 는 위 1~5를 전부 통과해야 한다.
