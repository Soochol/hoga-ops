# 총잔량 보조지표 알고리즘 분석

측정일: 2026-09-07. 분석 코드: `3fc19f903` (PR #1750 병합 내용).
범위: 총잔량 선·봉 내부 최댓값·급증 마커·과거 조회 비용. 아래 분석 이후 적용한 변경은 마지막 절에 기록했다.
특정 오류 신고의 재현이 아니라 알고리즘·성능 감사이므로 정상 경로의 비교 측정을 사용했다.

## 판단

계산식 전면 교체는 필요하지 않다. 이미 단일 GROUP BY 집계, 1분 정본 캐시,
과거/당일 분리 투영, 마지막 점 증분 업데이트를 사용한다. 최대벽에서 확인했던
대규모 구버전 캐시 재계산은 현재 총잔량 표본에서 나타나지 않았다.
원본 집계의 사전 스캔과 1분→1분 재집계를 줄이는 작은 최적화는 가치가 있다.

## 계산 규칙

- 과거 데이터는 `hoga/tables/snapshots.py::query_bucketed_ratio`에서 매도 10단계와
  매수 10단계 잔량을 각각 합한다. 시간은 HHMMSSmmm를 자정 이후 밀리초로 바꾼 뒤 버킷팅한다.
- 기본 선은 각 봉의 마지막 유효 연속거래 스냅샷 값이다. 봉 안의 평균이나 합계가 아니다.
  세션 경계와 3호가 붕괴 구조로 동시호가·VI를 제외한다. 완전히 제외된 봉은 (0,0)이다.
  유효 호가가 전혀 없는 퇴화 캡처의 fallback 계약은 별도로 존재한다.
- 분봉 내 최댓값 모드의 매도·매수는 각자 독립 최댓값이다. 두 최댓값의 시각은 다를 수 있다.
  기본 대표값 및 호가비 극값의 매도·매수 쌍은 각각 같은 스냅샷에서 함께 선택한다.
- 큰 분봉은 `indicator_reaggregate.reaggregate_ratio`로 1분 결과를 다시 묶는다.
  마지막 유효 대표값과 각 방향 max를 보존한다. 과거는 디스크+메모리 캐시,
  오늘은 짧은 프로세스 TTL로 1분 계산을 공유한다.
- 라이브 꼬리는 `createIncrementalHogaSeriesBuilder`가 SSE 총잔량 필드로 갱신한다.
  과거의 10단계 재집계와 입력 경로가 다르고, 당일 내부 max는 수신 표본에 의존한다.
- 급증 점은 `detectSurgeSide`의 하루별 상태 기계다. 기본값으로 이전 최고치의
  85% 미만으로 내려가면 재무장하고, 이후 95% 이상에 도달하면 표시한다.
  첫 값은 기준만 세운다. 재무장 전 더 높은 값이 나오면 기존 점이 새 꼭대기로 이동한다.
  따라서 확정 후 움직이지 않는 돌파 시각 표시는 아니다. 표시 시작 시각은 출력만 걸러낸다.
- 급증 판정은 최댓값 표시 모드에서도 마지막 대표값 기준이다. 점의 높이만 보이는 선을 따른다.
  선택적 호가단위 보정은 총잔량 선 자체가 아니라 급증의 비교 기준을 환산한다.
  tick 변화와 사다리 폭 확인 게이트를 함께 사용하며 기본 off이다(ADR-0151).

## 개선 후보와 우선순위

1. **사전 전체 스캔을 존재 확인으로 축소.** 현재 query_bucketed_ratio는
   `_last_continuous_intra_ms`로 마지막 시각을 전부 찾은 뒤 실제로는 None 여부만 사용한다.
   해당 호출만 동일 술어의 SELECT 1 ... LIMIT 1로 바꾸는 실험을 했다.
   원본 함수와 후보 함수를 같은 프로세스에서 번갈아 8회 실행하고 첫 회를 제외한 중앙값:

   | 날짜 / 종목 | 현재 | 존재 확인 후보 | 감소 |
   | --- | ---: | ---: | ---: |
   | 20260623 / 000660 | 34.327ms | 31.062ms | 9.5% |
   | 20260904 / 005930 | 58.742ms | 49.037ms | 16.5% |
   | 20260904 / 287840 | 18.281ms | 16.783ms | 8.2% |

   모든 반복의 결과가 같았다. 이득은 원본 계산에만 해당하며 캐시 적중 조회의 개선율이 아니다.
   실제 수정 시 마지막 시각이 필요한 다른 호출자는 유지하고, 퇴화·빈 데이터의 fallback을
   고정하는 테스트가 필요하다. 위 baseline과 앞 표는 서로 다른 측정 실행이다.
2. **1분 요청의 재집계 생략.** 이미 1분인 rows_1m을 1분으로 다시 묶는다.
   표본당 0.366~0.570ms를 사용했다. bucket_ms == 60000이면 원본 행을 바로 사용하는
   분기는 작고 효과가 명확하다. 반환 행의 불변성과 (0,0)·imb 동률 계약을 확인해야 한다.
3. **과거 추가 시 매수·매도의 공통 전처리 공유.** 두 선이 각각 갭 보충·정렬·축 변환을 한다.
   `withHogaGapSentinels`는 입력 복사 후 정렬하고, 결손 점이 생기면 다시 정렬한다.
   공유하거나 정렬된 입력용 병합 경로를 고려할 수 있지만, 데이터 순서·갭 연결선 계약이 있어
   정렬을 단순 삭제하는 것은 부적절하다. 단독 정렬의 절감량은 아래처럼 작다.

## 프론트 측정

현재 QUOTE_TOTALS_SPEC의 두 선 data()와 두 방향 markers()를 호출하는 임시 Vitest 하네스.
거래일당 390봉, 37봉마다 호가 결손이 있는 합성 데이터와 캔들 배열을 사용했다.
cold는 새 축으로 과거 캐시를 무효화한 변환, warm은 동일 축에서 마지막 매도값을 변경한 변환이다.
워밍 후 21회 중앙값이며 차트 라이브러리 setData·캔버스 그리기는 포함하지 않는다.

| 합성 거래일 / 호가 점 | 두 선 최초 변환 | 두 선 갱신 | 두 방향 급증 점 갱신 | 전체 배열 정렬 1회 |
| --- | ---: | ---: | ---: | ---: |
| 5일 / 1,895 | 0.946ms | 0.176ms | 0.052ms | 0.021ms |
| 30일 / 11,370 | 4.998ms | 0.311ms | 0.078ms | 0.185ms |
| 90일 / 34,110 | 20.531ms | 0.522ms | 0.046ms | 0.426ms |

과거/당일 분리 캐시가 잘 작동한다. 다만 concat과 seriesDataDiff의 이전 점 비교는 여전히
전체 길이에 비례하므로 틱 비용이 엄밀하게 O(1)인 것은 아니다. 과거 추가·축 교체 시에는
전체 투영과 setData가 필요하다. 최초 변환 개선이 반복 틱 최적화보다 우선이다.

## 후속 구현 (2026-09-07)

사용자 승인 후 개선 후보 1·2를 적용했다. 프론트 공통 전처리 공유는 적용하지 않았다.

- 총잔량 쿼리는 `_has_continuous_book_before_close`로 마감 경계 이전 deep book의
  존재만 확인한다. 기존 전체 MAX 스캔과 술어가 같으며 개장 하한을 새로 넣지 않는다.
  마지막 실제 시각을 사용하는 다른 지표의 `_last_continuous_intra_ms`는 유지한다.
- `reaggregate_ratio`는 1분 요청이면 정본 행 배열을 그대로 반환한다. 과거 캐시와
  오늘 TTL 호출자가 함께 이득을 얻는다. 행은 frozen이고 두 호출자는 읽기만 한다.
- 계산 결과와 캐시 스키마가 같으므로 캐시 버전을 올리지 않는다.

수정 전 신규 회귀 테스트 5개 실패를 확인했다. 수정 후 관련 테스트 151개 통과,
wallclock 1개 제외. 개장 전 deep만 있는 경우·마감 후 deep만 있는 경우·deep 부재의
fallback과 1분 정본 재사용을 포함한다.

실제 수정 함수를 기준 커밋의 함수와 교대로 실행했다. 원본은 워밍 제외 8회,
메모리 캐시 응답 생성은 워밍 제외 40회 중앙값이다. 앞선 탐색 실험과 별도 실행이라
공유 머신의 부하 차이가 있고, 작은 파일의 절대 이득은 특히 작았다.

| 날짜 / 종목 | 원본 계산 이전 → 이후 | 1분 캐시 응답 생성 이전 → 이후 |
| --- | ---: | ---: |
| 20260623 / 000660 | 32.988 → 28.438ms | 0.837 → 0.454ms |
| 20260904 / 005930 | 57.668 → 46.717ms | 0.887 → 0.483ms |
| 20260904 / 287840 | 12.483 → 12.011ms | 0.901 → 0.487ms |

매 반복의 전체 원본 반환값과 캐시 API 모델이 수정 전과 같았다. 세 파일 각각에서
1·3·5·10·15·30·60분 직접 집계와 1분 정본 파생 결과도 같았다.
이는 서버 계산 구간의 개선이며 브라우저 표시 전체의 개선율은 아니다.

최종 검증: 전체 Ruff 통과, 백엔드 전체 4,777개 통과·2개 생략·wallclock 13개 제외
(132.94초). 이번 구현은 백엔드만 변경했다.
