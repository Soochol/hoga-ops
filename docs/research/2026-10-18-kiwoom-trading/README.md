# 키움 주문 연동 검증 결과

2026-10-18 KST 기준으로 기존 주문 기능의 회귀, 키움 시세 인프라를 주문에 재사용할 때의
반례, 실전 주소의 계좌 조회 계약을 검증했다. **백엔드 264개와 프론트 181개가 통과했고,
실전 조회 26건을 수행했다. 신규·정정·취소 전송, WebSocket 신규 연결, 토큰 발급은 모두
0건이다.** 구현 설계는 [다중 증권사 주문 설계](../../plans/2026-10-18-multi-broker-trading.md)에 확정했다.

2026-10-19 구현 후 검증은 [implementation-validation.json](implementation-validation.json)에
별도로 기록했다. 백엔드 357개, 프런트 주문 관련 189개, 브라우저 81개와 핵심 반복 25회가
통과했다. 이 단계에서도 실제 증권사 주문은 보내지 않았다. 설정과 활성화 조건은
[호가주문 연동 안내](../../kiwoom-trading.md)를 참고한다.

사용자는 최초 모의환경 검증을 요청했다가, 모의 전용 인증 설정이 없는 것을 확인한 뒤
실전 주소 사용을 허용했다. 기존의 실계좌 주문 금지 조건은 유지했다. 모의서버 주문이나
실전 주문을 성공시켰다는 의미로 아래 로컬 테스트 결과를 해석하면 안 된다.

## 검증 범위와 증거

| 종류 | 실행 결과 | 증명하는 범위 |
|---|---|---|
| 기존 백엔드 회귀 | 216 통과 | 토스 주문·유량, 로컬 모의, 키움 REST·유량·세션의 현재 계약 |
| 새 조회 프로브 안전성 | 39 통과 | 허용한 조회만 전송, 주문·인증 TR 차단, 재시도·리다이렉트 금지, 토큰·출력 보호 |
| 설계 반례 | 9 통과 | 현행 시세 경로와 토스 모델을 그대로 주문에 적용할 때 생기는 제한 |
| 프론트 회귀 | 181 통과 | 주문창·계좌 패널·이벤트 병합·설정·접수 알림의 현재 동작 |
| 실전 주소 조회 | 26 요청, 24 정상, 2 업무 거절 | 6개 키의 계좌 연결, 조회 봉투, 휴장일 오류 확인 |
| 증권사 주문 수용 테스트 | 미실행 | 실계좌 주문 금지 유지. 키움 모의 인증 정보 없음 |
| 실시간 주문 이벤트 수용 테스트 | 미실행 | 기존 운영 연결 보호를 위해 새 소켓을 열지 않음 |

실행 건수와 제한은 [validation-summary.json](validation-summary.json)에 저장했다.
백엔드 테스트는 Python 프로세스에서 외부 TCP 연결을 차단하고 저장소 `.env` 자동 로드를
비활성화했다. 세션 종료 테스트에 필요한 루프백 TCP만 허용했다. 운영체제 전체에 적용되는
방화벽은 아니며, 검증에 선택한 테스트는 이 프로세스에서 실행된다.

첫 실행에서는 이 가드가 루프백 테스트까지 차단했다. 루프백 허용 후 전체를 다시 실행해
264개 모두 통과했다. 제품 코드의 실패를 무시하거나 테스트를 제외한 것은 아니다.

## 실전 조회 결과

주 계정의 기존 유효 토큰 캐시를 읽어 사용했다. 앱키 지문과 만료를 확인했으며, 캐시를
수정하거나 토큰을 재발급하지 않았다. 계좌번호·잔고 금액·주문번호·Bearer 토큰은 보고서에
저장하지 않았다. 요청 간격은 기본 1.1초이며 한도 경계나 최대 처리량을 측정하지 않았다.

처음 실행한 [real-readonly.json](real-readonly.json)의 결과는 다음과 같다.

| 조회 | 결과 | 설계에 반영할 사실 |
|---|---|---|
| `ka00001` | 정상, 10자리 계좌 식별 응답 | 키 이름이나 인덱스가 아닌 토큰의 실제 계좌로 연결 검증 |
| `ka10001` | 정상 | 현재가의 부호를 처리한 뒤 조회 가격 구성 가능 |
| `ka10075` 통합 미체결 | 정상, 빈 목록 | 조회 봉투 확인. 주문 행의 내용·상태 의미는 미확인 |
| `kt00007` 2026-10-16 전체 거래소 이력 | 정상, 빈 목록 | 조회 봉투 확인. 정정·취소 이력 복원은 미확인 |
| `kt00018` KRX | 정상, 빈 목록 | 조회 경로 확인. 보유 행·매도 가능 수량 의미는 미확인 |
| `kt00011` | 정상 | 미수불가 가능 금액·수량 등 필드 존재 확인. 현금 정책의 값 해석은 추가 검증 필요 |
| `kt00010` | HTTP 200, `return_code=20` | HTTP 성공과 업무 성공을 구별해야 함 |
| `kt00018` NXT | 정상, 빈 목록 | NXT 주문·실보유 잔고 정합성 검증을 대체하지 않음 |

`kt00010`에 선택 입력인 `io_amt`, `exp_buy_unp`까지 넣어 조회한 후속 실험에서도
`[2000](571489:장이 열리지 않는 날입니다.)`로 거절되었다. 후속 실험은 현재가 조회 1건과
금액 조회 1건이며, 결과는 [real-readonly-followup.json](real-readonly-followup.json)에 남겼다.
휴장일 응답은 조회 불가로 표시해야 하며, 매수 가능 금액 0원으로 치환해서는 안 된다.

이 계좌에는 조회된 미체결·이력·잔고 행이 없다. 따라서 두 거래소 잔고가 같은 범위인지,
서로 합산해도 되는지, 주문·체결 수량이 어떤 기준으로 누적되는지는 이번 실측으로 확정할 수 없다.

추가로 기존 키 6개의 `ka00001`을 조회했으며 **서로 다른 계좌 6개**가 반환되었다.
이어 주 계정 외 5개 계좌에 대해 같은 날짜의 주문 이력과 KRX 보유를 조회했고 모두 빈 목록이었다.
추가 16건은 모두 정상 응답했다. 계좌번호 대신 일회성 별칭으로 연결 관계를 보존한
[real-account-bindings.json](real-account-bindings.json)에 결과를 남겼다.
시세용 계좌 자동 전환은 이 환경에서 실제로 다른 계좌를 선택할 수 있으므로 주문 경로의
계좌 고정은 활성화 전 필수 조건이다. 서로 다른 앱키가 항상 다른 계좌라는 일반 규칙을 뜻하지는 않는다.

## 기존 인프라 재사용의 반례

다음은 실제 키움 주문 결과가 아닌, 현행 코드를 실행해 얻은 반례다. 테스트는
`tests/unit/live/test_kiwoom_trading_design_evidence.py`에 있다.

| 실험 | 관측 | 확정 결정 |
|---|---|---|
| 시세 접근 함수에 계정 A 클라이언트를 전달하고 A 버킷을 지연 | 계정 B 클라이언트가 호출됨 | 주문과 계좌 조회는 명시적으로 계정 고정 |
| 시세 스케줄러에 합성 주문 콜백을 넣고 A 인증 실패 주입 | A 다음 B로 재호출됨 | 주문 전송에는 시세 스케줄러의 계좌 선택·재시도를 사용하지 않음 |
| 계좌 없이 같은 중복 제거 키로 A·B 잔고 조회 | A 결과로 둘 다 완료 | 중복 제거·캐시·잠금에 계좌 문맥 포함 |
| 공식 문서의 `00`·`04` 예시를 현재 WebSocket 디스패처에 입력 | 계좌 이벤트가 콜백에 전달되지 않음 | 시세 파서 앞에서 별도 계좌 이벤트 경로로 분기 |
| 기존 세션이 있는 상태에서 시세 대상 종목을 비움 | 세션과 작업이 종료됨 | 주문 계좌의 연결 사용권을 별도로 유지 |
| 합성 주문 100주, 체결 30주, 취소 20주를 토스 모델로 표현 | 계산 잔량 70주, 실제 가정 잔량 50주 | 명시적 잔량과 주문 변경 연결 관계 필요 |
| 다른 증권사도 동일 숫자 계좌 ID를 사용하는 단순 브리지 | 기존 저널의 불명확 요청 구분 불가 | 증권사·환경·실제 계좌를 분리한 내부 참조 사용 |

잔량 실험은 토스 API 자체의 오류를 증명하지 않는다. 키움의 수량 의미를 확인하지 않고
현재 `TossOrder`에 매핑하는 방식이 충분하지 않다는 반례다.

## 공식 명세 예시의 역할

[공식 계약 fixture](../../../tests/fixtures/kiwoom_trading/official_contract.json)는
키움 공식 저장소의 커밋 `953e5dbff123f437ab4d11a78a95191a685eb51f`에서 추출했다.
출처는 파일 안에 고정했으며, 서버 수신 프레임과 구분해
`official_documentation_examples_not_server_capture`로 표시했다.

주문번호·모주문번호·명시적 잔량 필드가 있다는 사실은 공통 계약 설계에 사용했다.
실제 주문번호 연결, 정정 수량과 체결 누계의 범위, 이벤트 순서는 문서 예시를 실행하는
것만으로 검증되지 않는다. 원본에 JSON 구문이 맞지 않는 예시도 있어, 해당 예시는
수정한 서버 응답으로 둔갑시키지 않고 원문 문자열로 보존했다.

한도와 세션 제약은 [공식 이용 안내](https://openapi.kiwoom.com/intro)를 기준으로 보수적으로
설계했다. 이번 조회는 한도 실험이 아니므로 조회 5회/초 또는 주문 5회/초의 실제 경계,
앱키 간 독립성을 새로 실증했다고 주장하지 않는다.

## 재현 방법

프로젝트 개발 의존성이 설치된 Python으로 실행한다.

```bash
python scripts/run_kiwoom_trading_validation.py -q --tb=short
```

기존 프론트 테스트는 `frontend`에서 실행한다. 모두 API와 이벤트를 테스트 더블로 대체한다.

```bash
npm test -- --run src/api/trading.test.tsx src/api/tradingOrderEvents.test.ts src/live/workspace/OrderWindow.test.tsx src/live/workspace/AccountTradingPanel.test.tsx src/live/workspace/orderReceiptSound.test.ts src/state/orderWindowSettings.test.ts
```

실전 주소 조회를 다시 해야 할 때만 명시적인 환경파일·토큰 캐시를 지정한다. 만료한 캐시는
실패로 종료하며 이 도구가 발급하지 않는다. 환경을 생략하면 `mock`이며 실전으로 자동 전환하지 않는다.

```bash
python scripts/probe_kiwoom_trading_readonly.py \
  --environment real --env-file /path/to/.env \
  --token-cache /path/to/kiwoom-token.json \
  --order-date 20261016 --out /tmp/kiwoom-readonly.json
```

이 도구는 주문·신용·토큰 발급/폐기 TR을 최종 HTTP 전송 경계에서 거절한다. 임의의
API ID·호스트·WebSocket 연결을 지정하는 기능은 제공하지 않는다.
