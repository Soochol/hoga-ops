# 추가 측정: 프로그램·일별투자자 날짜 따라가기

후속: [구현 및 전후 측정 완료](2026-09-19-live-hover-implementation.md). 아래는 수정 전 조사 기록이다.

2026-09-19 · 기준 `8a16a20824542cdc354efbed1f0d715dc8b0b18b`.
[기존 차트만 측정](2026-09-19-live-hover-performance.md)에 사용자의 추가 제보를 반영했다.
[개선 플랜](../plans/2026-09-19-live-hover-performance.md)의 0단계를 새 최우선 범위로 추가했다.

## 결론

**이 경로는 실제로 큰 추가 비용을 만든다. 특히 일별투자자 창의 날짜 따라가기에서
긴 작업을 재현했다.** 단순 스크롤 위치 계산보다, 커서 전달·따라가기 상태 변경에 따른
**표 전체 재렌더와 수만 회 숫자 포맷팅**의 영향이 크다.

- 빠른 이동: 스크롤 0회/API 요청 0회여도 표 갱신 때문에 CPU 비용이 커졌다.
- 일봉에서 봉마다 450ms 머무름: 따라가기 ON에서 50ms 이상 작업이 **매 run 4회** 재현됐다.
- 투자자 따라가기만 OFF: JS **830.49 → 334.55ms**. 프로그램만 OFF: **722.03ms**.
- 두 창 모두 따라가기 ON을 유지하고 숫자 formatter를 실험적으로 재사용하면
  **176.15ms**, long task **0회**, 실제 스크롤은 기존과 동일한 **4회**였다.
- 로드되지 않은 과거 날짜로 가면 투자자 과거 조회와 표 행 확장이 추가돼 더 무거워졌다.

제품 코드 수정은 하지 않았다. 실험적 formatter 치환은 진단용 브라우저 안에서만 수행했다.
실제 사용자 지표/금액·수량 설정/과거 깊이/혼합 차트 배치와 완전히 동일한 환경은 아니다.

## 조건과 대조군

기존과 같은 production React + 실제 lightweight-charts, Chrome 153.0.8010.52,
**CPU 감속 없음**, 1800×1000, 툴팁 OFF, 종목 098460, 캔들 fixture.
차트 3개를 상단 60%, **프로그램 일별 창 + 일별투자자 창**을 하단 40%에 배치했다.
두 표 모두 **60행**, 투자자는 기본 수량/K·상위 주체/순매수·총매수·총매도 모두 표시,
프로그램도 일별 모두 표시/K. 데이터 날짜·단위·매매 기준을 요청과 맞춘 fixture를 사용했다.
호가/WS 실시간 부하는 없다. 필요한 투자자/프로그램 API는 모킹하며 그 요청도 기록했다.

- `baseline`: 데이터 창 호버 연동 ON + 두 창 커서 따라가기 ON.
- `follow-off`: 두 표의 커서 따라가기만 OFF. 표와 커서 구독은 그대로다.
- `linked-off`: 차트의 데이터 창 호버 연동 OFF. 세 차트 간 크로스헤어 동기화는 유지한다.
- `investor-follow-off` / `program-follow-off`: 각각 한 창의 따라가기만 OFF.
- `format-all-cache`: 따라가기·스크롤을 유지하고 locale/옵션별 Intl.NumberFormat 재사용.
  앞선 차트 실험의 ko-KR 기본값만 캐시하는 `format-cache`와 **다른 실험**이다.
  이 실험은 en-US 및 명시적 소수 옵션도 포함한다. 제품에는 전역 prototype 변경을 넣지 않는다.

빠른 이동은 60 mouse move ×3회 반복. 날짜별 dwell은 12 mouse move,
각 이동 후 450ms + 마지막 450ms 대기 ×2회 반복이다. 같은 동작 안의 중앙값을 비교한다.
표시 범위는 최근 50~5번째 봉이라 일봉에서는 60회 입력이 약 37개 봉 변경으로 이어진다.
120ms로 제한된 sidebar cursor의 실제 발행 횟수도 기록했다.

## 1. 빠르게 이동: 실제 스크롤 전부터 표 비용 발생

각 숫자는 60회 이동 한 run의 JS 시간 중앙값(ms), 3회 반복.

| 조건 | 일봉 JS | 분봉 JS | 일봉 숫자 포맷 호출 | 분봉 숫자 포맷 호출 |
|---|---:|---:|---:|---:|
| baseline | 662.53 | 691.83 | 36,267 | 40,098 |
| 따라가기만 둘 다 OFF | 651.92 | 689.17 | 36,267 | 40,098 |
| 데이터 창 호버 연동 OFF | **201.09** | **264.53** | 5,157 | 5,328 |
| locale/옵션별 formatter 캐시 | 278.81 | 303.19 | 36,267 | 36,438 |

**모든 run에서 실제 scrollTop 쓰기 0회, 투자자/프로그램 추가 API 요청 0회**였다.
그래도 일봉 약 461ms, 분봉 약 427ms의 차이가 데이터 창 커서 연동 유무에 따라 생겼다.
숫자 호출 수는 앱 전체에 설치한 계측의 합계다. 차트만의 5천여 회를 제외한 증가분이
데이터 창 갱신 비용을 보여준다. formatter 캐시는 호출 자체를 제거하지 않는다.
분봉 cache 시나리오는 더 빨라져 sidebar 발행이 19회→17회로 줄었으므로
그 총 시간 절감은 순수 formatter 함수 비용 감소만은 아니다.

분봉은 **같은 KST 날짜 안의 이동**이다. 날짜가 바뀌지 않았는데도 표가 다시 계산된다.
따라가기 OFF는 자동 스크롤 타이머만 끄며 커서 구독/표 렌더를 끊지 않으므로 이 비용이 남는다.

## 2. 450ms 머물기: 실제 날짜 따라가기에서 긴 작업 재현

일봉 12회 입력/약 8개 날짜 갱신, 각 조건 2회 반복의 중앙값.
앞선 빠른 이동 표와 입력 횟수·시간이 다르므로 절대값을 교차 비교하지 않는다.

| 조건 | JS(ms) | 포맷 호출/run | scrollTop 쓰기/run | 50ms 이상 작업(각 run) |
|---|---:|---:|---:|---|
| baseline | **830.49** | **37,680** | **4** | **4 / 4** |
| 둘 다 따라가기 OFF | 305.71 | 15,720 | 0 | 1 / 0 |
| 투자자만 따라가기 OFF | **334.55** | 15,720 | 프로그램 2 | 2 / 2 |
| 프로그램만 따라가기 OFF | 722.03 | 37,680 | 투자자 2 | 1 / 1 |
| formatter 캐시, 따라가기 둘 다 ON | **176.15** | 37,680 | **4** | **0 / 0** |

baseline long task는 첫 run `[51,51,50,50]ms`, 둘째 `[52,52,55,50]ms`였다.
따라가기 ON의 LayoutDuration은 약 **9.6ms/run**, formatter cache에서는 약 **9.1ms**였다.
스크롤을 동일하게 수행하면서 JS가 약 79% 줄었으므로, 레이아웃 읽기/scrollTop 쓰기보다
**상태 변경에 따라 반복하는 표 렌더·문자열 포맷**이 주요 최적화 대상이라는 근거가 된다.
정확한 비용을 100% 이 함수 하나로 귀속하는 측정은 아니다.

분봉 dwell에서는 같은 날짜라 따라가기 완료 후 재이동할 필요가 없다.
baseline JS 283.42ms, follow-off 315.36ms, 양쪽 long task 0회였다.
즉 “모든 분봉 호버에서 스크롤이 반복되어 느리다”는 가설은 맞지 않는다.
대신 1절처럼 **같은 날짜인데도 cursorMs 변경에 따라 표가 재렌더되는 비용**이 남는다.

## 3. 과거 날짜: 추가 조회 + 표시 행 확장

단일 탐색 run: 일봉 표시 범위를 최근 140~5번째 봉으로 넓히고,
12회 ×450ms 호버했다. 이후 **투자자 60→120행**, 포맷 **111,996회**,
JS **1,649.82ms**, 50ms 이상 작업 **11회**를 관측했다.
프로그램은 60행을 유지했고 이 시나리오의 과거 날짜는 프로그램 표시 기간 밖이다.

추가 API 요청은 3회:
1. 투자자 net history: 2026-01-02~05-11.
2. 확장된 기간의 buy: 2026-01-02~09-19.
3. 확장된 기간의 sell: 동일.

따라서 과거 호버에서는 **실제로 조회와 표 확장도 발생한다.** 다만 API 응답은 로컬 fixture여서
실제 벤더 지연은 측정하지 않았다. 1·2절의 로드된 날짜에서는 추가 조회가 전혀 없었으므로,
일반적인 호버 지연을 모두 네트워크 원인으로 설명할 수는 없다.
이 표 확장 결과는 1회 탐색이며 반복 통계로 해석하지 않는다.

## 코드 경로

1. `LiveChartRoot.scheduleSidebarCursor`: 커서를 120ms throttle로 발행.
2. `DataWindow.useGroupCursor`: `sidebarCursorMs`와 origin을 구독.
3. `InvestorDailyPane`: 날짜 문자열로 바꾸지만 자식 `InvestorDailyWindow`는 memo가 아니므로
   **날짜 문자열이 같아도** 부모 재렌더를 따라 표가 렌더된다.
4. `InvestorDailyWindow`: 날짜 변경 시 `cursorTarget` 초기화, 300ms 후 target 설정.
   이 상태들이 표와 같은 컴포넌트에 있어 follow 단계에서 전체 표 렌더가 추가된다.
5. `InvestorDailySummaryCell`: 60행 ×4주체 ×3매매 기준에 대해 보이는 문자열뿐 아니라
   title/aria-label의 exact 문자열도 다시 만든다. 기본 K 표시의 `formatInvestorK`는
   **en-US + maximumFractionDigits:0**을 매번 호출한다. ko-KR 전용 최적화로는 놓친다.
6. `ProgramDailySummary`: 매 렌더마다 rows를 복사·정렬하고 합계를 계산하며 셀도 재렌더한다.
   새 rows 배열이 따라가기 effect의 의존성이므로, **같은 날짜 분봉 이동에서도 300ms 타이머가
   취소/재예약**된다. 계속 움직이는 동안 프로그램 날짜 이동이 지연될 수 있는 별도 원인이다.
7. 투자자 `span===0`에서 과거 날짜가 없으면 `useInvestorDailyHistory.fetchNextPage`,
   필요한 행이 보이지 않으면 `setDepth`, 확장된 grossFrom으로 buy/sell 조회가 이어진다.

## 개선 우선순위

1. 일별 창을 날짜 단위로 구독하고, 동일 날짜 분봉 이동은 표 갱신을 생략한다.
2. 표의 행/셀 문자열을 데이터·표시 설정 기준으로 memo해 날짜 강조/따라가기 제어 상태와 분리한다.
3. ko-KR뿐 아니라 투자자 en-US 정수/K/금액 formatter를 옵션별로 재사용한다.
4. 프로그램 rows/totals 참조를 안정화해 동일 날짜 timer 재시작을 막는다.
5. 과거 조회와 행 확장은 유지하되, 증가한 행 전체를 이후 호버마다 재포맷하지 않도록 한다.

`따라가기 끄기` 또는 `호버 연동 끄기`를 최종 해결책으로 제안하는 것은 아니다.
기능을 유지하면서 비용을 줄이는 구체적 범위는 [개선 플랜 0단계](../plans/2026-09-19-live-hover-performance.md)에 기록했다.
