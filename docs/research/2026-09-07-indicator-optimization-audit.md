# 보조지표별 계산·조회 성능 조사

> 이 문서는 구현 전 조사 스냅샷이다. 이후 히트맵·프로그램 순매수·이동평균·POC 및 작은 서버 개선을 반영했다. 각 performance 보고서와 [후속 범위 판단](2026-09-07-indicator-followup-decisions.md)을 함께 참고한다.

조사일: 2026-09-07. 기준 코드: `d4ea967ca3a91e44f65ba69ac9ea90b055ae3e34`.
설정 화면의 14종 중 앞서 개선한 **당일 최대벽·총잔량을 제외한 12종**을 조사했다.
실제 소스의 호출 경로와 로컬 데이터/합성 입력 측정을 근거로 한 **개선 후보 보고서**다.
제품 코드 변경이나 개선안 적용 후 브라우저 검증은 수행하지 않았다.

## 판단

우선 **히트맵의 초기 전체 셀 생성**, 다음으로 **프로그램 순매수의 과거 캐시 유지**, **이동평균선 두 종류의 과거 재계산**을 줄이는 것이 좋다. **당일 최대 매물대의 불필요한 캔들 대체 계산**도 범위가 작은 개선 후보다.

모든 지표를 다시 작성할 필요는 없다. 거래량·호가비·외국인·기관·신규 거래원은 현재 캐시/계산 구조가 대체로 적절하다. 체결강도는 작은 정리만 권한다. 연속체결 매물대는 일반 조회보다 **과거 커서 시점 조회**에 개선 여지가 크다.

| 지표 | 판단 | 개선 대상 |
|---|---|---|
| 이동평균선 | 높음, 긴 이력·여러 선 | 캔들 변경 시 모든 선의 전체 SMA·좌표 생성·`setData` 반복 |
| 일봉 이동평균선 | 높음, 분봉 위 투영 | 날짜·좌표를 선마다 반복 조회하고 과거 분봉 전체 재생성 |

| 호가비 | 낮음, 유지 | 총잔량과 서버 조회 공유, 이미 과거 투영 캐시 |
| 체결강도 | 낮음, 작은 개선 | 1분 캐시를 1분으로 불필요하게 재집계 |

| 기관 순매수량 | 낮음, 유지 | 외국인과 같은 일별 응답·캐시 경로 |
| 신규 거래원 등장 | 낮음, 유지 | 이미 최초 등장 계산·09:00 공통 조회·과거 마커 캐시 |
| 프로그램 순매수 | 높음, 실시간 갱신 | 전체 배열 병합·정렬과 배열 참조 변경에 따른 과거 캐시 무효화 |

## 측정 조건과 한계

- 서버: 로컬 KRX hogaplay 실데이터 `20260623/000660`, `20260904/005930`, `20260904/287840`. 1종목·1일 단위. 최초 호출 후 5회 중앙값. 후보 대조는 7회.
- `raw`는 **지표 결과 캐시를 우회한 계산**이다. OS 파일 캐시를 비우지 않았으므로 디스크까지 완전히 cold인 시간이 아니다. `hot`은 격리한 임시 `PastIndicatorsCache`의 메모리 적중이다. 운영 캐시는 수정하지 않았다.
- 매물대/POC 측정은 가격 범위와 연속거래 종료 경계를 미리 구했다. 종료 경계 자체는 별도로 측정했다. 실제 범위 빌더도 두 지표에 같은 가격 범위와 종료 경계를 전달한다. 그 경계 비용을 지표마다 중복 합산하면 안 된다.
- 프론트: 실제 순수 함수를 jsdom/Vitest에서 호출. 5/30/90개의 합성 세션 × 하루 390개 1분봉. 선형 이력은 최대 35,100점, 투자자는 하루 1점, 거래원은 하루 24개 이벤트. MA는 6개 선(5/10/20/60/120/240), 히트맵은 매수·매도 각 10단계 전부 표시.
- 프론트는 2회 워밍 후 9회 중앙값. 아래 표는 다른 테스트와 분리한 마지막 실행 결과다. 반복 실행 시 90일 히트맵 전체 생성은 약 141~162ms로 변동했다. 비율을 성능 보증으로 사용하지 않는다.
- 프론트 시간은 React 전체 렌더·lightweight-charts의 `setData`/Canvas·실제 화면 표시 시간을 **포함하지 않는다**. MA는 effect의 데이터 생성 부분을 그대로 재현했다. 합성 90세션 결과를 실제 사용자의 화면 지연으로 단정하지 않는다.
- JSON 크기는 모델을 compact JSON으로 인코딩한 **비압축 크기**다. HTTP 압축·전송·브라우저 파싱 비용은 별도다. 외국인/기관의 외부 API cold 조회도 이번 조사에서는 호출하지 않았다.

## 지표별 근거와 개선 방향

### 1. 이동평균선

근거: `frontend/src/chart/projectors/movingAverage.ts`, `frontend/src/live/indicators/MovingAverageOverlay.tsx`.

`computeSMA`는 이미 이동합을 사용해 선 하나당 O(N)이다. 계산식을 바꾸는 것보다 **재계산 범위**가 문제다. effect는 캔들을 세션으로 걸러낸 뒤 선마다 가격 배열·SMA·가상 좌표·출력 배열을 다시 만들고 `setData`한다. 90세션·6선의 데이터 생성만 14.062ms였다.

같은 source의 가격 배열과 가상 좌표를 공유하고, 동일 봉 갱신/새 봉 추가에서는 필요한 꼬리만 계산·업데이트하는 방향을 권한다. 과거 prepend, 종목/봉/설정 변경, 데이터 정정 때는 전체 재구축해야 한다. **호가만 바뀌는 모든 SSE 틱에서 실행되는 것은 아니다.** 현재 stable chartBundle와 memo가 그 경로를 막고 있다.

### 2. 일봉 이동평균선

근거: `frontend/src/chart/projectors/dailyMovingAverage.ts`, `frontend/src/live/indicators/DailyMovingAverageOverlay.tsx`.

일봉 자체 SMA는 입력이 작다. 비용은 그 값을 과거의 모든 분봉에 투영할 때 발생한다. 각 선·각 분봉마다 `findByReal`로 날짜를 찾고 `toVirtual`로 좌표를 다시 찾는다. 90세션·6선 18.241ms였다.

분봉의 날짜/가상 좌표를 한 번만 구해 선들이 공유하고, 완료된 과거 날짜의 투영을 재사용하면 좋다. **현재가 변화는 오늘 날짜의 MA 값 전체를 바꾸므로 마지막 점 1개만 바꾸면 틀린다.** 오늘 분봉 구간 전체와 완료된 과거 구간을 분리해야 한다. 기존 일봉 조회의 90일 단위 범위 정렬·워밍업 구간은 유지한다.

### 3. 거래량

근거: `frontend/src/chart/projectors/volume.ts`.

과거 캔들 수·시각·양끝 참조·theme를 키로 과거 투영을 캐시하고, 이진 탐색으로 오늘 구간을 나눠 오늘만 투영한다. 90세션 hot 0.100ms. 누적 체결강도 옵션도 공용 누적 캐시를 사용한다. 최종 concat은 O(N)이지만 현재 절대 비용이 작아 별도 개선 우선순위는 낮다.

### 4. 호가비

근거: `hoga/api/bundle.py::build_quote_ratio_slice`, `frontend/src/chart/projectors/ratio.ts`, `pastCachedProjector.ts`.

총잔량과 같은 서버 시계열을 사용하므로 앞선 존재 여부 조회 최적화와 1분 재집계 생략의 수혜를 함께 받는다. 프론트는 세션 판정/좌표 투영 결합과 과거 캐시가 이미 적용돼 있다. 안정적인 context에서 90세션 hot 0.121ms다. 새 context 객체를 매번 생성하는 벤치마크는 캐시 미스를 만들어 잘못된 결론을 주므로, 최종 측정은 실제 `useShallow` 계약처럼 참조를 고정했다.

호가비 계산식 자체를 변경할 근거는 없다. 매수·매도 불균형 부호, outlier 필터, 동시호가/결손 마스킹을 유지한다.

### 5. 체결강도

근거: `hoga/api/bundle.py::build_fill_strength_slice`, `hoga/api/indicator_reaggregate.py::reaggregate_fill`, `frontend/src/chart/projectors/fillStrength.ts`.

서버는 가능한 경우 10초 체결 집계 파일을 쓰고 원시 체결로 폴백한다. 완료된 과거는 1분 합계를 캐시한다. 프론트의 매수·매도와 날짜별 누적선도 이미 캐시돼 있다. 누적 포함 3선 90세션 hot 0.259ms.

작은 개선은 **1분 요청에서 `reaggregate_fill`이 원본을 반환**하도록 하는 것이다. 현재는 390개 행을 dict에 다시 합치고 행을 다시 만든다. 단독 비용 0.141ms/일, 입력과 재집계 결과가 정확히 같음을 확인했다. 작지만 과거 여러 날 조회에 누적되는 비용이며 수정 범위도 좁다. 반환 리스트를 호출자가 변경하지 않는 계약과 5/15분 합계 동등성은 구현 시 확인해야 한다.

### 6. 연속체결 매물대 분포

근거: `hoga/api/bundle.py::build_volume_distribution_slice`, `hoga/tables/trades.py::query_continuous_trade_volume_distribution`, `frontend/src/live/useVolumeDistributionCutoffProfile.ts`.

종일 결과는 이미 캐시된다. 오늘 실시간 분포도 증분 체결 처리가 있다. 반면 과거 커서 시점별 조회는 cardinality 때문에 결과 캐시에서 제외돼 반복 SQL 집계를 한다. 무거운 샘플은 반복해도 약 50ms/조회다. 프론트는 요청 시점을 봉 단위로 정렬하지만 **새 봉으로 이동할 때의 계산**은 남는다.

고정 가격 구간에 대해 시간별 수량 증분과 누적합을 저장하면 cutoff 조회가 원시 체결 재스캔 없이 가능하다. 다만 1분 합계만 저장하면 API가 허용하는 **봉 내부 임의 밀리초 cutoff**를 정확히 복원하지 못한다. 봉 경계까지 prefix + 마지막 부분 구간 원시 조회, 또는 더 정밀한 정렬 인덱스가 필요하다. 가격 범위/구간 수/venue/연속거래 경계가 키에 들어가야 하며 모든 cutoff 결과를 무제한 캐시하는 방식은 피한다.

가격 범위를 생략한 단독 builder는 캐시 조회 전 캔들 가격 범위를 다시 읽어 hot 약 0.4~0.5ms가 걸린다. 그러나 실제 범위 빌더는 가격 범위를 미리 전달하므로 이를 주 병목으로 분류하지 않았다.

### 7. 당일 최대 매물대

근거: `frontend/src/live/useTradeVolumePoc.ts`, `frontend/src/live/tradeVolumePoc.ts::computeCandleVolumePocs`, `hoga/tables/trades.py::query_trade_volume_poc`.

오늘 체결은 이미 `IncrementalTradeVolumePoc`로 처리한다. 남은 문제는 `candleFallbacks`를 서버 seed 확인 **이전에 모든 날짜에 대해 계산**하는 것이다. 완료된 날짜 seed가 있으면 그 대체 결과를 뒤에서 버린다. 또한 `computeCandleVolumePocs`가 날짜마다 전체 캔들 배열을 `filter`해 날짜 수 D, 캔들 수 N에 대해 O(D×N) 스캔한다. 90세션 비용은 5.656ms였다.

먼저 seed/오늘 체결로 채워지지 않는 날짜만 대체 계산하고, 정렬된 캔들을 날짜별로 한 번 분할하거나 이진 탐색으로 잘라 쓰는 개선을 권한다. 데이터 미수신·일봉/저장뷰 폴백은 유지해야 한다.

서버에서는 같은 가격 구간의 분포와 POC를 모두 켜면 원시 체결 집계를 별도로 한다. 같은 bins·가격 범위·경계인 경우 공통 집계로 합칠 여지도 있다. **현재 분포의 qty만으로 POC를 바로 대체하면 안 된다.** 가격 구간별 최초 체결 시각과 동률 우선순위 등 필요한 정보까지 공통 결과가 보유해야 한다. 이 공통화의 실측 개선율은 아직 측정하지 않았다.

### 8. 호가 잔량 히트맵

근거: `frontend/src/live/DepthHeatmapOverlay.tsx`, `depthHeatmapAlpha.ts`, `depthHeatmapWire.ts`, `hoga/tables/snapshots.py::query_bucketed_depth_heatmap`, `hoga/api/bundle.py::build_depth_heatmap_slice`.

가장 확실한 개선은 **가시 범위가 아직 null인 초기 프레임의 전체 셀 생성 제거**다. 현재 초기 render에서 `[-Infinity, Infinity]`로 계산하고 다음 rAF에서 화면 범위로 줄인다. 90세션·전 10단계는 702,000개 셀을 만든다. 최종 실행에서 전체 161.689ms, 화면 300봉은 0.761ms였다. 서로 다른 출력 범위의 비용 비교이며, 곧바로 동일 화면의 end-to-end 개선율을 뜻하지 않는다. 초기 범위를 먼저 확보하거나 확보 전 셀 생성을 유보하는 구현과 실제 화면 확인이 필요하다.

그 다음은 다음 항목들이다.

- 보이는 구간만 이진 탐색으로 잘라 최대 수량/셀을 계산한다. 현재 두 루프는 각각 전체 이력을 훑는다. 90세션·300봉에서 0.761 → 0.429ms였고, **기존 가시 범위 결과와 후보 결과의 완전 일치**를 확인했다. 초기 전체 생성 제거보다 효과는 작다.
- hidden 상태에도 `useMemo`는 셀을 계산하고 `setCells`에서만 버린다. 셀 계산을 가시성으로 차단하되 레전드 조회는 별도 유지한다. 현재 primitive에는 프레임별 x/y 좌표 캐시가 있으므로 같은 최적화를 다시 할 필요는 없다.
- SQL의 마지막 연속호가 시각 조회는 여기서도 **존재 여부로만 사용**한다. 새 exists helper를 측정 프로세스에서만 주입했을 때 `77.622→68.701`, `83.281→78.538`, `41.844→39.894ms`였고 3샘플 출력이 동일했다. 약 2~9ms/일의 작은 backend 개선이다. 지표 본체의 20레벨 집계 비용은 여전히 남는다.
- 서버는 close·최대 총잔량 스냅샷·가격별 최대의 세 벌을 항상 계산/전달한다. 필요한 소스만 조회/전달하는 방안은 응답량을 줄일 수 있지만, 토글 즉시 전환·레전드·캐시 키 계약까지 설계해야 한다. 효과 수치는 아직 미측정이다.
- 이미 1분 캐시가 있을 때만 5/15분으로 파생하는 방안도 후보. `rep`는 마지막 행, 가격별 최대는 max 결합이 가능하다. 현재 docstring은 `rep_max`의 total이 wire에 없다고 설명하지만 **SQL total은 20레벨 수량 합이고 wire는 그 단계 수량을 보존하므로 합을 복원할 여지**가 있다. 별도 키가 반드시 필요하다고 단정하면 안 된다. 다만 `arg_max` 동률의 대표 행이 미정이라 원시/재집계 경로의 정본 정의와 cache version 변경·동등성 검증이 선행돼야 한다. 이번 조사에서는 coarse 파생을 구현하거나 등가성을 입증하지 않았다.

### 9. 외국인 순매수량

근거: `frontend/src/api/livePastInvestorNet.ts`, `frontend/src/chart/projectors/investorNet.ts`, `hoga/live/live_investor_net_backfill.py`.

하루 1점이고 90일 투영이 0.015ms다. 서버에는 배치/누락 구간 캐시와 동일 종목 동시 backfill 통합이 있다. 알고리즘 개선 우선순위가 낮다. 실제 느린 상황이 생기면 외부 페이지 조회, 누락 날짜, 스케줄러 대기 시간을 계측하는 쪽이 맞다. 이번에는 외부 cold 요청 지연을 측정하지 않았으므로 항상 빠르다고 보장하지 않는다.

### 10. 기관 순매수량

같은 응답의 `institution_net`을 읽으며 외국인과 조회 키·배치 캐시를 공유한다. 독립적으로 별도 대량 계산하지 않는다. 90일 투영 0.015ms. 외국인과 동일하게 현재 구조를 유지하는 편이 좋다. 수량/금액 축별 캐시와 응답 `unit` 계약을 보존해야 한다.

### 11. 신규 거래원 등장

근거: `hoga/tables/brokers.py::query_late_entry_events`, `frontend/src/chart/projectors/brokerLateEntryMarkers.ts`.

서버는 시각별 수량 집계 후 거래원 별칭을 정규화하고 첫 등장 이벤트를 구한다. 날짜 결과 캐시가 있고, 여러 기준 시각 설정도 서버에는 09:00 한 번만 요청한 뒤 클라이언트에서 거른다. 프론트는 과거 마커 캐시와 호가 앵커 이진 탐색을 쓴다. 90세션·일 24이벤트 hot 0.056ms였다.

최초 등장만 SQL에서 바로 구하는 추가 최적화는 별칭 통합·양/음 수량 상쇄 순서를 보존해야 한다. 현재 raw 4~6ms/일과 소량 출력에서는 우선순위를 높일 근거가 없다. Canvas 라벨 충돌 배치 자체는 이번 순수 투영 측정에 포함되지 않았다.

### 12. 프로그램 순매수

근거: `frontend/src/live/useLiveBundle.ts`의 `mergeProgramTradeSeriesWithLiveTail` 호출, `frontend/src/live/programTradeLiveTail.ts`, `frontend/src/chart/projectors/programTrade.ts::makeCachedProgramTradeProjector`.

실시간 꼬리를 합칠 때 저장된 전체 이력을 Map에 넣고 다시 정렬해 새 배열을 만든다. 과거 projector 캐시 키에 `programPoints` 전체 배열 참조가 있어 이 갱신은 과거 캐시를 무효화한다. projector의 기존 설명인 “SSE에 배열이 안정적”이라는 전제가 실시간 프로그램 병합 경로에서는 성립하지 않는다.

90세션 동일 배열 hot 0.471ms에 비해 **새 live 1점 병합+재투영 14.396ms**, 병합만도 2.530ms였다. 이것은 실시간 입력을 갱신하는 경우의 비교이고 모든 SSE 이벤트가 이 경로를 탄다는 주장은 아니다. 캐시 적중 0.471ms를 개선안 구현 후 보장 시간으로 제시하지 않는다.

저장 과거 배열과 변경되는 오늘 꼬리를 분리하고 과거 캐시를 유지하는 방향을 권한다. `todayProgram.filter`의 전체 스캔도 정렬 경계 탐색으로 줄일 수 있다. 다만 동일 timestamp last-wins, 역순 WS 도착, persisted max timestamp seam, 종목/venue/기간 변경, 과거 백필을 정확히 다뤄야 한다.

서버는 과거 저장 JSON의 mtime 캐시와 봉별 축소를 이미 쓴다. 축소 전에 원시 행마다 Pydantic 모델을 만드는 작은 여지는 있으나, 이번 1일 측정은 약 1.2~1.3ms로 프론트 문제보다 작다. **오늘 원해상도 유지**는 persisted/live seam 정확성 때문에 필요한 동작이라 제거하지 않는다.

## 실행 순서와 검증 기준

1. **히트맵 프론트**: 초기 전체 생성 제거 → 숨김 계산 차단 → 가시 구간 탐색. 가시 범위 최대 잔량 정규화, 3소스, 상위 N, 셀 높이, 팬/줌·첫 표시를 검증한다.
2. **프로그램 순매수**: 과거/오늘 병합·투영 캐시 분리. live 1점 변경 시 과거 projector가 호출되지 않는 결정적 테스트와 출력 동등성으로 검증한다.
3. **이동평균 두 종류**: 좌표/가격 입력 공유 후 과거 재사용. 분봉 꼬리 수정/추가, 일봉 오늘 전체 구간 갱신, prepend·설정 변경의 동등성을 검증한다.
4. **최대 매물대 프론트**: 필요한 날짜만 폴백 계산·날짜별 반복 전체 스캔 제거. seed 누락·오늘/저장뷰 fallback이 유지되는지 검증한다.
5. **작은 서버 개선**: 히트맵 exists helper, 체결강도 1분 fast path. 기존 fallback·세션·coarse 집계 회귀 테스트를 유지한다.
6. **설계가 필요한 후속 작업**: cutoff 매물대 prefix 집계, 분포/POC 공통 집계, 히트맵 선택 응답·1분 캐시 파생. 실제 사용 빈도와 추가 메모리 비용을 측정한 뒤 범위를 결정한다.
