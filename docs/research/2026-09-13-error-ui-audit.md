# 오류 UI 현황 조사 및 통일 제안

2026-09-13. 현재 체크아웃의 코드·설계 문서를 조사했다. UI 구현·API 요청 경로·배포는 변경하지 않았다. 아래 제안은 확정된 ADR이 아니다. 사용자가 보고한 ka90013 오류를 출발점으로 전체 오류 표현을 조사했다.

## 결론

오류 표시는 여러 곳에 분산되어 있다. 공용 렌더 컴포넌트와 일부 공통 진단 계약은 이미 있지만, 모든 오류를 아우르는 문구·노출·중복·해제 정책은 없다. 공용 UI를 처음부터 새로 만들기보다 기존 기반을 확장하는 것이 적합하다.

통일 대상은 **오류의 의미, 상세 형식, 표시 위치 결정, 복구와 알림 해제 규칙**이다. 입력 오류·부분 데이터 누락·전체 화면 렌더 실패를 모두 하나의 전역 팝업으로 옮기지는 않는다.

## 조사 범위 및 수치

`frontend/src`의 테스트 제외 TSX 파일에서 JSX 사용 파일 수를 집계했다. 오류 건수나 실제 동시 표시 개수가 아니며, 성공·정보 안내도 포함한다. 아래 수치는 서로 중복될 수 있다.

| 공용 표현 | 사용 파일 수 |
|---|---:|
| ToastCard | 11 |
| Banner | 5 |
| InlineState | 5 |
| RailState | 8 |
| 직접 role="alert"를 지정한 파일 | 12 |

`App.tsx`에는 공통 `ToastViewport` 아래 10개 호스트가 있다. `ToastViewport`가 위치·쌓임·aria-live를 공유하지만, 호스트별 알림 의미와 상태 관리는 별개다.

## 서버에서 화면까지의 계약

1. **HTTP 실패**: `hoga/api/error_codes.py`의 오류 코드와 detail.code/message → `api/client.ts`의 ApiError → 각 조회·폼·페이지의 오류 표현. 네트워크 예외는 그대로 다시 던져지며 모든 실패가 한 UI 정책으로 정규화되지는 않는다.
2. **성공 HTTP 응답 안의 부분 실패·정보**: `hoga/live/error_policy.py`, `data_warnings.py` → reason/msg/kind/is_failure → `api/dataWarnings.ts` → 차트 칩·빈 상태·REST 토스트·스크리너. 정보성 warning도 있으므로 배열 존재만으로 모두 오류라고 볼 수 없다.
3. **공급사 관측 실패**: `hoga/live/provider_errors.py` → provider_status.failures → ProviderServiceBanner. 위 data_warnings와 다른 kind 집합·문구·수명 규칙을 쓴다.
4. **운영 상태**: live/status의 supervised_tasks·disk 등 → 각각의 토스트 호스트.
5. **브라우저 렌더 예외**: React ErrorBoundary → 해당 범위의 대체 화면.

HTTP 오류 계약과 부분 성공 계약은 유지하고, 화면 표시용 변환 지점을 공유하는 편이 적절하다. 서로 다른 계약을 무리하게 하나의 서버 응답 형식으로 바꿀 필요는 없다.

## 확인된 문제와 제약

- `api/warningCopy.ts`의 공통 원인 사전은 transport·rate_limit 두 항목뿐이다. ProviderServiceBanner, LiveStateBanner, 개별 카드 등의 독립 사전이 병존한다.
- ProviderServiceBanner는 분류 불명에도 연결/응답 오류라고 단정한다. 이번 실제 ka90013 응답은 HTTP 200 + return_code 1 + 벤더 상세 1504(지원하지 않는 URI/API 조합)였으므로 연결 실패라는 표현이 부정확하다.
- 같은 REST 실패가 공급사 관측과 데이터 경고 경로에 각각 반영될 경우 배너·토스트·로컬 칩이 함께 뜰 수 있다. 이는 코드 경로상 중복 가능성이지, 이번 세 화면 동시 표시를 실측했다는 뜻은 아니다.
- 공급사 관측은 계정 클라이언트·operation별 성공으로 해제하고, REST 토스트는 별도 상태·5분 재알림 간격·수집 복구 신호를 사용한다. 디스크와 작업 중단은 상태 파생에 로컬 닫기 키를 더한다. 닫기·복구·재알림 의미가 서로 다르다.
- 오류 상세는 펼침 목록, 원문 error.message, HTML title, 오류 복사 등으로 나뉜다. 키보드로 여는 상세와 복사 경험도 공통 계약이 없다.
- ProviderFailure의 현재 전송 필드는 channel/kind/operation/observed_at_ms/code다. 종목·날짜 범위·창·요청 식별자가 없어 **어느 패널에 귀속할지와 다른 오류 경로와 같은 사건인지를 확정할 정보가 부족하다**. 작업 이름만 보고 모든 프로그램매매 패널을 실패로 표시하면 안 된다.
- observed_at_ms는 마지막 실패 시각이다. 최근에 재조회하지 않았다면 현재 실패 중인지 알 수 없다. 시간 경과만으로 복구 처리하거나 현재 장애라고 단정하면 안 된다.

## 권장 UI

**공통 상태창 + 발생 위치의 짧은 표시 + 일시적 행동 피드백**으로 통일한다.

| 상황 | 기본 표시 | 상세·행동 |
|---|---|---|
| 개별 데이터 일부 조회 실패, 기존 값 존재 | 해당 패널의 작은 상태 버튼, 기존 데이터 유지 | 상태창의 같은 항목 열기. 저장값/부분 데이터 여부와 기준 시각 표시 |
| 데이터 전부 조회 실패 | 해당 데이터 자리의 공용 오류 상태 | 유효한 재시도 또는 설정 행동, 상세 보기 |
| 저장·수정·입력 실패 | 폼/버튼 옆 공용 인라인 오류 | 입력 유지, 사용자에게 가능한 수정·재시도. 패널을 닫는 작업의 결과는 기존 토스트 예외 유지 |
| 지속되는 공급사·운영 장애 | 헤더의 공통 상태 버튼에 건수, 상태창 목록 | 영향받는 기능·마지막 관측·복구 여부 확인. 중대한 새 상태는 1회 알림도 제공 |
| 휴장·미수집·정상 대기 | 중립 상태 또는 필요할 때만 표시 | 오류 건수에서 제외 |
| 공식 점검 공지 | 서비스 상태창. 광범위한 중요 공지는 별도 공지 배너 가능 | 출처·예정 시간·영향 범위 |
| 렌더링 중단 | 앱/차트 ErrorBoundary 대체 화면 유지 | 재시도·새로고침·진단 복사 |

개별 API 실패는 기존 전역 상단 배너에서 제거한다. 상태창은 현재 열지 않은 패널의 오류도 확인할 수 있게 한다. 기존 StatusDot을 상태창 진입점과 어떻게 배치할지는 시안에서 결정하되, 앱 서버 연결과 키움 REST 연결의 의미를 섞지 않는다.

상태 항목의 공통 순서:

1. **영향**: 프로그램매매 조회 실패
2. **확인된 원인**: API 요청 경로가 올바르지 않습니다
3. **현재 데이터**: 저장 데이터 표시 중 / 일부 누락 / 표시할 데이터 없음 (확인된 경우만)
4. **시간·관측 상태**: 마지막 실패 22:38 / 재확인 전 / 복구 확인
5. **행동**: 상세 보기·진단 복사, 실제 가능한 경우에만 재시도·설정 열기
6. **접힌 기술 상세**: ka90013, 1504 등 안전한 진단 정보. 응답 원문을 무조건 표시하지 않음

## 공통화할 구현 책임

- 기존 ApiError, WireDataWarning, ProviderFailure, 운영 상태를 표시용 항목으로 변환하는 공통 모듈을 둔다. 원본별 변환은 분리하되 문구·행동·상세 형식을 공유한다.
- 표시 항목은 원인과 영향 범위를 구분한다. 기능/데이터 범위, 마지막 관측, 데이터 사용 가능 여부, 가능한 행동을 전달한다. 범위를 모르면 서비스 수준 항목으로 남기며 임의의 창에 붙이지 않는다.
- 중복은 operation 문자열만으로 합치지 않는다. 같은 사건임을 연결할 식별자가 있을 때 상태창의 한 항목과 로컬 표시를 연결한다. 식별자 미확보 시 서비스별 묶음 안에 별도 관측으로 보존한다.
- 반복 관측은 건수·시간을 갱신하고 매 폴링마다 토스트를 만들지 않는다. 닫기는 알림을 숨기는 동작, 복구는 동일 범위 성공 관측이다. 두 상태를 분리한다.
- 정상/비정상/부분 데이터 여부는 원본 데이터에서 파생하고, 공통 저장소에는 중복된 정상 판정 대신 항목 연결·알림 확인 상태 등 필요한 UI 상태만 둔다. 페이지 언마운트나 다른 계정의 성공을 복구로 취급하지 않는다.
- Banner/InlineState/RailState/ToastCard는 검증된 외형 기반으로 활용한다. 의미를 담는 공용 오류 안내·상세 컴포넌트를 그 위에 두고, 각 화면의 오류 문자열 조립을 점진적으로 걷어낸다.
- 오류 상세는 클릭·키보드로 열 수 있게 한다. 신규 사용자 작업 실패와 반복 폴링 상태에 같은 강도의 aria 알림을 사용하지 않는다.

## 기존 결정과의 관계

`docs/adr/0143-failure-diagnosis-layers.md`의 핵심인 진단 공통화·여러 렌더 채널 유지 원칙을 따른다. ADR-0143 §6은 동시 발생 조율을 보류했고 §7은 별도 심각도 통합을 불필요로 판단했다. 이번 상태창·중복 조율은 §6의 재검토이며, 색상 타입을 전부 합치는 작업까지 자동으로 포함하지 않는다.

`DESIGN.md`의 Error surfaces는 화면에 원인이 있으면 인라인, 없으면 토스트를 규정한다. 지속 장애의 주 표시를 상태창으로 옮기면 이 조항을 갱신해야 한다. 즉, 기존 규약을 그대로 적용하는 단순 스타일 정리가 아니라 새 UX 결정이 포함된다.

## 권장 진행 순서 및 검증

1. 공급사 실패를 공통 상태창으로 이동하고 상단 API 오류 배너 제거. 안전한 원인 분류·재확인 전 상태 표시를 함께 정리한다.
2. REST·작업 중단·디스크 토스트를 같은 상태창에 연결하고 반복·닫기·복구 정책 통일. 중요한 장애의 최초 알림은 보존한다.
3. 차트·스크리너·개별 카드에 공용 로컬 오류 표시 및 같은 상세 형식 적용. 데이터 범위 식별이 가능한 것부터 연결한다.
4. 폼·목록의 인라인 오류를 공용 표현으로 교체하고 렌더 실패 대체 화면의 상세 표현을 맞춘다.

검증 시나리오: 휴장 정상 대기에서 오류 0건; 한 API 실패와 다른 API 성공이 공존; 저장값 유지; 동일 실패의 폴링 중복 알림 없음; 닫아도 미복구 내역 보존; 동일 범위 성공 후 복구; 다른 계정·종목·날짜의 성공으로 오해제되지 않음; 관측 중단은 복구와 구분; 키보드 상세 열기와 진단 복사; 차트·앱 렌더 실패 복구 경로 유지.

정적 현황 조사이므로 테스트·브라우저 시안 검증은 수행하지 않았다. 구현 시 위 시나리오를 단위/통합/E2E로 검증해야 한다. 별도로 확인된 ka90013 요청 경로 버그는 이번 UI 통일과 구분해 해결해야 하며, UI 변경만으로 API 실패가 해결되지는 않는다.
