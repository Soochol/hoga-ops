### 같은 검색 결과를 유지한 SQL 실험

프로덕션 SQL 컴파일러는 그대로 두고, 입력 파일/선행 코드 필터만 바꿨다. 별도 Python 프로세스 측정이므로 위 HTTP 시간과 직접 비교하지 않는다. ETF 판정은 양쪽 모두 동일한 로컬 종목 명부를 사용했으며, 운영 서버의 메모리상 심볼 마스터를 복제한 실험은 아니다.

| 입력·필터 | SQL 중앙값, 각 3회 | 결과 검증 |
|---|---:|---|
| 전체 이력 8,959,939행 | 1,296.4 ms | 기준 533종목 |
| 전체 이력 + 동일 Universe를 먼저 코드 필터링 | 1,366.9 ms | 종목별 모든 응답 값 동일 |
| 종목별 최근 499봉, 총 1,806,745행 | 236.3 ms | 종목별 모든 응답 값 동일 |
| 최근 499봉 + 선행 코드 필터 | 216.7 ms | 종목별 모든 응답 값 동일 |

**가장 근거가 강한 최적화는 계산할 이력의 축소**다. 단독 최근 이력 실험은 중앙값 약 82% 감소. 반면 Universe 선행 필터만으로는 이 표본에서 개선되지 않았다.

499봉은 이번 조건과 현재 SQL의 윈도우 정의에서 필요한 `lookback + period - 1`이다. 일반 조건 전체에 고정 적용하면 안 된다. MA, 전일종가 LAG, 여러 조건의 최대 필요 길이, 신규상장과 부족한 이력 가드, 장중 overlay를 함께 고려해야 한다.

**전처리는 별도 1,347.1 ms** 걸렸다. 매 요청마다 파일을 자르면 이득이 사라진다. 일봉 갱신 시 최근 이력 파일을 원자적으로 준비하고, 필요한 길이가 파일 범위를 넘으면 전체 이력으로 돌아가는 방식이 적합하다. 원본/수정주가 변경에 따른 버전 무효화와 신규상장·분할·결측·동률 경계의 결과 동등성 검증이 선행돼야 한다. 실험은 한 조건 조합의 EOD 데이터만 검증했으며, 모든 검색의 속도·정확성을 보장하지 않는다. 결과 비교는 코드별 값 기준으로, 거래대금 동률의 행 순서는 비교하지 않았다.

## 2. 우선 해결할 문제

### P1 — 장중 데이터 일부 미반영이 화면에서 드러나지 않는다

장중 API 3회 모두 `warnings: ["intraday_quote_invalid"]`를 반환했다. 화면은 「오늘 장중: 키움 시세 반영」으로 표시하며 이 경고는 안내하지 않았다.

백엔드는 유효하지 않은 OHLC나 거래량이 없는 종목을 overlay에서 제외한다. 그 종목의 과거 일봉은 검색 입력에 남는다. 프론트는 `intraday_quote_invalid`와 `intraday_volume_unavailable`을 원인 후보에서 제외하고, `intraday_partial`이나 전량 fallback이 없는 경우 안내문을 만들지 않는다. 따라서 일부 종목은 과거 데이터로 평가돼도 장중 조회와 구분되지 않는다. 이번 응답으로는 영향을 받은 종목 수 및 최종 결과 포함 여부까지 알 수 없다.

개선: 응답에 요청 종목 수·장중 반영 수·미반영 사유별 수와 코드별 평가 기준일을 제공한다. 「장중 2,xxx / 대상 2,xxx · 일부 전일 기준」처럼 표시하고, 필요하면 ‘장중 데이터 확보 종목만’ 옵션을 둔다. 거래량 0인 종목의 처리 정책도 명시해야 한다.

근거: [장중 데이터 검증](/home/dev/.codex/worktrees/9497/hoga-ops/hoga/api/screener_intraday.py:201), [안내문 생성](/home/dev/.codex/worktrees/9497/hoga-ops/frontend/src/screener/intradayDegradation.ts).

### P1 — 결과 수백 건이 화면 밖 실시간 구독을 소모한다

532건 결과에서 DOM에 생성된 행은 19개였으나 「실시간 구독 슬롯 부족 · 20개 대기」안내가 발생했다. 기존 구독과의 경쟁이 있는 환경이며, 다른 창을 닫지 않고 관찰했다.

정확한 구조는 **전체 결과 REST 시세 10초 폴링 + 코드순 최대 300종목 WS 구독**이다. 결과가 532건이라고 WS 532개를 모두 요청하는 것은 아니다. 하지만 상한 안의 구독 대상도 현재 보이는 행이나 선택 종목을 우선하지 않는다. 표를 가상화해도 네트워크·서버 구독 비용은 함께 줄지 않는다.

개선: 결과 전체는 느린 시세 갱신/정렬용 데이터로 유지하고, WS는 보이는 행+앞뒤 여유 행+선택 종목을 우선한다. 화면 이동 시 교체를 짧게 묶고 구독 소유권을 공유해 다른 패널의 구독을 해제하지 않도록 한다. 정렬을 보이는 행 데이터에만 의존시키면 전체 순위가 틀어지므로 전체 정렬 데이터와 표시용 틱을 분리한다. REST 감속은 실제 요청량·신선도 요구를 측정한 후 정한다.

검증: 1,000건 검색에서 스크리너의 추가 구독 수가 결과 수 대신 뷰포트 크기에 비례하고, 정렬/스크롤 후 노출 종목이 우선 갱신되며, 패널 종료 시 소유 구독이 반환돼야 한다.

근거: [결과 전체 시세 연결](/home/dev/.codex/worktrees/9497/hoga-ops/frontend/src/screener/useScreenerRowsLive.ts:33), [구독 상한 및 코드순 선택](/home/dev/.codex/worktrees/9497/hoga-ops/frontend/src/api/liveTickOverlay.ts:202).

### P2 — 가상화 행 높이 측정이 실패한다

콘솔에서 `Missing attribute name 'data-index={index}' on measured element.`가 반복됐다. 렌더된 행의 `data-index`는 null, 실제 높이는 25px인데 위치 계산은 추정치 28px를 사용한다. 가상화 자체는 작동하지만 실제 높이를 반영하는 계약이 끊겨 있다. 높이가 다른 배지 행의 겹침 가능성은 별도 검증이 필요하며 이번 조사에서 겹침 자체를 재현하지는 않았다.

개선: `vi.index`를 ResultRow의 실제 측정 DOM까지 전달하고 `data-index`를 지정한다. 정렬되는 표이므로 `getItemKey`는 종목 코드로 고정한다. 비가상화 구간에서는 virtualizer의 관찰을 끄는 것도 검토한다. 기존 E2E는 DOM 개수·최하단 접근만 검사해 이 결함을 놓친다. 실제 높이가 다른 행과 정렬 후의 측정·위치를 검증하도록 보강한다.

근거: [가상화 설정 및 행 전달](/home/dev/.codex/worktrees/9497/hoga-ops/frontend/src/screener/ResultTable.tsx:215). `measureElement`와 `data-index`의 연결은 [TanStack 공식 문서](https://tanstack.com/virtual/latest/docs/api/virtualizer)에도 명시돼 있다.

### P1 — 1,000건 상한과 부분 정렬을 전체 결과로 오인할 수 있다

동일한 넓은 조건에서 API `limit=1000`은 1,000행, `limit=2000`은 2,000행을 반환했다. 응답에는 전체 건수·상한 도달 여부·다음 페이지가 없다. 페이지는 기본 limit 1,000을 사용한다.

서버는 거래대금 상위 결과를 자른 후 내려주고, 프론트에서 등락률 등을 재정렬한다. 따라서 넓은 조건에서 ‘등락률 높은 순’은 **전체 매칭 종목의 상위 등락률**이 아니라 **먼저 받은 거래대금 상위 1,000종목 안의 정렬**이다.

개선 1단계: `has_more`를 위해 limit+1건 확인 후 「상위 1,000건 표시 · 범위를 좁혀 주세요」안내. 개선 2단계: 서버 정렬/페이지네이션 또는 버전이 있는 결과 스냅샷. 총건수를 계산하면 비용이 추가되므로 먼저 상한 여부부터 제공한다. 실시간 등락률 정렬의 정확도를 보장하려면 정렬에 쓰는 시세 스냅샷과 기준시각도 정의해야 한다.

### P2 — 검색 엔진이 필요한 범위보다 긴 이력을 반복 처리한다

`adj`를 바탕으로 최신행, 거래대금 기간, 신고가, MA 등을 계산한다. 전체 시장 조회에는 필요한 거래일 길이를 기준으로 입력을 줄이는 경로가 없다. 위 실험에서 최근 이력의 효과가 확인됐다.

개선: 조건별 필요 봉 수 산정 → 갱신 시 최근 이력 준비 → 스캔에서 적합한 입력 선택. 이미 동일 요청의 동시 실행 병합, 장중 15초 캐시, 범위 제한이 구현돼 있으므로 이를 새 기능처럼 중복 도입할 필요는 없다. 완료된 검색 결과 캐시는 데이터 버전·장중 시세·총잔량 갱신을 반영한 무효화 설계 없이는 도입하지 않는 편이 낫다.

| 1 | **종목별 검색 충족 근거** | ‘250일 중 어느 날 거래대금 1,000억을 넘었는지’, ‘신고가 발생일·기준값’을 결과에서 바로 확인 | 중간. 조건별 평가 결과를 서버 응답에 추가하고 필요 시 상세 조회 |
| 2 | **검색 당시 값 / 현재 시세 구분** | 과거 기준 검색인데 현재 시세가 조건을 벗어난 이유를 이해 | 작음~중간. 조회 당시 가격·등락률·거래대금·평가기준일과 현재 시세를 별도로 표시 |
| 3 | **결과 내 종목 검색·다중 선택·관심그룹 일괄 추가·CSV** | 수백 건을 빠르게 추려 다음 작업으로 연결 | 중간. 검색 범위가 ‘받은 결과 내’임을 명시하고 CSV에 조건·기준시각·평가값 포함 |
| 4 | **풀페이지에서도 자동 재조회·신규 편입/이탈 확인** | 조건 편집과 관찰을 한 화면에서 수행 | 중간. 우측 패널에는 이미 모니터링·신규 편입 강조·안정 정렬이 있으므로 공용화. 이탈 이력은 추가 |
| 5 | **조건 잠시 끄기·조건별 통과 건수·0건 원인** | 조건을 삭제하지 않고 영향 비교, 너무 강한 조건 발견 | 중간. 조건별 매번 전체 쿼리를 실행하면 느려지므로 공용 계산 결과 활용 |
| 6 | **MA 교차·이격률·거래량 배수 조건** | 현재 ‘이평 위/아래’보다 사건과 강도를 표현 | 중간. 교차는 직전 봉과 현재 봉, 거래량 배수는 기준 평균·현재 봉 포함 여부를 명시 |
| 7 | **OR 그룹** | ‘가격 돌파 OR 거래량 급증’ 후 공통 유동성 조건 적용 | 큼. 기존 AND 저장본을 유지하는 조건 트리·저장 포맷 이행·설명 UI 필요 |
| 8 | **과거 날짜 기준 재검색** | 당시 조건에 해당했던 종목을 복기 | 큼. 과거 시점의 Universe/ETF/거래정지·상장 상태와 수정주가 기준 검증 필요. 단순 날짜 필터만으로 완성되지 않음 |

새로운 조건을 늘리기 전에 1~4번이 현재 업무 흐름에 더 직접적인 효과를 준다. 이미 16개 조건 타입, 사전필터, 저장·복제·이름변경, 다중 관심그룹 연결, 열별 정렬, 총잔량 커버리지 안내가 있다. 이것들을 신규 기능으로 제안하지 않는다.

거래대금은 현재 `(O+H+L+C)/4 × 거래량` 추정치이며, 결과표에서는 조회 당시 값을 유지한다. 가격·등락률은 이후 시세로 바뀐다. 「거래대금(조회 시점·추정)」표기부터 개선할 수 있다. 장중 공식 누적 거래대금을 쓰는 확장은 과거 일봉과 계산 의미가 달라지는 만큼 별도 기준을 설계해야 한다.

## 4. 추가로 확인할 코드 위험

아래는 코드 경로에서 확인한 사항이며 장시간·실패 상황의 UI 재현은 하지 않았다.

- [모니터링의 동일 종목 집합 생략](/home/dev/.codex/worktrees/9497/hoga-ops/frontend/src/screener/ScreenerDrawer.tsx:279): 종목 집합이 같고 depth 값이 없으면 상태 저장을 통째로 생략한다. 새 `warnings`, `intraday_failure`, 거래대금, 조회시각도 반영되지 않는다. 행 배열 재사용과 조회 메타 갱신을 분리해야 한다. 30분 TTL과의 상호작용도 검증 대상이다.
- [총잔량 배지 side 판정](/home/dev/.codex/worktrees/9497/hoga-ops/frontend/src/pages/Screener.tsx:221): 페이지는 당일 peak 타입만 ask/bid로 잡고 기간내 peak 타입은 포함하지 않는다. 기간내 총잔량 조건의 검증 배지가 누락될 수 있다. 현재 편집 조건이 아니라 마지막 조회 조건을 기준으로 배지 의미를 고정하는 것도 함께 검토한다.
- [문서의 Screener 정의](/home/dev/.codex/worktrees/9497/hoga-ops/CONTEXT.md:551)는 여전히 장중 KIS/카탈로그 9종으로 설명하지만 실행 구현은 키움/16종이다. 다음 기능 구현 전에 관련 문서의 소스·조건 목록을 맞출 필요가 있다.

## 5. 권장 실행 순서와 완료 기준

1. **작은 정확성 수정:** 장중 일부 미반영 안내, 가상화 `data-index`, 1,000건 상한 안내, 모니터링 메타 갱신. 완료 기준은 각각 부분 데이터 안내 노출, 측정 경고 0건, 상한 도달 표시, 같은 종목 집합에서도 새 경고·시각 반영.
2. **실시간 구독 개선:** 가시행 우선 구독과 전체 결과 정렬용 데이터 분리. 완료 기준은 1,000건 조회·스크롤·정렬·패널 동시 사용에서 구독 수와 슬롯 대기를 측정하고, 최신성 및 정렬 정확도를 유지하는 것.
3. **조회 엔진 개선:** 최근 이력의 버전 관리 및 재사용. 이번 대표 EOD 조건의 SQL 중앙값 300ms 이내를 초기 목표로 삼되, 다양한 기간·조건과 cold/warm cache를 나눠 재측정한다. 전체 요청 지연의 목표는 장중 외부 데이터 준비 시간을 따로 측정한 뒤 정한다.
4. **업무 기능:** 충족 근거 → 결과 내 검색·일괄 작업 → 풀페이지 모니터링 → 새 조건/OR/과거 재검색 순.

수정 코드를 작성한 검토가 아니므로 빌드·전체 테스트 통과를 주장하지 않는다. 이번 검증은 실제 UI/콘솔 관찰, API 11회(주요 시나리오 9회+limit 비교 2회), SQL 12회 비교다. 모바일, 장마감, 수시간 모니터링, 생산 빌드의 LCP/INP·번들·CPU 프로파일은 측정하지 않았다.
