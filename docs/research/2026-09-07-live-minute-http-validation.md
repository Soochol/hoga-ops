# /live 분봉의 잔여 HTTP 수신 지연 검증

2026-09-07. [적용 후 UI 검증](./2026-09-07-live-minute-deployed-validation.md)의
후속이다. 2·3·4번 개선 이후 남긴 1번, 외부 HTTP 수신 지연을 다시 측정했다.

## 결론

**연결을 재사용하는 실제 분봉 요청에서도 9.28초 지연을 재현했고, 그중 8.68초가
응답 본문 수신이었다.** 별도 반복에서 1.42/1.55초 요청의 본문 수신 동안 이벤트
루프 밀림은 최대 1.43/1.86ms였다. 이 격리 실험의 초 단위 지연은 UI·지표 계산이나
애플리케이션 큐 없이도 발생하며, 로컬 이벤트 루프 정체로 설명되지 않는다.

수신 out-of-order 증가도 함께 관측했다. 그러나 이것만으로 손실, 특정 hop, Wi-Fi,
ISP 또는 키움 서버 중 원인을 확정하지 않는다. 현재 경로가 Wi-Fi인 것은 확인했지만
유선/다른 회선 A/B는 사용자 환경상 현재 불가능하다. 같은 연결에서 HTTP 클라이언트를
교차 비교하니 curl에서도 3.28초 지연이 재현됐다(아래 후속 검증). 따라서 Python/httpx만의
문제라는 설명도 지지되지 않는다. **네트워크 원인을 해결한 성능 패치는 아니다.**

## 재현과 조건

- 실행 서버 `/health`는 `0.12.45.0 / 4e0cd6704`. 사용자 main 소스와 서버 설정은 수정하지 않았다.
- 실제 `KiwoomRestClient.call('ka10080', …)`로 삼성전자 005930, 20260907,
  `tic_scope=1`, `upd_stkpc_tp=0`의 동일 요청을 반복했다. 모두 900행으로 성공했다.
- 기존 계정 5의 토큰 캐시를 읽기만 했다. 환경 자격증명 로딩·토큰 발급·갱신·무효화,
  운영 분봉 캐시 삭제·기록, WS 연결은 없다. 원본 응답과 인증 헤더도 증거에 저장하지 않았다.
- 1·2차는 앞선 조사 harness를 재사용했다. 격리 scheduler worker 1, rate 1/s,
  headroom 포함 발사 간격 약 1.25초. 표의 HTTP 시간은 큐·페이싱 대기 이후부터다.
  실행 서버 scheduler의 실제 대기 시간을 의미하지 않는다.
- 새 CLI는 scheduler 없이 같은 REST seam을 호출하며, **각 응답 완료 후 1.25초** 쉰다.
  현재 제품의 HTTP transport 정책(keepalive 90초, 연결 단계 retry 1)을 사용한다.
  한 요청의 전체 deadline은 30초, CLI 표본 수는 1–20회로 제한했다.
- Python 3.12.13 / httpx 0.28.1 / httpcore 1.0.9. 세 배치는 각각 새 client로 시작하고
  배치 안에서 연결 풀을 재사용했다. 배치 간 시간과 페이싱이 달라 A/B 성능 비교로 쓰지 않는다.

첫 명령은 다음과 같으며, **exit 1 / SLOW_REPRODUCED / 8회 중 3회 >1,000ms**였다.
날짜·경로가 고정된 조사 harness는 증거 디렉터리에 보존했다.

```bash
PYTHONPATH=. uv run python /tmp/minute-http-current-baseline.py
```

## 측정 결과

모두 HTTP 호출부터 실제 REST 응답 파싱 완료까지의 시간이다. UI 첫 표시 시간과 다르다.

| 배치 | 표본 수 | 1초 초과 | 전체 시간 범위 | 비고 |
|---|---:|---:|---:|---|
| 기존 chunk/TCP harness | 8 | 3 | 61–9,282ms | 본문 수신 지연 재현 |
| 이벤트 루프 감시 추가 | 8 | 2 | 59–1,549ms | 10ms 주기 감시 |
| 정리한 CLI 실제 실행 | 6 | 0 | 50–253ms | 계측 동작 확인, 이 배치에서는 미재현 |

핵심 느린 표본:

| 표본 | 전체 | 본문 수신 | chunk 사이 최대 공백¹ | out-of-order 증가 | 이벤트 루프 최대 밀림 |
|---|---:|---:|---:|---:|---:|
| 1차 #1, 새 연결 | 4,125ms | 3,286ms | 1,174ms | 41 | 미측정 |
| 1차 #2, 연결 재사용 | **9,282ms** | **8,681ms** | **2,792ms** | 24 | 미측정 |
| 1차 #3, 연결 재사용 | 1,386ms | 1,343ms | 1,033ms | 21 | 미측정 |
| 2차 #6, 연결 재사용 | 1,424ms | 1,382ms | — | 131 | 1.43ms |
| 2차 #7, 연결 재사용 | 1,549ms | 1,520ms | — | 38 | 1.86ms |

¹ 헤더 수신 후 첫 chunk까지의 대기도 포함한다. TCP packet 간격이 아니라 HTTP stream이
Python 소비자에게 chunk를 넘긴 간격이다. 표본별 전체 값은 `summary.json`과 원본 JSON에 있다.

1차 #2는 새 TCP/TLS 이벤트가 없고, 응답 본문은 약 176.6KB였다. 큐·페이싱 대기는
0.07ms였다. 느린 요청에서도 정상 900행이 반환돼, 빈 응답/실패를 빠른 성공으로 세지 않았다.
빠른 표본에서도 out-of-order가 증가한 경우가 있으므로 그 수치를 단독 판정식으로 쓰면 안 된다.
Linux TCP_INFO offset은 현재 시스템 헤더의 `offsetof` 결과로 확인했다.
로컬 송신 retrans=0은 상대 서버가 재전송하지 않았다는 증거가 아니다.

22회 중 5회라는 비율로 일반적인 발생률이나 p95를 추정하지 않는다. 마지막 배치가 빨라진
것도 코드 개선 효과가 아니다. 제품 HTTP 정책은 변경하지 않았고 시간에 따른 변동이 크다.

## 가설 검증 결과와 수정 판단

1. **네트워크 수신 지연**: 긴 본문 공백과 TCP out-of-order가 함께 관측돼 지지된다.
   발생 구간은 미확정이다. 인터페이스의 누적 rx_errors/rx_dropped=0만으로 네트워크
   문제를 배제할 수 없다.
2. **로컬 이벤트 루프 정체**: 2차의 느린 표본에서도 주기 감시가 정상에 가까워,
   그 표본의 주원인이라는 가설은 지지되지 않는다. 별도 프로세스의 관측이므로 실행 중인
   FastAPI 서버의 이벤트 루프가 언제나 정상이라는 주장으로 확장하지 않는다.
3. **키움 서버가 본문을 늦게 전송**: 배제하지 못했다. 동일 시점의 다른 경로 또는
   packet 수준 비교가 없어서 경로 문제와 완전히 분리되지 않는다.

연결 재사용 중에도 지연이 발생하므로 keepalive 수치 변경을 추가 처방으로 선택하지 않았다.
읽기 timeout을 줄이거나 즉시 재시도/중복 요청을 넣으면 성공하던 느린 조회를 실패로 바꾸거나
벤더 부하를 늘릴 수 있고, 현재 실측은 그 변경의 효과를 입증하지 않는다.
worker/계정 증설 역시 HTTP 한 요청의 본문 지연을 줄인다는 근거가 없다.

## 추가한 재사용 진단 명령

[`scripts/probe_kiwoom_http_latency.py`](../../scripts/probe_kiwoom_http_latency.py)는
현재 날짜·계정에 맞는 **기존** 토큰 파일을 명시해 실행한다. 기본은 6회다.

```bash
uv run python -m scripts.probe_kiwoom_http_latency \
  --token-file /home/dev/.local/share/hoga-ops/data/.local/kiwoom-token-5.json \
  --code 005930 --date 20260907 --samples 6 \
  --assert-under-ms 1000 --out /tmp/kiwoom-http-path-a.json
```

- TCP/TLS·요청 송신·헤더·본문 단계, HTTP 전체, chunk 크기·최대 공백, 이벤트 루프 밀림을 기록한다.
  없는 단계는 기록하지 않는다. 예를 들어 연결 재사용에서는 TCP/TLS가 없으며,
  계측 미지원 transport를 써도 가짜 0ms로 만들지 않는다.
- auth/rate/read/전체 deadline 오류 또는 빈 행 결과가 나오면 즉시 중단한다.
  토큰을 재발급하거나 응답 이후 실패를 재시도하지 않는다. 제품 transport의 연결 retry는 유지한다.
- 종료 코드: `0=NOT_REPRODUCED`, `1=SLOW_REPRODUCED`, `2=ERROR`.
  **0은 영구 해결의 판정이 아니라 해당 표본에서 임계치를 넘지 않았다는 뜻이다.**
- 기존 출력 파일·토큰 파일을 덮어쓰지 않는다. 토큰 파일과 같은 경로, 심볼릭 링크,
  하드 링크도 검사한다. 진단 명령을 실행하지 않을 때 제품 서버에 추가 비용은 없다.
- TCP_INFO의 OS별 offset은 이 범용 명령에 넣지 않았다. 이번 Linux 전용 실험의 수치와
  검증용 C 코드는 별도 증거로 보존했다.

유선 연결 비교는 사용자 환경상 현재 불가능하므로 필수 후속 작업에서 제외했다.
네트워크 설정이나 접속 회선을 변경하지 않고 아래 대체 검증을 수행했다.

## 유선 없이 수행한 대체 검증: httpx / curl 교차 비교

같은 PC·Wi-Fi·토큰·분봉 요청을 사용하고 두 클라이언트 모두 **HTTP/1.1, 요청마다 새 연결**로
맞췄다. `httpx → curl → curl → httpx` 순서를 3회 반복해 순서 편향을 줄였다.
응답 완료 뒤 다음 요청까지 1.25초 쉬었으며, 총 12회의 조회로 제한했다.
httpx는 앞의 진단 도구, curl은 설치된 curl 8.18.0 / libcurl / OpenSSL을 사용했다.
curl의 설정 파일 자동 로딩·프록시·추가 retry는 끄고, 인증 헤더는 argv나 파일 대신 stdin으로
전달했다. 응답 원문은 메모리에서 성공 코드와 행 수만 확인한 뒤 버렸다.

| 클라이언트 | 표본 수 | 1초 초과 | 전체 시간 범위 | 응답 |
|---|---:|---:|---:|---|
| Python/httpx | 6 | 1 | 77–2,606ms | 모두 HTTP 200, 900행 |
| curl | 6 | 2 | 63–3,282ms | 모두 HTTP 200, return_code=0, 900행 |

curl의 두 느린 요청은 1,811ms / 3,282ms였다. 첫 응답 바이트는 각각 75ms / 83ms에
도착했고, 이후 완료까지 1,735ms / **3,199ms**가 걸렸다. curl의 `time_starttransfer`는
첫 바이트 기준이므로, 그 차이를 httpcore의 정확한 본문 단계 시간과 동일시하지 않는다.
다만 TLS는 각각 46ms / 39ms에 완료돼 연결 이후 수신 대기가 길다는 점은 확인된다.
httpx의 2,606ms 표본은 TLS 1,067ms, 본문 1,476ms, 이벤트 루프 최대 밀림 2.34ms였다.

모든 curl 요청의 `num_connects=1`·HTTP/1.1, 모든 httpx 요청의 TCP/TLS trace를 확인했다.
httpx 전체에는 토큰 읽기·JSON 파싱이 포함되고 curl 전체는 curl의 전송 시간이다.
둘의 작은 차이로 상대 성능이나 개선율을 계산하는 실험이 아니다.

**판단:** 지연 재현에 Python/httpx HTTP 수신 구현이 필수인 것은 아니다. curl로 교체하면
해결된다는 수정안은 채택하지 않는다. 시간상 인접한 양쪽 표본이 느렸지만 동시 요청이
아니므로 동일한 네트워크 사건이라고 확정하지도 않는다. Wi-Fi·외부 경로·키움 서버의
구분은 미확정으로 남으며, 현재 불가능한 유선 비교를 진행의 선행 조건으로 삼지 않는다.

[cross-client.json](./2026-09-07-live-minute-http-evidence/cross-client.json).
제품 소스·설정 변경은 없다. 이번 추가 작업은 실제 요청 비교와 문서 갱신이므로 아래

## 머지 전 계측 보완과 재검증

독립 리뷰에서 진단 도구의 다섯 경계를 보완했다.

- REST 경고뿐 아니라 httpx/httpcore DEBUG 로그도 해당 진단 호출 문맥에서만 억제해,
  전송 예외의 원문이 출력되지 않게 했다. 다른 task의 로그와 호출 후 로깅은 유지한다.
- 최상위 JSON이 배열/null이거나 행 배열에 null/숫자가 들어 있으면 `ERROR`로 끝낸다.
  진단 실패를 지연 재현(exit 1)이나 빠른 성공으로 분류하지 않는다.
- 마지막 body chunk/JSON 처리 직전 동기 정체가 발생하면 주기 감시 task가 깨어나기 전에
  취소될 수 있었다. 완료 시 아직 반영되지 않은 감시 구간도 계산해 이 누락을 막았다.

초기 2차 느린 표본의 기록을 재확인하면 1,424ms 중 1,414ms, 1,549ms 중 1,538ms가
주기 감시 표본으로 설명돼, 마지막 누락 가능 구간은 각각 약 10ms였다. 초 단위 동기 정체가
그 구간에 숨어 있지는 않았다. 다만 범용 진단 도구에는 위 보완이 필요했다.

보완한 명령으로 실제 키움 API를 6회 더 측정했다. 모두 정상 900행이었고, 5번째 요청은
**1,206ms 중 본문 수신 1,175ms**, 최대 chunk 공백 **1,054ms**였다. 완료 직전 구간까지
